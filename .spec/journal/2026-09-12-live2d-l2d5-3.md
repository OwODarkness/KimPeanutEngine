## 1. Fixture

`asset/live2d/mao/` is the SDK's `Samples/Resources/Mao`, imported to the
`.live2d` product by `KimPeanutAssetTool import-live2d`. `asset/*` is
git-ignored, so the model is **locally provisioned content**, never a
redistributed artifact — the plan's requirement and L2D4.0 output 6 both hold.
`config/live2d.json` stays on the always-present fixture; Mao is selected for a
run by the new `--live2d-model` flag rather than by editing tracked config.

Making Mao importable required fixing V1 importer defect #1 from the L2D6.0
characterization (an expression's display `Name` was resolved as a file path).
That correction is recorded as an addendum in
[2026-09-12-live2d-l2d6-0.md](2026-09-12-live2d-l2d6-0.md); defects #2 and #3
there stand.

## 2. Blend-mode coverage asserted from fixture data (item 9)

Blend mode is authored inside the `.moc3` and cannot be recovered from a
capture, so the claim is read from the loaded model by a new read-only Runtime
command, `live2d.model_report`, contributed by the viewer host through
`IApplicationHost::RegisterHostCommands`. It reports the product actually
loaded, so a run that silently fell back to the configured fixture cannot read
as evidence about the requested one.

Verbatim, one run per backend (`--agent-port`, viewer mode, 720×960):

```
RESULT list.backend=vulkan commands=['commands.list', 'help', 'live2d.model_report', 'window.resize']
RESULT report.backend=vulkan status=success message='Live2D model report'
RESULT report.backend=vulkan data={"additive_drawable_count": 15, "covers_all_blend_modes": true, "drawable_count": 262, "model": "live2d/mao/mao.live2d", "multiplicative_drawable_count": 8, "normal_drawable_count": 239, "unknown_blend_mode_count": 0}
RESULT cover.backend=vulkan covers_all_blend_modes=True
```

```
RESULT list.backend=opengl commands=['commands.list', 'help', 'live2d.model_report', 'window.resize']
RESULT report.backend=opengl status=success message='Live2D model report'
RESULT report.backend=opengl data={"additive_drawable_count": 15, "covers_all_blend_modes": true, "drawable_count": 262, "model": "live2d/mao/mao.live2d", "multiplicative_drawable_count": 8, "normal_drawable_count": 239, "unknown_blend_mode_count": 0}
RESULT cover.backend=opengl covers_all_blend_modes=True
```

239 + 15 + 8 = 262 = `drawable_count`, so the three modes partition the model.

**Negative control** (Hiyori, Vulkan) proves the report discriminates instead of
always answering true:

```
{"additive_drawable_count": 0, "covers_all_blend_modes": false, "drawable_count": 134, "model": "live2d/hiyori_pro/hiyori.live2d", "multiplicative_drawable_count": 0, "normal_drawable_count": 134, "unknown_blend_mode_count": 0}
```

This is why Mao is the blend fixture: the L2D4 regression fixture exercises
**no** additive or multiplicative drawable, so before this stage the item-9
claim had no fixture behind it at all.

## 3. Cross-backend captures

Captured with `--capture --capture-view live2d --capture-alpha transparent`,
frozen L2D4.0 tolerances (`--tolerance 0.0078431 --edge-tolerance 0.0156863`).
All files are under `save/screenshots/validation/`.

### Hiyori — the representative clipped model (L2D4 fixture)

720×960 — every region inside tolerance:

| Region | Pixels | max abs | mean abs | over tolerance |
| --- | --- | --- | --- | --- |
| non-edge opaque | 95140 | 2 | 0.0004 | 1 |
| partial alpha | 2292 | 1 | 0.0022 | 0 |
| transparent background | 589771 | 0 | 0.0000 | 0 |
| filtered edge | 6289 | 1 | 0.0010 | 0 |

Coverage sums to the full 691200 pixels, so the regions partition the image.
The sha256 values reproduce the L2D4.5 journal byte-for-byte
(`3723ec7e…` Vulkan, `d045f677…` OpenGL), which also confirms the shared render
path did not regress while this stage was in flight.

1024×768 — partial alpha, transparent background, and filtered edge PASS;
non-edge opaque reports `pixels=109050 max_abs=3 channels_over_tolerance=2`,
which the comparator marks FAIL because the frozen parity tolerance is 2/255.
This is the **previously recorded residual**, reproduced exactly: 81 differing
pixels of 786432, max 3/255, on 2 channel-samples of 436200. It is a 1/255
overshoot of ordinary rasterization order, not a coordinate, gamma, blend, or
mask-polarity disagreement.

### Mao — the blend fixture

| Extent | non-edge opaque | partial alpha | transparent bg | filtered edge |
| --- | --- | --- | --- | --- |
| 720×960 | `max_abs=254` FAIL | `max_abs=150` FAIL | `max_abs=13` FAIL | `max_abs=55` FAIL |
| 1024×768 | `max_abs=254` FAIL | `max_abs=44` FAIL | `max_abs=13` FAIL | `max_abs=55` FAIL |

Roughly 0.40% of pixels differ at both extents, identically. This is a **new
defect, not a tolerance miss** — see §6. Mao's captures are recorded here as a
fixture characterization and are **not** offered as backend-parity evidence.

### Blend-mode regions in the comparator

The plan asked for blend-mode regions to be added to the comparator's region
set. **They cannot be added, and the tool now documents why**: a drawable's
blend mode is authored inside the `.moc3` and a capture carries only composited
RGBA, so no per-pixel function of the image can recover which drawable wrote a
pixel or under which blend. The four regions the comparator does report are all
derived from alpha topology, which is exactly why they are derivable. The
item-9 intent is satisfied from engine model data instead (§2). This is a
deliberate deviation from the plan's wording, recorded rather than silently
skipped.

## 4. The risk item 11 exists to bound is now demonstrated

Item 11's residual risk was stated as "an engine-side systematic deviation that
cross-backend agreement cannot detect because both backends share the engine's
PMA and blend equations." §6 shows the complementary failure: the two backends
*disagree*, and cross-backend comparison identifies that a disagreement exists
but cannot say which side is correct. That is the concrete cost of not having an
official reference, and it is why item 11 is worth more than a formality.

## 5. Official reference — accepted limitation

The build branch is **blocked by the environment**, verifiably:

- the pinned SDK ships the OpenGL demo project at
  `Samples/OpenGL/Demo/proj.win.cmake/CMakeLists.txt`, and the VS2022 Core libs
  it needs are present (`Core/lib/windows/x86_64/143/`);
- it requires **GLEW 2.2.0**, which the SDK does not ship — it must be fetched
  by `Samples/OpenGL/thirdParty/scripts/setup_glew_glfw.bat`;
- GitHub is unreachable from this environment (`curl` to
  `https://github.com` and `https://www.google.com` both time out after 12 s
  with 0 bytes, while `https://pypi.org` returns HTTP 200, so the block is
  host-specific);
- GLEW is absent from the machine — a bounded search of `D:/` and
  `C:/Users/17519` to depth 6 found no `glew.h`, `glew32.lib`, or `glew-2.2.0*`.
  GLFW 3.4 *is* available (`third_party/glfw`, `D:/library/glfw-3.4`), so GLEW
  is the sole blocker.

**Limitation.** The affected claim is *"the engine's output matches the official
renderer."* No official-reference capture exists, so that claim is unproven.
**Residual risk:** an engine-side systematic deviation that cross-backend
agreement cannot detect because both backends share the engine's PMA and blend
equations — and, per §6, a deviation severe enough that the two backends
disagree about the image while agreeing about the drawable set. **Unblocking
step:** obtain GLEW 2.2.0 into a directory outside both the repository and the
SDK tree, then build `proj.win.cmake` to an out-of-tree binary directory.

## 6. Defect found: Mao renders differently on the two backends

OpenGL and Vulkan produce **deterministically different images** for Mao.
Established facts:

- **Reproducible and frame-independent.** Vulkan captured at `frame_sequence` 2
  and 3 produce one identical image; OpenGL at `frame_sequence` 1 and 2 produce
  another. Removing `--resize` changes the frame numbers and not the pixels.
  Vulkan-vs-Vulkan across three separate runs is byte-identical.
- **Same work submitted on both.** Both log `draws 150, mask_sources 40,
  mask_contexts 14, position_upload_bytes 48160`. The count does not differ, so
  no drawable is being culled on one side.
- **Geometry agrees exactly.** An exhaustive shift search finds identity is the
  best alignment by an order of magnitude (mean abs diff 1.91 at `(0,0)` versus
  18.97 at the next-best shift); flips and rotations are far worse. Pose,
  position, and silhouette match.
- **Only the face diverges.** The differing pixels occupy `x[282..404]
  y[191..410]`, 2792 pixels (0.40%), plus a small blob on a hand.
- **RGB only, never alpha.** Of the pixels differing by >16, `rgb-only=1203`,
  `alpha-only=0`, `both=0`; mean alpha is 255.0 on both sides. Coverage and
  topology agree; only colour disagrees.
- **Vulkan is the side missing detail.** Its face is a pale, flat wash; OpenGL
  shows irises, lashes, blush, and a mouth. Pooled across all 4758 differing
  channel samples, Vulkan is essentially never more detailed (only 156 are
  darker), and it fits as roughly a 13%-white composite over OpenGL
  (slope 0.87, intercept 49) with a large residual, consistent with the pale
  *base* face being revealed where detail drawables are absent rather than with
  a single uniform overlay.

**Leading hypothesis (not confirmed).** Clipping. The discriminating variable
between the two fixtures is mask use, not texture count — Mao has one texture
and fails; Hiyori has two and passes. Mao needs 14 mask contexts and 40 mask
sources; Hiyori needs 2 and 2. The mask planner assigns `slot / 9` to an atlas
channel, so Hiyori touches only atlas channel 0 while Mao spans channels 0 and
1. If multi-context mask-atlas rendering is wrong on one backend, the affected
drawables read coverage 0, are clipped away entirely, and leave the opaque base
face showing — which is exactly the observed signature (RGB differs, alpha does
not, geometry intact, same draws submitted). Capacity is *not* the cause: the
limit is 36 contexts and Mao uses 14.

**What would confirm it.** Dump the context-to-channel assignment and check that
every Vulkan-missing pixel belongs to a channel-1 context, or render a synthetic
fixture whose masks force channel 1. No GPU-side cross-backend mask test exists
today: the Live2D tests that run in CI are SDK-free CPU contract tests, so
multi-region and multi-channel mask atlas rendering has **never** been covered
cross-backend.

**Recommendation.** This is outside L2D5.3's scope and is not fixed here.
It needs its own stage. It also means Mao cannot serve as a cross-backend
regression fixture until resolved — item 9's blend claim is safe because it is
read from model data and is identical on both backends, but no *image* claim
about Mao may be made.

## 7. Tooling

`tools/kp.ps1` gains a Live2D rule: changes under `engine/module/live2d/` or
`engine/test/unit/live2d/` map to area `live2d`, build the five Live2D test
executables, and run one `ctest -R Live2D` instead of falling through to a full
build. Live2D is excluded from the generic `engine/module/` rule the way TTS
already is.

Two details worth recording:

- A single `Live2D` regex is used rather than one regex per executable. A test
  *executable* is named for one of the suites it contains —
  `Live2DMaskPlannerTest` also defines `Live2DMaskAtlasPlannerTest`, and
  `Live2DCoreTest` also defines `Live2DAssetTest`, `Live2DRendererTest`, and
  `Live2DSettingsFixture` — so `-R <target>` silently skipped part of each
  binary. The target-name form ran 10 of the 52 Live2D tests; the suite regex
  runs all 52.
- `Add-UniqueValue` declared `[Parameter(Mandatory = $true)][ArrayList]$List`
  without `[AllowEmptyCollection()]`. PowerShell refuses to bind an empty
  collection to a mandatory collection parameter, and every accumulator in
  `Get-ValidationPlan` starts empty, so **the first `Add-UniqueValue` call of
  any plan threw and `kp.ps1 validate` never reached a build at all** — for
  every file, not just Live2D. Verified pre-existing by reproducing it on
  `engine/runtime/core/base/log_config.cpp`, which touches only long-standing
  rules. Fixed with `[AllowEmptyCollection()]`.

## Remaining risks

1. **Mao's cross-backend divergence** (§6) — open, unowned, needs its own stage.
2. **Item 11 unproven** (§5) — no official reference; residual risk named.
3. **Non-edge opaque at 1024×768 exceeds the frozen tolerance by 1/255** on 2
   channel-samples — carried from L2D4.5, reproduced not introduced.
4. `save/screenshots/validation/` is not checked in: the fixtures are licensed,
   so the comparison results above are reproducible only with a locally
   provisioned `asset/live2d/`, by design.
