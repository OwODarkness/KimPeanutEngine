# L2D5.0 — Evidence Contract Freeze (2026-09-12)

Plan: [L2D5.0](../..//docs/live2d/.plan/L2D5.0.md) ·
Parent: [L2D5](../../docs/live2d/.plan/L2D5.md)

## Objective

Freeze the capture-view, resize, shutdown-accounting, fixture, and
official-reference decisions before L2D5 changes a Render contract, a launch
surface, or a checked-in asset. This stage changes no production code.

## Why the stage was needed

L2D5's remaining work was being carried as four loose TODO lines and a
"Remaining work" list in the L2D4.5 journal. Three of the four subtasks change a
contract that later evidence depends on, so the decisions had to be made before
any of them was implemented rather than discovered during it.

## Design boundary

In: the evidence contract for V1 acceptance items 8–11, plus three carried
residuals. Out: any playback work (L2D6), the frozen L2D4.0 capture tolerances,
and any change to the viewer's rendering behavior.

## Evidence gathered

All of the following is source reading, not execution. No build was run for this
stage because it changes no production code.

### Capture view

| Fact | Location |
| --- | --- |
| `CaptureView` declares a module-named value | `engine/runtime/render/render_capture_service.h:27` |
| The deferred renderer excludes it **by name** to decide whether a capture is deferred | `engine/runtime/render/deferred_renderer.cpp:611-614` |
| The capture service whitelists it | `engine/runtime/render/render_capture_service.cpp:29` |
| Render already special-cases a non-debug view by name | `engine/runtime/render/render_system.cpp:582-586` |
| The module produces it (resolver, startup request) | `engine/module/live2d/live2d_viewer_host.cpp:185`, `:206` |
| Generic tooling maps the string `"live2d"` to it | `engine/runtime/screenshot/screenshot_command_provider.cpp:73` |

Conclusion: `CaptureView` mixes *deferred* views, which the deferred renderer
services through its own pass, with *host-resolved* views, whose target the host
supplies through `CaptureTargetResolver`. `EngineWindow` is the second
host-resolved value and is handled by a different special case. The negative
predicate is what forced a module name into Render: there was no positive way to
say "this is a deferred view".

### Resize

- The viewer window extent is hard-coded 720×960
  (`live2d_viewer_host.cpp:89-92`, `:148`).
- `Live2DRenderer::ResizeOutput` is called **every frame** from the backend
  extent (`live2d_viewer_host.cpp:292`, `:301`), so the code path runs but has
  never observed a change.
- No launch option sets a size. `ParseArguments` accepts exactly `--mode`,
  `--agent-port`, `--graphics-api`, `--startup-level`, `--capture`,
  `--capture-view`, `--capture-alpha`, `--exit-after-capture`; anything else is
  rejected (`launch_options.cpp:249-252`).
- No resize command exists, and the command transport is refused in viewer mode
  (`launch_options.cpp:261-264`), so `capture.screenshot` cannot reach it either.
- Nothing in the viewer calls `SetWindowSize`; only the GLFW framebuffer
  callback and the graphics example do (`rhi_example.cpp:734`, `:1112`).
- `ResizeOutput` requires only a non-null `backend_`, which `Initialize`
  supplies, and is transactional by construction: the replacement is created and
  its view resolved *before* `WaitIdle` and before the old target is destroyed
  (`live2d_renderer.cpp:217+`). Zero extents are rejected; an unchanged extent
  returns early.
- A `FakeBackend final : public graphics::RenderBackend` already exists
  (`engine/test/unit/render/render_system_test.cpp:130`), so a backend-driven
  test is feasible without a GPU.

Conclusion: **there is no way to change the output extent from a scripted run.**
The resize half of V1 item 10 is unproducible, not merely unproven.

### Shutdown accounting

- `Live2DRenderer::GetLiveGpuHandleCount()` sums the renderer's live pipeline,
  texture, buffer, sampler, mask-atlas, and output handles
  (`live2d_renderer.cpp:557-577`). The header records zero as the shutdown
  contract.
- Its only production observer is a warning in `Live2DViewerHost::CleanupGpu()`
  (`live2d_viewer_host.cpp:542-561`) and an ImGui profiler line (`:512-513`)
  that is invisible to headless runs.
- `CubismLifecycle::LiveModelInstanceCount()` (`live2d_cubism_lifecycle.cpp:304-307`)
  *is* asserted, in `Live2DCoreTest.RejectsShutdownWhileModelLeasesAreAlive`.
- **No test references `GetLiveGpuHandleCount()`.**
- There is **no Vulkan validation-error counter**: the debug-utils callback logs
  and returns (`vulkan_device.cpp:37-55`), so "exits without Graphics validation
  errors" can only ever be a log observation.

### Fixture and reference

- The pinned SDK ships sample **sources** (`Samples/OpenGL`, `Samples/Vulkan`,
  `Samples/D3D11`, each with `Demo/proj.win.cmake/` and `proj_msvc20*.bat`) and
  `Samples/Resources/` with eight official models (Haru, Hiyori, Mao, Mark,
  Natori, Ren, Rice, Wanko).
- No `.exe`, no build directory, and no `.sln` exist anywhere in the SDK or on
  the machine. `Samples/Resources/` contains no per-model license or readme.
- `tools/compare_capture_regions.py` is the frozen comparator and requires equal
  dimensions. `tools/kp.ps1` has **no Live2D rule**: any `engine/module/` path
  sets `$fullBuild = $true`, so Live2D changes only ever get a full build.

## Frozen decisions

| # | Decision | Classification |
| --- | --- | --- |
| 1 | Rename the module-named capture value to a role-named one for "the standalone host's own output target, resolved by the host's resolver." No host-view registry. Implemented as `HostOutput`. | contract |
| 2 | Replace the negative deferred test with a positive predicate over the views the deferred renderer converts: the ten diagnostic views only. `SceneColor` is read back directly and needs no conversion, so it is excluded. Implemented as `RequiresCaptureViewConversionPass`. | contract |
| 3 | Keep `"live2d"` as a tooling-level alias for the capture-view string so recorded L2D4.5 procedures keep working; document it as a launch-time alias, not a Render semantic. | policy |
| 4 | Add a validation-only launch option that changes the viewer's window extent once mid-run. | contract |
| 5 | Split the shutdown assertion: a renderer-level test for the contract, a viewer run for the process. | policy |
| 6 | Fixture is synthetic; the licensed model stays an environmental prerequisite and is never redistributed. | policy |
| 7 | Attempt the official sample build in an output directory outside both the repository and the SDK tree. | contract |
| 8 | Assert blend-mode coverage from fixture data, not from draw counts or code reading. | policy |
| 9 | The missing-`.moc3`/invalid-MOC import tests and the `--capture-alpha` regression test are L2D5 scope. | policy |
| 10 | The `model/rock1-bl/rock2` content gap is deferred as unrelated to Live2D. | policy |

Decisions 1, 2, 4, and 7 are contract changes and must be implemented in that
order; the rest are policy that shapes tests and evidence.

### User decisions

Decisions 4, 6, and 7 were escalated because they add user-facing CLI surface,
carry licensing consequences, and write build output outside the repository
respectively. All three were confirmed as recommended:

- **4** — a validation launch option is added, on the same recorded
  justification as `--exit-after-capture` (`launch_options.h:41-44`): without it
  the path can never execute.
- **6** — synthetic fixture; the licensed model remains locally provisioned and
  non-redistributed. Accepted residual: full blend-mode coverage may not be
  expressible without authoring a MOC.
- **7** — the official sample build is attempted. The SDK's `Samples/` sources
  were previously believed unusable; they are present and buildable, so item 11
  is unblockable in principle. Provenance: the reference executable is built
  from the pinned `5-r.5` sources, never redistributed.

## Validation

No build or test was run: this stage changes no production code, so compilation
is not evidence for anything it claims. Every fact above is a source-reading
claim with a file and line, and the build/test evidence for the L2D5 subtasks is
recorded in their own journals.

## Remaining risks

1. **The fixture residual is real.** Without an authored MOC, "all three blend
   modes" may not be provable from a synthetic fixture, in which case item 9
   stays partly open and must be recorded as such rather than claimed.
2. **The official sample build may fail or be slow.** It is the only path to
   item 11, but a sample that builds is not automatically a *usable* reference:
   camera, canvas transform, and clear color must be matched to the engine's
   captured configuration, or the comparison is meaningless even if it runs.
3. **"No validation errors" remains unassertable.** With no Vulkan
   validation-error counter, that half of item 10 can only be evidenced by a
   clean log. This is a limitation of the current backend, not of this plan, and
   should not be reported as an assertion.
4. **The `"live2d"` tooling alias is a deliberate exception.** It keeps recorded
   validation procedures working, but it does mean a module name survives in
   generic tooling. The V1 criterion names Render and Graphics, so the letter is
   satisfied; the spirit is only partly.

does not depend on any later choice.
