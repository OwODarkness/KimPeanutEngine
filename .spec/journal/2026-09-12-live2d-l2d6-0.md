# Live2D L2D6.0 — Playback contract freeze

- Status: complete
- Date: 2026-09-12
- Spec: [live2d-authored-playback](../specs/live2d-authored-playback.md)
- Plan: [L2D6.0](../../docs/live2d/.plan/L2D6.0.md) (parent [L2D6](../../docs/live2d/.plan/L2D6.md))
- Parent roadmap: [Live2D Module Roadmap](../../docs/live2d/TODO.md)

## Objective

Freeze the authored-data, ownership, time, priority, fade, event, expression,
and parameter-update rules before L2D6.1 changes the native product or any stage
constructs SDK motion objects. This task is investigation and scaffolding only:
no production behavior changed.

## Design boundary

All new code is probe/test scaffolding:

- `engine/test/probe/live2d_playback_probe/` — a standalone MSVC-only probe that
  builds the pinned R5 `Motion/` translation units the engine deliberately does
  not link, drives them with a caller-supplied clock, and prints observable
  parameter/queue/event state. It is **not** added to the parent build.
- `engine/test/unit/live2d/live2d_asset_test.cpp` — one added characterization
  test that drives the real V1 importer against a synthetic animation fixture.

No file under `engine/module/live2d/` was modified.

## 1. V1 product/importer characterization (investigation 1 and 2)

### 1.1 How V1 actually represents model3 references

`engine/module/live2d/runtime/live2d_import.cpp` walks `FileReferences` and, for
**every string leaf**, stores a chunk whose *name is the slash-joined JSON key
path* and whose *payload is the bytes of the file that string names*
(`AddReferenceValue`, lines 141–177). `Moc` and `Textures` are skipped and stored
in their own typed fields (line 293).

The checked-in Hiyori package, flattened the way V1 walks it:

| Stored as | Chunk name | Payload |
| --- | --- | --- |
| typed field | — | `hiyori_pro_t11.moc3` (444 480 B) |
| typed field | — | 2 texture paths in `.archive/` |
| chunk | `Physics` | `hiyori_pro_t11.physics3.json` |
| chunk | `Pose` | `hiyori_pro_t11.pose3.json` |
| chunk | `DisplayInfo` | `hiyori_pro_t11.cdi3.json` |
| chunk ×10 | `Motions/<group>/<index>/File` | one `motion3.json` per motion |

Chunk names are *derived from JSON key text*, so the only thing that tells a
motion apart from a physics file is the literal substring `Motions/`. Nothing in
the product is typed.

### 1.2 The required fixture, and what V1 does with it

The checked-in Hiyori package cannot exercise the animation path at all: it has
**no `Expressions` array, no per-motion `FadeInTime`/`FadeOutTime`, no `Sound`,
and no user events.** All 10 motions are `Loop: true`, durations 1.6–8.57 s.

I therefore built the fixture L2D6.0 requires (two motion groups, model3 fade
overrides on two entries, two named expressions, one optional sound reference,
plus `Groups`) and drove the **real** importer through
`Live2DAssetTest.CharacterizesV1AnimationMetadataLoss`, copying Hiyori's real
`.moc3` and a real texture beside it.

Observed, verbatim:

```text
[v1-char] with-expressions: imported=0 diagnostic='Live2D source file is missing or too large:
          C:/Users/.../Temp/kpengine_live2d_v1_char_root/live2d/probe/Shy'
[v1-char] motion-only: imported=1 diagnostic=''
[v1-char] motion-only: moc=444480 textures=1 chunks=4
[v1-char] motion-only:   'Motions/Alpha/0/File' (221 bytes)
[v1-char] motion-only:   'Motions/Alpha/0/Sound' (9 bytes)
[v1-char] motion-only:   'Motions/Alpha/1/File' (221 bytes)
[v1-char] motion-only:   'Motions/Beta/0/File' (221 bytes)
```

Three separate V1 defects, all demonstrated rather than inferred:

1. **V1 cannot import any `model3.json` containing `Expressions`.** The array is
   walked as references, so the *display* name `"Shy"` is resolved as a *file
   path*. The importer fails with `Live2D source file is missing or too large:
   .../probe/Shy` and publishes nothing. This is not a corner case; it is every
   standard Live2D model that ships expressions.

   > **Correction (2026-09-12, L2D5.3).** This defect is **fixed in V1**. A leaf
   > entry under `FileReferences` — a motion or an expression — names its file
   > under `File` and carries its remaining members as metadata, so the walk now
   > descends into `File` and `Sound` only and skips a leaf's other members
   > (`live2d_import.cpp`, `IsFileEntry`). The characterization now reports
   > `with-expressions: imported=1 diagnostic=''` with six chunks, none derived
   > from a display name, and
   > `Live2DAssetTest.ResolvesExpressionEntriesByFileNotByName` pins the
   > behavior. The claim above was true when written and is false as of this
   > correction; it was fixed early because L2D5.3's blend fixture (the SDK's
   > Mao) ships expressions and could not be imported otherwise. **Defects 2 and
   > 3 above stand unchanged** — numeric fade metadata is still dropped and
   > `Groups` is still not imported, so V1 remains unable to recover typed
   > identity and the no-heuristic-upgrade rule in §1.3 is untouched.
2. **Numeric metadata is silently dropped.** `AddReferenceValue` branches only on
   `is_string()`, `is_array()`, `is_object()`. `FadeInTime: 0.25`,
   `FadeOutTime: 0.75` and `FadeInTime: 2.0` fall through every branch with no
   chunk, no diagnostic, and no failure. The four chunks above are the *complete*
   inventory: the fade overrides are absent.
3. **Top-level keys are never imported.** The walk starts at `FileReferences`, so
   `Groups` (authored `EyeBlink` / `LipSync` parameter targets) is not stored at
   all. L2D6's motion model curves need those effect IDs without re-opening the
   source file.

### 1.3 Proof that `optional_chunks` cannot recover typed identity

The parent plan requires that V1 never be *heuristically upgraded*. That is not
merely a policy preference — the information is genuinely absent:

- **The name is a key path, not a type.** `Motions/Alpha/0/File` is a string. To
  learn that it is a motion, which group it belongs to, and that its index is
  positional, a reader must already know the `model3.json` schema. That is
  exactly the "source knowledge" the plan forbids.
- **Numbers have no representation.** A chunk payload is `std::vector<std::byte>`
  and a chunk name is a key path. A fade override has neither a chunk nor a
  field; V1 discards it before serialization, so no reader — however clever —
  can recover `FadeInTime: 0.25` from the V1 bytes. The data is gone, not hidden.
- **Identity is ambiguous by construction.** `Motions/Alpha/0/Sound` is a sound
  only because of the trailing key word. A group literally named `Sound` would
  make `Motions/Sound/0/File` indistinguishable from a motion named `Sound` whose
  sound reference is `0/File`. Nothing in the encoding disambiguates.
- **Distinct types share one namespace.** Physics, pose, display-info and motion
  bytes are all "an opaque chunk with a path-shaped name". Any V2 reader that
  reconstructed types from names would be executing a private, unversioned schema
  and would silently mis-handle any future exporter change.

Conclusion: V1 → V2 must be a **reimport**, and playback over a V1 product must
report a stable "reimport required" diagnostic, exactly as the parent plan
states.

## 3. Probe: official input sequences and expected outputs (investigation 4, deliverable 1)

Command:

```bash
cmake -S engine/test/probe/live2d_playback_probe -B build-l2d6-probe -G "Visual Studio 17 2022" -A x64
cmake --build build-l2d6-probe --config Debug
./build-l2d6-probe/Debug/Live2DPlaybackProbe.exe \
    asset/live2d/hiyori_pro/runtime/hiyori_pro_t11.moc3
```

Fixture: Hiyori Pro `.moc3`, probe parameter `ParamAngleX` (index 0, range
[-30, 30], default 0, target +30). Synthetic `motion3.json` clips emit one
numeric literal per line — the R5 numeric reader terminates only on `,` or `\n`
and rejects a space before `]`, which is why the official exporter formats the
same way.

Fade weight is recovered as `(observed − source) / (target − source)`.

### 3.1 Priority (S1, S2)

| Step | Input | Observed | Interpretation |
| --- | --- | --- | --- |
| 1 | `ReserveMotion(1)` on idle manager | accepted, reserve=1 | — |
| 2 | `ReserveMotion(1)` again | **rejected**, reserve=1 | strictly greater-than, not ≥ |
| 3 | `ReserveMotion(0)` | rejected | 0 is not a reservable priority |
| 4 | `ReserveMotion(-1)` | rejected | negative is not reservable |
| 5 | `ReserveMotion(2)` | accepted, reserve=2 | — |
| 6 | `StartMotionPriority(m,false,2)` | current=2, **reserve=0** | starting consumes the reservation |
| 7 | `ReserveMotion(1)` | rejected | 1 ≯ current 2 |
| 8 | `ReserveMotion(3)` | accepted | — |
| 9 | `ReserveMotion(3)` again | rejected | strictly greater-than |
| 10 | start at priority 5, then `ReserveMotion(4)` | rejected | current 5 blocks 4 |
| 11 | `StartMotionPriority(m2,false,4)` anyway | **both entries queued**, current=4 | start never enforces priority; the 5-entry got `fadeOut=1` |

`ReserveMotion` alone is exactly the parent plan's rule. Step 11 is the reason
`RespectPriority` must be implemented engine-side: the SDK start call cannot
reject anything, so a rejected request has to be refused *before* it is made.

### 3.2 Replacement cross-fade (S3)

Clip A target +30, fade in/out 0.5 s; clip B target +1, fade in/out 0.5 s,
started at t=0.5 with priority 2. `delta = 0.25 s`.

| t | param | entries |
| --- | --- | --- |
| 0.250 | 0.000 | A w=0.0000 |
| 0.500 | 15.000 | A w=0.5000 |
| 0.500 | — | start B; A marked `fadeOut=1` |
| 0.750 | 30.000 | A w=1.0000 (end 1.25), B w=0.0000 |
| 1.000 | **8.000** | A w=0.5000 (end 1.25), B w=0.5000 |
| 1.250 | 1.000 | A w=0.0000, B w=1.0000 |
| 1.500 | 1.000 | B alone |
| 2.000 | 1.000 | B alone |

Three separate facts:

- **The first update after a start contributes nothing.** At t=0.25 the weight is
  0.000 even though the clip was started "at t=0". `SetupMotionQueueEntry` anchors
  `startTime` and `fadeInStartTime` at the first update, so `fadeIn = sine(0) = 0`.
  Authored playback therefore has a one-advance delay unless the engine accounts
  for it.
- **The outgoing end time is `firstUpdateTimeAfterTheReplacement + fadeOut`**, not
  `start + duration − fadeOut`. A's end moved from 4.25 to 1.25. The entry is
  removed once `endTime < userTimeSeconds`.
- **Overlapping entries blend sequentially, each toward its own target from the
  model's current value.** At t=1.0: A gives `0 + (30−0)·0.5 = 15`, then B gives
  `15 + (1−15)·0.5 = 8`. The observed 8.000 matches exactly. This is the golden
  for the cross-fade tests.

### 3.3 Natural completion (S4, S10)

Clip duration 1.0 s, fade-in 0.5, no fade-out.

| t | updated | finish callback | current priority | entries | param |
| --- | --- | --- | --- | --- | --- |
| 0.250 | 1 | 0 | 1 | 1 | 0.000 |
| 1.000 | 1 | 0 | 1 | 1 | 30.000 |
| **1.250** | 1 | **1** | **0** | **0** | 30.000 |
| 1.500 | **0** | 1 | 0 | 0 | 0.000 |

Natural completion fires `_onFinishedMotion` exactly once, clears current
priority to 0, and removes the entry. The following update reports `updated = 0`.
Discarding the model and re-loading the checkpoint drops the parameter back to its
default — playback leaves no residue.

### 3.4 Cancellation (S5)

| Mode | Input | finish callback | entries | effect |
| --- | --- | --- | --- | --- |
| Immediate | `StopAllMotions()` | **0** | 0 at once | parameters revert to the checkpoint on the next update |
| Authored fade | `entry->SetFadeout(0.4f)` at t=0.25 | **0** | removed at t=1.0 | end time became **0.900**, not `start + duration` |

Fade-out weights: t=0.5 → 0.5000; t=0.75 → 0.2061 (`sine(0.15/0.4) = sine(0.375)`
= 0.2061); t=1.0 → entry gone. Neither cancellation path invokes the finish
callback, so **terminal events cannot be derived from the SDK callback**;
`MotionCancelled` and `MotionInterrupted` must come from engine-side intent
bookkeeping.

### 3.5 User events (S6)

Clip: 2.0 s, events at 0.0 (`ev_zero`), 0.5 (`ev_half_a`), 0.5 (`ev_half_b`),
1.0 (`ev_one`), and 2.5 (`ev_past_end`, beyond `Duration`).

| Sequence | Fired, in order |
| --- | --- |
| 0.25 s steps | t=0.25 `ev_zero`; t=0.75 `ev_half_a ev_half_b`; t=1.25 `ev_one`; never `ev_past_end` |
| 0.5 s steps | t=0.5 `ev_zero`; t=1.0 `ev_half_a ev_half_b` |
| 0.1 s then one 5.0 s step | `ev_half_a ev_half_b ev_one ev_past_end`, finish callback = 1, entries 0 |
| single 5.0 s first step | `ev_zero` only, `t=5.0`, `end=7.0`, **not finished** |

- The window is `(lastCheckTime, currentTime]` measured in motion-local seconds,
  so an event authored at exactly `0.0` **does** fire, on the first advance.
- Co-authored events at the same time fire in array order (`ev_half_a` first).
- **One large advance batches every event in its window**, including one authored
  past `Duration`, because the fired list is collected *before* the finished flag
  is processed. Events are not lost to a big delta, but they are all delivered on
  the same call and lose their timing.
- A large **first** advance is absorbed: `SetupMotionQueueEntry` anchors the clock
  at that update, so the clip restarts from local t=0 and does not complete.
- **`_eventCallback` is called with no null check.** The isolated child-process
  run (S6b) dies with `0xC0000005` on the first fired event when no callback is
  registered:

  ```text
  [S6b] child exit status=-1073741819 (0xC0000005)
  conclusion: null callback dereferences immediately; a callback must always be set
  ```

  The engine must therefore always install a callback; "no callback" is a crash,
  not "events ignored".

### 3.6 Motion fade weight (S7)

fade-in 1.0 s, fade-out 0.5 s, duration 2.0.

| local time | weight | easing check |
| --- | --- | --- |
| 0.0 (first update) | 0.0000 | `sine(0)` |
| 0.25 after first update | 0.1464 | `sine(0.25) = 0.5 − 0.5cos(0.25π)` |
| 0.5 | 0.5000 | `sine(0.5)` |
| 0.75 | 0.8536 | `sine(0.75)` |
| 1.0 | 1.0000 | clamped |
| 2.0 | 0.5000 | fade-out `sine(0.5)` |
| 2.25 | entry removed | `end 2.25 < userTime` |

Fade-out is computed from `GetEndTime() − userTimeSeconds`, so a fade-out runs
*into* the end time and the entry disappears at exactly that time.

### 3.7 Expressions (S8, S9)

Clip: one parameter, value 0.6, fade in/out 1.0 s, `Add`.

| t | param | fadeWeight(0) |
| --- | --- | --- |
| 0.25 (first update) | 0.000 | 0.0000 |
| 0.5 | 0.088 | 0.1464 |
| 0.75 | 0.300 | 0.5000 |
| 1.0 | 0.512 | 0.8536 |
| 1.25 | 0.600 | 1.0000 |
| 2.0 | 0.600 | 1.0000 |

Same easing and same first-update-anchoring as motions. Starting a **second**
instance of the same expression while the first is at full weight (t=2.25):
the old entry gets `end 3.25` and fades out over 1.0 s while the new entry fades
in; the *parameter stays 0.6 throughout*, because both entries drive the same
value. A same-name restart is therefore observable only as a transition, not as
a value change. `StopAllMotions()` removes all entries at once and the parameter
returns to the checkpoint.

Blend math at a **non-zero** base of 12.0, value 0.6, fade-in 0, applied as the
official transaction does (`LoadParameters → base write → SaveParameters →
expression`, with no second save):

| Blend | frame 1 | frame 2 | Formula |
| --- | --- | --- | --- |
| `Add` | 12.600000 | 12.600000 | `base + value` |
| `Multiply` | 7.200000 | 7.200000 | `base · value` |
| `Overwrite` | 0.600000 | 0.600000 | `value` |

Identical across frames ⇒ **the expression is a non-persistent relative layer**.
Because it runs after `SaveParameters` and is never re-saved, the next frame's
`LoadParameters` erases it and it is recomputed from the persisted base. It does
not accumulate. Probing `Multiply` against a zero base would have returned 0 for
both the correct and the "no contribution" case, which is why the non-zero base
matters.

Note the expression-neutral value: an expression entry disappears as soon as its
weight reaches 0, so `Add` on top of the checkpoint is stable but a parameter the
motion also drives is blended twice in one frame unless the base is re-established
first — which is exactly why the base write must precede the motion.

### 3.8 Delta-time edges (S10)

| Sequence | Observed |
| --- | --- |
| `delta = 0`, three times | `updated=1` each time, `t` stays 0.000, weight 0.000, entry never progresses |
| one `delta = 1000` as the first advance | absorbed; `t=1000`, `end=1001`, weight 0, **not finished** |
| `0.25` then `delta = 1000` | natural completion, callback = 1, entry removed |
| `+0.5` then `delta = −0.25` | `t` rewinds 0.500 → 0.250; the clip re-evaluates backwards |
| `delta = −1.0` as the first advance | `t = −1.0`, `end = 0.0`, never finishes; `endTime > 0` is false so the time-based finish check can never fire |

`delta = 0` is harmless but inert; a negative delta rewinds the clock and can
**strand an entry** with a non-positive end time so it never completes. A large
first delta silently restarts the clip. All three must be rejected by
`AdvancePlayback` before touching the SDK, which is what the parent plan
requires.

### 3.9 Loop flag (S11)

| Authored `Loop` | `GetLoop()` | `GetDuration()` |
| --- | --- | --- |
| `false` | 0 | 1.5000 |
| `true` | **0** | 1.5000 |

`CubismMotion::Create` never reads `Loop` from JSON. **One-shot is already the SDK
behavior**, so L2D6's one-shot-only stance needs no suppression logic — but it
does mean Hiyori's ten `Loop: true` motions all complete naturally and can be
used as one-shot fixtures.

### 3.10 Model-target opacity (S12)

A `Target: "Model"` / `Id: "Opacity"` curve is recognized
(`IsExistModelOpacity()=1`, `GetModelOpacityIndex()=0`) and writes the model
opacity: 1.0000 before, 0.2500 after one update. This is a **model** curve, not a
parameter curve, so the engine's parameter checkpoint transaction does not
restore it — it is recomputed from the motion each frame and reverts to 1.0 when
no clip is active. The parent plan's parameter-only scope holds, but the render
side must not assume opacity is a parameter.

### 3.11 Overlap capacity (S13)

| Overlapping `StartMotionPriority` calls | Queue entries |
| --- | --- |
| 8 | 8 |
| 32 | 32 |
| 64 | 64 |

The SDK imposes **no** bound and no rejection at any count; the queue is an
unbounded `csmVector`. Bounding overlapping fades is therefore an engine-side
policy, not an SDK property, and the failure must be produced before mutating the
manager.

## 4. Hiyori comparison and synthetic fixture requirements (investigation 5, deliverable 2)

### 4.1 What Hiyori can and cannot prove

Hiyori Pro: 7 motion groups (`Idle`, `Flick`, `FlickDown`, `FlickUp`, `Tap`,
`Tap@Body`, `Flick@Body`), 10 motions, 2 textures, `Groups` = `LipSync`
(`ParamMouthOpenY`) and `EyeBlink` (`ParamEyeLOpen`, `ParamEyeROpen`).

| L2D6 case | Hiyori | Consequence |
| --- | --- | --- |
| Motion bytes, `(group, index)` identity | yes (7 groups) | directly usable |
| `Groups` parameter targets | yes | directly usable |
| Natural one-shot completion | yes (loop ignored) | directly usable |
| Model3 fade overrides | **no** (`FadeInTime` absent on all 10) | needs a synthetic `model3.json` |
| Named expressions | **no** `Expressions` array | needs a synthetic `exp3.json` + `model3.json` |
| Authored sound reference | **no** `Sound` key | needs a synthetic `model3.json` |
| Authored user events | **no** `UserData` array, `UserDataCount = 0` | needs a synthetic `motion3.json` |
| Priority / cancellation / delta edges | fixture-independent | synthetic clips are cleaner |

Hiyori is therefore sufficient for identity, wiring and lifecycle evidence, and
insufficient for every authored-metadata case. Those need synthetic `model3.json`,
`motion3.json` and `exp3.json` files, which this task already produces inside its
tests and probe.

### 4.2 Redistribution status

| Artifact | Redistributable? | Basis |
| --- | --- | --- |
| Synthetic `model3.json` / `motion3.json` / `exp3.json` authored here | **yes** | original text, no Live2D content |
| Hiyori Pro `.moc3`, textures, motions | **no** | Live2D *Free Material License Agreement* + *Terms of Use* (`asset/live2d/hiyori_pro/ReadMe.txt`); additionally `/asset/*` is git-ignored, so the package is machine-local and never committed |
| A `.moc3` for a runtime instance test | **not synthesizable** | the SDK ships no public MOC compiler; a live model needs an authored/exported MOC |

Practical rule for L2D6.1–L2D6.4:

- Codec, importer and validation tests must use **synthetic JSON only** and can
  run anywhere. The existing `Live2DAssetTest` targets already require the
  locally provisioned Hiyori package; that dependency should not grow.
- Only tests that build a live `CubismModel` need a real `.moc3`, and those must
  keep treating `asset/live2d/hiyori_pro` as an environment prerequisite (as the
  current suite does), not as committed content.
- No official sample executable is available in this environment for an
  independent visual reference comparison; the pinned Framework source and the
  probe are the reference. This is the same limitation already recorded against
  L2D5.

## 6. Public value/API sketch and product V2 limits (deliverable 4 remainder)

The parent plan's sketch survives contact with the evidence unchanged, with four
additions it could not have known before the probe:

1. **`Live2DPlaybackUpdateResult` needs a "clock anchored" notion.** Because the
   first advance after a start contributes weight 0 and anchors the fade clock
   (decision 6), the engine either accepts the one-advance delay or advances the
   clock at `PlayMotion` time. The frozen choice is to accept the SDK's anchoring
   and document it, so `PlayMotion` stays free of time state and the transaction
   remains the only place time moves.
2. **`Live2DMotionStartMode::RespectPriority` must be checked before the SDK
   call** (decision 4). `PlayMotion` therefore performs its own comparison against
   engine-tracked current/reserved priority; it cannot delegate the rejection to
   `StartMotionPriority`.
3. **Terminal events are engine-derived** (decisions 12–14). Only natural
   completion has an SDK hook; interruption and cancellation are computed from
   the token bookkeeping the controller already owns. The `MotionUserEvent` token
   stays invalid (decision 21).
4. **A mandatory event callback** (decision 20) means instance creation always
   registers one, and the callback never invokes user code — it only appends into
   preallocated storage drained by `AdvancePlayback`.

Product V2 limits to carry into L2D6.1:

| Limit | Value | Note |
| --- | --- | --- |
| per clip / expression-name / sound-field bytes | 1 MiB | same field bound as V1 |
| motions, expressions, parameter groups, optional chunks | 4096 each | same collection bound as V1 |
| total product bytes | 512 MiB | unchanged |
| motion group order | canonical bytewise on the object keys | matches V1's existing object iteration order |
| motion array order | authored | never reordered |
| expression order | authored | never reordered |
| parameter-group order | authored | preserved with IDs |
| fade presence | explicit presence bit + value | absent ≠ 0; absent means "SDK default 1.0 s" |
| sound | opaque `std::vector<std::byte>`, may be empty | presence is `!empty()` |

## Remaining risks and unverified areas

- **L2D5 entry-gate evidence is still incomplete.** The parent plan depends on
  L2D5 proving one model through update, snapshot, submission, presentation,
  capture, resize and clean shutdown. `docs/live2d/TODO.md` still lists
  `CaptureView::Live2D` in Render's capture enum as a known defect, resize is
  unevidenced, and the official-reference comparison is blocked (no sample
  executable). L2D6.0's semantic gate closes, but the L2D5 handoff is not
  actually proven and should be reconciled before L2D6.4's aggregate acceptance.
- **Product V2 bounds are proposed, not yet implemented.** The 1 MiB per-clip
  bound is inherited from V1's shared field limit; a motion3.json above 1 MiB
  would be rejected. No fixture here exceeded 1 MiB, so the bound is
  unexercised.
- **The cross-fade golden assumes queue-order sequential blending.** Measured at
  one overlap depth (2 entries). Three-way overlap was not measured; the formula
  is confirmed by source at every depth, but only 2 entries were observed.
- **Expression + motion interaction on the same parameter** was reasoned from the
  transaction order and the base-write rule, not measured end-to-end with both
  active in one frame. L2D6.3 should add that golden.
- **`TotalUserDataSize`** is read by `CubismMotionJson` but unused by
  `CubismMotion::Create`; the probe writes it for fidelity only.
- **S13 measured 64 entries, not a limit.** The real capacity policy number is an
  engine choice and is not fixed here; only the requirement that the SDK imposes
  none is.
- The characterization test takes ~7 s (texture cooking) and depends on the
  locally provisioned `asset/live2d/hiyori_pro` package, like the pre-existing
  tests in that file.
