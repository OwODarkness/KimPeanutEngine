# MODE1.4 — Startup validation and viewer evidence

Date: 2026-09-11

## Objective

Complete the mode-selection policy and prove that the standalone Live2D
viewer can resize, present, and capture Hiyori without constructing the
traditional Scene3D services.

## Landed changes

- Added `RuntimeLaunchOptions::startup_capture_override` and the viewer-only
  `--capture save/screenshots/validation/*.png` option.
- Rejected `--startup-level` and `--agent-port` in `live2d-viewer`; rejected
  `--capture` in `scene3d`.
- Added a runtime scene-service state seam. `Scene3DHost` verifies its lazy
  service construction, while viewer startup rejects an already initialized
  scene composition.
- Added Live2D output-target resize handling. The host reads the current
  backend extent after `BeginFrame`; the renderer recreates only its own color
  target at a safe `WaitIdle` boundary. Vulkan/OpenGL swapchain policy stays in
  the backend.
- Added host-owned startup capture using the existing API-neutral render
  capture and Runtime PNG export services. The request captures the presented
  viewer image: before OpenGL swap and after Vulkan present.
- Aligned the viewer's cross-backend color path without changing the existing
  PBR path: OpenGL keeps its sRGB-capable default framebuffer, while Vulkan's
  UNORM presentation path applies the matching linear-to-sRGB conversion in
  the Live2D color shaders through the existing graphics API shader macro.
- Widened the viewer-only Hiyori framing by 1.25x horizontally while preserving
  the vertical fit and center. The scene renderer and model geometry are not
  changed.

## Reference gate

- Sakura's standalone Live2D Viewer sample supports keeping the viewer as a
  process-level composition with its own window/render loop. This supports
  keeping viewer capture and resize policy in `Live2DViewerHost`.
- gkNextEngine's frame submission path treats minimize/out-of-date acquire and
  present as recoverable and defers swapchain recreation; its dedicated
  screenshot service sits above renderer readback. KimPeanut follows the same
  ownership split: backend owns swapchain recovery, the host owns the viewer
  capture request, and shared services expose only API-neutral image data.

## Validation

- `cmake --build build --config RelWithDebInfo --target RuntimeLaunchOptionsTest KimPeanutEngine -j 1` — passed.
- `ctest --test-dir build -C RelWithDebInfo -R RuntimeLaunchOptionsTest --output-on-failure` — 7/7 passed.
- Standalone OpenGL viewer with `--capture save/screenshots/validation/mode1-4-hiyori-opengl.png` — process reached the render loop and exported a non-empty Hiyori PNG.
- Standalone Vulkan viewer with `--capture save/screenshots/validation/mode1-4-hiyori-vulkan.png` — process reached the render loop and exported a non-empty Hiyori PNG.
- Both captures were visually inspected. Generated captures remain validation artifacts and are not source changes.
- Final corrected captures were inspected after the color/framing fix:
  `mode1-4-hiyori-opengl-final2.png` and `mode1-4-hiyori-vulkan-final2.png`.
  Both show the same widened Hiyori character and matching character colors;
  the remaining backdrop tone difference is the backend presentation clear
  behavior, not a change to the character shader or PBR scene path.

## Remaining risk

The resize path is exercised by the backend extent query and target recreation
logic, but this run did not automate a live window drag/resize event. A future
host-control seam can add that without changing Scene3D or RenderSystem.
