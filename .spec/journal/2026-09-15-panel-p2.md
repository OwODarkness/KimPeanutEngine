## Objective

Make the panel visible for the first time. P0 and P1 produced a representation
and real baked glyphs, but nothing drew them: `ToAsciiArt` was the only way to
see any output, and both panel libraries were linked by tests alone.

## 1. Core: single-channel payloads

`BytesPerPixel` returned 0 for `R8_UNORM`, so `IsTextureMipChainValid` demanded
empty pixels and `TextureManager::CreateTexture` rejected any R8 texture that
carried a payload.

Before changing it, the allocation-only path was checked, because it is what
makes the G-buffer object-mask attachment legal: `CreateTexture` tests
`IsGpuAllocationOnlyTexture` **first** and skips validation entirely, so an
empty-pixel R8 texture is unaffected. `LeavesAllocationOnlyR8ToTheTextureManagerGuard`
pins that boundary explicitly — the validator still rejects an empty R8 payload,
because it is not the thing that makes allocation-only textures legal.

The change is deliberately not exhaustive: the other uncompressed formats still
return 0, and the comment says so, so a reader does not mistake the function for
a complete table.

## 2. Planner and renderer

The planner is CPU-only and compiles without Render or a backend, in the same
shape as `Live2DRenderPlannerTest`. Seven tests assert the pass is a target (never
presentation), that both descriptors sit at set zero, that the viewport covers
the output, that no scissor is set, and that a missing pipeline, mask, sampler,
target, vertex buffer, index buffer, index count, or output extent each produce a
failed plan with **no** published work.

The renderer test reuses `engine/test/support/fake_render_backend.h`, extracted
during L2D5.2. Ten tests cover handle minting, the recreate-and-release mask swap,
transactional resize, failed-create paths, and cleanup.

Two problems surfaced while writing it:

- **The probe has no texture-destroy event.** So "the previous mask was released"
  cannot be asserted directly. It is asserted indirectly and more strongly: the
  live handle count must be *unchanged* across an upload, which a leak would
  grow.
- **`Record` needs an active frame.** Four tests failed with "render submission
  requires an active frame context" until the harness bracketed the call with
  `frame.Begin`/`frame.End`, as the Live2D harness does. The bracket is part of
  the production sequence, not test scaffolding.

`panel_renderer_test.cpp` also needed `copy_runtime_dependencies`, because
linking Render pulls a runtime DLL and the executable could not start at all —
gtest reported a *discovery* failure rather than a build error, and the raw
process exit was 127 with the reason only visible outside the pipe.

## 3. Hosting

The panel gets its own application mode rather than being loaded by the Live2D
viewer, because that would make one module depend on the other.

**The first run crashed**: `Assertion failed: global_editor_context.window_system_`
at `engine/editor/editor.cpp:49`. `Engine::Initialize` branches on the application
mode, and only `Live2DViewer` was enumerated as a standalone viewer. Rather than
add `PanelViewer` to each check — and leave the same trap for the next mode —
the concept was named once as `Engine::IsStandaloneViewerMode()` and all three
branches now use it. `Engine::SetStartupCaptureOverride` had the same problem and
was generalized the same way.

Two build errors were mechanical: `CommandRegistration` is move-only, so the
command provider's results could not be `const`; and `PanelRenderer` had to be
included rather than forward-declared, because the host owns a `unique_ptr` to it.

disagree about. `live_gpu_handles 6` in every run — pipeline, sampler, two
buffers, dot mask, output target.

Captures are under `save/screenshots/validation/`, which is git-ignored.

## 5. Corrections to earlier claims

- **`--capture-view live2d` now means the product view for the panel too.** The
  option is owned by whichever standalone host runs; only the options naming one
  host's own content are exclusive to it. The spelling is a misnomer for a panel
  run and is recorded as an open decision rather than changed, since a neutral
  spelling would touch Live2D's documented surface.
- **Error messages changed** from "only valid in live2d-viewer mode" to "only
  valid in a viewer mode" for the capture, resize, and exit options. No test
  pinned those strings; the checks were made before changing them.

## 6. Addendum — the bezel, and who owns the target

*Added 2026-09-15, after the stage was committed.*

The captures above render the dot pattern correctly, and they do not look like a
dot-matrix display. The panel was reviewed and the observation was exact: five
lit dots in a row fused into one solid bar, so the panel read as a
low-resolution image rather than as a matrix of elements. At the captured two
pixels per dot, adjacent lit dots are contiguous pixels with nothing between
them.

That is a **display** defect, not a representation one. `DotMatrix` stores one bit
per dot and should not know that gaps exist; if the gap were content, every
glyph, effect, and test would have to carry it. The bezel belongs in the fragment
shader, and it now lives there: `fract(fragUV * textureSize(dotMask, 0))` gives
the position within the current dot, and a margin is left dark on every side.

Two things were needed, not one.

**Resolution.** The first capture was a 1024x512 target for a 512x256 dot grid —
two pixels per dot, so a 25% gap is half a pixel. The render target is now sized
to the **panel** times a pixels-per-dot constant (eight, so 4096x2048), rather
than to the window. A display device has its own resolution; tracking the window
made the dot size a function of how large the window happened to be. As a
consequence `--resize` no longer changes what is captured, so the host no longer
defers its capture on a resize, and the resize-wait machinery is gone. The
renderer's `ResizeOutput` remains — it is still tested, and a scene-placed panel
will want it — but the host no longer calls it per frame.

**The gap is a fraction of a dot, not a pixel count**, so the bezel is resolution
independent and survives any zoom or viewing distance. It is carried as a
uniform in a `params` vec4 with the other lanes reserved and required to be zero;
the planner writes all four lanes rather than leaving three indeterminate,
because the shader reads the whole vec4.

Measured, five adjacent lit dots at dot row 12, columns 1..5:

```
before   ##########                                         one fused slab
after    ..####....####....####....####....####..          five distinct cubes
```

Each lit dot is a 4x4 fragment square inside its 8x8 cell. Both backends remain
byte-identical, `md5 776e6395dc823b311d82b6f556131e87`, 79 lit dots, six live GPU
handles, at a 4096x2048 target.

The lesson worth keeping: the P2 captures were verified by decoding the dot grid,
which confirms the *content* is right and says nothing about whether it *looks*
like the thing it is meant to be. Both checks were necessary and only one was
done.

## 7. Addendum — the look becomes a parameter

*Added 2026-09-15, after the bezel stage was committed.*

The gap and colours were already parameters of `PanelRenderPlanOptions`, so they
were tunable in code but not at run time. `panel.set_appearance` now changes
them, `--panel-dot-color` sets the starting colour for a capture run, and
`panel.report` reports the appearance it rendered with — for the same reason it
reports the glyph product: an image cannot say which gap or colour produced it.

Only the fields a caller sets are applied, so the gap can change without
restating the colours. A gap the shader would clamp is rejected rather than
reported as applied, so success never means something other than what was asked.

### A colour has a space

The panel's target is sRGB, so the hardware **encodes on store**. A colour picked
as a hex literal therefore has to be linearised before it reaches the shader, or
it comes out lighter than requested — the same trap Live2D hit for its viewer
clear colour. The planner does the conversion, so every caller speaks the display
space a person picks in.

Verified end to end rather than argued: a capture taken with
`--panel-dot-color "#FFB000"` decodes to a lit dot of exactly `(255, 176, 0)`, and
the unlit gap pixel is `(0, 0, 0)`, so the bezel survives the colour change. White
and black are fixed points of the curve, which is why the earlier byte-identical
captures are unaffected. An existing planner test had asserted the constants
carried the *requested* colour; it now pins the canonical sRGB curve instead
(0.25 to 0.050876, 0.5 to 0.214041, 0.75 to 0.522522) so changing the curve has
to change the test.

### Two gaps found while proving it

**The viewer has no on-demand capture.** `capture.screenshot` is registered by the
Scene3D command path, not by `InitializeCommandServices`, so a standalone viewer
can only capture at startup. That is the whole reason `--panel-text` and
`--panel-dot-color` exist: without them a capture run cannot show anything but the
defaults. Registering a host-resolved `capture.screenshot` for viewer modes — the
way `window.resize` already resolves its window through the host — would remove
the need for both options.

**The viewer window shows nothing.** The panel draws to its own offscreen target
and nothing presents it, so `--mode panel-viewer` opens a window that stays blank.
Fine for a capture run, wrong for a viewer.

Both are recorded in [TODO.md](../../docs/panel/TODO.md) rather than fixed here.

### A papercut

`dot_gap` is declared `Float`, and a schema `Float` requires a JSON *double*.
`{"dot_gap": 0}` is refused because the transport types a literal by its value;
`0.0` is accepted. The handler reads a double directly rather than also tolerating
an integer that cannot arrive — a tolerant reader would be dead code, since the
schema rejects the value first. A test pins both sides.

### One mistake worth recording

The first runtime check reported `panel.set_appearance` as "not registered". That
was not a defect: the engine binary had not been rebuilt since the command was
added. `commands.list` showed five commands, and six after a rebuild. The lesson
is small but real — a stale binary produces a confident false negative.

## 8. Addendum — the colour ramp, and two defects found on the way

*Added 2026-09-15.*

`panel.set_appearance` can run a colour ramp from `dot_color` to `accent_color`,
horizontally, vertically, or outward from the middle, optionally animating, with
`--panel-accent-color` and `--panel-gradient` for capture runs. It needs no new
data: parameters and fragment arithmetic. The ramp is a cosine, so it loops
without a seam when animated and returns to the first colour at both ends.

### The ramp has to span the content, not the panel

The first version normalised across the panel. Measured, `OvO 中文` moves only
from `(255, 106, 0)` to `(239, 133, 105)` across the whole line, because the text
occupies the left twelfth of a 512-dot panel. A gradient that is invisible over
the thing it colours is not a feature.

The span is now the **lit extent**, measured in `PanelRenderer::UploadPanel` —
where the mask is measured — and carried on the proxy beside the mask handle,
because it describes the mask rather than the appearance. Measured after the fix,
across the same text:

```
before   (255,106,0) ................................. (239,133,105)
after    (254,107,18) ....... (42,227,252) ....... (255,106,2)
                              at the centre
```

A blank panel keeps the whole panel rather than an inverted or zero-width extent,
and the shader guards the division.

### Two defects in the previous commit, both found by writing this one down

**The commands raced the render thread.** `panel.set_text` assigned a
`std::string` that `RecordFrame` reads, from the game thread. The engine already
solves this the same way elsewhere — `window.resize` queues and the window thread
applies — so the host now records intent under a mutex and the render thread
applies it before its next frame, publishing an applied snapshot that
`panel.report` reads instead of reading live render state.

**`RefreshDotMask` was only called at startup.** It was called in `Initialize`
and never in `RecordFrame`, so `panel.set_text` changed the logical panel and the
dot mask was **never re-uploaded**. A command that reports success and draws
nothing is worse than one that fails. The mask is now refreshed per frame, before
the frame bracket, because the upload waits for the device and that must not
happen between `BeginFrame` and `EndFrame`.

Both were shipped in the previous commit and neither was caught by its tests,
because the tests exercise the provider and the planner rather than the host's
frame loop. That is the gap worth noting: the host had no test, and the two
defects both lived there.

## Remaining risks

1. **Outline rasterisation at 16x16** is legible but coarsens ASCII strokes. A
   bitmapped CJK font would be crisper; the product format does not change.
2. **The glyph product is local and non-redistributable**, so the captures above
   are reproducible only on a machine with a CJK face at the configured path.
3. **`R8_UNORM` is now payload-valid.** Other uncompressed formats still return
   zero bytes per pixel from `BytesPerPixel` and are accepted only as
   allocation-only textures. That is recorded in the code, not fixed.
4. **No Asset-system registration.** The host reads the product directly, so the
   panel is not yet part of the asset dependency graph.
5. **`.gitignore` carries both this stage's shader exceptions and an unrelated
   uncommitted change of the user's.** They will be in the same file until the
   user's change is committed separately.
