# Engine MODE1.1 — host composition seam

## Objective

Introduce the first engine-level mode boundary for `3DSceneHost` and
`Live2DViewerHost` without changing the existing scene/PBR startup path or
adding a Runtime → Live2D dependency.

## Landed

- Added the Runtime-owned `ApplicationMode`, `IApplicationHost`, and
  `ApplicationHostRegistry` contract under `engine/runtime/host/`.
- Added strict `--mode scene3d|live2d-viewer` parsing. Omitting the option
  preserves the existing `scene3d` startup behavior.
- Added application composition wiring so the parsed mode reaches `Engine`.
- Added provider registration and early validation. `live2d-viewer` currently
  reports a clear missing-provider error until MODE1.3 supplies the concrete
  Live2D host; it does not silently boot the scene renderer under the wrong
  mode.
- Added unit coverage for defaults, parsing, invalid/duplicate values, and
  factory registration/creation.

The shared `EngineServices` view is deliberately not fabricated yet. The
current `RuntimeContext` still owns scene-specific startup and GPU lifecycle;
MODE1.2/1.3 will extract genuinely shared services while moving each host's
ownership to its correct module.

## Validation

- `cmake --build build --config Debug --target RuntimeLaunchOptionsTest`
  passed. MSBuild emitted the repository's existing `LIBCMT` default-library
  warning while linking.
- `RuntimeLaunchOptionsTest.exe` passed all 7 tests, including
  `ApplicationHostRegistryTest.RegistersAndCreatesOneProviderPerMode`.
- `ctest --test-dir build -C Debug -R RuntimeLaunchOptionsTest
  --output-on-failure` passed the 6 CTest-registered launch option cases.
- `git diff --check` passed.

## Remaining limitation

No concrete `3DSceneHost` or `Live2DViewerHost` is created by this stage.
MODE1.2 must first make the existing scene path explicit; MODE1.3 can then
register and drive the standalone Live2D viewer host.
