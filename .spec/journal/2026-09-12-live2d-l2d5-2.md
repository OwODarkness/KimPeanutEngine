## Objective

Close V1 acceptance item 10 — the viewer resizes, captures a stable frame at the
post-resize extent, and exits without Graphics validation errors, leaked Cubism
objects, or live GPU handles — with evidence a build would fail without.

At the start of this stage, `Live2DRenderer::ResizeOutput` was called every frame
and had never seen a changed extent, and the shutdown counts were read out of a
log rather than asserted. Both halves of the item were unproven.

## The resize did not reach Vulkan

The first resize run captured 720×960 on Vulkan while OpenGL captured 1024×768,
and the two branches of `GetRenderExtent()` explain it. OpenGL returns the cached
`width_`/`height_`; Vulkan returns `swapchain_->GetExtent()`, and
`VulkanSwapchain::ChooseSwapChainExtent` prefers `capacity.currentExtent` — the
window's real size — over the cached fallback.

`WindowSystem::SetWindowSize` only assigned `width_ = width; height_ = height;`
and never called `glfwSetWindowSize`, so *application* code could not change the
window size at all: on OpenGL the cached value made the resize appear to work
while the window never moved, and on Vulkan nothing happened.

My first attempt was a symptom patch: gate the capture on the output target
reaching the requested extent, with a frame budget. That produced an honest
diagnostic rather than a fix —

```
Live2D viewer resize to 1024x768 never reached the output target within 241 frames
```

— which is what located the real defect. The fix is
`WindowSystem::RequestWindowSize`, overridden in `GLFW_WindowSystem` to call
`glfwSetWindowSize`. The base implementation dispatches a `ResizeEvent`; the GLFW
override must **not**, because the framebuffer-size callback already dispatches
the size the platform actually granted, and a synthesized event would describe a
size the window does not have — which is exactly what a Vulkan backend reads back
when it recreates its surface. After the fix Vulkan resolved the capture at
frame_sequence 5 instead of exhausting the budget.

`engine/runtime/graphics/example/rhi_example.cpp:734-735` still uses the
cache-only `SetWindowSize` form. It was left alone deliberately: it is outside
this stage's boundary and the change is a separate finding, recorded below.

## Renderer contract

`ResizeOutput` was covered, not changed. The plan required extending or sharing
the existing backend double rather than weakening the test, and there is no
shared-test-header convention anywhere under `engine/test`, so
`TargetRecord`/`BackendProbe`/`FakeReadback`/`FakeCommandRecorder`/`FakeBackend`
(383 lines) moved out of `render_system_test.cpp` into
`engine/test/support/fake_render_backend.h` under `namespace kpengine::test`.
Two deliberate extensions were needed for the new assertions:

- `BackendProbe::render_extent`, replacing the hard-coded `{320, 200}` return —
  the default is preserved, so the render tests are unaffected.
- `BackendProbe::viewports` / `draw_count`, so "leaves the renderer usable" is
  provable from the recorded submission instead of inferred. The resize test
  asserts the *frame's own viewport* carries the new extent, which is what makes
  the claim about the renderer rather than about a field.

`Live2DRenderer::Initialize` needs a real MOC and real shader programs, so the
test lives in the SDK-gated `Live2DCoreTest` target, which already has the
Cubism include dirs, the MSVC runtime property, and the assimp runtime copy. The
fixture is imported from the checked-in
`live2d/hiyori_pro/runtime/hiyori_pro_t11.model3.json` through the ordinary
`ImportProviderRegistry` and `AssetManager` path, so the renderer sees the same
product and texture dependencies the viewer does. `asset/` is gitignored, so an
absent model leaves the `AssetID` invalid and the suite skips with the import
diagnostic — the same environmental-prerequisite treatment `KPENGINE_LIVE2D_MOC_PATH`
already gets.

### The tests are falsifiable, and this was demonstrated

Five green tests prove nothing on their own, so each case's defect was injected,
built, and observed:

| Injected defect | Result |
| --- | --- |
| `WaitIdle()` moved after the old target's release | `ResizeOutputSwapsTheTargetAfterWaitingIdle` fails on `waited_before_release` |
| failure branch also clears `proxy_.output_target` / `output_view_` | `FailedResizeKeepsThePreviousTargetAndView` fails — target id becomes invalid (`4294967295`), extent becomes 0×0, and the follow-up `RecordFrame` fails |
| the same-extent early return disabled | `SameExtentResizeIsANoOp` fails — 23 target creates vs 2, 3 destroys vs 2 |

Exactly the three intended tests failed and the other two stayed green. The
injections were then reverted; `git diff` on `live2d_renderer.cpp` afterwards
shows only the pre-existing L2D5.2e change.

## Viewer runtime evidence

Both backends, resize to 1024×768, capture after the resize, self-exit:

```powershell
build/Debug/KimPeanutEngine.exe --mode live2d-viewer --graphics-api opengl `
  --resize 1024x768 --capture save/screenshots/validation/l2d5-resize-opengl.png `
  --capture-view live2d --capture-alpha transparent --exit-after-capture

build/Debug/KimPeanutEngine.exe --mode live2d-viewer --graphics-api vulkan `
  --resize 1024x768 --capture save/screenshots/validation/l2d5-resize-vulkan.png `
  --capture-view live2d --capture-alpha transparent --exit-after-capture
```

Both exited 0. Each log contains **0** lines at `[Error]` or `[Warning]` level
and **0** lines matching `validation error`, `VUID`, or `leak` — the only match
for the bare word `validation` is the capture path itself — and each ends at

```
Live2D.Cubism: [Debug] [CSM][I]CubismFramework::Dispose() is complete.
```

| | OpenGL | Vulkan |
| --- | --- | --- |
| resize log line | `resize to 1024x768 requested; backend reports 1024x768` | `resize to 1024x768 requested; backend reports 720x960` |
| capture | `frame_sequence 3, draws 125, mask_sources 2, mask_contexts 2` | `frame_sequence 5, draws 125, mask_sources 2, mask_contexts 2` |
| exported dimensions | 1024×768 | 1024×768 |

The Vulkan `backend reports 720x960` is the extent at *request* time — the line
reads the backend immediately after asking, before the platform has granted the
size. The settled extent is evidenced by the exported 1024×768 dimensions and by
the capture resolving at frame_sequence 5 rather than running out the budget.

`--capture-alpha` is part of the command, not a detail: run with `opaque` and the
export has **0** transparent pixels (`transparent background: no pixels`), which
is why the recorded evidence uses `transparent`. Repeating a run with the same
alpha mode and extent reproduces the recorded file byte for byte on both
backends (sha256 match, 0 differing pixels), so the captured frame is stable and
the comparison below is not comparing two different animation frames.

### Cross-backend comparison

`tools/compare_capture_regions.py` requires equal dimensions, so the resized
captures are compared against the other backend at the same extent:

| Comparison | Result |
| --- | --- |
| resize OpenGL vs Vulkan, 1024×768 | 3 of 4 regions PASS |
| resize OpenGL vs OpenGL repeat | identical, 0 differing pixels |
| resize Vulkan vs Vulkan repeat | identical, 0 differing pixels |
| no-resize OpenGL vs Vulkan, 720×960 | 4 of 4 regions PASS |

The 720×960 no-resize pair was re-run after every change in this stage and still
passes all four regions, which is the regression evidence that the window and
blend changes did not alter the rendered result.

## Not closed: the 1024×768 tolerance miss

At 1024×768 the cross-backend `non-edge opaque` region exceeds the frozen
tolerance:

```
non-edge opaque: pixels=109050 max_abs=3 mean_abs=0.0002 channels_over_tolerance=1 (FAIL)
partial alpha: pixels=2569 ... channels_over_tolerance=0 (PASS)
transparent background: pixels=671031 ... (PASS)
filtered edge: pixels=6349 ... (PASS)
all pixels: total=786432 differing=81 (0.01%) max_abs=3
```

81 of 786432 pixels differ with `max_abs` 3. This is the same phenomenon as the
720×960 baseline (117 differing pixels, `max_abs` 2, inside tolerance there), one
channel past the flat tolerance once the model is drawn larger. The differing
pixels sit on internal high-gradient boundaries — clip/mask and internal
silhouette edges — that the comparator's alpha-discontinuity edge mask cannot
classify, so they are counted as flat-color pixels. It is **not** claimed green
and is left for L2D5.3 to disposition, either by widening the comparator's
internal-edge classification or by a recorded decision to accept it.

## Remaining risks

1. **The 1024×768 tolerance miss above.** Item 10's criterion is about the viewer
   resizing, capturing, and exiting cleanly, and every part of that is evidenced.
   Cross-backend pixel agreement at the resized extent is *not* part of item 10,
   but a reader will reasonably conflate them, so it is stated here explicitly.
2. **The shared double is now two callers' contract.** `render_system_test.cpp`
   and `live2d_renderer_test.cpp` both assert against `BackendProbe`. A change to
   the double for one caller can silently change the other's fixture; the default
   `render_extent` and the render tests' full pass are the current guard.
3. **The suite got noticeably slower.** `gtest_discover_tests` runs each
   `Live2DRendererTest` case in its own process, and each process pays the
   ~10 s product import and Cubism init, so the five new cases add roughly 50 s
   to `ctest`. This matches how `Live2DAssetTest` already behaves in this target,
   but it is a real cost and would be the first thing to reconsider if it grows.
4. **`rhi_example.cpp:734-735` still resizes the cache only.** It cannot resize a
   Vulkan surface. Separate from this stage; recorded rather than changed.

## Remaining work

L2D5.3 — fixture and blend-mode coverage, the official-reference build attempt,
and disposition of the tolerance miss above. Item 10 is closed by this stage; the
V1 acceptance line must be updated with the caveat in "Remaining risks 1".
