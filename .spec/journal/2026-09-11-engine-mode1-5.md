# MODE1.5 — Live2D scene-extension retirement

Date: 2026-09-11

## Objective

Finish the host split by removing the temporary Live2D `IRenderExtension`
registration path from the traditional scene renderer, while preserving the
standalone viewer and the existing deferred/PBR pipeline.

## Reference gate

- SakuraEngine commit `c0fdb2bb` keeps `SkrLive2D` as a feature module and its
  `live2d-viewer` sample composes its own window, renderer, model state, and
  RenderGraph loop. This supports direct ownership by `Live2DViewerHost`.
- Sakura's `RenderDevice` and `RenderGraphBackend` separate device/frame
  execution from renderer policy. KimPeanutEngine already has the smaller
  API-neutral `RenderSubmission`/executor seam, so this stage preserves that
  seam instead of coupling it to `RenderSystem`.
- gkNextEngine's renderer-first direction supports keeping renderer policy
  above backend execution and not making the scene renderer the owner of every
  feature. Its broader Vulkan/GPU-driven systems are not imported here.

## Landed changes

- Removed `IRenderExtension` registration, initialization, frame recording,
  output lookup, and cleanup from `RenderSystem`.
- Removed the obsolete `Live2DModule` scene lifecycle and the unused scene
  editor Live2D preview registration.
- Made `Live2DRenderer` a concrete host-owned renderer. The standalone viewer
  still uses its initialization, generic submission recording, output target,
  and cleanup APIs directly.
- Kept `RenderSubmission`, `RenderSubmissionExecutor`, `FrameContext`,
  Graphics/RHI contracts, and the deferred/PBR pass schedule unchanged.

## Remaining risk

The shared `CaptureView::Live2D` enum remains available to the standalone
capture service for feature-targeted tooling, but `RenderSystem` no longer
resolves or records a Live2D target. A future multi-host capture service can
move that semantic out of the scene capture enum if more standalone viewers
are added.
## Shared presentation backdrop follow-up

The standalone Live2D viewer now reads `window_background_color` from the
shared `config/settings.json`; the existing `background_color` remains owned
by the editor/ImGui theme. The window value is attached only to its
presentation submission.
The API-neutral command-recorder contract forwards an optional presentation
clear to OpenGL and Vulkan; omitted colors retain each backend's existing
default, so the deferred/PBR scene path is not changed. The viewer's offscreen
fallback target uses the same configured color.

## ImGui viewer shell follow-up

The standalone `Live2DViewerHost` now reuses `EditorUI` only for ImGui context,
backend presentation, and theme lifecycle. It does not create the scene editor
workspace or any `RenderWorld` service. The host renders Live2D into its
feature-owned offscreen target and supplies a viewer callback that composes:

- a central `Live2D Viewer` image panel;
- the existing `OutputLog` component;
- a compact `Performance Profiler` with frame, recorder, and ImGui timings.

The target is `RGBA8_UNORM` for the ImGui path. OpenGL linearizes the configured
display-space clear before the target clear because its Live2D shader path
encodes the final color; Vulkan keeps the configured value in its existing
shader-output path. This removes the prior visible OpenGL/Vulkan backdrop
mismatch without modifying the deferred/PBR renderer.
