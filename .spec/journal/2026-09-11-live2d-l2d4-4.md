# L2D4.4 — Packed mask planning and generic passes

Date: 2026-09-11

## Design boundary

The concrete question was how to add Cubism ordinary/inverted clipping without
teaching generic Render or Graphics about Live2D mask semantics. The local
L2D4 architecture already freezes one 256² `RGBA8_UNORM` inverse mask atlas,
four channels, nine 3×3 regions per channel, a 5% model-space margin, and
capacity failure. Existing local reference findings for the Cubism Framework,
Sakura, and bgfx support keeping CPU model extraction and GPU render planning
separate from generic execution. The GitHub MCP reference tools were not
available in this session, so no new external repository inspection was
claimed.

## Landed

- Added `Live2DMaskAtlasPlanner`, which validates the value-only snapshot,
  interns equal ordered source sets, ignores contexts without visible consumers,
  unions consumer bounds, applies the 5% margin, assigns deterministic atlas
  channel/region slots, and emits model-to-mask and model-to-atlas-sample
  matrices.
- Added diagnostics for empty source/consumer geometry, zero-area or
  non-finite bounds, and atlas capacity overflow. The planner has no Graphics,
  backend, or Cubism dependency.
- Extended the Live2D resource/proxy boundary with mask-source, masked-color,
  and mask-atlas pipeline/texture/target handles. The six existing unmasked
  pipeline selections are unchanged.
- Extended `Live2DRenderPlanner` to emit an ordinary mask pass followed by the
  ordinary color pass. The mask pass uses region scissors and mask-source
  constants; masked color draws bind the model texture and atlas texture and
  carry channel/polarity/sample-matrix constants. Generic Render remains
  semantic-free and the existing executor required no changes.
- Added focused CPU planner and two-pass submission tests. The mask target is
  expected to be created by the resource owner as linear `RGBA8_UNORM` cleared
  to one; output-target clear policy remains owned by target creation.

## Remaining gate

This stage has not added Live2D shader source, pipeline creation, mask-target
creation, viewer scheduling, or OpenGL/Vulkan pixel readback. Therefore the
CPU planning and generic-submission portion is landed, while end-to-end clipped
visual validation remains for the later resource/viewer integration work.
