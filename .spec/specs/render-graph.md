# Render Graph R3.2 — Pure Graph Model and Compiler

- Status: complete
- Owner: Render runtime
- Parent TODO: [Render Graph roadmap](../../docs/render/render_graph/TODO.md)
- Stage plan: [R3](../../docs/render/.plan/R3.md)
- Architecture: [Render Graph plans](../../docs/render/render_graph/PLANS.md)

## Objective

Add a Render-owned, backend-independent graph model with SSA-style typed
texture and buffer versions, imported/exported resources, pass declarations,
dependencies, optional conditions, and side effects. Compile declarations into
a deterministic live-pass order with diagnostics and logical lifetime
intervals. Compilation performs no Graphics or GPU work.

## Current state

The compiled graph plan is the only authority for pass order and logical
resource flow. The fixed sequence that served as the R3.3–R3.4 compatibility
oracle has been removed, so no second authored pass order exists.

## Scope and non-goals

In scope: graph-scoped typed handles, versioned writes, imported/transient
logical resources, pass reads/writes, explicit dependencies, exports, side
effects, optional disabled conditions, deterministic ordering, reachability
culling, diagnostics, and live-use intervals.

Out of scope: Graphics calls, physical allocation, native resource state,
barriers, command recording, transient pooling/aliasing, fixed-schedule
migration, and Vulkan/OpenGL runtime changes.

## Invariants

- Graph handles carry graph identity and resource version; cross-graph handles
  are rejected.
- A transient version must have a producer before it can be read. Imported
  version zero is the only externally produced initial version.
- A write consumes one logical version and returns a new version; a pass cannot
  write one resource twice. This SSA-style lineage is authoritative for graph
  dependencies.
- Declaration order is the tie-break for independent enabled passes.
- Only passes reachable from exports or enabled side effects are compiled.
- The graph owns logical planning only; Graphics retains physical GPU and
  synchronization ownership.

## Stages

1. Review the Sakura evidence and R3 ownership boundary.
2. Implement the pure builder/compiler and focused tests.
3. Validate the Render target and graph test target.
4. Record implementation evidence and leave R3.3 compatibility proof as the
   next stage.

## Acceptance criteria

- [x] Typed texture/buffer handles and graph-scoped version validation.
- [x] Imported/exported resources and explicit side-effect roots.
- [x] Pass declarations, resource-derived edges, explicit dependencies, and
  deterministic stable topological order.
- [x] Reachability culling and first/last live-use intervals.
- [x] Diagnostics for invalid declarations/handles, missing producers, cycles,
  conditional dependencies, duplicate names/exports, and duplicate writes.
- [x] Compilation contains no Graphics dependency or GPU calls.
- [x] Unit tests cover ordering, culling, lifetimes, missing producers, cycles,
  conditions, cross-graph handles, and duplicate writes.

## Validation plan

```powershell
cmake --build build --config Debug --target RenderGraphTest
ctest --test-dir build -C Debug -R "^RenderGraphTest\\." --output-on-failure
cmake --build build --config Debug --target Render
git diff --check
```

R3.3 must add fixed-schedule compatibility proof before any runtime execution
path changes. Vulkan/OpenGL captures and per-pass profiling remain the R3.0
oracle and are not regenerated by this pure CPU-only stage.

## Risks and follow-up

- The current API models whole logical resources only; subresource ranges and
  portable usage/stage state remain R3.5 work.
- The compiler is structural and not yet a persistent cached topology object;
  cache measurements and policy belong to the migration work.
- R3.3 must prove the eight-pass graph against `FixedRenderPassSequence`
  before R3.4 changes execution.
