# R5 — Render configuration, graph execution, and ownership

**Status:** active; R5.0 is closed and R5.1 is complete (2026-09-28). R5.2
typed role/outcome groundwork is in progress. GPU tuning is paused. R5 retains
its original Render/Graphics decoupling goal, now
based on the current general-scene PT renderer rather than the September 22
R4.6 dispatch blocker. Runtime extraction remains gated on the affected-path
baselines recorded in the [R5 execution spec](../../../.spec/specs/render-r5-render-configuration-graph-ownership.md).

**Baseline:** source commit `9089df26325b5976b0ab2bc20bde46febd2ac9a2` plus the
existing documentation changes. The user describes the current phase as R4.8;
no Render R4.8 plan, review, or spec was found in this tree. R5.0 records that
as a label-only reconciliation: it does not infer R4.8 acceptance or rename
R4.7 evidence. See the [R5.0 spec](../../../.spec/specs/render-r5-render-configuration-graph-ownership.md)
for the frozen ownership table, comparison rules, and incomplete baseline rows.

**Owners:** Render owns configuration resolution, scene/pass policy, logical
resources and graph execution policy. Graphics owns GPU allocation, native
commands, synchronization and retirement. Editor and Runtime submit copied
requests; Runtime never depends on Editor. This is the canonical cross-module
plan, indexed by both roadmaps.

## What changed since the original plan

The original plan required closing R4.6 native dispatch before any extraction.
Later correction records show active Cornell/Sponza PT, while quality,
fallback and lifecycle acceptance remain partly open. Preserve those open
items without treating the historical dispatch blocker as a current fact.
See [R4.7.2 correction](../.review/R4.7.2.md),
[R4.7 CPU work](R4.7.md), and [GPU strategy](R4.7-gpu.md).

Current behavior includes scene/material revision reuse, Graphics-owned scene
reference tables, frame-slot/history binding reuse, inline query visibility,
ray-cone experimentation, one-SPP preview and four-SPP denoising. These are
migration constraints, not features to reimplement. The
[controlled investigation](../.review/R4.7.8.md#controlled-gpu-investigation--2026-09-27)
found that default World Normal demand adds raster diagnostics during PT, and
that the probe enum couples output, visibility and quality controls. Temporary
experiments were restored; no measured optimization default is installed.

R5 targets understandable behavior and ownership. It does not promise 60 FPS,
accept rejected shader experiments, or close outstanding R4 acceptance gates.

## Intended frame flow

```text
Editor / Runtime copied requests
  -> RenderSystem request snapshot at a frame boundary
  -> Render-owned resolved settings + active consumer demand
  -> scene coordinator / immutable frame inputs
  -> DeferredRenderer facade: select plan and coordinate owners
      -> compiled graph + typed physical binding table
      -> Render graph executor: transitions, outcomes, terminal handoff
      -> shadow / deferred / PT / post-capture collaborators
  -> Graphics common handles and recorder
      -> Vulkan/OpenGL resource owners, submission and retirement
```

Names in this diagram are responsibilities, not mandatory new classes. Reuse
existing frame records and concrete collaborators before adding abstractions.
Callbacks must not capture pointers that outlive their frame or resource lease.

## Stage gates and implementation order

### R5.0 — reconcile the current baseline and freeze behavior

Freeze the baseline, ownership/cache map and comparison conditions before
extracting an affected runtime path. Keep unrelated design and CPU-contract work
moving while a specific visual baseline is unresolved. The concrete checklist
and exit gate live in [R5.0](R5.0.md); captured evidence and the closed exit
review live in the [baseline journals](../../../.spec/journal/2026-09-27-r5-0-baseline-freeze.md)
and [R5.0 review](../../../.spec/journal/2026-09-28-r5-0-exit-review.md).

### R5.1 — separate configuration, demand and failure semantics

Define copied frame-boundary settings, independent consumer demand, and required
producer failure propagation before extracting graph or pass owners. Preserve
common Graphics ownership and the shader ABI. The actionable contracts and
validation matrix live in [R5.1](R5.1.md); implementation and runtime evidence
live in the [R5.1 journal](../../../.spec/journal/2026-09-27-r5-1-settings-demand-failure.md).

### R5.2 — extract typed graph binding and frame execution

Concrete file/symbol mapping, typed binding/provider contracts, graph pass
context, five implementation slices and acceptance tests live in
[R5.2](R5.2.md). The graph is the authority for dependencies, execution order,
transitions, attachment boundaries, transient leases and required-output failure;
the extraction must not introduce a parallel manual schedule.

1. Build a typed per-frame binding table from current resolver code. Replace
   `SceneGeometry`/`SceneBLAS` string branches with typed resource identity.
   One logical import may bind many physical members; every member and intended
   access must be enumerated, including AS build/read inputs.
2. Move binding validation, transient leases, transition application, attachment
   brackets, callback dispatch and outcome/profile collection into one
   Render-side executor. Feed it a compiled plan, borrowed common recorder,
   typed bindings and frame inputs. It does not load assets or choose lights.
3. Preserve the existing target pool, history imports, external Editor terminal
   ordering and submission ownership. Finalize/rollback must release each lease
   once while respecting Graphics retirement. Do not add aliasing or queues.

**Exit:** missing/extra bindings, one-to-many coverage, failed producers,
transient rollback and terminal ordering have contract tests. Raster and PT use
the same executor without resource-name special cases. Extraction matches the
R5.0 images and cache/allocation behavior.

### R5.3 — extract pass-family state by lifetime

Concrete owner/method/state/struct mapping, shared helpers, graph integration,
seven implementation slices, lifecycle/invalidation rules and facade-size
acceptance live in [R5.3](R5.3.md). Move definitions and values with their owners;
pass owners record through typed graph context and do not schedule each other.

Move one cohesive owner at a time: shadow; deferred/environment;
tone-map/capture; RT scene preparation; PT history/filtering. Keep
`DeferredRenderer` as the initialization/record/finalize/resize/capture facade.
Reuse immutable section/frame packets; do not duplicate scene tables per pass.

Before each move, write its inputs, outputs, persistent handles, frame borrows,
cache revisions and destruction order. Move the fields together with setup,
record, invalidation and cleanup. Preserve unchanged-frame scene-record/table
reuse and frame-slot descriptor/history-parity keys from R4.7. History reset
must respond to camera, extent, scene/material/light, estimator/SPP and
visibility changes; filter-only/output-only changes need an explicit rule
based on which accumulated data they consume. Scene edits invalidate the
relevant record/AS caches rather than forcing unrelated rebuilds.

**Exit per owner:** initialization rollback, repeated cleanup, scene reload,
transform/material edits, resize, settings changes and close are verified.
Steady unchanged frames retain zero unnecessary table packing/upload and
binding allocations. No pass owns another pass's hidden GPU state.

### R5.4 — narrow Graphics contracts and audit RT retirement

Move Render shader uniform schemas out of common Graphics while preserving
binary layout and shader bindings. Replace the Render-specific profile count
with caller-supplied stable timing IDs/capacity validation. Retain
`RenderBackend` as the composition/factory/frame facade; do not introduce one
virtual interface per pass.

Audit AS, immutable reference tables, binding sets, RT pipeline and SBT across
create/bind/dispatch/destroy, rejected submissions and device failure. Pipeline
destruction currently directly invokes native cleanup; establish whether every
caller guarantees idle before changing it. Test or enforce safe retirement
before splitting private Vulkan owners. Keep native types below Graphics.

**Exit:** layout/contract tests and OpenGL-only/Vulkan builds pass; teardown
safety has runtime evidence and a written split/no-split decision. No new
Runtime-to-Editor or Graphics-to-Render dependency is introduced.

### R5.5 — optional graph extensions, deferred unless justified

Keep eager variants and existing non-aliasing targets unless R5.0 measurements
show a concrete problem. On-demand variant caching, generic transients,
aliasing, async compute and multi-queue scheduling require separate consumers,
measurements and lifetime designs. This stage may close with a documented
no-change decision. Wavefront tracing, SER, payload tuning and texture/AS
experiments remain outside R5 while GPU optimization is paused.

### R5.6 — cross-backend and lifecycle closure

Follow the [validation matrix](../../validation_matrix.md): focused graph,
schedule, RenderSystem and Graphics contracts, then broad tests for shared API
changes. Use Debug with Vulkan validation for correctness and rebuilt
RelWithDebInfo for timing. Never compare Debug timing as performance acceptance.
Launch the visual engine on the user's normal desktop, outside the sandbox.
Use Runtime commands and `capture.screenshot`/`poll`; store fresh PNGs under
`save/screenshots/validation/` and inspect them.

Required runtime cases: Vulkan/OpenGL raster; Cornell/Sponza PT; raw Beauty,
query visibility, preview and denoise including supported combinations;
viewer hide/show and multiple capture demands; RT on/off and unsupported
capability; scene reload/edit; camera motion; resize/minimize/restore; failed
required recording; close with work in flight. Do not inject device loss merely
to test a refactor. Filtering motion/disocclusion limitations remain explicit.

Compare equal settings and sample counts for parity; compare changed quality
budgets separately. Record repeated timing windows without concurrent builds,
tests or profilers. R5.0 must set numerical regression tolerances before source
work; none is invented here. No 60 FPS acceptance gate is added.

**Exit:** no unexplained visual change, validation error, lifetime defect,
required-pass false success or regression beyond the agreed budget. Outstanding
R4 correctness/quality items remain linked and independently open.

## Migration and execution records

Implement in the order R5.0 -> R5.1 -> R5.2 -> R5.3 -> R5.4 -> R5.6; R5.5 is
conditional. Keep each owner extraction reviewable and validate before the next
move. Avoid changing resource ownership, shader algorithms and default quality
in the same patch. Roll back an extraction if parity fails rather than masking
it with a quality or sample-budget change.

The `.spec/specs/` execution spec records exact baselines, acceptance budgets,
and missing rows. Record per-stage evidence in `.spec/journal/`; update
[Render TODO](../TODO.md),
[Graphics TODO](../../graphics/TODO.md) and [status](../../status.md) as facts
change. The [R5 review](../.review/R5.md) preserves historical findings and dated
rechecks. The existing [Sakura source study](../render_graph/sakura_analysis.md)
supports builder/compiler/executor separation, but not importing its raw RHI,
per-frame rebuilding or queue framework. No foreign implementation is copied.
