# R4.7 GPU path-tracing strategy

Date: 2026-09-27. Status: R4.7.11–R4.7.13 prototypes implemented and
measured; per-stage acceptance is recorded in the matching reviews. R4.7 GPU
attribution and parent performance acceptance remain open.
Parent: [R4.7](R4.7.md); acceptance: [spec](../../../.spec/specs/render-r4-7-path-tracing-performance.md).

## Question and measured constraint

Which GPU work should be reduced to improve general-scene path tracing after
R4.7.4, without disguising reduced sampling as equivalent-work optimization?

The corrected R4.7.4 median PT GPU p50 is 25.173 ms and total GPU p50 is
29.339 ms, approximately 34.1 FPS. Their ratio is about 86%; percentile ratios
are an attribution clue, not an exact per-frame breakdown. The first window's
CPU fence-wait p50 is 24.522 ms. These results indicate GPU-limited operation,
but do not distinguish traversal, texture bandwidth, ALU, or low occupancy.
Scene-table CPU packing snapshots are about 0.043–0.054 ms; eliminating that
work alone cannot plausibly deliver a large FPS change.

With roughly 4.17 ms of other GPU work unchanged, a 60-FPS GPU budget would
leave about 12.5 ms for PT. That illustrative budget requires approximately
halving PT cost; it is not a promised result. Rerun the current baseline before
each experiment rather than comparing against an obsolete R4.7.0 baseline.

## R4.7.8 — Attribute GPU cost before structural changes

Record shader register usage, spills, occupancy, texture/cache throughput and
traversal utilization with Nsight Graphics when supported. Inspect spatial
hotspots and BLAS bounds. Add optional diagnostic ray counts by depth/type and
termination reason if the profiler cannot answer the question. Reduce counters
per subgroup/workgroup where practical; disable instrumentation for acceptance
timing. Probe modes and shader ablations change work and are diagnostic only.

The Performance Profiler's Advanced GPU section should expose engine-owned
timing freshness and summary, RT workload/AS/table activity, and texture
residency. These values provide capture context, not substitutes for vendor
hardware counters. Keep unsupported counters explicitly unavailable.

Inspect the raygen live state across `traceRayEXT`: `primary`, `surface`,
`next_surface`, throughput, view direction and radiance. Do not infer register
allocation from GLSL struct size. Separate hit-shading and traversal evidence;
record unavailable profiler features rather than substituting guessed metrics.

**Gate:** name the dominant limiter and the evidence supporting the next
experiment. Preserve 1094×619, four SPP, eight bounces, camera, scene lighting,
texture residency, active RT mode and driver/power conditions.

## R4.7.9 — Reduce hit cost and live state first

Local target: `asset/shader/ray_tracing_path_tracer.rchit` currently loads three
positions, transforms each to world space and interpolates them for the hit
position. Test world ray origin plus hit distance times world ray direction
instead. This can remove position loads/transforms, while indices, UVs and
normal interpolation remain necessary. Validate numerical error and secondary
ray offsets at large coordinates, grazing hits, mirrored/nonuniform transforms
and thin surfaces; retain barycentric reconstruction if robustness regresses.

Audit `HitPayload` across raygen, closest-hit and miss together. Remove or
derive only fields proved unnecessary; constrain variable lifetimes around
trace calls. Compare full-surface payload against a compact hit record followed
by material evaluation in raygen only if profiling warrants it. Moving shading
can increase dependent fetches or registers: smaller payload is not sufficient
evidence of a win. Preserve scalar visibility payload and its SBT selection.

Packed metallic/roughness lookup, primary reuse, builtin normal transform and
Russian roulette already exist: do not claim them as new optimizations.
Avoid creating many material shader variants for the current single PBR model.

**Gate:** reduced hit instructions/fetches or live-state pressure, plus a
repeatable PT p50 improvement without p95 or equal-sample image regression.

## R4.7.10 — Improve traversal only when measured

Inspect instance AABB overlap and empty space before changing BLAS grouping.
Use general spatial/topology criteria, stable material/geometry mapping and
authored transforms. Test static fast-trace BLAS independently from TLAS flags,
then consider static compaction if memory pressure is evident. Compaction needs
GPU size queries, replacement storage, address/TLAS refresh and safe retirement.

NVIDIA recommends evaluating AS layout and static compaction; those are
starting hypotheses, not evidence that every scene benefits. Prior R4.7.3
fast-trace attempts did not establish a static-BLAS timing gain. Repeat only
after correctness is stable; keep startup latency and AS memory in the result.

Do not remove off-camera transport geometry or change mesh detail in this
track. Opaque geometry flags must reflect authored semantics; future alpha
testing must preserve visibility rather than forcing everything opaque.

**Gate:** traversal improvement at unchanged geometry/lighting, bounded memory,
valid mappings, and no submission/lifetime errors through scene replacement.

## R4.7.11 — Coherence experiments, conditional on profiling

Try supported SER/hit-object variants before a full wavefront rewrite if
divergent hit shading is the limiter. Graphics owns extension/feature checks,
pipeline creation and fallback; Render selects a portable optional policy.
Query actual support and compiler capability on the RTX 4070 Laptop system;
GPU model alone is insufficient. Preserve original sample/RNG identities.

If SER is unavailable or insufficient, prototype bounded GPU queues for
continuation rays, shading and visibility, preserving pixel/sample/depth IDs.
Compact surviving paths; optionally group by material/texture access. Render
owns graph passes; Graphics owns queue buffers, barriers and indirect execution.
Guard overflow and never drop rays silently. Account for extra memory traffic,
dispatches and compaction/sorting time in total GPU timing. The pbrt queues are
architectural evidence; the current simple PBR model may not justify their cost.

Inline ray query is another measured prototype, not a default replacement.
It removes shader-call structure but retains traversal state and can increase
register pressure or divergence. Leave recursion depth one; eight sequential
continuation bounces do not require pipeline recursion depth eight.

The R4.7.11 Sponza prototype selects inline `rayQueryEXT` only for direct-light
visibility through the `ray_query_visibility` probe. `beauty` retains the
scalar-payload `traceRayEXT` visibility route. Three 120-warmup/300-sample
windows per mode measured 23.188/27.903 ms mean PT/total-GPU p50 for Beauty and
21.940/26.636 ms for query visibility (5.38%/4.54% lower). Debug Vulkan
validation and a query-mode capture passed. Keep this opt-in until Cornell
and general-scene coverage close the review. The current common RT contract
requires ray query; query-disabled RT device support is a separate portability
change.

**Gate:** feature-disabled fallback works; all added scheduling cost is included,
and total GPU p50/p95 improves with equivalent accumulated samples.

## R4.7.12 — Texture footprint and sampling experiments

The closest-hit shader samples metallic/roughness at explicit LOD zero;
base-color sampling has no explicit ray footprint. First profile texture cache
misses and bandwidth. Then study ray-cone/differential footprint propagation
and choose a consistent mip for secondary hits and all surface channels. This
changes texture filtering and potentially transport, so use a separate visual
acceptance track; do not label arbitrary higher mip bias unchanged quality.
Keep streamed mip identity and accumulation invalidation correct.

For many authored lights, evaluate importance-sampled direct lighting with
correct selection PDFs/MIS instead of testing every light at every bounce.
The current light loop alone is not proof that light sampling is the bottleneck.
Measure variance/convergence per second as well as GPU time. Defer ReSTIR GI
until reservoir ownership, reprojection and bias/visibility semantics have a
dedicated design; changing the estimator is beyond a shader micro-optimization.

**Gate:** texture detail and indirect lighting remain acceptable under motion,
with equal-wall-time error and raw output reported separately from frame time.

The R4.7.12 `ray_cone_filtering` prototype estimates pixel angular spread,
propagates a bounded roughness cone through continuation hits, and derives
base-color mip LOD from triangle UV/world area. It intentionally leaves default
Beauty filtering and metallic/roughness LOD unchanged. Three matched windows
measured 22.729/27.355 ms PT/total p50 for ray cone versus 22.399/27.063 ms for
Beauty, a 1.47%/1.08% regression, after fixing a missing closest-hit cone-width
propagation assignment and repeating all windows. It remains an opt-in quality
experiment and is not a performance default. The Sponza fixture's single
authored light did not justify an importance-sampling test.

## R4.7.13 — Optional interactive reconstruction

Extend R4.7.6 only after a separate design: one path per pixel plus temporal/
spatial denoising, with four-SPP/eight-bounce reference still available. NRD
provides a concrete guide-buffer contract, not a drop-in postprocess over the
current accumulated Beauty image. Generate motion/depth/normal/roughness,
separate diffuse/specular signals and meaningful hit distances, then validate
disocclusions, camera/material/light edits and moving geometry.

Include guide generation, reconstruction and presentation in total GPU cost.
Record raw and reconstructed captures, ghosting, detail loss, history resets,
latency and convergence per second. Reduced resolution and upscaling remain
explicit optional settings. No vendor library is installed by this plan.

**Gate:** improved interactive frame time with an explicit quality tradeoff;
never compare one-SPP reconstructed output as equivalent four-SPP raw work.

R4.7.13 currently provides an opt-in one-SPP preview with progressive history,
a primary normal/view-distance guide, and a 3x3 edge-aware spatial filter.
Render owns the guide's declared use and DeferredRenderer target lifetime;
Graphics owns its native image and transition. It does not yet provide motion,
roughness/albedo guides, disocclusion handling, or split diffuse/specular
signals. On Sponza, mean total-GPU p50 was 11.091 ms at one SPP versus
27.094 ms at four-SPP Beauty, with mean tone-map p50 0.0829 versus 0.0307 ms.
This is an explicit one-quarter sample-budget tradeoff, not equal-work
denoising. The preview remains opt-in pending motion/edit, multi-scene and
convergence/error review.

### Accumulated Beauty denoising follow-up

The separate `beauty_denoise` mode keeps the four-SPP progressive Beauty
estimator and filters its accumulated mean for presentation. The ray-generation
history stores centered luminance sample variance in alpha, merged as batches
are accumulated; storing normalized variance avoids an ever-growing M2 sum in
the existing RGBA16F history. Tone mapping uses one 5x5 à-trous level at stride
two, guided by that variance, primary world normal, relative view depth, and
luminance edges. Raw `beauty` and the one-SPP `low_spp_preview` remain separate.

This is an SVGF-inspired spatial denoiser, not full SVGF: it has no motion-vector
reprojection, temporal disocclusion rejection, multi-level wavelet chain, or
diffuse/specular guides. It targets static-view residual noise and may soften
fine texture or moving content. The current Sponza captures show visible grain
reduction while retaining broad fabric folds and tile layout, but lack a
strictly sample-matched image-error metric. Keep the new mode opt-in until
matched-count raw/filtered captures, motion/edit cases, another fixture, and
long-run history stability are reviewed. The design follows the variance-guided
À-trous direction in [SVGF](https://research.nvidia.com/labs/rtr/publication/schied2017spatiotemporal/);
NRD and OIDN were evaluated as alternatives, but their motion/guide contracts
or added runtime dependency exceed this first spatial pass.

## Order, ownership and acceptance

Start R4.7.8 → R4.7.9; choose R4.7.10 or R4.7.11 from the measured limiter.
R4.7.12–13 are separate filtering/sampling/reconstruction decisions. Continue
R4.7.5 CPU cleanup where useful, but do not expect it to remove GPU trace cost.

For each retained experiment: serial Debug validation and Cornell/Sponza/general
scene captures; serial RelWithDebInfo runs with 120 warm-up and 300 samples,
at least three matched windows; PT and total GPU p50/p95, CPU work/wait,
memory, startup and residency. Hold clocks/power/thermal conditions as steady
as practical and record changes. No builds during sampling. Reject a win that
only moves time from PT to another pass or changes sample/geometry workload.
Compiler/reflection, descriptors, SBT, AS, queue buffers and retirement stay
in Graphics; Render retains integrator policy, graph and history semantics.

This plan authorizes no performance claim by itself. Runtime candidates and
their evidence are tracked in the linked stage reviews; each optimization must
meet its own correctness, workload-equivalence and quality gates before default
adoption.
