# R5.1 — Settings, Demand, and Failure Semantics

**Status:** complete (2026-09-28). See the
[execution journal](../../../.spec/journal/2026-09-27-r5-1-settings-demand-failure.md)
for implementation decisions, test results, captures, and remaining limits.

**Parent:** [R5 stage map](R5.md) ·
[execution contract](../../../.spec/specs/render-r5-render-configuration-graph-ownership.md)

## Objective

Make frame settings, optional diagnostic work, and pass failure explicit before
extracting graph execution or pass-family ownership. Settings and diagnostic
consumers are separate inputs to frame planning.

## Design boundary

- Runtime and Editor submit copied values; Render validates and applies one
  settings snapshot at a frame boundary.
- Render resolves requested versus effective settings against common Graphics
  capabilities and exposes fallback reasons. Backend-native types remain below
  Graphics; shader uniform layout stays stable.
- Legacy probe/mode commands remain adapters with explicit field mappings.
  Independent settings updates must not be silently overwritten by adapter
  defaults.
- Diagnostic demand is scoped to concrete consumers. Viewer visibility and
  capture/readback lifetime are independent; the frame plan is based on their
  union and releasing one consumer does not cancel another.
- Required producers gate dependent outputs. Optional work may fail without
  poisoning unrelated Scene Color output. Failed or dependency-skipped work is
  reported distinctly; stale history is not success.
- Capture readback and Viewer conversion write separate Render-owned targets so
  simultaneous consumers can request different semantic views.

## Implementation sequence

1. Add a validated copied settings value and frame-boundary application path;
   retain the legacy command adapter and verify explicit precedence/mappings.
2. Resolve requested/effective settings and fallback reporting without changing
   the common Graphics contract or shader ABI.
3. Track Viewer and capture demand independently, including release on hide,
   output change, cancellation, and destruction. Keep GPU lifetime governed by
   submitted-work safety.
4. Classify required and optional graph work. Propagate required-producer
   failure to dependent passes, terminal composition, and readback while
   allowing independent work to proceed.
5. Give Viewer and capture conversion separate graph outputs, transitions,
   profiling, and Runtime command coverage.

## Acceptance

- CPU contracts cover setting validation, adapter mapping, consumer release,
  required failure, dependent skip, and independent output behavior.
- Runtime verifies Beauty and diagnostic transitions, default Scene Color,
  viewer/capture concurrency, and distinct simultaneous outputs on Vulkan.
- A Debug build with Vulkan validation succeeds. Focused graph and RenderSystem
  contracts pass; captures use the checked-in fixture and Runtime command path.
- Unsupported capability combinations and unvalidated quality combinations
  remain reported as limitations rather than implied support.
