## Status and implementation gate

**R3.2 pure compiler complete; runtime migration remains gated.** R3.0 baseline
work and the pinned Sakura source analysis are complete. The scoped R3.1 design
review is recorded in [R3.1 review](../.review/R3.1.md). This implementation

Sakura's source informed handle scoping, phase boundaries, imported-state
handoff, and the separation of cached topology from frame-local bindings. The
[study](../render_graph/sakura_analysis.md) is evidence rather than a source to
copy.

## Objective

Introduce a Render-owned compiled graph that becomes the single authority for
pass dependency order and cross-pass logical resource flow, then migrate the
current fixed deferred frame without changing its visible behavior. Establish
the resource-state and lifetime boundary needed by later ray-tracing work while
preserving Render/Graphics ownership.

## Current state

`FixedRenderPassSequence` describes eight typed passes and coarse logical
`Read`/`Write` uses. `FixedRenderPassFrame` executes the same fixed order and
tracks conditional/external outcomes. The model successfully prevents order
drift, but it intentionally does not:

- construct or sort a dependency graph;
- version logical resources;
- cull unreachable passes;
- calculate resource lifetimes;
- express usage/stage/subresource state;
- produce transitions or allocate transients;
- represent compute, acceleration-structure, or ray-tracing work.

Backend target managers currently own native attachment transitions around
`BeginRenderTarget`/`EndRenderTarget`. `DeferredRenderer` owns the actual pass
recording methods and persistent frame targets. `RenderSystem` owns the backend
frame bracket and external Editor terminal call.

## Concrete design question

How can the existing fixed declaration evolve into a compiled dependency graph
without replacing the renderer, duplicating the RHI, exposing native state,
adding speculative pass polymorphism, or regressing a CPU-bound raster frame?

## Chosen direction before the reference gate

1. Keep `RenderSystem`, `RenderSceneCoordinator`, `DeferredRenderer`,
   `FrameContext`, and `CommandRecorder` in their current ownership roles.
2. Add a Render-private graph frontend, compiler, immutable compiled plan, and
   executor.
3. Let the renderer declare logical resource versions and pass callbacks.
4. Let the compiler validate/order/cull and calculate logical lifetimes and
   portable transition intents.
5. Let Graphics resolve/allocate physical resources and translate transitions.
6. Let existing pass recorders run only as graph execution callbacks.
7. Migrate persistent raster targets first; add non-aliasing transients only
   after parity.

The authoritative architecture and resource rules are in
[Render Graph plans](../render_graph/PLANS.md); this stage document owns the
migration and acceptance boundary.

- Add access, usage, stage, attachment operation, and whole-resource range.
- Compile portable transition intents.
- Carry portable initial/final usage across imports without exposing native
  backend state to Render.
- Move cross-pass transition authority to the compiled plan while Graphics
  retains native translation and synchronization ownership.
- Preserve Vulkan/OpenGL behavior and validation cleanliness.

### R3.6 — transient resources

- Declare transient textures/buffers by description.
- Allocate/reuse through a Graphics-owned frame-safe pool.
- Handle resize, graph recompilation, partial execution, and shutdown.
- Do not alias memory in this stage.

### R3.7 — separately gated extensions

Subresources, aliasing, async compute, parallel recording, and ray-tracing
resource kinds require their own consumer, plan, measurement, and validation.

## Invariants

- Asset and Resource ownership do not move into the graph.
- Render owns policy and logical dependencies; Graphics owns GPU objects and
  synchronization.
- Common contracts expose no Vulkan/OpenGL implementation types.
- Declaration/compilation perform no GPU work.
- A graph handle cannot outlive or escape its graph-defined scope.
- Imported resources are borrowed; transient physical resources are
  Graphics-owned.
- Existing renderer failure remains observable and does not present partial
  required output as success.
- The graph is not credited with submission-performance gains it does not
  produce.

## Rejected starting points

- **Delete the renderer and make graph nodes own all policy.** The graph is a
  scheduler/resource planner, not the scene/material/visibility system.
- **Put the graph wholly in Graphics.** That would make RHI own Render pass
  policy and logical scene dependencies.
- **Record RHI commands during graph construction.** It prevents validation,
  culling, reordering, and cached compilation.
- **Make GPU pipelines read/write graph resources.** Pipelines are immutable
  executable state selected inside a pass, not cross-pass data.
- **Begin with transient aliasing or multiple queues.** They combine correctness
  migration with optimization before the basic ownership model is proven.
- **Copy a reference engine's graph API.** Its backend, threading, allocator,
  and renderer constraints do not automatically apply here.

## Risks and open decisions

- The current composite `GBuffer`/shadow logical names may be too coarse for
  transition inference; R3.1 must decide when to expose individual attachments.
- Cached topology conflicts with dynamically changing pass I/O unless graph
  variants or explicit recompilation rules are clear.
- Moving render-target begin/end into the executor may require a richer common
  attachment contract than R3.4 should introduce.
- Callback captures must not retain frame-local references across compilation
  or execution boundaries.
- Graph bookkeeping can worsen the already CPU-bound Sponza path unless its
  phases are cached and measured separately.
- External Editor composition must remain terminal without letting Editor own
  graph or resource lifetime.
