## Status and implementation gate

Implemented and reviewed on 2026-09-02. R1.2's ownership shape remains
stable, its predecessor evidence gate is closed, and the R1.3 focused/full
tests, dual-backend smoke, and fresh startup-level captures pass. The original
Windows SDK permission failure is retained as historical evidence in the
execution journal.

R1.3 is a fixed-sequence correctness stage. It is not a render-graph stage and
does not authorize feature, shader, target, synchronization, or RHI changes.

## Objective

Replace the current declaration-only `RenderPassSchedule` plus the separately
hard-coded `DeferredRenderer::RecordFrame()` call list with one immutable,
typed, ordered sequence that drives both validation and execution.

The sequence must represent the current renderer exactly:

- three distinct shadow target producers;
- required G-buffer, deferred-lighting, and tone-map stages;
- a capture-conversion stage that runs only for non-SceneColor capture views;
- an optional external editor-composite stage that is terminal when invoked.

Success means pass order can no longer drift without changing the same entry
that declares the pass identity, resource uses, execution owner, and condition.

## Current state

R1.2 has moved the renderer policy and pass-private state into
`DeferredRenderer`, but R1.3's defect remains local and observable:

- `ConfigurePassSchedule()` builds six string-named declarations;
- one `ShadowDepthPass` declaration claims three shadow outputs, while
  `RecordFrame()` invokes three independent shadow recorders;
- `RecordFrame()` manually calls directional shadow, spot shadow, point shadow,
  G-buffer, deferred lighting, tone map, and optional capture in a second order
  definition;
- each recorder independently calls `pass_schedule_.IsValid()`, even though the
  schedule is immutable after successful renderer initialization;
- `RenderSystem::ExecuteEditorCompositePass()` separately checks schedule
  validity and owns a second once-per-frame flag for the declared terminal pass;
- capture declaration is unconditional, but execution is conditional and a
  SceneColor request needs no conversion pass at all;
- `RecordGBufferDebugViewPass()` is a private recorder with no live call site
  and no declaration;
- pass recorders return a mixture of `void` and `bool`, so the current
  `normal_recording_completed` result cannot describe required-stage failure.

The validator currently checks only non-empty names/resources, writer-before-
reader ordering, one writer per logical resource, valid resource IDs, and a
terminal-last flag. It cannot reject a missing pass identity, duplicate pass
identity, unsafe conditional dependency, premature external invocation, or
declaration/execution drift.

## Concrete design question

How can KimPeanutEngine make a closed fixed sequence the single source of pass
order and per-pass policy while preserving the current fail-soft renderer,
conditional capture behavior, and externally recorded editor terminal pass—
without adding graph compilation, pass polymorphism, or another RHI layer?

## Chosen design

Replace `RenderPassSchedule` with a Render-private `FixedRenderPassSequence`
and a short-lived `FixedRenderPassFrame`. The immutable sequence owns pass
definitions; the frame cursor owns per-frame execution position and outcomes.
`DeferredRenderer` remains the owner of actual recording methods and maps each
typed pass ID to exactly one operation.

```text
Canonical fixed pass entries (immutable after Initialize)
   id + name + resource uses + owner + condition + terminal policy
                              |
                              v
FixedRenderPassFrame (one cursor per active frame)
   execute/skip/fail each entry in table order
                              |
                              v
DeferredRenderer::ExecutePass(FixedRenderPassId)
   typed ID -> existing recording operation
                              |
                              v
CommandRecorder / external editor callback
```

The sequence never chooses a different order, allocates transient resources,
inserts barriers, culls unused producers, or reasons about queues. It only
validates and executes the authored fixed order.

## Canonical pass sequence

The canonical table is the only authored order. Resource declarations are
conservative logical uses, not a new synchronization contract.

| Order | Typed ID | Logical resource uses | Owner | Condition | Current operation |
| --- | --- | --- | --- | --- | --- |
| 1 | `DirectionalShadow` | write `DirectionalShadow` | Renderer | Always | `RecordDirectionalShadowPass()` |
| 2 | `SpotShadow` | write `SpotShadow` | Renderer | Always | `RecordSpotShadowPass()` |
| 3 | `PointShadow` | write `PointShadow` | Renderer | Always | `RecordPointShadowPass()` |
| 4 | `GBuffer` | write `GBuffer` | Renderer | Always | `RecordGBufferPass()` |
| 5 | `DeferredLighting` | read `GBuffer` and all three shadows; write `SceneHdr` | Renderer | Always | build lighting binding, then `RecordDeferredLightingPass()` |
| 6 | `ToneMap` | read `SceneHdr`; write `SceneColor` | Renderer | Always | `RecordToneMapPass()` |
| 7 | `CaptureView` | conservatively read `GBuffer`, all shadows, and `SceneColor`; write `CaptureOutput` | Renderer | `DiagnosticCaptureRequested` | `RecordCaptureViewPass()` |
| 8 | `EditorComposite` | read `SceneColor` | External | `ExternalRequest` | caller-supplied editor callback |

### Shadow stages

The current grouped `ShadowDepthPass` declaration is split into three entries
because there are three target lifetimes and three recording operations. Their
order remains directional → spot → point. A missing light or caster is not a
skipped stage: the operation still begins/ends its fixed target when possible
to preserve clear/layout behavior and reports successful no-draw execution.

### Capture stage

`CaptureView` means diagnostic conversion, not readback submission. Its frame
condition is true only when a pending capture view is not `SceneColor`.

- No capture request: mark the stage `SkippedCondition`.
- SceneColor request: also mark conversion `SkippedCondition`; SceneColor is
  already the readback target, so `capture_target_ready` is true.
- Non-SceneColor request: execute conversion to `CaptureOutput`; the target is
  ready only if the operation succeeds.

The static declaration is the union of resources that any supported diagnostic
conversion may use. R1.3 does not derive per-view barriers or lifetimes from
that union.

### Editor terminal stage

`EditorComposite` is the sole external pass, is optional per frame, and must be
the final entry. `RecordFrame()` advances the cursor to this armed terminal
entry. `ExecuteEditorCompositePass()` may execute it exactly once. If Runtime
ends the frame without an editor callback, finalization records
`SkippedExternal`; this is valid and preserves headless/runtime behavior.

No renderer-owned stage may execute after the external terminal entry, whether
it was executed or skipped.

## Data model

Names are contract-level; exact spelling may follow local style while retaining
the same semantics.

```cpp
enum class FixedRenderPassId : uint8_t
{
    DirectionalShadow,
    SpotShadow,
    PointShadow,
    GBuffer,
    DeferredLighting,
    ToneMap,
    CaptureView,
    EditorComposite,
    Count,
};

enum class RenderPassExecutionOwner : uint8_t
{
    Renderer,
    External,
};

enum class RenderPassCondition : uint8_t
{
    Always,
    DiagnosticCaptureRequested,
    ExternalRequest,
};

struct FixedRenderPassEntry
{
    FixedRenderPassId id;
    std::string name;
    std::vector<RenderPassResourceUse> resources;
    RenderPassExecutionOwner owner;
    RenderPassCondition condition;
    bool terminal = false;
};
```

`FixedRenderPassSequence::Create()` accepts the complete definitions, validates
them, and returns either an immutable sequence or a diagnostic. Do not retain a
public `AddPass()` mutation API after initialization.

The closed `FixedRenderPassId::Count` set is intentional. Multiple renderer
implementations and arbitrary pass registration are not current requirements.

## Static validation rules

Sequence creation must reject all of the following before a frame begins:

1. Empty sequence, empty name, or empty resource-use list.
2. Unknown ID/resource/access/owner/condition enum values.
3. Missing or duplicate typed pass IDs; every ID before `Count` appears once.
4. Duplicate human-readable names.
5. Duplicate use of the same logical resource inside one entry.
6. A read before any compatible writer.
7. More than one writer for a logical resource in this fixed phase.
8. A required/always reader that depends only on a conditional writer.
9. A conditional reader whose writer is neither `Always` nor guarded by the
   same condition.
10. An external entry that is not terminal, is not last, or is not the only
    external entry.
11. A terminal entry that writes a renderer resource or any entry after the
    terminal entry.

The resource rules continue to validate logical data flow only. They do not
promise physical aliasing, synchronization, load/store inference, or automatic
layout transitions.

## Per-frame execution contract

`FixedRenderPassFrame` is created from the immutable sequence and frame
conditions. It is move-only and owned by `DeferredRenderer` only while a Render
frame is active.

It provides three operations:

1. Execute renderer-owned entries in order through a supplied typed-ID
   executor. A false condition records a skip without invoking the executor.
2. Execute the currently armed external terminal entry exactly once through a
   supplied callback.
3. Finalize the frame, marking an unrequested external terminal as skipped and
   rejecting any incomplete required entry.

Each entry receives one outcome:

```text
Executed
SkippedCondition
SkippedExternal
Failed
```

The cursor advances after `Failed` and continues later stages. This explicitly
preserves today's fail-soft behavior; R1.3 must not introduce fail-fast frame
cancellation or change `RenderSystem::BeginFrame()` success semantics. The
aggregate renderer result can finally set `normal_recording_completed = false`
when a required operation fails, but that result is diagnostic until a separate
error-policy decision gives it a caller-visible effect.

The frame object must reject:

- a second renderer execution;
- external execution before renderer entries reach the terminal stage;
- an unknown or non-external ID;
- a second editor callback;
- external execution after finalization;
- reuse in a later frame.

## DeferredRenderer integration

### Initialization

- Replace `ConfigurePassSchedule()` with construction of the canonical fixed
  entries.
- Validate once in `DeferredRenderer::Initialize()` and retain the immutable
  sequence.
- Remove per-recorder `IsPassScheduleValid()` checks; an initialized renderer
  cannot contain an invalid sequence.

### Frame preparation

Before sequence execution, preserve the current non-pass preparation:

- borrow the active `FrameContext` and `RenderWorld`;
- copy camera and update environment bindings;
- schedule directional, spot, and point shadow frame values;
- clear per-frame shadow-recorded flags.

These calculations prepare pass inputs but do not create a hidden second pass
order.

### Typed operation dispatch

`DeferredRenderer::ExecutePass(FixedRenderPassId)` contains an exhaustive switch
that maps every renderer-owned ID to one existing operation. It contains no
ordering decisions. `EditorComposite` is rejected there because its operation
belongs to the external cursor path.

Move resolved-shadow collection and `FrameLightingBinding` creation into the
`DeferredLighting` operation immediately before lighting recording. This
removes the current undeclared preparation block between point shadow and
G-buffer without inventing a fake GPU pass.

Convert pass recorders to return a small result or `bool`:

- beginning and ending a target with zero draws is success;
- unavailable recorder/target, failed required resource preparation, invalid
  binding allocation, or failure to begin the target is failure;
- every begun target must still be ended on each return path;
- the sequence records the outcome but continues in fixed order.

`RecordGBufferDebugViewPass()` is not part of the canonical sequence because it
has no live caller. R1.3 must re-audit references immediately before editing:
remove it if still unreachable, or give a proven consumer its own typed,
declared conditional stage. Do not leave an executable `Record*Pass` method
outside the fixed sequence.

### Capture handoff

Rename or reinterpret `DeferredRendererFrameResult::capture_view_recorded` as
`capture_target_ready`. Its value is:

- false when diagnostic conversion was required and failed;
- true when diagnostic conversion executed successfully;
- true for a pending SceneColor request because conversion is unnecessary;
- irrelevant/false when no capture is pending.

`RenderSystem` retains readback enqueue/rejection ownership exactly as in R1.2.

### External editor and finalization

`RenderSystem::ExecuteEditorCompositePass()` keeps lifecycle, active-context,
and callback validation, then delegates execution-once enforcement to
`DeferredRenderer`. Remove `RenderSystem::editor_composite_recorded_`.

`RenderSystem::EndFrame()` asks the renderer to finalize its pass frame before
ending `FrameContext` and the backend frame. Unexpected active-frame shutdown
does the same before resource teardown. Finalization is idempotent only for the
same active-frame cleanup path; it must not allow a stale cursor to enter the
next frame.

## Invariants

- `RenderSystem` remains the Runtime-facing lifecycle and backend-frame facade.
- `DeferredRenderer` remains the sole owner of renderer policy, targets,
  pass-private state, and the fixed pass sequence.
- The canonical entry table is the only source of pass order.
- Every executable render pass has one typed ID and one declaration; helper
  functions are not pass entries unless they independently own a logical stage.
- Gameplay, Asset, Resource, Editor, and Graphics ownership boundaries do not
  broaden.
- Fixed target formats, load/clear behavior, shader ABI, descriptor bindings,
  shadow budgets, draw order, capture names, and editor composition remain
  unchanged.
- Conditional capture and optional editor composition never make a required
  reader depend on a skipped writer.
- An execution failure is reported and execution continues, preserving the
  existing fail-soft frame policy.
- Common contracts expose no Vulkan/OpenGL types.

## Non-goals

- No render graph, DAG, topological sort, pass culling, transient resource
  aliasing, automatic barriers, queue scheduling, or load/store inference.
- No dynamic pass registration, renderer plugin interface, pass inheritance
  hierarchy, or one heap object per pass.
- No RHI command, synchronization, render-target, or backend API changes.
- No shader/material/light/environment/capture feature changes.
- No R1.4 Asset/resource ingestion work.
- No new frame-failure policy, retry, rollback, or public diagnostic API.

## Rejected alternatives

- **Store only a vector of callbacks:** order would be unified, but pass
  identity, condition, external ownership, and resource validation would remain
  implicit and hard to test.
- **Store `std::function` recorders inside public pass declarations:** this
  couples generic validation data to a captured renderer lifetime and obscures
  copy/move ownership. Typed IDs keep definitions value-only.
- **One virtual class per pass:** the present passes share one renderer lifetime
  and have no independent consumer. A class hierarchy adds interfaces without
  solving a current ownership problem.
- **Execute by sorting dependencies:** authored fixed order is sufficient and
  already validated visually. Sorting would be a graph migration with new
  ambiguity around external and conditional stages.
- **Keep the grouped shadow declaration:** one declaration would still map to
  three operations/targets, leaving the exact drift R1.3 is meant to remove.
- **Fail the whole frame on the first pass error:** this changes behavior and
  needs a separate backend/frame-abort contract.
- **Treat readback as a GPU pass:** capture request/callback/readback ownership
  is already a focused service; only conversion records renderer commands.

## Reference discovery gate

The R1.2 implementation, current schedule validator, pass recorders, capture
handoff, editor terminal path, and tests were inspected before external study.
The following source snapshots were read directly on 2026-09-02:

- [Filament `FrameGraph::addPass` at `9b97cdd`](https://github.com/google/filament/blob/9b97cdd44ba52e2eca8ee0e25fba79f53588e0d0/filament/src/fg/FrameGraph.h)
  accepts setup and execute callables under one named pass, so declared resource
  use and execution share one identity. R1.3 adopts that identity pairing, but
  rejects Filament's graph compilation, asynchronous execution, resource
  virtualization, culling, and arena-stored captured lambdas.
- [O3DE `RenderPass` at `40b15f1`](https://github.com/o3de/o3de/blob/40b15f133b1b0736a06d88accea7a1fa892c2d48/Gems/Atom/RPI/Code/Include/Atom/RPI.Public/Pass/RenderPass.h)
  places `SetupFrameGraphDependencies()` and final command-list dispatch on the
  same pass identity. R1.3 adopts the rule that declaration and operation cannot
  be anonymous strangers, but rejects O3DE's pass-object hierarchy, templates,
  frame-graph scopes, queries, and attachment system.
- [bgfx view-order contract at `67edbbd`](https://github.com/bkaradzic/bgfx/blob/67edbbd72a03a9feb116f7a7fa32b67b86d81f9d/include/bgfx/bgfx.h)
  makes submission order explicit through `ViewId` and `setViewOrder()`. R1.3
  adopts explicit order as data, while retaining KimPeanutEngine's logical
  resource validation because bgfx view ordering alone does not prove producer/
  consumer correctness.

These references support identity and explicit-order principles, not importing
a render graph or external engine framework.

## Acceptance criteria

- [ ] R1.2's ownership and required validation evidence are closed or an
  explicit predecessor waiver is recorded.
- [ ] One immutable canonical table contains every fixed pass exactly once and
  is the only authored execution order.
- [ ] Directional, spot, and point shadows have separate typed entries and
  resource writers.
- [ ] Missing/duplicate IDs, duplicate names, invalid/out-of-order resources,
  unsafe conditional dependencies, and invalid terminal/external layouts fail
  validation with deterministic diagnostics.
- [ ] Renderer-owned entries execute by table order; no manual pass call list
  remains in `RecordFrame()`.
- [ ] Diagnostic capture executes only when conversion is required; direct
  SceneColor capture still succeeds without conversion.
- [ ] Editor composite can execute exactly once only at the armed terminal
  position, and a headless frame can finalize it as skipped.
- [ ] Every pass outcome is recorded; required failure makes aggregate normal
  recording false while later stages continue.
- [ ] No live `Record*Pass` method exists outside the typed sequence.
- [ ] Per-recorder schedule-validity checks and the facade's duplicate editor
  once flag are removed.
- [ ] Focused sequence/Render tests, full Debug build, complete CTest,
  Vulkan/OpenGL smoke, and deterministic captures pass without visual or ABI
  regression.

## Validation

This stage changes a Render public header, fixed frame orchestration, capture
conversion gating, and editor terminal state. Follow validation-matrix Levels
2–4: focused contract tests during development, then full Debug build/CTest,
both GraphicsSmoke backends, and inspected runtime captures. Compilation alone
is insufficient.

## Remaining uncertainty

- `RenderPassScheduleTest` is an established CTest target name. The production
  type should be renamed to `FixedRenderPassSequence`, but the target may keep
  its old name to avoid needless CI churn.
- The outcome report can remain Render-private unless a concrete diagnostic
  consumer appears. R1.3 must not create a public profiling/telemetry API only
  to expose it.
- If a live G-buffer debug producer appears before implementation, it needs a
  typed conditional entry and a real condition. Otherwise the current
  unreachable recorder should be removed rather than preserved outside the
  sequence.
