# R1.2 — Deferred Renderer and Pass-Owned State

- Parent stage: [R1 — RenderSystem responsibility split](R1.md)
- Roadmap: [Render TODO](../TODO.md)
- Execution spec: [render-system-r1-2](../../../.spec/specs/render-system-r1-2.md)
- Risk register: [Render risks](../risks.md)

## Status

Implementation started on 2026-09-02. R1.1 supplies the lifecycle and
orchestration characterization baseline. R1.2 remains an ownership-preserving
extraction; it does not authorize feature changes, a render graph, or the R1.3
and R1.4 migrations. Final build, smoke, and visual evidence is pending the
current Windows SDK probe blocker.

## Objective

Make the existing deferred-PBR renderer a cohesive Render-owned collaborator
whose state and cleanup no longer live on the Runtime-facing `RenderSystem`
facade. Preserve the current frame order and public behavior while giving all
pass-private GPU state one explicit lifetime owner.

The success criterion is an ownership change, not merely moving methods to a
different translation unit or reducing line count.

## Current state

The live `RenderSystem` implementation is 2,492 lines and its header is 312
lines. One class currently owns or coordinates all of the following:

- backend and `FrameContext` lifecycle;
- async request consumption and the render cache;
- source registries, worlds, camera selection, and material resolution;
- seven named frame targets and pending viewport extent;
- the declaration-only `RenderPassSchedule`;
- shadow selection and frame state for directional, spot, and point lights;
- deferred, shadow, tone-map, debug, and capture pass recording;
- lazy creation and destruction of pass pipelines, samplers, and the fullscreen
  mesh;
- environment source resolution and the active/fallback IBL bindings;
- capture conversion and readback enqueueing;
- editor terminal composition and facade cleanup.

R1.1 now proves lifecycle rollback, the observed target/pass sequence,
conditional capture, resize waiting, editor composition, and teardown. GP7 has
also removed the legacy bootstrap scene/source transfer. The remaining Asset
loads used by queue consumption and lazy pass shader preparation are real but
belong to R1.4, not this extraction.

## Concrete design question

What is the smallest concrete collaborator that can own the present deferred
renderer's targets, pass policy, pass-private handles, environment bindings,
shadow frame state, and recording code while `RenderSystem` remains the only
Runtime-facing frame/lifecycle facade?

## Chosen boundary

Add one concrete, non-polymorphic `DeferredRenderer`. Do not add an
`IRenderer`, renderer registry, service locator, or one class per pass.

```text
Runtime / Editor / Gameplay capabilities
                  |
                  v
RenderSystem
  owns: lifecycle, backend bracket, FrameContext slots, registries/worlds,
        camera, materials/resolver, request cache, capture service
                  |
                  | immutable frame input + active FrameContext
                  v
DeferredRenderer
  owns: named targets, pending extent, declaration schedule, shadows,
        environment bindings, pass recording, pass-private GPU handles
                  |
                  v
RenderBackend / CommandRecorder
  owns: physical resources, native translation, submission, synchronization
```

### `RenderSystem` retains

- `RenderBackend` creation, initialization, `BeginFrame()`/`EndFrame()`,
  `WaitIdle()`, and backend cleanup;
- `FrameContext[]`, active-frame selection, and the public lifecycle state;
- renderable, light, camera, and environment source registries;
- `RenderWorld`, `LightWorld`, camera selection, and immutable snapshot
  production;
- `MaterialSystem`, `MaterialAssetResolver`, `RenderResourceResolver`, and the
  request/render cache until R1.4;
- `RenderCaptureService` request/callback ownership and the public
  `IRenderCaptureService` capability;
- the Runtime/Editor facade: source sinks, SceneColor view, extent request,
  editor composition, diagnostics, and the existing graphics-context escape
  hatch;
- lifecycle rollback and reverse-order shutdown orchestration.

`RenderSystem` must not retain a pass-specific pipeline, sampler, environment
binding bundle, active shadow frame, shadow-recorded flag, named target set, or
`Record*Pass`/`Prepare*PassResources` method after R1.2.

### `DeferredRenderer` owns

- `RendererFrameTargets` and the pending SceneColor extent;
- the existing declaration-only `RenderPassSchedule` until R1.3 replaces it;
- directional, spot, and point shadow selection, matrices, job descriptions,
  record-success state, and the point-shadow profile one-shot flag;
- G-buffer, deferred-lighting, tone-map, debug/capture conversion, and shadow
  recording;
- all pass-private pipelines, samplers, and the fullscreen mesh;
- active, baseline, fallback, and failed-source environment binding state;
- transient per-render-call lighting binding state if it cannot remain a local;
- creation, resize, and cleanup of every resource above.

The renderer owns the pipeline/sampler/mesh/target handles it creates and
destroys them through `RenderBackend`. Environment texture bindings are
borrowed handles produced and owned by `RenderResourceResolver`; the renderer
must clear those values before resolver cleanup but must not destroy their
textures or samplers as if it owned them.

## Collaborator contracts

Names below are intended contract names. Exact field spelling may follow local
style during implementation without changing the boundary.

### Initialization dependencies

`DeferredRenderer` receives and stores only the collaborators required by the
existing renderer for its initialized lifetime:

```cpp
struct DeferredRendererInitInfo
{
    graphics::RenderBackend& backend;
    resource::ResourcePipeline& resource_pipeline;      // transitional: R1.4
    RenderResourceResolver& resource_resolver;
    MaterialSystem& materials;
};
```

Initialization also receives the initial extent, creates the complete named
target set, configures and validates the existing schedule, and returns a
diagnostic result. A failure must retire every target or handle created by the
attempt and leave the renderer non-ready. It must not initialize or clean up
the borrowed collaborators.

The `ResourcePipeline` dependency is deliberately visible as transitional.
Lazy pass shader loading/processing moves with `Prepare*Resources` in R1.2 so
the facade loses pass knowledge; R1.4 later replaces that Asset-loading path
with ready render artifacts.

### Immutable frame input

`RenderSystem` drains mutable registries before constructing one frame input.
The renderer borrows it only for the synchronous recording call:

```cpp
struct DeferredRendererFrameInput
{
    const RenderWorld& render_world;
    const std::vector<Light>& lights;
    const RenderCamera& camera;
    std::optional<EnvironmentSourceDesc> environment;
    std::optional<EnvironmentSourceHandle> environment_handle;
    std::function<bool(ShadowHandle)> is_shadow_handle_valid;
    std::optional<CaptureView> pending_capture;
};
```

The shadow-validity callable is a narrow, non-owning frame capability over the
registry's private generational handle table. It prevents `DeferredRenderer`
from owning or mutating `LightSourceRegistry`, while keeping shadow scheduling
inside the renderer. It must not be retained after the call.

Do not pass `RenderSystem&`, a universal context struct, Runtime state, the
source registries themselves, Asset paths, or native graphics objects.

### Safe-boundary resize

`RequestSceneRenderTargetExtent()` remains public on `RenderSystem` and
delegates to `DeferredRenderer::RequestExtent()`. At the next Ready-state frame
boundary, before `RenderBackend::BeginFrame()`, `RenderSystem` calls the
renderer to apply a pending extent. The renderer retains the current
`RendererFrameTargets::RebuildForExtent()` behavior, including `WaitIdle()`
only for an actual size change.

The renderer exposes a borrowed const SceneColor `RenderTarget` view for the
existing editor capability. No ownership or raw backend target escapes.

### Recording and capture handoff

After the backend and active `FrameContext` have begun, `RenderSystem` calls a
single renderer recording entry point:

```cpp
DeferredRendererFrameResult RecordFrame(
    FrameContext& frame_context,
    const DeferredRendererFrameInput& input);
```

The result reports at least whether normal recording completed and whether the
requested capture view is ready for readback. The renderer records a semantic
debug conversion when required; `RenderSystem` then asks its
`RenderCaptureService` to enqueue the readback. This keeps callback/thread-safe
request ownership on the facade side while all attachment and conversion
knowledge remains renderer-private.

SceneColor capture remains a direct readback of the renderer-owned SceneColor
target. Other semantic views resolve to the renderer-owned CaptureOutput. The
capture service's target resolver delegates to `DeferredRenderer` and never
stores a target handle across renderer cleanup.

### Editor terminal pass

Editor composition remains external and terminal. R1.2 preserves
`ExecuteEditorCompositePass()` and its once-per-frame/state checks. The
declaration/execution relationship between the renderer's fixed sequence and
this external terminal pass remains characterized but is not redesigned until
R1.3.

## Frame sequence after extraction

The observable sequence must remain:

1. Consume the current request budget and refresh materials.
2. Drain renderable/light/camera/environment source commands.
3. Apply `RenderWorld` commands and produce immutable light/environment/camera
   inputs.
4. Apply a pending target extent at the safe boundary.
5. Begin the backend frame and active `FrameContext`.
6. Ask `DeferredRenderer` to schedule shadows, create the lighting binding, and
   record shadow → G-buffer → deferred-lighting → tone-map → optional capture.
7. Optionally execute one external editor composite.
8. End the `FrameContext`, then end the backend frame.

Do not use R1.2 to execute the `RenderPassSchedule` entries. The schedule still
validates declarations while the renderer retains the characterized manual
calls. R1.3 is the stage that makes declaration and invocation one source of
truth.

## Initialization and shutdown order

### Initialization

1. Create material/resource-processing collaborators.
2. Create and initialize the backend.
3. Create the resource resolver and bind it to materials.
4. Initialize every `FrameContext` slot.
5. Construct and transactionally initialize `DeferredRenderer` targets and
   schedule.
6. Construct `RenderCaptureService` with target/frame resolvers that borrow the
   initialized renderer and facade.
7. Apply the default camera and enter `Ready`.

Any failure executes the same cleanup path and returns the facade to
`Uninitialized`, preserving R1.1 semantics.

### Shutdown

1. Close an unexpected active frame bracket.
2. Clear source registries/worlds and release material asset records.
3. Wait for submitted backend work and drain pending readbacks.
4. Destroy `RenderCaptureService`, completing/cancelling its callback exactly
   once.
5. Clean up `FrameContext` transient buffers and binding sets.
6. Call `DeferredRenderer::Cleanup()`: destroy renderer-owned targets,
   pipelines, samplers, and fullscreen mesh; clear borrowed environment
   bindings and all frame state.
7. Clean up `RenderResourceResolver`, then the Resource pipeline.
8. Clean up and destroy the backend.

The exact order of target versus pass-handle destruction inside the renderer
must be documented in its implementation and covered by the backend probe. No
renderer-owned handle may be destroyed after backend cleanup.

## Implementation stages

### R1.2.A — strengthen the ownership baseline

- Extend the shared backend probe to record pipeline, sampler, mesh, and target
  destruction, not only frame/cleanup events.
- Preserve the existing orchestration assertions for target order, capture,
  resize, editor composition, and shutdown.
- Add an assertion that every successfully created renderer-owned handle is
  destroyed exactly once before `backend_cleanup`.

### R1.2.B — introduce the renderer shell and move targets

- Add `deferred_renderer.h/.cpp` and wire them into the Render target.
- Move `RendererFrameTargets`, pending extent, schedule configuration, and
  SceneColor/capture target resolution behind the renderer.
- Delegate the existing facade accessors without changing their public types.
- Make renderer target initialization transactional and failure-injectable
  through the existing backend double.

### R1.2.C — move environment and shadow policy/state

- Move environment binding bundles, fallback preparation, failed-source
  suppression, and environment resolution into the renderer.
- Pass the active source value/handle and shadow-validity capability in the
  immutable frame input.
- Move all directional/spot/point shadow scheduling structs, helpers, matrices,
  record flags, and profiling state.
- Keep `LightWorld`, `LightSourceRegistry`, and `EnvironmentSourceRegistry`
  owned and drained by `RenderSystem`.

### R1.2.D — move pass recording and pass-resource preparation

- Move shadow, mesh, G-buffer, deferred-lighting, tone-map, debug, and capture
  methods without changing algorithms, constants, shaders, formats, descriptor
  layouts, culling, or draw order.
- Move every pass-private pipeline, sampler, fullscreen mesh, and lazy-prepare
  guard into the renderer.
- Replace the manual pass block in `RenderSystem::BeginFrame()` with one
  `DeferredRenderer::RecordFrame()` call and the capture readback handoff.
- Keep Asset/Resource calls inside the moved preparation code visibly marked
  as R1.4 debt; do not redesign them here.

### R1.2.E — consolidate cleanup and facade shape

- Make `DeferredRenderer::Cleanup()` idempotent and responsible for all of its
  owned handles and logical state.
- Call it at the documented safe point before resolver/backend cleanup.
- Remove the moved members, nested structs, helpers, and includes from
  `render_system.h/.cpp`.
- Verify the public `RenderSystem` API and Runtime/Editor call sites are
  unchanged except for internal delegation.

### R1.2.F — evidence and handoff

- Run the targeted ownership, lifecycle, pass, material, capture, environment,
  and RenderWorld suites.
- Run full Debug build and CTest because production headers and CMake wiring
  change.
- Run `GraphicsSmoke` sequentially on Vulkan and OpenGL.
- Launch deterministic PBR, directional/spot/point-shadow fixtures through the
  Runtime command transport; inspect SceneColor plus relevant shadow/capture
  views on both backends.
- Record commands, results, skipped evidence, and remaining R1.3/R1.4 debt in
  a new R1.2 journal. Update TODO/status only after the evidence is real.

## Expected file map

```text
engine/runtime/render/
  deferred_renderer.h              # renderer contract and owned state
  deferred_renderer.cpp            # existing deferred policy/recording moved here
  render_system.h/.cpp              # facade, worlds, frame bracket, delegation
  renderer_frame_targets.*          # unchanged focused target owner used by renderer
  render_pass.*                     # unchanged declaration validator until R1.3
  CMakeLists.txt

engine/test/unit/render/
  render_backend_test_double.h      # shared only if duplication justifies extraction
  deferred_renderer_test.cpp        # direct ownership/init/record/cleanup tests
  render_system_test.cpp            # facade/orchestration regression tests
  CMakeLists.txt
```

The shared test double is optional: extract it only when both test files use
it. Production code must not gain a second backend interface for testing.

## Invariants

- Runtime owns exactly one `RenderSystem`; no caller owns or selects a
  `DeferredRenderer`.
- `RenderSystem` owns the backend frame bracket. `DeferredRenderer` neither
  begins nor ends backend frames.
- Gameplay publishes copied source values and never observes renderer, world,
  material, target, or Graphics handles.
- Render chooses passes, targets, lights, shadows, materials, and capture
  semantics; Graphics owns physical GPU resources, command translation,
  synchronization, and destruction safety.
- Asset owns identity/loading and Resource owns CPU artifact processing. R1.2
  may preserve the existing transitional calls but must not create a new path
  around those owners.
- All common contracts remain Vulkan/OpenGL-neutral.
- Visual output, shader ABI, target formats/extents, binding numbers, shadow
  budgets, light selection, draw order, and capture names remain unchanged.
- Resize and shutdown wait only at the existing safe ownership boundaries.
- Initialization rollback and shutdown remain deterministic and idempotent.

## Non-goals

- No render graph, pass culling, dependency sorting, transient aliasing, or
  automatic barrier generation.
- No unification of declaration and execution; that is R1.3.
- No ready-artifact ingestion redesign or removal of `LoadSync()`; that is
  R1.4.
- No renderer plugin interface, forward renderer, path tracer, class-per-pass
  hierarchy, generic GPU-handle wrapper, or universal context object.
- No change to public editor `GraphicsContext`, material semantics, light ABI,
  capture protocol, Runtime scheduling, shaders, or scene content.
- No opportunistic deferred-PBR feature or performance work.

## Reference discovery gate

The local architecture and live call path were inspected before external
comparison. The following sources were then read directly on 2026-09-02:

- [O3DE `RenderPipeline` at `40b15f1`](https://github.com/o3de/o3de/blob/40b15f133b1b0736a06d88accea7a1fa892c2d48/Gems/Atom/RPI/Code/Include/Atom/RPI.Public/RenderPipeline.h)
  and its [implementation](https://github.com/o3de/o3de/blob/40b15f133b1b0736a06d88accea7a1fa892c2d48/Gems/Atom/RPI/Code/Source/RPI.Public/RenderPipeline.cpp)
  show a renderer/pipeline object owning a root pass tree and per-frame views,
  while higher-level system/scene objects schedule pipelines. This supports a
  concrete owner for pass state below the system facade. O3DE's asset-authored
  pass templates, mutable pass tree, feature processors, and RHI scale do not
  fit R1.2 and are rejected.
- [Filament `FRenderer` at `9adcd39`](https://github.com/google/filament/blob/9adcd39174ee43bd5bab974233b7461ac418282a/filament/src/details/Renderer.h)
  retains a narrow begin/render/end surface while its implementation owns
  render-pass construction and renderer-local resources and explicitly waits
  before terminating them. This supports one renderer collaborator with an
  explicit cleanup boundary. Filament's frame graph, render thread, job
  system, and feature breadth are not transferred.
- [Godot `RendererSceneRender` at `6220ead`](https://github.com/godotengine/godot/blob/6220ead4fa06611918e371e6f51d7b9a3aefe53c/servers/rendering/renderer_scene_render.h)
  exposes a very broad `render_scene` parameter surface spanning buffers,
  camera, geometry, lights, probes, decals, environment, atlases, shadows, and
  GI. That breadth is justified by Godot's mature renderer variants but is a
  warning here: R1.2 uses one small synchronous frame input and no speculative
  virtual renderer interface.
- The local [gkNextEngine study](../../graphics/gknext_reference.md) separates
  renderer policy from device execution and warns against making the system
  integration point own every runtime concern. R1.2 applies that conclusion
  without adopting Vulkan-only or GPU-driven assumptions.

## Acceptance criteria

- [ ] `DeferredRenderer` is the sole owner of named frame targets,
  pass-private pipelines/samplers/fullscreen mesh, environment binding state,
  shadow frame state, and pass recording/preparation methods.
- [ ] `RenderSystem` remains the sole public facade and owns no moved
  pass-specific member or method.
- [ ] The Runtime, Gameplay, Editor, capture, material, Asset/Resource, and
  common Graphics contracts do not broaden.
- [ ] Existing manual pass and terminal editor order remains byte-for-behavior
  equivalent to the R1.1 characterization; R1.3 remains open.
- [ ] Resize is applied before backend frame begin and retains the current
  change-only `WaitIdle()` behavior.
- [ ] Capture requests complete exactly once and select SceneColor versus
  CaptureOutput exactly as before.
- [ ] Renderer initialization failure rolls back all resources created by the
  attempt and leaves `RenderSystem` non-ready.
- [ ] Every renderer-owned GPU handle is destroyed exactly once before
  resolver/backend cleanup; borrowed resolver bindings are only cleared.
- [ ] Focused Render tests, full Debug build, and complete CTest pass.
- [ ] Vulkan and OpenGL `GraphicsSmoke` pass, and deterministic SceneColor plus
  directional/spot/point capture views are freshly captured and inspected.

## Remaining uncertainty

- The exact value/callable representation for shadow-handle validation should
  be chosen for C++17 without retaining the callback beyond `RecordFrame()`.
  This is an implementation detail as long as registry ownership does not move.
- Lazy pass shader preparation still invokes Asset/Resource services. R1.2
  isolates that debt inside the renderer; R1.4 must replace it with ready
  render artifacts rather than treating the new location as the final design.
- `RendererFrameTargets::RebuildForExtent()` currently performs `WaitIdle()`
  internally. R1.2 preserves it. Moving the wait to a higher lifetime service
  requires a separate measured synchronization decision.
