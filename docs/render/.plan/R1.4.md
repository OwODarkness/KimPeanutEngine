## Status and implementation gate

Implemented on 2026-09-02. R1.3 is implemented, reviewed, and validated, and
the R1.4 catalog/preparation migration is landed with focused and full-build
validation. The source review findings are addressed and fresh PBR,
point-shadow, and spot-shadow Runtime captures pass on both APIs and were
inspected. Direct dual-backend smoke still emits fresh captures, but its strict
cross-backend silhouette comparator rejects a small edge difference; that is
the only remaining R1.4 evidence follow-up.

R1.4 changes the Asset → Resource → Render handoff. It does not authorize a
general streaming system, hot reload, eviction, renderer feature changes, or
new Graphics/RHI contracts.

## Objective

Make Render consume only validated, lifetime-pinned CPU assets and derived
artifacts. Disk loading, path interpretation, dependency validation, shader
processing, and environment IBL processing must finish before the resulting
catalog is passed to `RenderSystem`.

Success means:

- no file path reaches `RenderSystem`, `DeferredRenderer`, material resolution,
  or `RenderResourceResolver`;
- no Render frame or lazy pass-preparation path calls `AssetManager::LoadSync`,
  `ResourcePipeline::ProcessShader`, or `ProcessEnvironmentIbl`;
- one immutable prepared catalog supplies authored and renderer-built-in
  assets by typed `AssetID` or closed logical role;
- Render remains responsible for API-neutral GPU descriptions and its GPU
  handle caches, while Graphics remains the GPU owner;
- the unused path-based request queue and request-ID render cache are removed
  instead of being mistaken for a working streaming system.

## Current state

The live code has four distinct boundary violations:

1. `RenderSystem::ConsumeOne()` accepts an `AssetLoadRequest` containing a path,
   calls `AssetManager::LoadSync()`, may process shaders, and then creates GPU
   resources. The queue has no production producer; only tests construct one.
2. `DeferredRenderer` lazily loads and processes five private shader programs:
   deferred lighting, G-buffer debug, tone mapping, capture conversion, and
   directional shadow depth.
3. `MaterialAssetResolver::WarmBuiltInTextures()` loads the white and flat-normal
   fallback textures from paths, while material resolution and
   `RenderResourceResolver` query the global `AssetManager` directly.
4. Environment activation performs CPU IBL processing inside
   `DeferredRenderer` before creating its GPU bindings.

The apparent frame budget does not make these paths asynchronous:

- `kMaxRuntimeLoadsPerFrame` limits item count, not load/compile/upload time;
- the queue passed from `RuntimeContext` is never populated in production;
- the request state and type-erased payload fields are not used as the comments
  describe;
- `IsReady(RequestID)`, `GetCached(RequestID)`, and `GetPipeline(RequestID)` have
  no production callers.

GP7 already removed bootstrap scene transfer, environment path matching, and
hard-coded startup Actors. R1.4 must not recreate them in a renderer manifest.
The selected level remains the authored root; renderer built-ins are a separate,
closed engine requirement set.

## Concrete design question

How should Runtime prepare the selected level's renderable dependency closure
and the renderer's closed built-in requirements so Render receives stable CPU
payloads and derived artifacts—but no paths, loading policy, or processor—while
preserving current material, environment, pass, and GPU-cache behavior?

## Chosen design

Introduce an immutable `PreparedRenderAssetCatalog` built transactionally by a
Runtime-owned `RenderAssetPreparer` before `RenderSystem::Initialize()`.

```text
selected level AssetID + closed Render built-in requirements
                         │
                         ▼
Runtime RenderAssetPreparer
  ├─ AssetManager: load/validate built-ins and walk ready dependencies
  ├─ ResourcePipeline: process shader variants and environment IBL
  └─ freeze payloads, dependency IDs, derived data, and statistics
                         │
                         ▼
const PreparedRenderAssetCatalog
  ├─ RenderSystem / material resolver / DeferredRenderer
  ├─ RenderResourceResolver: PipelineDesc, mesh, texture, sampler caches
  └─ Graphics/RHI: GPU creation, synchronization, destruction
```

This is a startup-ready catalog, not a general asset database. It snapshots only
the payloads and dependency relationships Render needs, pins them with shared
ownership, and remains immutable until Render shutdown.

### Ownership

| Concern | Owner after R1.4 |
| --- | --- |
| Path choice for the selected level | Bootstrap/CLI selection in Engine |
| Built-in Render requirement declarations | Render, as a closed logical-role table |
| Path normalization, loading, type validation, dependency graph | Asset |
| Shader and environment CPU processing | Resource pipeline driven by Runtime |
| Prepared catalog construction and startup transaction | Runtime composition |
| Catalog lookup, material interpretation, GPU-description policy | Render |
| GPU handles, uploads, synchronization, safe destruction | Graphics/RHI |

`RuntimeContext` owns the prepared catalog for at least as long as
`RenderSystem`; Render receives a non-null `shared_ptr<const ...>`. Catalog
records pin CPU payloads independently of Asset wrapper lifetime. GPU handles
remain exclusively in `RenderResourceResolver`, `DeferredRenderer`, and the
backend managers and are destroyed in the existing order.

## Contracts

### Closed built-in roles

Use a typed role rather than string lookups inside Render:

```cpp
enum class BuiltInRenderAsset : uint8_t
{
    DeferredLightingProgram,
    GBufferDebugProgram,
    ToneMapProgram,
    CaptureViewProgram,
    DirectionalShadowProgram,
    DefaultWhiteTexture,
    DefaultFlatNormalTexture,
    Count,
};
```

The Render-owned requirement table maps each role to one relative asset path
and expected `AssetType`. Runtime may read that declaration to ask Asset to
load it, but `RenderSystemInitInfo` receives only the finalized role →
`AssetID` bindings. The catalog validator rejects missing or duplicate roles,
wrong types, stale IDs, null payloads, and unexpected path-bearing data.

The role table is engine configuration, not scene authoring. Do not put these
pass shaders into every level or add renderer-specific fields to `*.level`.

### Prepared asset records

The catalog stores a closed render-facing payload variant:

```cpp
using PreparedRenderPayload = std::variant<
    asset::MeshPtr,
    asset::TexturePtr,
    asset::ShaderPtr,
    asset::ShaderProgramPtr,
    asset::MaterialPtr>;

struct PreparedRenderAssetRecord
{
    asset::AssetID id;
    PreparedRenderPayload payload;
    std::vector<asset::AssetID> dependencies;
};
```

The exact spelling may change during implementation, but these rules do not:

- the record has no path, request state, GPU handle, or backend type;
- `id.type` must match the active variant;
- dependency IDs are copied in authored order and validated before freeze;
- shader resources in a published program are already `Ready` for the selected
  `GraphicsAPIType`;
- records are immutable and payload pointers are non-null;
- duplicate packed IDs are rejected rather than overwritten.

The catalog exposes typed read-only operations such as `Get<T>(AssetID)`,
`ResolveDependency(owner, index, expected_type)`, and
`GetBuiltIn(BuiltInRenderAsset)`. These replace direct global
`AssetManager` lookup from Render.

### Derived environment data

Environment IBL output is CPU-derived data and remains Resource-owned in
vocabulary. The prepared catalog stores a derived record keyed by the source
texture `AssetID`:

```cpp
struct PreparedEnvironmentIbl
{
    asset::AssetID source_texture;
    resource::EnvironmentIblData data;
};
```

The preparer identifies the selected level's optional environment through its
validated dependency index, verifies the RGBA16F texture payload, and runs
`ProcessEnvironmentIbl()` before catalog publication. `DeferredRenderer`
creates only the panorama and derived GPU bindings from this ready record. A
missing or failed required environment preparation aborts startup; Render does
not retry CPU processing during a frame.

### Shader processing

The preparer walks the loaded level dependency closure plus built-in programs.
Every reachable `ShaderProgramResource` is processed before publication.
Process all declared variants during R1.4 because backend bindless capability
is not known until Render initializes the backend; this preserves later variant
selection without moving Resource processing back into Render.

Publication validates, per selected API:

- every selected stage pointer and `ShaderData` is present;
- status is `Ready`, not `Uncompiled`, `Compiling`, or `CompileFailed`;
- `ShaderData::api` matches the startup API;
- a program cannot be published with a partially processed variant.

Processing remains fail-soft within a batch so diagnostics can name all failed
stages, but catalog construction is transactional: any required failure rejects
the whole startup catalog.

## Startup flow

1. `Engine::LoadStartupLevel()` continues to choose and synchronously load the
   selected level under Asset ownership.
2. Before Render initialization, Runtime requests the closed built-in table and
   invokes `RenderAssetPreparer` with the startup level root and API type.
3. The preparer loads built-ins through `AssetManager`, validates each expected
   type, and traverses the ready dependency closure without interpreting scene
   policy.
4. The preparer processes all shader variants and the optional environment IBL,
   then freezes the catalog and preparation statistics.
5. `RenderSystemInitInfo` receives the immutable catalog instead of an async
   path queue.
6. `RenderSystem`, `MaterialAssetResolver`, `DeferredRenderer`, and
   `RenderResourceResolver` resolve CPU inputs only from the catalog.
7. Render creates GPU objects at its existing initialization or lazy-use points;
   no disk or CPU resource processing is permitted there.

The existing startup ready/commit-or-abort handshake remains unchanged. Catalog
failure occurs before Render publishes ready, and existing startup cleanup
releases the partial Runtime state.

## Render-side migration

### `RenderSystem`

- Replace `load_queue` in `RenderSystemInitInfo` with the immutable catalog.
- Remove `ConsumeRequests`, `ConsumeOne`, `RenderCacheEntry`, `render_cache_`,
  and the item-count budget.
- Remove request-ID polling APIs after a final caller audit confirms they remain
  test-only.
- Keep `GetLoadedShaderCount()` as a tooling metric backed by catalog preparation
  statistics, not a Render-owned processor.
- `BeginFrame()` starts with material/source refresh; it performs no load or
  CPU resource-processing drain.

### `MaterialAssetResolver`

- Resolve material, shader-program, and texture dependencies through the
  catalog's copied dependency contract.
- Replace `WarmBuiltInTextures()` and path constants with the two typed built-in
  texture roles.
- Preserve current fallback choice, canonical parameter order, pending/failed
  semantics, and material-record lifetime.

### `RenderResourceResolver`

- Replace the `ResourcePipeline` dependency with a const catalog dependency.
- `ResolveTemplate()` verifies prepared shader stages and creates pipeline
  descriptions; it never compiles.
- `ResolveInstance()` obtains prepared texture data from the catalog and retains
  existing color-space, sampler, and cache-key behavior.
- Mesh, texture, sampler, pipeline, and descriptor-set GPU caches remain here.

### `DeferredRenderer`

- Replace five `LoadSync`/`ProcessShader` blocks with a shared helper that
  retrieves a typed built-in program and validates its prepared stages.
- Retain lazy GPU pipeline creation so R1.4 does not alter pass initialization
  order or partial GPU-resource rollback.
- Resolve the environment source texture and prepared IBL record from the
  catalog; retain current fallback bundle and failed-source suppression.
- Remove the `ResourcePipeline` pointer from `DeferredRendererInitInfo`.

## Legacy queue removal

Delete the unused path-based contract after its last caller is removed:

- `asset/asset_load_request.h` and its Render-specific request state;
- `RuntimeContext::async_load_queue_`;
- `RenderSystemInitInfo::load_queue`;
- the render request-ID cache and polling API;
- tests that characterize path consumption rather than prepared inputs.

Keep `core/async::AsyncQueue<T>` because it is generic and may have unrelated
users. Mark the existing async-resource-queue document as a superseded proposal.
A future streaming stage must start from an actual producer and transport
ready, typed packets; it must not revive a path consumer inside Render.

## Failure policy

- Missing root, built-in, dependency, payload, processed stage, or required IBL
  artifact fails catalog construction with a role/AssetID-qualified diagnostic.
- The catalog is published only on total success; partial catalogs are never
  visible to Render.
- Duplicate requirements or records are configuration errors.
- A lookup for an ID outside the immutable catalog returns `Pending` only where
  the current material/source contract already supports pending data; startup
  built-ins instead fail initialization immediately.
- GPU creation failure retains current Render failure behavior and cleanup. It
  is not reclassified as an Asset or Resource failure.

## Threading and lifetime

- R1.4 preparation is synchronous startup work. It completes before the Render
  frame loop and therefore needs no new worker or cross-thread state machine.
- `AssetManager` retains its existing locking and loader serialization.
- `ResourcePipeline` is driven only by the Runtime preparer during this stage.
- The immutable catalog may be read on the render thread without mutation or
  internal locking.
- Catalog payload pins outlive every Render GPU cache entry. Render releases GPU
  state first; Runtime releases the catalog after `RenderSystem::Shutdown()`.

## Implementation stages

### R1.4.A — characterize and close the contract

- Add tests proving the production queue has no producer and the polling API has
  no non-test caller before removal.
- Characterize current built-in roles, authored dependency closure, shader
  variants, environment IBL, fallback textures, and cleanup order.
- Record the reference gate and baseline results in a new R1.4 journal.

### R1.4.B — immutable catalog and validation

- Add the closed built-in role table and prepared record/catalog types.
- Implement duplicate, type, payload, dependency, shader API/status, built-in,
  and environment-derived-data validation.
- Add focused unit tests using synthetic AssetIDs and payloads.

### R1.4.C — Runtime preparation transaction

- Implement closure traversal from the selected level plus built-ins.
- Move `ResourcePipeline` driving out of Render and process all shader variants.
- Prepare optional environment IBL and freeze statistics/catalog only on success.
- Wire the existing startup abort path to preparation diagnostics.

### R1.4.D — Render consumers

- Inject the immutable catalog into `RenderSystem`, material resolution,
  `RenderResourceResolver`, and `DeferredRenderer`.
- Replace global Asset lookup, fallback path loading, lazy pass shader loading,
  and in-frame IBL processing.
- Preserve all current GPU cache keys, pass resources, fallbacks, and teardown.

### R1.4.E — remove legacy request/cache surface

- Remove `AssetLoadRequest`, the unused Runtime queue, request drain, request-ID
  cache/polling APIs, and stale budget constants/comments.
- Update tests and the async/resource documentation to describe the landed
  startup catalog and leave future streaming explicitly unimplemented.
- Run an include/dependency audit proving Render has no AssetManager or Resource
  processor dependency.

### R1.4.F — evidence and handoff

- Run focused Asset, Resource, Render, Runtime, and material tests.
- Run the full Debug build and CTest.
- Run Vulkan and OpenGL GraphicsSmoke.
- Capture and inspect PBR, point-shadow, and spot-shadow startup fixtures on both
  backends.
- Update status, risk, roadmap, and journal records only after evidence passes.

## Rejected alternatives

### Keep the current path queue and add a worker

Rejected for R1.4. There is no production requester, cancellation contract,
priority policy, or dynamic streaming consumer. Adding a worker would expand
scope while retaining paths and type erasure at the Render boundary.

### Put renderer pass shaders into every level asset

Rejected. Level assets author scene dependencies; tone mapping, capture, and
shadow pass programs are renderer implementation requirements. Combining them
would recreate bootstrap coupling and duplicate engine policy in content.

### Let Render load built-ins but move the calls to one helper

Rejected. Smaller call sites do not change ownership or remove synchronous disk
and CPU processing from the renderer.

### Publish only AssetIDs and query `AssetManager` globally

Rejected as the final R1.4 shape. IDs preserve identity but do not pin payload
lifetime, snapshot dependencies, prove processing readiness, or make tests
independent of the global cache.

### Store GPU handles in Asset or Resource records

Rejected. GPU objects are backend- and device-lifetime state; Graphics owns them
and Render owns the policy/cache that requests them.

### Eagerly create every GPU object during catalog preparation

Rejected. The preparer has no Graphics ownership, and R1.4 should not change
lazy pass GPU initialization or backend rollback behavior.

### Build a general hot-reload/streaming registry

Rejected until there is a real runtime producer, consumer, cancellation rule,
and measured frame-budget need. The immutable startup catalog is intentionally
smaller.

## Reference discovery gate

GitHub MCP was not available in this session, so the read-only discovery pass
used the repositories' GitHub source pages at the following branch tips on
2026-09-02. No source was copied.

### O3DE

- Revision studied: `development` at `1242766`.
- Source: [`AssetManager.h`](https://github.com/o3de/o3de/blob/1242766/Code/Framework/AzCore/AzCore/Asset/AssetManager.h).
- Observed pattern: loading is asynchronous, readiness notification is explicit,
  and `FindAsset` locates an existing in-memory asset without initiating a load.
- Adopt: distinguish producer-side load/readiness from consumer-side ready lookup.
- Reject: O3DE's event bus, asset container, catalog, and handler framework are
  disproportionate to the current startup-only KimPeanutEngine need.

### Godot

- Revision studied: `master` at `6220ead`.
- Sources: [`ResourceLoader`](https://github.com/godotengine/godot/blob/6220ead/core/io/resource_loader.h),
  [`ImageTexture`](https://github.com/godotengine/godot/blob/6220ead/scene/resources/image_texture.cpp),
  and [`RenderingServer`](https://github.com/godotengine/godot/blob/6220ead/servers/rendering/rendering_server.h).
- Observed pattern: threaded resource loading is a distinct API; texture GPU
  creation accepts an already-materialized `Ref<Image>` and returns/updates a
  rendering RID.
- Adopt: pass ready CPU data across the rendering boundary and keep GPU creation
  on the rendering side.
- Reject: a general `Resource` object hierarchy that owns rendering RIDs would
  conflict with KimPeanutEngine's Asset/Render/Graphics ownership split.

### bgfx

- Revision studied: `master` at `780f7bf`.
- Sources: [`bgfx.h`](https://github.com/bkaradzic/bgfx/blob/780f7bf/include/bgfx/bgfx.h)
  and the [`nanovg` integration](https://github.com/bkaradzic/bgfx/blob/780f7bf/examples/common/nanovg/nanovg_bgfx.cpp).
- Observed pattern: shader and texture creation consume caller-provided memory or
  dimensions and return opaque handles; the rendering API does not load asset
  paths.
- Adopt: keep Graphics creation memory/description based and handle returning.
- Reject: bgfx's internal submission threading and memory ownership model are not
  needed to repair KimPeanutEngine's higher-level ingestion boundary.

## Remaining uncertainty

- Processing every shader variant may add startup time. Measure it before adding
  a capability-aware second preparation phase; correctness and boundary closure
  come first.
- The current GPU resolver caches until shutdown. Per-level eviction and hot
  reload remain later work and must define safe GPU retirement first.
- Future streaming may use immutable prepared batches derived from this catalog,
  but R1.4 deliberately does not design that protocol without a consumer.
