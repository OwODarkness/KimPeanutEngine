# R5.3 — Pass-family ownership: implementation plan

**Status:** planned; no implementation or acceptance claimed.
**Parent:** [R5](R5.md#r53--extract-pass-family-state-by-lifetime).
**Prerequisite:** [R5.2 executor/binding acceptance](R5.2.md), plus the affected
R5.0 baselines in the [execution spec](../../../.spec/specs/render-r5-render-configuration-graph-ownership.md).

## Objective and boundary

Reduce the 4,587-line `deferred_renderer.cpp` inspected at HEAD
`01d2242caac1ffafcc4c600d54d0b0fc129e9029` plus current R5.1 working-tree changes.
Extract methods, structs, fields, constants, cache keys and cleanup together.
Do not make several source files that still implement one oversized class.

Keep `DeferredRenderer` as the composition facade for initialize, resolve frame
settings/conditions, prepare owner inputs, execute the graph, finalize, resize,
capture views and cleanup. RenderSystem retains backend/frame/submission and
consumer-demand ownership. Graphics retains native allocations and retirement.

**Render graph is authoritative:** pass owners expose declaration/recording
contracts and consume `RenderGraphPassContext`. They do not schedule each other,
choose execution order, issue graph-owned transitions, open target brackets or
allocate/release graph transient leases. Persistent histories/caches belong to
owners, but their reads/writes and consumers belong in graph declarations.

## Proposed concrete owners and current symbol mapping

Files below are proposed, not existing APIs. Place pass implementations under
`engine/runtime/render/passes/`, RT preparation under `render/ray_tracing/`;
register `.cpp` files in the existing Render target. No per-pass virtual hierarchy.

| Owner / files | Move current functions | Move current state and definitions |
| --- | --- | --- |

| `DeferredLightingPass`, `passes/deferred_lighting_pass.{h,cpp}` | `RecordGBufferPass`, `RecordDeferredLightingPass`, `PrepareDeferredLightingPassResources`, `UpdateEnvironment`, `PrepareEnvironmentIbl`, `ResolveLevelEnvironment`, `EnsureEnvironmentFallbackBindings` | `EnvironmentBindingBundle`, active/level environment and failed-source state; deferred/query pipelines, frame lighting binding; GBuffer uniform key |
| `ToneMapPass`, `passes/tone_map_pass.{h,cpp}` | `PrepareToneMapPassResources`, `RecordToneMapPass` | Tone-map pipeline/signature and exposure/transfer policy constants; raster/PT choose graph input, not separate recording algorithms |
| `CaptureViewPass`, `passes/capture_view_pass.{h,cpp}` | `PrepareGBufferDebugPassResources`, `PrepareCaptureViewPassResources`, `RecordCaptureViewPass` | Debug/capture conversion pipelines and per-consumer conversion inputs; independent CaptureOutput/DebugViewOutput bindings |

Move resource creation and destruction from facade `Initialize`/`Cleanup` into
the same owner as the corresponding handles. Split current mixed teardown by
resource kind; no pass destroys another pass's descriptors, tables or pipeline.
Public RenderSystem/DeferredRenderer compatibility methods delegate during moves.

### Two justified shared helpers

- `SceneDrawRecorder`, `scene_draw_recorder.{h,cpp}`: move `FrameObjectState`,
  object/material binding caches, immutable world snapshot and revision-stable
  section packets, `BuildSectionCandidatesProfiled`, `BuildVisibleSectionsProfiled`,
  `RecordShadowCaster`, `RecordMeshProxy` and associated draw accounting. It owns
  one shared CPU draw cache used by shadow/GBuffer; frame uniforms/bindings remain
  FrameContext-owned. Reuse existing submission/draw-list helpers where they fit;
  do not build a second packet interpreter or copy tables per pass.
- `FullscreenPassResources`, `passes/fullscreen_pass_resources.{h,cpp}`: move
  the fullscreen mesh and common linear sampler from
  `PrepareFullscreenPassResources`. Tone-map/capture/deferred owners borrow its
  readonly handles. Shadow owns the shared depth samplers currently created from
  multiple preparation methods; consumers borrow those handles explicitly.

`RendererFrameTargets` already owns persistent logical targets. Retain it rather
than redistributing the same targets among passes. Graph transients stay with
R5.2. PT owns its persistent ping-pong/guide wrappers and supplies typed imports.

## Struct, value and header placement rules

| Category | Destination |
| --- | --- |
| Owner-private frame structs, descriptor keys, cache records | Owner's private declaration or `.cpp`; use a private implementation only when it meaningfully isolates dependencies |
| Actual cross-owner borrowed outputs | Small adjacent headers: `shadow_frame_output.h`, `environment_frame_bindings.h`, `ray_tracing_scene_view.h` |
| Existing settings/profiles/capture requests | Keep existing `path_trace_settings.h`, `render_profile.h`, capture contracts; do not duplicate them |
| Graph bindings/context/outcomes | R5.2 graph headers, not pass headers or `deferred_renderer.h` |
| CPU-to-shader packed scene records | `ray_tracing/path_tracing_scene_data.h`, shared only by scene packing and PT consumption; size/alignment/offset assertions |
| Camera/uniform schemas presently in Graphics | Preserve current ABI/location during these moves; R5.4 owns their later boundary correction |
| Owner-specific numeric policy and uniform keys | Owner `.cpp`; keep integrator, RNG, exposure and atlas values unchanged |

Do not create `render_types.h` or a shared mutable `DeferredRendererState` bag.
Forward-declare collaborators where possible. No owner may be `friend` to the
facade as an escape hatch, keep a facade pointer or access sibling internals.
Cross-owner views contain copied values or frame-bounded spans/common handles,
never backend-native objects or writable references to another owner's cache.

## Graph integration and data flow

At frame start, the facade resolves the already-authored R5.1 settings/demand
snapshot, then creates one frame draw view. Shadow prepares selected jobs and
reuse dispositions; deferred prepares environment/light inputs; RT scene
prepares records/build inputs; PT prepares history imports and descriptor keys.
Preparation cannot secretly execute another pass.

Owners provide typed inputs and borrowed outputs; the facade selects the compiled
variant and assembles R5.2 bindings/callbacks. Every callback reads/writes only its
declared graph resources. A concrete owner may provide a declaration fragment,
but the single authored frame declaration remains canonical and the compiled
graph derives order. No owner's call order substitutes for graph dependencies.

Specific dependency edges to preserve:

- Shadow maps → deferred lighting and requested shadow diagnostics. Cache reuse
  is decided before target clearing; only valid reused content satisfies reads.
- GBuffer → raster lighting and requested diagnostics; PT Scene Color alone does
  not acquire unwanted raster demand.
- Geometry/instance/scratch inputs → BLAS/TLAS builds → PT and hybrid query reads.
- Prepared RT scene reference table → PT; table updates/build recording are not
  hidden operations inside a generic pass dispatch switch.
- Previous PT history → PT → current HDR/guide → tone map/filter consumption.
  Actual reconstruction uses stay explicit; do not add a filter pass merely to
  fit the diagram if filtering currently runs in the existing shader.
- Scene Color/diagnostic imports → independent capture and Viewer conversions;
  exported scene and Viewer output → host external terminal/readback consumers.

`ShadowFrameOutput` supplies validity, selected light/slot, matrices and borrowed
targets/samplers. `EnvironmentFrameBindings` supplies sampled textures, intensity
and readiness. `RayTracingSceneView` supplies TLAS, reference table, declared
buffer groups, counts and revisions. PT depends on that view and independently
owns its descriptors/history; it cannot mutate scene caches.

Scene packing currently occurs during `RecordRayTracingPathTracePass`. Move it
to the RT scene owner while preserving the legal upload/AS-reference timing. Use
the R5.2 preparation/provider contract; if GPU work remains necessary, declare
its producer and consumers in the graph rather than uploading behind a callback.
Zero-work unchanged frames must retain table, address and descriptor reuse.

## Lifecycle, commit and invalidation contract

Write an ownership worksheet before each extraction: constructor borrows,
persistent handles, returned views, frame borrows, revision keys, init rollback,
resize steps and release order. Keep the currently required idle/retirement
preconditions; this stage does not certify or redesign R5.4's native retirement.

Initialize shared fullscreen resources before their borrowers. Clear active
executor callbacks/views before owner cleanup. Release PT descriptor references
before their scene table/TLAS/history providers; release pass bindings/pipelines
before shared targets/samplers/meshes. Graphics must still retain submitted work
until safe. Partial initialization rolls back completed owners in reverse
dependency order; cleanup is repeatable and cannot access a destroyed backend.

| Change | Expected owner invalidation |
| --- | --- |
| Transform / visibility / retained mesh-section changes | Draw/visibility and affected shadow/RT geometry or instance caches; history responds to the resulting scene revision |
| Material edit / residency or texture binding change | Resolved material/RT table and dependent PT binding/history revisions; no unrelated target recreation |
| Light position/color/intensity/rectangle axes | Shadow policy where relevant, RT light-table signature and PT history; preserve finite-area sampling and existing scalar material colors |
| Environment source/intensity/enabled | Deferred environment view and dependent PT signature/bindings; fallback behavior preserved |
| Camera / extent / estimator / SPP / visibility method | Existing PT history-reset rules; extent also rebuilds required targets and dependent descriptors |
| Output probe / reconstruction / texture policy | Preserve and test current settings-signature rule; document any ambiguity before moving, rather than installing a new reset policy |
| Capture/Viewer show/hide | Consumer demand and graph variant/conversion; never steal another consumer's output or erase estimator history without the established rule |

PT history commit moves from `FinalizeFrame` to `PathTracingPass::CommitFrame`
(proposed name), consuming executor outcomes. Advance samples/parity only under
the current success contract. Failed required producer/terminal recording does
not advertise successful new history. Record versus submit semantics remain the
existing RenderSystem contract; do not silently reinterpret them.

MIS, area-light algorithm changes or native Vulkan ownership refactors.

## Validation and completion criteria

Add focused contract tests beside existing Render tests for the extracted owners:
partial init rollback, double cleanup, expired frame views, shared draw-cache
reuse, shader/target/descriptor cache keys and history commit after failure.
Keep graph executor tests in R5.2; owners must not duplicate scheduler tests.

Build affected targets serially via `tools/kp.ps1 -Configuration Debug build
RenderPassScheduleTest`, `build RenderSystemTest`, and the engine; run relevant
render/graphics contracts. Shared headers/CMake require full Debug build/tests.
Runtime and regression conditions follow [R5.2 validation](R5.2.md#validation-and-acceptance):
Debug Vulkan validation on the approved Default desktop, OpenGL raster, current
Cornell area-light and Sponza PT baselines, equal-sample captures, demand/settings
transitions, scene edits/reload, resize/minimize/restore and safe close. Rebuilt
RelWithDebInfo measures matched regression only; no tuning or 60 FPS promise.

Structural acceptance:

- `deferred_renderer.h` contains facade contracts and owner members, not the
  private shadow/RT/history/cache structs or their former field groups.
- `deferred_renderer.cpp` contains composition/delegation, not pass recording,
  pipeline descriptions, scene-table packing, barriers or history algorithms.
- No facade backpointer, friend access, mutable shared-state bag, duplicate
  per-pass scene table or manual pass schedule is introduced.
- Report before/after source/header size and largest function sizes. A facade
  `.cpp` around 800–1,200 lines is a planning target, not a measured promise or
  an excuse to move code without ownership. A remaining long function requires
  a named responsibility and written reason.
- Existing required output/failure behavior, resource lifetime and zero-work
  static reuse hold; numerical regression gates in the execution spec pass.

Record execution in `.spec/journal/`, then review in `.review/R5.3.md` when source
work actually exists. This document is an implementation plan, not that review.
