## Status and implementation gate

**Proposed. Design only.** No implementation is authorized by this document.

This design authorizes **a seam, not a restructuring of visibility policy**. It
does not authorize a render graph, changing shadow-caster selection, GPU-driven
culling, occlusion culling, or removing the explicit pass schedule.

The honest framing, stated up front: **phase 1 is architecture, not
performance.** Measurements taken on 2026-09-14 (below) show the current workload
does not benefit from a BVH, and that the dominant culling cost is not the
frustum test an index would accelerate. What phase 1 buys is a decision
*surface*: one place to select a spatial strategy, and the metrics that make
later decisions measured rather than assumed. This is the rule the module already
applies to the render graph — a later decision "that requires measured
dependency, aliasing, or scheduling pressure" ([PLANS.md](../PLANS.md)).

## Objective

Give the renderer one renderer-facing spatial query boundary —
`RenderSpatialIndex` — so that *where* visibility culling happens and *what
structure* backs it can change without touching pass policy, materials,
scheduling, or draw ordering. Provide `Flat`, `BVH`, and later `Auto` strategies
behind that boundary, plus instrumentation that measures workload so the choice
is evidence-based.

## Current state

### The pipeline today

`RenderSceneCoordinator::PrepareFrame` drains sources into `RenderWorld` and
applies commands (`render_scene_coordinator.cpp:40`). The renderer then does:

```text
RenderWorld::Snapshot()            copies every MeshProxy, sorts by handle.id   (per frame)
BuildSectionCandidatesProfiled()   expands EVERY section of EVERY proxy        (memoized, once)
FilterVisibleSections()            linear 6-plane test over all packets        (G-buffer only)
SceneDrawListBuilder / sort / Record
```

### The shadow invariant that constrains this design

`deferred_renderer.cpp:879-882` states the rule outright:

```cpp
// Camera frustum culling applies only to GBufferPass. Shadow casters
// come from the full render-world snapshot, so fit the directional
// volume to their world bounds instead of a camera-derived box.
```

All six shadow call sites (`:884 :968 :999 :1106 :1161 :1208`) read the same
**unculled** candidate vector. Six of the seven consumers of
`frame_section_packets_` need the full, non-camera set; only the G-buffer wants a
frustum. `RecordDirectionalShadowPass` (`:1105-1118`) is the strongest case: it
records **every** candidate with no frustum, no cone, no sphere, and not even a
`flags.visible` re-check. Any pruning upstream of it is a silently lost shadow.

`scene_visibility.h:36-40` records the same intent for the API itself:

```cpp
// Shadow fitting and non-camera light volumes need section identities
// without applying a camera frustum.
```

### `ComputeDirectionalShadowStamp` is order-sensitive

It is an FNV-1a fold over the candidate list *in iteration order*
(`deferred_renderer.cpp:322-339`), and `Snapshot()` sorts by `handle.id`
(`render_world.cpp:88-90`). If the index ever becomes the source of the shadow
candidate list, any permutation difference changes the stamp and the Stage 6.1
directional-shadow cache (`directional_shadow_cache_hit_`, `:624-627`) misses on
every frame. Any index feeding a stamp-hashed consumer must preserve
`handle.id` order. This coupling is invisible from either side.

### Measured facts driving the design

From the 2026-09-14 investigation (Debug, `level/sponza.level`):

| fact | value |
|---|---|
| section packets built per frame | **738** |
| of which survive the camera frustum | **285** (39%) |
| `cpu_section_packet_build_ms` | **2.87 ms** — accumulates candidate build *and* filter |
| the filter's share of that | ~29.5 us (~1%) |
| per-call `LinearBVH` build vs the linear filter | **57x slower**; ratio worsens with scale |
| `LinearBVH` traversal vs the linear filter at 39% survival | **1.08x slower** |
| `LinearBVH` traversal at ~1% survival | **14x faster** |

Two existing counter bugs not to replicate: `section_packets_built` counts
738 + 285 = 1023 because both build sites add to it
(`deferred_renderer.cpp:504` and `:523`), and `cpu_section_packet_build_ms` is the
sum of both phases, so it cannot be read as "the cost of culling".

### Key structural conclusion

The expensive step is the **eager, shared, whole-scene section expansion**, and it
is eager even when every shadow pass rejects everything (sponza reports
`directional_shadow.sections = 0` yet still builds all 738 packets). A spatial
index does **not** fix that; making the expansion lazy per consumer would. The
index's leverage is different, and appears only when there are many renderables
or many per-pass region queries.

## Concrete design question

How can the renderer acquire one spatial-query boundary that (a) keys on stable
render identity, (b) can swap a flat scan for a hierarchy without any pass
knowing, (c) does not let a spatial structure decide visibility *policy*, and
(d) reports enough measured workload to justify its own strategy selection —
while preserving the shadow invariant and leaving today's behaviour
byte-identical?

## Chosen design

### The seam

```cpp
// render/render_world/render_spatial_index.h
enum class SpatialStrategy : uint8_t { Flat, Bvh, Auto };

class RenderSpatialIndex
{
public:
    // Phase 1 is explicit selection; Auto is phase 2 and defaults to Flat.
    void SetStrategy(SpatialStrategy strategy) noexcept;
    SpatialStrategy Strategy() const noexcept;

    // Applied once per frame, immediately after RenderWorld applies its
    // commands. Decides Build / Refit / Rebuild / unchanged internally.
    void ApplyWorldChanges(const RenderWorld &world, const RenderWorldFrameDelta &delta);

    // Spatial query only. Returns which renderables the frustum may touch,
    // conservatively. No material, pass, ordering, or pipeline decision.
    void QueryFrustum(const Frustum &frustum, std::vector<RenderableHandle> &out) const;

    const RenderSpatialIndexStats &Stats() const noexcept;
    void Clear() noexcept;
};
```

`QueryFrustum` is the only query in phase 1. It takes `render::Frustum` because
the index is a *render* abstraction; `LinearBVH` never sees it.

### Strategy set

| strategy | behaviour | when it is the right answer |
|---|---|---|
| `Flat` | iterate slots, `frustum.Intersects(slot.bounds)` | today's scenes; small n; high survival |
| `Bvh` | `LinearBVH` over slot bounds, predicate traversal | many renderables, low survival, stable set |
| `Auto` | policy over measured stats (phase 2) | once the metrics exist |

All three must return **identical handle sets** for the same world state. That is
the central correctness contract and is directly testable.

`Flat` is the default and reproduces today's behaviour exactly, which is what
makes phase 1 safe to land with no performance claim.

### Identity: handle-keyed slots

```cpp
struct Slot
{
    RenderableHandle handle;
    spatial::AABB bounds;
};
std::vector<Slot> slots_;                                   // BVH primitive id -> slot
std::unordered_map<RenderableHandle, uint32_t> slot_of_;    // handle -> slot
```

`std::hash<kpengine::Handle<Tag>>` already exists (`base/handle.h:91-97`) and
`Handle::operator==` is defined, so a handle-keyed map works today with **no core
change**. The mapping from BVH primitive id to renderer identity is
`order_[node.first + k] -> slot -> slot.handle`.

Snapshot indices are never used, so `Snapshot()`'s sort order and any vector
reordering cannot silently change object identity.

### Update lifecycle

This requires a change signal that does not exist today: `ApplyPendingCommands()`
returns `void` and destroys the batch (`render_world.cpp:75`). Add a minimal,
single-site change record — the old proxy is still in hand at the assignment
that discards it (`render_world.cpp:60`), so bounds/transform comparison lands in
exactly one place:

```cpp
struct RenderableProxyChange
{
    RenderableHandle handle;
    spatial::AABB world_bounds;
};

struct RenderWorldFrameDelta
{
    std::vector<RenderableProxyChange> created;
    std::vector<RenderableProxyChange> bounds_changed;
    std::vector<RenderableHandle> destroyed;
    uint64_t world_epoch = 0;
    bool Empty() const noexcept;
};
```

`RenderWorld` maintains this as a member buffer (clear-and-refill, no steady-state
allocation) and exposes it via `const RenderWorldFrameDelta &LastDelta()`.
`ApplyPendingCommands()` keeps its signature so existing callers are unaffected.

Change detection is viable because command presence already correlates with real
change: `RenderSourceRegistry::ResolveRecords` is change-gated and gameplay's
`FlushSourceUpdate` early-returns unless a source is dirty. Two caveats the delta
must absorb rather than assume away: a record flipping from `Pending` to `Ready`
can emit an update whose desc is identical to what is stored (so compare, do not
trust), and a retire/recreate cycle can re-issue the *same logical object* with a
new handle.

**Why the epoch is not optional.** `RenderWorld::Clear()` does `handles_ = {}`,
resetting `generations_` to empty rather than bumping it. A handle captured
before the clear (`{0,0}`) becomes valid *again* after a clear plus one create,
and compares and hashes equal while pointing at a different object.
`world_epoch` is bumped in `Clear()` and stored by the index; a mismatch forces a
full rebuild and makes the ABA case detectable instead of silent.

The policy:

| condition | action | cost |
|---|---|---|
| `world_epoch` changed | **Rebuild** | O(n log n) |
| `created` or `destroyed` non-empty | **Rebuild** | O(n log n) — `LinearBVH` has no incremental insert/remove |
| `bounds_changed` empty | **Unchanged** | zero — the tree is reused as-is |
| `bounds_changed` <= 25% of n | **Refit** | O(n) sweep, topology preserved |
| `bounds_changed` > 25% of n | **Rebuild** | refit degrades SAH quality; many movers favour a fresh balanced build |
| strategy is `Flat` | nothing to build | the slot array is the structure |

Note the honest consequence: **`Refit` is O(n), the same order as the flat scan**,
so a frame that refits gains nothing over not having a tree. The tree only pays
on frames that are *unchanged*.

### Query API and the core addition it needs

`LinearBVH` today has `Build`, `Refit`, `IntersectRay`, `IntersectRayAll`, and
`QueryOverlap(const AABB&)`. A frustum is not an AABB, so the `Bvh` strategy needs
one of:

- **recommended** — re-add the predicate traversal to `LinearBVH`,
  `QueryFiltered(Accept, out)`, and have `RenderSpatialIndex` pass a lambda
  capturing `render::Frustum`. This keeps `spatial` free of render policy, gives
  exact per-plane pruning, and remains renderer-agnostic. It was added and removed
  on 2026-09-14 precisely because it had no consumer; this design is that
  consumer.
- *rejected* — `QueryOverlap(frustumWorldAABB)`: no core change, but the frustum's
  AABB includes everything behind the camera, collapsing the pruning the tree
  exists for.

Also recommended: an optional
`LinearBVHQueryStats { uint32_t nodes_visited; uint32_t primitives_tested; }`
out-parameter, because "visited nodes" and "pruning ratio" are not derivable from
outside the traversal. It is the only way to obtain the instrumentation the
objective asks for.

### Granularity decision

**Phase 1 does not change granularity.** The index keys on renderables, but the
section-packet pipeline is untouched, so behaviour is byte-identical and the
abstraction can land and be tested in isolation.

Evaluating "query renderables first, then expand only survivors": it is the right
end state, but it is not a free win, for a reason the code states outright. Shadow
casters must come from the full snapshot, so the full expansion remains necessary
whenever any shadow scheduler runs. Applying the coarse query to the G-buffer
alone would *add* a second expansion, not remove one, unless the shared full
expansion is first made lazy per consumer.

The specific breakages if the camera frustum were applied to the shared list are
worth recording, because each is silent rather than loud:

- the directional fit shrinks to on-camera casters, so an off-camera occluder
  stops shadowing a visible receiver, and with zero visible casters the fit falls
  back to a fixed camera-local box (`:905-915`);
- the directional stamp becomes camera-dependent, so its cache misses on every
  camera move, undoing Stage 6.1;
- spot and point lights whose only casters are off-camera lose their shadow map
  **entirely** — the `has_caster` gate returns `nullopt` and the lighting pass
  skips the binding (`:693-704`) — rather than degrading partially;
- partially-pruned lists produce missing shadows, not a clean failure.

So the ordering is: make the shared expansion lazy (its own change, measurable on
its own), *then* let the index serve per-pass region queries. Reversing that
ordering produces a regression that looks like a spatial-index problem but is not.

One more reason phase 3 is not bit-exact: section bounds are derived as
`TransformAABB(section.local_bounds, proxy.world_transform)` with a fallback to
`proxy.world_bounds` (`scene_visibility.cpp:87-92`), and section bounds are
computed with a quantization epsilon on the native import path
(`native_model.cpp:244-250`). Section within proxy holds *in practice* but is not
guaranteed bit-exactly, so rejecting at proxy level and expanding only survivors
introduces a new conservative-error surface the current per-section filter does
not have.

### Visibility vs rendering policy

`RenderSpatialIndex` answers spatial questions only. It does not read
`RenderableFlags.opaque`, decide draw class, choose materials or pipelines,
schedule passes, or order draws.

`RenderableFlags.visible` is applied as a **query-time filter** rather than by
excluding invisible renderables from the index, so toggling visibility never
forces a topology rebuild. This is load-bearing, not a nicety: `BuildSections`
enforces the flag (`scene_visibility.cpp:59-65`) but the draw-list builder does
not re-check it, so an index returning an invisible proxy makes invisible
geometry draw in the G-buffer.

## Ownership and lifetime

`RenderSpatialIndex` is **derived scene state**, exactly like `LightWorld`, and
belongs beside `RenderWorld` in `RenderSceneCoordinator`
(`render_scene_coordinator.h:70-72`):

- **Updated** at `PrepareFrame`, immediately after
  `render_world_.ApplyPendingCommands()` (line 40), before the frame input is
  returned — the single point where the proxy set has just become immutable for
  the frame, the same place every other inbox is drained.
- **Published** by adding `const RenderSpatialIndex &spatial_index;` to
  `RenderSceneFrameInput`, which already carries `const RenderWorld &` the same
  way. `DeferredRenderer` already borrows `const RenderWorld *` for the frame and
  nulls it at frame end; the index follows that pattern and owns nothing.
- **Reset** in `RenderSceneCoordinator::Clear()` immediately after
  `render_world_.Clear()` (line 81). Mandatory, not hygiene: this is the epoch
  boundary from the update lifecycle. Note `Clear()` also resets
  `material_asset_resolver_` and nulls `resource_resolver_` (`:84-91`), so the
  index must be a default-constructible value that drops any resolver pointer.

The index owns only its slots, the optional tree, and its stats. It holds **no
reference to `RenderWorld`** between calls and no `MeshProxy` copies.

## Threading

Single-threaded on the render thread. `PrepareFrame` runs there; producers enqueue
under `RenderWorld`'s mutex and the delta is read after the lock is released, so
the index never takes `RenderWorld`'s mutex. Const queries are safe to call
concurrently on a built index, matching `LinearBVH`.

## How this changes the current render pipeline

Phase 1, concretely: **nothing observable changes.**

- `Snapshot()` still runs; the index is fed from the same applied state.
- `BuildSectionCandidates` / `FilterVisibleSections` keep running unchanged.
- `RecordGBufferPass` is untouched.
- The only added work is the index's own upkeep: gathering slot bounds (O(n) on
  topology change only) and, under `Bvh`, a build or refit.

For `Flat`, upkeep is the slot gather on change frames and nothing else. That is
the configuration that ships by default.

Phase 2 wires `QueryFrustum` into `BuildVisibleSectionsProfiled` as a *replacement
for the linear filter*, gated on measurement.

## Profiling and debugging plan

There is **no recording API** — `RenderProfileSnapshot` is a flat struct of public
fields accumulated inline with `steady_clock` pairs and `++`
(`render_profile.h:86-137`). This is additive but touches several call sites by
hand.

New fields on `RenderProfileSnapshot` (scalars only — the snapshot is copied by
value three times per frame): `spatial_primitive_count`, `spatial_visible_count`,
`spatial_cpu_build_ms`, `spatial_cpu_refit_ms`, `spatial_cpu_query_ms`,
`spatial_nodes_visited`, `spatial_primitives_tested`, `spatial_moved_count`,
`spatial_query_calls`, `spatial_strategy`.

Surfaced as flat `spatial.*` keys and, for percentiles, one new
`RenderProfileCpuSubphase::SpatialIndex` entry. **Three places must change in
lockstep and there is no compile-time check on the mapping:** the enum, the
positional array literal in `RenderProfileWindow::Observe`
(`render_profile.cpp:56-65`), and `CpuSubphaseName`
(`performance_stats_command_provider.cpp:54-78`) — plus bumping
`static_assert(Count == 8)`. Miss the middle one and percentiles silently attach
to the wrong name.

Flat counters go in `AddCpuStats`; per-pass metrics in `AddGpuStats`. A spatial
metric is not a pass and must not be added to `RenderProfilePass` /
`FixedRenderPassId`, which are manually parallel enums.

Derived and worth reporting because they are the actual decision inputs:
`pruning_ratio = 1 - primitives_tested / primitive_count` and
`survival_ratio = visible_count / primitive_count`.

Accumulation must sit **after** `RecordFrame`'s early return
(`deferred_renderer.cpp:597-601`), which follows `profile_ = {}` at line 590 and
would otherwise zero it.

Debug surface: `SpatialStrategy` should be settable at runtime through a command
so a capture run can compare `Flat` and `Bvh` on the same fixture without a
rebuild. That is also how the A/B evidence gets produced.

## Switching policy (`Auto`, phase 2)

Deliberately simple and conservative, with hysteresis to prevent thrashing:

```text
promote Flat -> Bvh   when primitive_count >= 4096 AND last survival_ratio <= 0.15
demote  Bvh -> Flat   when primitive_count <= 1024 OR  last survival_ratio >= 0.30
otherwise             keep the current strategy
```

The bands are separated by 4x on count and 2x on survival so a scene hovering at
a boundary cannot oscillate. Both thresholds derive from the 2026-09-14
measurements rather than being guessed: traversal only beats the scan below
roughly 10% survival, and the build only amortises at high counts with a stable
tree.

`Auto` may additionally demote when measured `build_or_refit + query >
flat_query` over a sampling window — a direct cost comparison, which is the most
honest rule and the one to prefer once the metrics are trusted.

Phase 3 may add movement rate and queries-per-frame. **Do not** add them in phase
2; the two rules above are enough to keep `Auto` on `Flat` for every scene this
engine currently has, which is the correct outcome.

## Static vs dynamic content

**Recommendation: one `LinearBVH` with refits.** Not static-BVH + dynamic-flat,
and not static-BVH + dynamic-BVH, for phases 1 and 2.

Reasons, in order of weight:

1. There is no static/dynamic flag anywhere. `MeshProxyDesc` and
   `RenderableFlags` carry no such field, and adding one is a cross-module change
   (gameplay source desc -> `MeshProxyDesc` -> `MeshProxy`) for an unproven
   benefit.
2. The split only pays when the static set is large *and* the dynamic set is small
   *and* the frustum rejects most of the static set. None holds today.
3. The split is an internal strategy, not an interface change: it can be added
   later as `SpatialStrategy::Split` behind the same `RenderSpatialIndex` with no
   caller change — which is precisely what the abstraction is for.

The `Refit` path already gives dynamic content a correct, cheaper-than-rebuild
update; that is the "consider dynamic content" answer for this phase.

## Future extension

The seam must not preclude, and phase 1 does not implement: spatial grids, world
cells / world partition, GPU instance hierarchies, cluster hierarchies,
HZB-assisted culling, GPU-driven visibility. Two properties keep them reachable —
the strategy is an enum behind one class, and the query returns handles rather
than touching GPU state. A GPU-driven strategy would need the query to produce a
GPU-consumable buffer; that is a later decision and is not designed here.

## Implementation stages

**R2.A — change signal (no index).** Add `RenderWorldFrameDelta` + `WorldEpoch()`
to `RenderWorld`, populated inside `ApplyPendingCommands`. Tests: created /
destroyed / bounds-changed classification; unchanged frames produce an empty
delta; `Clear()` bumps the epoch. Lands independently and is measurable on its
own.

**R2.B — the seam, `Flat` only.** `RenderSpatialIndex` with the slot table and
`Flat`; wired into `RenderSceneCoordinator` and `RenderSceneFrameInput`; reset in
`Clear()`. Behaviour must be byte-identical; equivalence tests against direct
iteration.

**R2.C — instrumentation.** Profile fields, `stats` keys, subphase entry, and a
runtime strategy override. Landed before `Bvh` so the baseline exists first.

**R2.D — `Bvh` strategy.** Re-add `QueryFiltered` (+ query stats) to `LinearBVH`;
implement `Bvh` behind the seam; the Build / Refit / Rebuild / unchanged policy.
Tests prove `Flat` and `Bvh` return identical handle sets across topology
changes, moves, clears, and malformed bounds.

**R2.E — phase 2 `Auto`.** Hysteresis policy, gated on R2.C data.

**R2.F — phase 3 (gated, likely deferred).** Make the shared section expansion
lazy per consumer, then let the index serve per-pass region queries. Requires its
own measurement of union-of-region coverage across all passes; if the union
covers the scene, the change is a regression and is not made.

Two constraints specific to this stage. The index would become the natural owner
of **section-level** boxes too — today recomputed every frame in `BuildSections`
— which is where the real cost sits, but which also makes the index's bounds
shadow-correctness-critical. And whatever replaces `Snapshot()` as the frame's
immutable view must stay immutable for the whole frame, because
`ScheduleDirectionalShadow` (`:918`) and `RecordDirectionalShadowPass` (`:1106`)
read the *same* cached list precisely so the light fit and the recording cannot
disagree; a mid-frame change must invalidate `frame_section_packets_ready_`.

## Acceptance criteria

- [ ] `RenderSpatialIndex` is the only renderer-facing spatial query;
      `RenderableHandle`, `MeshProxy`, materials, and `spatial::LinearBVH` do not
      appear in its callers.
- [ ] `spatial` gains no renderer type; `LinearBVH` is unchanged in that respect.
- [ ] `Flat` and `Bvh` return identical handle sets for identical world state,
      including after creates, destroys, moves, visibility toggles, and `Clear()`.
- [ ] An unchanged frame performs no build work.
- [ ] Topology change triggers a rebuild; a small bounds change triggers a refit;
      a large one triggers a rebuild.
- [ ] The ABA case is caught: a handle captured before `Clear()` never resolves to
      the new object.
- [ ] `stats` reports primitive count, visible count, build/refit/query time,
      visited nodes, tested primitives, moved count, and queries per frame.
- [ ] Default configuration is `Flat` and reproduces pre-change frame output.

## Rejected alternatives

- **Repeat stage 2 — build a tree in one call and discard it.** Measured 57-70x
  slower; rejected on evidence, not intuition.
- **`QueryOverlap` with the frustum's world AABB.** No core change, but the AABB
  covers everything behind the camera, collapsing pruning.
- **Section-packet-level index.** Packets are per-frame temporaries with no stable
  identity, so a persistent structure cannot key on them. Renderable level is the
  only stable choice.
- **Static/dynamic split now.** See above.
- **Reusing `ComputeDirectionalShadowStamp` as the dirty check.** It is
  anonymous-namespace-local, shadow-specific, whole-scene equality with no
  per-object attribution, and recomputed unconditionally even on a hit.
- **A virtual `ISpatialBackend` hierarchy.** A single concrete class with an enum
  matches the module's stated preference for concrete collaborators over a
  "speculative class-per-pass hierarchy" ([design.md](../design.md)).

## Fragilities in the current renderer this design must not inherit

1. **`Snapshot()` deep-copies every proxy — including its `section_materials`
   vector — and sorts, every frame, holding the mutex for the whole copy.** This
   is the only per-element heap allocation in the frame's bounds traffic; the
   section packets are deliberately allocation-free ~120-byte flat copies. The
   index does not remove the snapshot. Do not attribute its cost to the index,
   and measure it separately before blaming culling.
2. **The shared eager section expansion is billed twice and built for passes that
   reject everything** (`directional_shadow.sections = 0` yet 738 packets built).
   This — not the frustum test — is the lever, and it lives in shadow scheduling.
3. **`VisibleMeshSection` embeds a full `MeshProxy` copy**, so 738 packets means
   738 proxy copies per frame. The packet copy, not the plane test, dominates. It
   is allocation-free because `MakeSectionPacketProxy` leaves `section_materials`
   empty — a deliberate fix that must not be undone. (`issue-9.7.md:246-248`
   still describes the pre-fix behaviour and is stale on this point.)
4. **The shadow invariant**: casters come from the full snapshot, and
   `RecordDirectionalShadowPass` records all of them unconditionally.
5. **The directional stamp is order-sensitive.** Any index that feeds a
   stamp-hashed consumer must preserve `handle.id` order.
6. **`flags.visible` is enforced in `BuildSections` but not re-checked by the
   draw-list builder**, so an index returning an invisible proxy makes invisible
   geometry draw in the G-buffer.
7. **`RenderWorld::Clear()` resets generations**, creating the ABA hazard. The
   epoch is the mitigation; do not drop it.
8. **`RenderableHandle` generation is `uint16_t`** and wraps after 65536
   create/destroy cycles on one slot. A long-running session with heavy churn can
   alias. Out of scope here, but it weakens handle identity as a long-term key.
9. **`Render` has no precedent for owning a `spatial::` type.** This establishes
   it; keep the dependency one-directional (render -> spatial).
10. **No `operator<` on `Handle`**, so handle-keyed ordering must sort by
    `handle.id` as `Snapshot()` does.
11. **`std::hash<Handle>` shifts by 32 bits**, which is UB on a 32-bit `size_t`.
    Guarded by the current win64 build; note it if that ever changes.
12. **`draw_lists.alpha_blend` is built and never read** in `RecordGBufferPass`,
    so visibility work for blended sections is currently discarded. Not this
    design's problem, but do not measure its cost as if it were useful.

## Relationship to the recorded spatial-bvh reopen condition

`.spec/specs/spatial-bvh.md` already defines the precondition for revisiting BVH
in the renderer: *"a persistent, content-stamped tree shared across the G-buffer
filter and every per-light shadow filter in `DeferredRenderer`, keyed on the
proxy set rather than rebuilt per call."* This design matches that shape, and the
update lifecycle above supplies precisely the content stamp that sentence asks
for.

The burden of proof it sets is explicit and accepted here: the tree must be
justified against the **57-70x per-call build** numbers, not against the 29.5 us
G-buffer filter. That is why `Auto` defaults to `Flat` and why phase 1 claims no
speedup.

## Open questions

- Should phase 2's `Auto` land before a scene justifies it? The metrics may show
  it would only ever select `Flat`, in which case the policy is a switch that
  never flips and should be documented as such rather than tuned.
- The 25% refit threshold is a guess in the same sense the old BVH threshold was.
  It should be replaced by measurement before `Auto` trusts it.
- Whether `Snapshot()` should eventually be replaced by per-handle lookup for
  survivors — a larger change, and the only one that removes fragility 1.
- Whether the predicate query belongs on `LinearBVH` or should wait until R2.D is
  reached, so the core API grows only when its consumer is actually being written.
