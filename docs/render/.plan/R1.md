# R1 — RenderSystem Responsibility Split

Parent: [Render plans](../PLANS.md) · Roadmap: [Render TODO](../TODO.md) ·
Risk register: [Render risks](../risks.md)

## Status

R1.1 landed 2026-09-01. This document records a cleanup boundary; it does not
authorize a broad refactor or a render-graph migration.

## Local problem

`RenderSystem` is the correct Runtime-facing Render facade, but its current
implementation has accumulated most Render integration work in one class:

- `render_system.cpp` is about 2,400 lines and its header is about 290 lines;
- startup/bootstrap conversion, synchronous Asset loading, Resource processing,
  render-cache lookup, source draining, camera selection, shadow scheduling,
  pass-resource creation, pass recording, capture routing, resize, editor
  composition, and teardown all change the same class;
- `RenderPassSchedule` validates one declaration list while `BeginFrame()`
  independently calls `Record*Pass()` methods in a manually maintained order;
- pass-private pipelines, samplers, environment bindings, active shadow frames,
  and completion flags are stored directly on the facade and destroyed by one
  long manual shutdown sequence;
- initialization returns `void`, can return early after partial construction,
  and uses `backend_ != nullptr` as an incomplete lifecycle sentinel;
- no unit test constructs `RenderSystem` or proves its initialization rollback,
  actual pass execution order, resize boundary, or teardown order.

The problem is responsibility and lifetime coupling, not the raw line count.
Splitting text into files without moving ownership would not fix it.

## Concrete design question

How can `RenderSystem` remain the one Runtime-facing composition root and frame
facade while current renderer policy, render-resource ingestion, and pass-owned
GPU state become independently testable and lifecycle-safe—without adding a
general render graph or a second RHI abstraction?

## Target boundary

```text
RuntimeContext
    |
    v
RenderSystem                     thin facade + composition root
    |- RenderBackend             frame acquire/submit/present and GPU services
    |- FrameContext[]            frame-local allocations and bindings
    |- source registries/world   copied Gameplay values and Render snapshots
    |- RenderResourceIngestor    request budget, ready AssetIDs, render cache
    `- DeferredRenderer          renderer policy and pass-owned state
           |- FixedPassSequence  one declaration/execution source of truth
           |- frame targets
           |- shadow family
           |- G-buffer/lighting/tone-map/capture recording
           `- renderer-private pipelines, samplers, and environment bindings
```

Names other than `RenderSystem` are provisional; the ownership is not.

### `RenderSystem` remains responsible for

- owning and wiring the Render collaborators;
- exposing the existing narrow source, capture, target-view, and editor
  composition capabilities;
- enforcing explicit lifecycle state and the frame bracket;
- beginning/ending the backend frame and selected `FrameContext`;
- handing immutable scene/light/camera inputs to the selected renderer;
- shutting collaborators down in the reverse of successful initialization.

It must not contain shader-specific pass preparation, shadow projection math,
fullscreen pipeline handles, environment bindings, Asset path classification,
or individual draw recording.

### `DeferredRenderer` owns one renderer implementation

The current deferred-PBR path becomes a cohesive renderer object. It owns
`RendererFrameTargets`, the fixed pass sequence, shadow scheduling/recording,
G-buffer/deferred/tone-map/capture policy, and every pipeline/sampler/binding
used only by those passes. It borrows common backend recording/resource
services only for its initialized lifetime.

Do not create one polymorphic class per pass. The first extraction may keep
private pass methods on `DeferredRenderer`; separation is earned by distinct
state, lifetime, or reuse—not method count.

### One fixed-pass source of truth

The explicit schedule remains appropriate. Each fixed stage must pair its
logical resource declaration with the recording operation executed for that
stage. Validation and execution consume the same ordered entries, including an
explicit rule for conditional capture and the external terminal editor pass.

This is not dependency sorting, transient aliasing, automatic barriers, pass
culling, or a render graph. It closes the current possibility that declarations
remain valid while manual `BeginFrame()` calls drift.

### Render-resource ingestion

A focused ingestor owns queue budgeting, request state, payload pinning, and
the request-to-render-cache transition. The durable target is a queue item with
an already loaded, validated AssetID plus type/status—not an arbitrary path that
causes `RenderSystem` to call `AssetManager::LoadSync()` during `BeginFrame()`.

`RenderResourceResolver`, `ResourcePipeline`, `MaterialSystem`, and
`MaterialAssetResolver` retain their current ownership contracts. The cleanup
must not merge them into a generic resource manager. GP7 level-asset migration
should remove bootstrap scene/path interpretation rather than moving that
special case into the new ingestor.

### Explicit lifecycle

Use a small lifecycle state such as `Uninitialized`, `Ready`, `FrameActive`,
and `ShutDown`. Initialization reports success/failure with a diagnostic and is
transactional: failure rolls back every successfully initialized collaborator.
`BeginFrame`, editor composition, `EndFrame`, resize, and shutdown reject
invalid states deterministically. Shutdown stays idempotent.

Avoid a new service locator or a large `RenderContext` bag. Collaborators take
the narrow references required for their full lifetime, and frame functions
receive a small immutable frame input plus the active `FrameContext`/recorder.

## Migration stages

### R1.1 — characterization and lifecycle contract ✅ landed 2026-09-01

- Add an injectable existing-`RenderBackend` factory seam for tests; do not add
  another device/RHI interface.
- Record the current frame sequence, conditional-capture behavior, resize
  boundary, editor terminal pass, and teardown ordering in orchestration tests.
- Make initialization transactional and introduce explicit lifecycle state.
- Preserve current Vulkan/OpenGL images before moving behavior.

Landed shape: `RenderSystemInitResult` reports a diagnostic, initialization
rolls back all partially created collaborators, and the public frame bracket is
state-checked. `RenderSystemTest` uses a backend double through the existing
RHI contract to characterize target/pass order, conditional readback, resize
safe-point waiting, editor terminal composition, and teardown ordering.

### R1.2 — deferred renderer and pass-owned state

- Move targets, pass-private pipelines/samplers/bindings, environment state,
  shadow frame state, scheduling, and `Record*Pass`/`Prepare*Resources` logic
  into `DeferredRenderer`.
- Keep source registries, `RenderWorld`, `LightWorld`, and camera selection in
  `RenderSystem` for this stage; do not add a wrapper with no second consumer.
- Make renderer cleanup own all of its handle retirement before backend
  teardown.

### R1.3 — fixed sequence declaration/execution unification

- Replace the declaration-only `RenderPassSchedule` use with one fixed ordered
  sequence whose entries carry both resource uses and the operation invoked.
- Test missing, duplicate, out-of-order, conditional, and terminal stages.
- Keep graph algorithms and automatic resource lifetime out of scope.

### R1.4 — resource ingestion boundary and bootstrap removal

- Extract request budgeting/cache transition from the facade.
- Change the producer/consumer contract so disk loading and path/type validation
  finish under Asset ownership before Render consumes the request.
- Coordinate with [GP7](../../../.spec/specs/gameplay-level-asset.md) to remove
  `BootstrapSceneInfo`, bootstrap source transfer, and environment path matching
  from Render rather than preserving them in a new class.

### R1.5 — facade hardening and evidence

- Reduce `RenderSystem::BeginFrame()` to high-level scene drain, backend/frame
  bracket, renderer invocation, and state transition.
- Review public accessors. Keep capability-oriented source/capture/target seams;
  document or replace the raw `GraphicsContext` editor escape hatch separately
  rather than widening it.
- Run focused orchestration/Render tests, full Debug build and CTest, then
  Vulkan/OpenGL smoke and inspected captures. Record the migration in a journal.

## Invariants

- Runtime continues to own exactly one `RenderSystem` and destroys Gameplay
  sources before Render.
- Render owns renderer policy, scene snapshots, materials, pass order, and
  logical target choice; Graphics owns GPU resources, synchronization, native
  translation, and safe destruction.
- Asset owns identity, loading, and CPU asset lifetime. Resource processing
  creates CPU render artifacts but owns no GPU object.
- Common Render/Graphics contracts expose no Vulkan/OpenGL implementation type.
- The same `RenderWorld`, light snapshot, camera value, material semantics, and
  fixed pass order drive Vulkan and OpenGL.
- No extraction may change visual output, shader ABI, target formats, shadow
  budgets, or source-token behavior without a separate feature decision.

## Rejected alternatives

- **Build a render graph first:** rejected because the immediate defect is
  ownership and duplicated fixed-order truth, not missing graph algorithms.
- **One class per pass immediately:** rejected because it creates interfaces
  before pass state/lifetime demonstrates the boundary.
- **Move everything into `RenderScene`:** rejected because resource ingestion,
  backend lifecycle, and renderer policy have different owners and lifetimes.
- **Keep `RenderSystem` large but split its `.cpp`:** rejected because file
  layout alone does not change ownership or testability.
- **A universal `RenderContext` parameter bag:** rejected because it hides
  dependencies and recreates the god object as a struct.
- **Move renderer policy into Graphics:** rejected because Graphics executes
  API-neutral descriptions; it does not choose scene, visibility, material,
  lighting, shadow, or pass policy.

## Reference comparison

- [O3DE `RPISystem`](https://github.com/o3de/o3de/blob/development/Gems/Atom/RPI/Code/Include/Atom/RPI.Public/RPISystem.h)
  is a composition root for RHI and focused material/model/shader/pass systems;
  [O3DE `Scene`](https://github.com/o3de/o3de/blob/development/Gems/Atom/RPI/Code/Include/Atom/RPI.Public/Scene.h)
  owns render pipelines, while
  [`RenderPipeline`](https://github.com/o3de/o3de/blob/development/Gems/Atom/RPI/Code/Include/Atom/RPI.Public/RenderPipeline.h)
  owns its pass tree and views. KimPeanut adopts the separation between system,
  scene data, and renderer/pass policy, but not Atom's feature processors, job
  system, asset-authored pass trees, or scale.
- [Filament `Renderer`](https://github.com/google/filament/blob/main/filament/include/filament/Renderer.h)
  presents a narrow `beginFrame`/`render`/`endFrame` contract, while its
  [implementation](https://github.com/google/filament/blob/main/filament/src/details/Renderer.h)
  uses focused render-pass command machinery and borrows broader resource
  ownership from `Engine`. KimPeanut adopts a narrow frame-facing facade and
  renderer-owned helpers, but not Filament's threading or feature breadth.
- [Godot `RendererSceneRender`](https://github.com/godotengine/godot/blob/master/servers/rendering/renderer_scene_render.h)
  shows the cost of a very broad renderer interface: `render_scene` requires a
  large scene/light/environment/shadow parameter surface. That breadth matches
  Godot's mature renderer variants, but would merely replace KimPeanut's god
  object with a god interface. R1 therefore uses a small immutable frame input
  and existing focused services instead.
- The existing [gkNextEngine study](../../graphics/gknext_reference.md) already
  warns that `RenderSystem` must not become owner of every runtime concern and
  recommends separating renderer policy from device execution. R1 applies
  that conclusion to the current live call path.

## Acceptance criteria

- [ ] `RenderSystem` remains the sole Runtime-facing facade but has no
  pass-specific pipeline/sampler/environment/shadow-frame members and no
  `Record*Pass` or `Prepare*PassResources` methods.
- [ ] The declared fixed pass sequence is the sequence actually executed; a
  test fails if declaration and invocation order differ.
- [ ] Initialization failure rolls back to a valid non-ready state; frame and
  shutdown operations are state-checked and shutdown is idempotent.
- [ ] Render no longer calls `AssetManager::LoadSync()` or classifies bootstrap
  Asset paths during the frame loop.
- [ ] Pass-owned GPU handles have one collaborator owner and are retired before
  backend teardown.
- [ ] Direct orchestration tests cover success, partial-init failure, normal
  frame, conditional capture, resize, editor terminal pass, and teardown.
- [ ] Existing focused tests, full Debug build/CTest, Vulkan/OpenGL smoke, and
  visually inspected captures pass without output or ABI regression.

## Validation

This cleanup changes Render public/private headers, lifecycle, resource
ingestion, pass execution, and GPU ownership. Follow validation-matrix Levels
2–4: targeted unit/contract tests after each stage, then sequential full Debug
build, complete CTest, both `GraphicsSmoke` backends, runtime capture inspection,
resize, and teardown validation. Compilation alone is not completion.

## Remaining uncertainty

- The resource-ingestion queue producer may need to move before GP7 or as part
  of it; preserve one owner for that migration rather than building two queues.
- GPU-handle wrappers may become useful after renderer extraction, but R1 does
  not assume a generic RAII handle until destruction dependencies are explicit.
- Multiple renderer implementations are not a current requirement. The
  `DeferredRenderer` boundary is justified by present ownership and testability,
  not speculative renderer plugins.
