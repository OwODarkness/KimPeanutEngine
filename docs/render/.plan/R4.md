# R4 — Ray-Tracing Foundation and Render-Graph Integration

- Parent module: [Render plans](../PLANS.md)
- Parent roadmap: [Render TODO](../TODO.md)
- Render-graph architecture: [Render Graph plans](../render_graph/PLANS.md)
- Render-graph roadmap: [Render Graph TODO](../render_graph/TODO.md)

- Status: R4.0 complete (2026-09-19); R4.1 is the next gate

## Objective

Add the smallest end-to-end ray-tracing path justified by one named rendering
consumer while preserving the Render/Graphics ownership split. R4 extends the
completed raster graph rather than reopening R3: Render declares logical ray
work and dependencies; Graphics owns acceleration structures, native pipelines,
scratch storage, synchronization, capability discovery, and safe retirement.

## Current state

R3 is complete for the existing raster frame, but the graph and common Graphics
contract do not yet provide the contracts required by ray tracing:

- selected first consumer: ray-query hard-shadow visibility for the directional
  light contribution, with the existing directional shadow-map path as the
  fallback;
- no common acceleration-structure handle, capability, pipeline, binding, build,
  or ray-dispatch command;
- no storage-image, acceleration-structure, or ray-stage usage vocabulary;
- logical graph buffers do not resolve to physical buffers or execute state
  requirements;
- graph textures are resolved through the raster-only `RenderPassResource`
  ordinal convention rather than an explicit frame binding table;
- a write creates a new logical version but does not create a dependency on the
  producer of the previous version, which is insufficient for load/update and
  read-modify-write flows;
- transition failures are not propagated to pass/frame failure;
- declared callback uses remain authored rather than enforced;
- the current smoke executable can return success while Vulkan validation emits
  image-layout errors, so validation-clean runtime evidence is not yet a gate.

The in-progress attachment-scope work is part of the raster baseline. It must be
closed and validated before R4 changes synchronization vocabulary again.

## Scope and non-goals

R4 includes:

- one explicitly named first RT consumer and its raster/OpenGL fallback;
- Vulkan capability discovery and common API-neutral feature reporting;
- Graphics-owned BLAS/TLAS resources and lifetime-safe retirement;
- the minimum shader, pipeline, resource-binding, build, and dispatch commands
  required by that consumer;
- graph resource/usage/stage extensions justified by the selected path;
- explicit per-frame graph-resource-to-physical-resource bindings;
- focused compiler, contract, backend, and runtime validation.

R4 does not include a general-purpose RT framework, denoiser, path tracer,
multi-queue scheduler, memory aliasing system, or OpenGL emulation of native
acceleration structures. Do not add callable/miss/hit-group flexibility that the
selected consumer does not use.

## Ownership and data flow

```text
RenderWorld immutable geometry/instance snapshot
        ↓ Render policy
BLAS/TLAS build-or-update declarations + first RT consumer
        ↓ compiled Render Graph
portable buffer / AS / storage-output requirements
        ↓ common Graphics commands
Vulkan AS resources, scratch memory, barriers, pipelines, dispatch, retirement
        ↓
RT output → existing raster composite / tone map / capture
```

- Gameplay and Asset never receive Graphics or graph handles.
- Render owns participation policy, instance selection, pass declarations, and
  the fallback decision.
- Graphics owns physical AS objects, device addresses, scratch buffers, native
  flags, queues, fences, and destruction.
- Graph handles remain graph/frame scoped and never become persistent material
  or scene identity.
- OpenGL reports the feature unavailable and follows the authored raster
  fallback; it does not manufacture placeholder AS objects.

## Stage sequence

### R4.0 — consumer and clean-baseline gate

- Selected consumer: ray-query hard-shadow visibility for the directional-light
  contribution. The consumer reads the frame's imported TLAS and the
  directional-light ray origin/direction policy, writes a one-bit visibility
  result used by deferred lighting, and updates once per frame when the camera
  or participating instance snapshot changes. It is not a full RT pipeline,
  reflection, or denoiser.
- The fallback is the existing directional shadow-map sampling path. OpenGL
  always selects it; Vulkan selects it when the complete ray-query capability
  contract is unavailable. The fallback remains graph-authored and visible in
  the same deferred-lighting output.
- Finish or separate the current attachment-scope work.
- Runtime smoke now fails after orderly Vulkan cleanup when the debug messenger
  observed a validation error, and preserves the diagnostic through teardown.
- The Vulkan prerequisite contract is `VK_KHR_acceleration_structure`,
  `VK_KHR_ray_query`, `VK_KHR_deferred_host_operations`, and
  `VK_KHR_buffer_device_address`, with `rayQuery` and
  `accelerationStructure` features enabled together. The minimum hardware
  contract is a Vulkan 1.2-capable device exposing all four extensions and
  those features; otherwise the authored shadow-map fallback is selected.
- The current attachment-scope work is separate from the RT contract and is
  validated as part of the raster baseline.
- The cross-module execution spec and scoped R4.0 review are recorded before
  R4.1 interface work.

### R4.1 — graph correctness prerequisites

- Make writes that preserve or update prior contents depend on the preceding
  logical version's producer; keep discard/clear writes explicit where no such
  dependency is required.
- Propagate failed state requirements and unresolved physical bindings to
  required-pass/frame failure.
- Replace ordinal `RenderPassResource` resolution with an explicit frame-local
  binding table for every imported and transient graph resource.
- Execute buffer requirements rather than dropping non-texture transition
  intents.
- Add focused tests for write-after-write, update/read-modify-write, missing
  bindings, buffer hazards, and failed transitions.

### R4.2 — common Graphics RT contract

- Add effective capability reporting only when both the backend and the common
  contract support the complete selected path.
- Add opaque generational AS and RT-pipeline handles with explicit ownership.
- Add the minimum geometry/instance descriptors, build/update commands, resource
  bindings, storage output, and dispatch operation needed by the consumer.
- Keep Vulkan structs, device addresses, build flags, and shader-group handles
  below the common contract.
- Define submission-safe scratch reuse and BLAS/TLAS retirement before exposing
  resource creation to Render.

### R4.3 — graph RT vocabulary and imported-TLAS slice

- Add an acceleration-structure graph resource kind and only the portable
  usages/stages exercised by the consumer: AS build input/output, AS read,
  storage read/write, and the selected shader stage.
- Bind a Graphics-owned TLAS into one frame plan and declare the RT consumer's
  read/output hazards through the graph.
- Initially permit BLAS/TLAS construction outside the graph at a documented
  Graphics ownership boundary. This proves the consumer and imported-state
  contract before graph-scheduled builds expand the surface.
- Preserve explicit capability/fallback variants rather than compiling a pass
  that the active backend cannot execute.

### R4.4 — graph-scheduled AS build/update

- Move BLAS/TLAS build or update work into graph passes only after the imported
  TLAS slice is correct and measured.
- Declare geometry, instance, scratch, AS, RT output, and composite dependencies
  without native state in Render.
- Rebuild, refit, reuse, and retirement decisions must be driven by stable
  geometry/instance revisions, not by unconditional per-frame rebuilding.
- Keep one graphics queue unless a measurement separately unlocks async compute.

### R4.5 — integration and evidence

- Integrate the selected output into the existing composite/tone-map/capture
  path without duplicating pass order outside the graph.
- Validate static geometry, moving instances, resize, feature-unavailable
  fallback, failed build/dispatch, capture, orderly close, and shutdown.
- Report AS counts, build/update/dispatch CPU and GPU time, scratch/AS memory,
  cache hits, and fallback state without crediting the graph for unrelated
  performance changes.

## Acceptance criteria

- [x] R4.0 names one first consumer and its Vulkan/OpenGL behavior before API
  design or implementation begins.
- [x] The selected consumer has a cross-module execution spec and reviewed
  interface/ownership boundary before common headers change.
- [x] The pre-RT raster baseline is validation-clean; a smoke run cannot report
  success while relevant Vulkan validation errors are present.
- [ ] Common Render/Graphics contracts expose no Vulkan/OpenGL implementation
  types.
- [ ] Unsupported backends select an explicit tested fallback before graph
  execution.
- [ ] Write/update lineage, physical resource bindings, buffer requirements, and
  failed transitions are deterministic and covered by CPU/contract tests.
- [ ] Graphics owns every BLAS, TLAS, scratch allocation, native pipeline, and
  retirement decision; Render owns only logical participation and scheduling.
- [ ] The first consumer works through a graph-imported TLAS before AS build
  scheduling is expanded.
- [ ] Graph-scheduled AS work, if added, declares all build/consume/output
  hazards and never relies on an implicit backend order.
- [ ] Vulkan validation is clean for build/update/dispatch, resize, capture, and
  shutdown; the selected raster/OpenGL fallback remains visually valid.
- [ ] Runtime and resource-lifetime completion is supported by captures,
  command reports, and orderly-close evidence rather than compilation alone.

## Validation plan

R4 changes common headers, Graphics ownership, Render scheduling, and backend
execution, so it requires validation level 4 plus runtime evidence:

```powershell
cmake --build build --config Debug --target RenderPassScheduleTest GraphicsContractTest GraphicsSmoke
ctest --test-dir build -C Debug -R "RenderGraph|RenderSubmission|Graphics" --output-on-failure
cmake --build build --config Debug
ctest --test-dir build -C Debug --output-on-failure
```

Run checked-in startup fixtures through the Runtime command endpoint on Vulkan
and OpenGL/fallback, capture the selected RT output and final SceneColor, inspect
Vulkan validation logs, and verify orderly close. Add a hardware-unavailable
contract test so CI does not require an RT-capable GPU to cover fallback policy.

## Risks and open decisions

- R4.0 fixes the first consumer as ray-query directional hard-shadow visibility
  with the existing directional shadow-map fallback. Capability discovery and
  shader/resource contracts remain open for the later RT implementation stage;
  they must not be smuggled into the graph API without a scoped review.
- Device-address-bearing geometry may require a new Graphics buffer role and
  immutable upload contract; do not expose raw addresses to Render.
- Dynamic geometry and skinned meshes can turn BLAS updates into the dominant
  cost. Exclude them from the first slice unless the consumer explicitly needs
  them.
- Descriptor lifetime and AS lifetime must be retired together after the last
  submitted user.
- Attachment, mip/layer, and AS state granularity must remain separate concepts;
  the in-progress attachment scope is not a substitute for buffer or AS ranges.
- Debug Vulkan performance is not representative while validation layers are
  enabled; use `RelWithDebInfo` for performance conclusions after correctness is
  established.
