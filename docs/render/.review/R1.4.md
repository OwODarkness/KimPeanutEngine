## Scope and baseline

This review covers the current uncommitted R1.4 implementation: Runtime-owned
startup preparation, the prepared Render asset catalog, built-in role
publication, Render consumer migration, removal of the old request/cache path,
focused tests, and the matching Render plans/spec/journal/module records.

Streaming, hot reload, eviction, background scheduling, and render-graph
compilation remain out of scope. R1.3 is treated as closed because its formal
review records all findings addressed and the required focused, full, smoke,
and capture evidence passing.

## Review round 1 — 2026-09-02

### F1 — the public catalog factory accepts unprepared shaders and unusable programs

- Priority: P2
- Location: `engine/runtime/render/prepared_render_asset_catalog.cpp:76-146`,
  `engine/test/unit/render/prepared_render_asset_catalog_test.cpp:24-39,67-75`
- Status: addressed

`PreparedRenderAssetCatalog::Create()` validates pointer/type agreement,
dependency presence, built-in AssetID types, and IBL shapes, but it does not
validate the readiness contract that makes the catalog safe to publish. The
build has no selected API, so the factory cannot reject a `Ready` shader whose
`ShaderData::api` is unknown or wrong, nor a Vulkan shader with empty byte code
or an OpenGL shader with empty source. It also does not prove that a built-in
`ShaderProgramResource` binds the required stages or that those bindings agree
with the record's dependency IDs.

The positive catalog test demonstrates the gap: it leaves every shader API and
artifact empty, creates an unbound program, assigns that same program to all
five program roles, and expects publication to succeed. Such a catalog cannot
construct the renderer's pipelines, so failure is deferred from the promised
all-or-nothing Runtime transaction into lazy Render use.

Carry the selected API in the build/catalog and validate every shader's status,
data, API, stage, and backend artifact, plus each program's required variant
and stage bindings against its dependency records. Alternatively, make the
factory private to a preparer path that proves and freezes those properties.
Add negative tests for wrong API, empty artifact, missing stage, and a binding
that disagrees with the dependency snapshot.

### F2 — a const catalog exposes mutable asset payloads

- Priority: P2
- Location: `engine/runtime/render/prepared_render_asset_catalog.h:48-50,79-89`
- Status: addressed

The catalog is held as `shared_ptr<const PreparedRenderAssetCatalog>`, but
`Get<T>() const` returns `shared_ptr<T>` and the payload variant itself stores
mutable resource pointers. Any Render consumer can therefore change shader
status/data, texture data, program bindings, or material contents after the
catalog has been validated and published. The catalog does not provide the
immutable, lock-free snapshot promised by the plan; its correctness continues
to depend on every reader voluntarily avoiding mutation.

Publish const payload ownership or immutable snapshot/view types, and ensure
consumer APIs cannot recover mutable access through the catalog. Add a compile-
time or focused contract test showing that lookup through a const catalog
cannot mutate a published resource.

### F3 — built-in role identity is duplicated and not checked against its ordinal

- Priority: P2
- Location: `engine/runtime/render/prepared_render_asset_catalog.cpp:9-26,113-126`,
  `engine/runtime/render_asset_preparer.cpp:55-66`
- Status: addressed

The closed requirement table stores each role redundantly while its array
ordinal is separately treated as the role during catalog validation. Runtime
publishes by `requirement.role`, but `Create()` validates by table index and
never checks that `requirement.role == static_cast<BuiltInRenderAsset>(index)`.
Swapping the role fields of two same-type program rows would therefore load and
publish each path under the wrong role while the catalog still validates. This
is the same declaration/identity drift class closed for fixed passes in R1.3.

Derive the role from the table ordinal or validate the ordinal/role bijection
mechanically. Add a focused invariant test so a future table edit cannot
silently exchange two program roles.

### F4 — the new Runtime preparation transaction has no direct tests

- Priority: P2
- Location: `engine/runtime/render_asset_preparer.cpp:28-294`,
  `engine/test/unit/runtime/runtime_startup_test.cpp`
- Status: addressed

The central R1.4 transaction recursively walks the level closure, loads the
seven built-ins, processes shaders for the selected API, prepares optional IBL,
and publishes only at the end, but no unit or contract test calls
`RenderAssetPreparer::Prepare()` or `RuntimeContext::PrepareRenderAssets()`.
The catalog tests bypass the transaction with a hand-built invalid catalog,
and the Runtime startup tests cover only finalization. Consequently, closure
traversal, API-specific preparation failures, built-in failures, environment
failure, and all-or-nothing publication are protected only by manual launch
evidence.

Introduce an injectable Asset/Resource preparation seam and cover successful
Vulkan/OpenGL publication plus failures for a missing dependency, failed
built-in, shader compile/API mismatch, and invalid environment. Verify each
failure publishes no catalog and prevents Render initialization.

### F5 — durable module records still describe the removed ownership path

- Priority: P2
- Location: `docs/render/render_module.md:66-121`,
  `docs/asset/asset_module.md:205-206`
- Status: addressed

The Render module document still says Render loads and processes shaders,
owns `ResourcePipeline`, and drains the removed async request queue. The Asset
module recommends that same removed queue for future streaming. These durable
records disagree with the current Runtime preparation and catalog-consumption
boundary. This review leaves R1.4 open in the roadmap because the spec's
required smoke/capture gate is still unchecked, the journal records that the
dual-backend smoke comparator exits nonzero, and the fixture captures were not
rerun.

Update the durable module documents to the Runtime preparation → immutable
catalog → Render consumption boundary, describe future streaming without the
deleted queue, and leave R1.4 open until the source findings and required
visual evidence are closed. Preserve the current failed smoke and skipped
capture evidence as factual journal history.

## Positive observations

- Production startup prepares the catalog before starting the Render thread and
  aborts initialization when preparation fails.
- Render no longer calls `LoadSync`, path helpers, `ProcessShader`,
  `ProcessEnvironmentIbl`, or the global `AssetManager`.
- The old request queue, request cache, request polling surface, and unused
  `AssetLoadRequest` type are removed instead of being retained without a
  producer.
- The selected-level dependency closure, all shader records, built-in roles,
  and optional environment IBL are assembled before catalog publication.
- Runtime retains catalog ownership until after Render cleanup, and no backend-
  specific types cross the common Render catalog contract.

## Review disposition

Round 2 closes the five source findings. The catalog now validates selected-API
readiness and program/dependency agreement, const lookup cannot recover mutable
payloads, built-in roles are checked against their ordinals, the preparer has an
injectable transaction seam with direct success/failure coverage, and durable
module records describe the Runtime → catalog → Render boundary. The required
fixture captures pass and were inspected. R1.4 remains open only for the
pre-existing strict GraphicsSmoke D5 silhouette comparator, which still exits
nonzero after both backends render; it is recorded as follow-up evidence rather
than a catalog/preparation failure.
