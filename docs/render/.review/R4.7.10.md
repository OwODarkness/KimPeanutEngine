# R4.7.10 — Static BLAS traversal policy

Date: 2026-09-27. Status: candidate evaluated and rejected on the measured
Sponza workload; broader acceptance checks remain open.

## Change under evaluation

`engine/runtime/graphics/backend/vulkan/vulkan_acceleration_structure_owner.cpp`
adds `VK_BUILD_ACCELERATION_STRUCTURE_PREFER_FAST_TRACE_BIT_KHR` only when
building a non-updatable bottom-level acceleration structure. The existing
build-info flags are also used for the size query, so sizing and construction
use the same policy. Updateable BLAS and TLAS flags are unchanged. No Render or
common Graphics contract, geometry, instance mapping, lifetime owner, or
compaction policy changed.

Vulkan defines this flag as a preference for trace performance over build time
([flag reference](https://docs.vulkan.org/refpages/latest/refpages/source/VkBuildAccelerationStructureFlagBitsKHR.html)).
That is a driver hint, not evidence of a gain on this GPU; BLAS compaction was
not attempted because no measured memory-pressure case was established.

  and the engine executable linked successfully. Tests were not run.

  comparison. Raw window: `save/diagnostics/r410-baseline-sponza-window-1.json`;
  GPU samples: `save/diagnostics/r410-baseline-sponza-gpu-1.csv`.
- A later baseline launch initialized, then failed GPU timestamp reads and
  command-buffer submission. The system log recorded NVIDIA `nvlddmkm` Event

  `save/logs/2026-09-27/KimPeanutEngineLog-2026.09.27-18.19.47.txt`.
  Sampling stopped at this device fault. The candidate was not launched.

## Acceptance still required

- The first local comparison collected three 120-warm-up/300-frame windows per
  variant at 1094x742, Vulkan Sponza, Beauty, 4 SPP/eight bounces, with all
  469,885,796 tracked texture bytes resident. The candidate was measured first,
  then the baseline; the user-edited light intensity of 1000 was preserved.

  | Variant | PT GPU p50 windows (ms) | PT p50 mean | PT p95 mean | Total GPU p50 windows (ms) | Total p50 mean | Total p95 mean |
  |---|---:|---:|---:|---:|---:|---:|
  | No preference | 27.749 / 27.746 / 27.771 | 27.755 | 30.541 | 32.430 / 32.431 / 32.478 | 32.446 | 35.454 |

  The policy was 5.2% slower for PT GPU p50 and 5.0% slower for total GPU
  p50; mean p95 regressed 8.8% and 7.7%, respectively. No AS-memory result was
  retained for the candidate, and clocks/temperature were not sampled during
  these windows. Treat this as strong rejection evidence for the current
  workload, not a cross-scene acceptance comparison.
- The `PREFER_FAST_TRACE` flag is removed from the working tree and the
  RelWithDebInfo no-preference build passes. Re-test only if another fixture or
  a corrected clock-controlled experiment gives a reason to revisit it.
- Candidate and baseline image equivalence, candidate AS storage/build time,
  Debug Vulkan validation, scene replacement, and Vulkan lifetime/retirement
  checks remain unverified.
- Check geometry grouping/AABB overlap before attempting a BLAS layout change.
  Consider static compaction only if measurements show meaningful memory
  pressure and include its build, replacement and retirement costs.

The earlier R4.7.3 static-BLAS fast-trace trial also stopped on an upload queue
device-loss error; its cause was not established. The current candidate flag
has since been removed from the working tree after the matched regression
measurements above; it is not accepted as a performance improvement. The listed
correctness, memory and cross-scene checks remain useful only if a future,
evidence-backed experiment revisits this hint.

## Independent source and evidence review — 2026-09-27

Scope: working tree against `54283a6`, especially Vulkan owner `BuildOne`,
Render BLAS creation and the existing failed-baseline artifacts.
Plan: [R4.7 GPU strategy](../.plan/R4.7-gpu.md#r4710--improve-traversal-only-when-measured).
At the time of this source review, no runtime retry had been made after the
recorded driver errors; the matched comparison below was performed later.

### Source assessment

At `engine/runtime/graphics/backend/vulkan/vulkan_acceleration_structure_owner.cpp:1104`,
the flag is selected only for bottom-level, non-updatable resources. The same
`build_info` goes to the size query at `:1120` and build command at `:1159`;
there is no sizing/build flag mismatch. Updateable BLAS and TLAS policy are
unchanged. Render creates its current BLAS with `allow_update=false` in
`engine/runtime/render/deferred_renderer.cpp:952`, so this candidate affects
the current scene's BLAS rather than being an unused code path.

The [Vulkan flag contract](https://docs.vulkan.org/refpages/latest/refpages/source/VkBuildAccelerationStructureFlagBitsKHR.html)
permits this preference; it does not guarantee faster traversal or unchanged
allocation/build cost. No new mapping, resource-lifetime or API defect was
demonstrated in the five-line policy change. AS grouping, scratch allocation,
synchronization and retirement are existing infrastructure, not redesigned here.

### F1 — P2, open: unmeasured policy is enabled in the working-tree default

Location: Vulkan owner `:1104–1107`. The candidate applies automatically to all
non-updatable BLAS, but has no candidate correctness/timing/memory/startup data.
Compilation does not establish a safe or beneficial default. Keep it explicitly
experimental and do not merge it as an accepted optimization until matched
candidate runs and lifetime checks pass; otherwise retain the proven policy.
Do not infer a candidate regression from a failure in the recorded baseline.

### F2 — P2, resolved in working tree: submission failure discarded VkResult

Location: `engine/runtime/graphics/backend/vulkan/vulkan_frame_context.cpp:86–89`.
The queue-submit branch compares its return value directly against success,
then logs only "Failed to submit commandbuffer". Both reviewed stage failures
therefore omit the Vulkan error code that distinguishes device loss from other
submission errors. NVIDIA Event 153 is supporting driver evidence, not a
replacement for that missing result or a faulting GPU-command report.

The working-tree fix stores the `vkQueueSubmit` result, logs its numeric value,
and includes it in the propagated exception. The RelWithDebInfo build passes.
No new launch was made, so runtime formatting and the cause of the earlier
18:19:47 failure remain unverified. That historical log confirms the timestamp
warning and submission error; post-cleanup zero AS counts cannot establish what
was built before failure. This fix improves later evidence but does not prove
that fast-trace caused the failure or resolve NVIDIA Event 153 causality.

### Acceptance and verdict

The first candidate comparison favors no preference across all three matched
windows, but it lacks in-window clock telemetry, candidate memory data and
image comparison. The known-good no-preference policy is restored. Do not keep
the candidate enabled by default. The runtime failure result logging fix is
still present in the working tree; its formatting and the cause of the earlier
NVIDIA Event 153 remain unverified. AABB overlap inspection, static compaction
and cross-scene comparisons remain outside the rejected hint experiment.
R4.7.10 is not complete; the specific `PREFER_FAST_TRACE` candidate is
rejected for this measured configuration.
