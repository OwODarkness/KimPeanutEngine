# R4.7.5 — Revision-driven CPU scene records and graph preparation

**Date: 2026-09-27. Status: implementation is in place; the stage acceptance matrix remains open.**

R4.7.5 targets two repeated CPU costs after R4.7.4 made GPU scene tables
persistent: reconstructing geometry/instance/material records every frame, and
preparing shadow maps that the selected graph may not read. This stage does not
change the shader table layout or Graphics ownership.

## Implementation

- `RenderWorld` advances a revision when queued proxy create/update/destroy
  commands change the published world, and when `Clear` changes its contents.
- `MaterialSystem` advances a revision for template/instance edits, resolver
  changes and resource-resolution transitions. This lets Render invalidate
  records when resolved material/texture bindings change.
- `DeferredRenderer::PrepareRayTracingScene` retains geometry descriptors,
  instance transforms and path-tracing material records while the world and
  material revisions and PT mode remain unchanged. Static frames skip geometry
  queries, per-section material reads, full-table packing and address-patch
  generation. Authored light values still use a small signature check and can
  independently dirty the GPU table.
- Any world or material revision conservatively rebuilds the whole CPU record
  table. This avoids stale indices after insertion/removal/reorder; per-range
  updates are not claimed.
- Shadow preparation is now selected after `GetFramePlan`. It runs when the
  compiled graph actually contains a directional, spot or point shadow pass.
  Raster and capture/debug plans keep their consumers. The Sponza runtime used
  the `capture` plan (the Editor World Normal viewer was active), so it did not
  exercise a graph with no shadow-map consumer.
- Runtime stats expose cumulative scene-record cache hit/miss counts.

Architecture impact: revision identity is added only at the RenderWorld and
MaterialSystem producers. Render remains the CPU-policy owner; Graphics remains
the GPU table/AS owner. No Vulkan/OpenGL type was added to common Render APIs.

## Evidence

Debug validation and runtime:

- `Debug` and `RelWithDebInfo` engine builds passed with
  `tools/kp.ps1 -Configuration <config> build KimPeanutEngine`.
- Debug Vulkan Cornell ran with PT active. Static snapshots reported 1,052
  scene-record cache hits and 2 misses, with zero table records packed/uploaded
  and 0 ms table-pack time. Reloading the level incremented misses from 2 to 3
  while PT recovered with the scene populated.
- In Sponza, moving actor `Sponza` from local X 0 to 0.01 advanced the cache
  miss count from 37 to 38. Restoring X to 0 advanced it to 39. Static frames
  then continued hitting the cache with zero packed/uploaded records.
- All four runtime logs from these checks were free of new `[Error]`, `VUID`,
  Vulkan validation or `VK_ERROR_DEVICE_LOST` entries.
- A 512-pixel `scene_color` Runtime capture visually matches the R4.7.4 Sponza
  reference. Files: `save/screenshots/validation/r475-sponza-relwithdebinfo.png`
  and `save/screenshots/validation/r474-sponza-relwithdebinfo.png`.

Three serial fully resident Sponza windows used Vulkan, RelWithDebInfo,
1094×619 mailbox output, active PT, 4 SPP/eight continuation bounces, and 120
warm-up plus 300 measured frames. Tracked texture residency was complete in
every window (469,885,796 resident bytes); the selected graph mode was `capture`.

| Window | PT GPU p50 / p95 (ms) | Total GPU p50 / p95 (ms) | CPU total p50 / p95 (ms) |
| --- | ---: | ---: | ---: |
| 1 | 24.568 / 26.019 | 28.610 / 30.245 | 28.258 / 30.340 |
| 2 | 24.596 / 26.869 | 28.658 / 31.030 | 28.332 / 31.643 |
| 3 | 24.083 / 26.375 | 28.463 / 30.838 | 28.178 / 30.841 |
| Median | 24.568 / 26.375 | 28.610 / 30.838 | 28.258 / 30.841 |

R4.7.4 medians were 25.173/27.664 ms PT GPU, 29.339/32.092 ms total GPU,
and 29.310/32.160 ms CPU total. The observed R4.7.5 medians are lower by
2.4%, 2.5% and 3.6% at p50 (4.7%, 3.9% and 4.1% at p95). Since GPU time also
moved and R4.7.5 changes only CPU extraction/graph preparation, these runs do
not isolate a causal CPU-cache speedup. Treat this as an encouraging candidate
comparison, not a closed performance gate. The old per-frame table-pack
snapshot was about 0.05 ms; R4.7.5 steady snapshots report zero packing.

Raw windows are saved under `save/diagnostics/r475-sponza-candidate-window*.json`.

## Remaining checks

Direct Runtime coverage is still needed for material parameter edits, texture
residency transitions, recovery after RT-off and a graph without capture or
debug-view consumers. RT-off startup did disable RT/PT and submit raster draws,
but its 512px capture is mostly black; raster visual acceptance remains open.
The timing comparison also does not prove an improvement beyond run variation.
R4.7.7 retains the repeatable performance and broader quality/lifecycle gates.
