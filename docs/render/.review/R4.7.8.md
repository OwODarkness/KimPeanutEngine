GPU query frame/sample freshness, total GPU p50/p95, optional backend GPU

## Successful GPU Trace — 2026-09-27

After GPU-counter access was enabled, Nsight Graphics 2026.3.1 exported a
Vulkan GPU Trace from the RelWithDebInfo Sponza launch. The captured run waited
12 seconds, then traced three frames with Ada Throughput Metrics, multi-pass
metrics and real-time shader profiling; GPU clocks were locked to base. The
report is `build/NsightGPUTrace/KimPeanutEngine_2026_09_27_21_41_24.ngfx-gputrace`.
Runtime stats from the same launch configuration separately confirmed active
Beauty path tracing, 4 SPP, eight continuation bounces, 1094x742 viewport and
complete 469,885,796-byte texture residency. The captured GPU trace itself
sampled ray-generation, closest-hit and internal RT shader stages.

Across the three captured frames, mean unit throughput was approximately 24.8%
SM, 34.3% RT Core, 40.8% L2 and 62.7% DRAM. DRAM reads averaged 61.3% of peak;
the L1 texture sector hit rate was 50.9%, with an 81.2% L2 sector hit rate.
Long-scoreboard stalls attributed to RT Core averaged 6.2% of peak and L1TEX
5.0%. Memory traffic is the strongest observed pressure, but DRAM is not fully
saturated; this does not establish a purely bandwidth-bound workload or prove
that AS policy, texture filtering or payload reduction will improve it. The
sample is only three frames, and does not provide reliable ray counts,
per-shader register/spill totals or per-pass counter attribution. The first
short startup trace reported zero RT-Core activity and is superseded by this
delayed, shader-profiled capture.

The R4.7.10 static-BLAS fast-trace candidate was later compared in three matched
resident Sponza windows per variant. It regressed PT GPU p50 by 5.2% and total
GPU p50 by 5.0%; the flag was removed and the no-preference RelWithDebInfo
build passes. Clock telemetry, candidate AS memory, image equivalence, Debug
validation and scene-lifetime checks remain open. See the
[R4.7.10 review](R4.7.10.md) for the evidence and limits.

### F1 — P2, open: default diagnostic demand adds a raster workload to PT

`engine/editor/ui/component/editor_debug_viewer_component.h:29` defaults to
World Normal. Its constructor at `editor_debug_viewer_component.cpp:80`
requests that view, and `editor_ui.cpp:741` creates the panel open by default.
Render converts the requested view in `deferred_renderer.cpp:1505`; the
`RasterDiagnostic` condition in `render_pass_declaration.cpp:37` therefore
keeps GBuffer alive even with PT active. The baseline's GBuffer GPU p50 is
about 4.43 ms, plus about 0.05 ms capture conversion. Raw PT does not consume
that GBuffer: its normal/depth guide is generated by raygen.

A temporary one-line default of Scene Color selected the `path_tracing`
graph; stats confirmed GBuffer and capture-view GPU times unavailable, with
PT still active. Total GPU p50 fell to 28.204 ms in the repeat windows.
The initial Scene Color-only windows averaged 28.955 ms, so do not claim the
entire isolated GBuffer duration always transfers directly to total savings.
World Normal remains a legitimate requested diagnostic; the proposed fix is
explicit demand and cancellation when hidden, rather than suppressing it.
There is no hide/destruction cancellation in this component's current code.

### F2 — resolved as triage: textures matter, but the simple ablation overstates attribution

`no-textures` skips base-color and metallic/roughness samples. It changes
albedo, metallic, roughness, BSDF direction selection, throughput and roulette,
so its roughly halved PT duration is not a texture-only cost or a usable
optimization.

The controlled pair sets transport albedo/metallic/roughness to the same
authored material factors in both variants. The fetch variant consumes sampled
values through a small additive emissive contribution, keeping the reads live
without feeding them into BSDF sampling or roulette. The no-fetch variant
uses the same expression with material constants. Normal, geometry, RNG,
visibility and continuation rules remain shared. This isolates a measurable
material-fetch/UV-work effect in that simplified transport workload:
16.021 → 13.307 ms, a 2.714 ms (16.94%) PT p50 difference. Compilation/live-state
changes are included in this delta; it is not pure DRAM bandwidth and is not
a prediction for full Beauty. No texture filtering/compression redesign is
accepted from this diagnostic. In particular, the failed R4.7.12 LOD candidate
is not revived by this result.

### F3 — resolved as candidate selection: simple live-state changes did not win

The exported frame table additionally contains compute-category warp-launch
register-allocation stalls averaging 17.615% of peak and compute-category
active warp occupancy averaging 24.076% of peak. These are aggregate counters,
not per-shader register counts, spill bytes, PT-only occupancy or proof that
payload size is the dominant limiter. The regimes export has a header and no
per-pass data rows. See [NVIDIA's metric interpretation](https://docs.nvidia.com/nsight-graphics/UserGuide/gpu-trace-system-architecture.html).

`compact-beauty` removes cone fields and aliases mutually exclusive hit
albedo/miss radiance storage. This reduces source payload fields by five
floats, not a measured register count. Its PT median improvement was only
0.35%, total median 0.14%, while PT p95 increased 7.05%: do not retain it.
`specialized-beauty` additionally fixes the probe mode at compile time and
regressed PT p50 3.30%. `no-primary-retention` trades a retained primary record
for re-tracing that hit in each continuation sample and regressed 8.60%.
Neither experiment justifies a production rewrite. No compact-hit/material
queue or wavefront implementation was tested.

### F4 — P2, open: measured direction has remaining correctness/quality gates

Inline ray-query visibility reduces total p50 from the same-session repeat
Beauty's 28.204 to 26.250 ms (6.93%), with four SPP/eight bounces. Against the
initial default diagnostic-active baseline, the measured Scene Color-only
query configuration is 19.59% lower total GPU p50. This supports on-demand
diagnostics plus the existing opt-in visibility strategy; it does not establish
60 FPS at unchanged four-SPP work.

The existing one-SPP preview without raster diagnostics measures 9.474 ms
total p50 and 10.150 ms p95, within a 16.667 ms GPU budget on this static view.
It retains eight bounces but changes sample count and filtering. Its visibility
still uses `traceRayEXT`: the current probe enum cannot combine preview,
Beauty denoising and query visibility. No combined low-SPP/query speedup was
measured. A future policy should separate visibility choice, sample budget and
output reconstruction.

Runtime screenshot requests/polls exported baseline, compact/specialized,
Scene Color-only Beauty/query and preview captures under
`save/screenshots/validation/r478-investigation-*.png`. Baseline/query/preview
were visually inspected: broad indirect lighting and shadows remain present;
preview softens detail and remains noisy. Counts were not exactly matched, and
these are not numeric image-equivalence evidence. Debug validation, Cornell,
another scene, camera/object/material/light motion, resize/toggle/failure
coverage and per-shader counters remain open before any default adoption.
