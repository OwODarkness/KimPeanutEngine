## Candidate decision

1. **Selected — ray-query directional hard-shadow visibility.** It has one
   boolean-visible output, a frame-boundary update policy, and exercises the
   future imported-TLAS read without requiring a complete RT pipeline.
2. **Deferred — ray-traced reflections.** The first slice would also need a
   storage-image output, roughness policy, temporal filtering, and a larger
   composite contract.
3. **Deferred — full ray-tracing pipeline output.** It would add ray-generation,
   miss, hit-group, shader-binding-table, and output-composite ownership before
   the AS boundary is proven.

The existing directional shadow-map path is the explicit fallback. OpenGL is
fallback-only; Vulkan selects fallback when the complete extension/feature set
is unavailable.

## Findings and decisions

1. **Resolved — R4.0 does not add RT API surface.** The selected consumer is
   recorded in the cross-module execution spec; AS handles, device addresses,
   pipelines, bindings, and dispatch remain R4.2–R4.3 work.
2. **Resolved — validation errors become runtime failure evidence.** Vulkan's
   debug callback records an error diagnostic in `VulkanDevice`; `RenderBackend`
   exposes only an optional text diagnostic; `GraphicsSmoke` checks it after
   backend cleanup and before reporting success. Native Vulkan types remain
   below the common boundary.
3. **Resolved — callback failure is not implemented with exceptions.** Vulkan
   callbacks may run on validation-owned threads and cannot safely throw across
   the API boundary. An atomic count plus a mutex-protected last message makes
   the failure durable through orderly teardown.
4. **Resolved — attachment scopes remain raster baseline work.** They narrow
   G-buffer transitions to the attachments each pass declares. They are not
   reused as a future AS range or shader-stage vocabulary.
5. **Open — capability discovery implementation.** The named extension/feature
   contract is a policy gate only; effective capability reporting belongs to
   R4.2 after R4.1 graph prerequisites are proven.

## Review conclusion

No blocking R4.0 finding remains. R4.1 is authorized for graph correctness
prerequisites only. It must not add acceleration-structure or RT-pipeline
contracts until explicit frame bindings, update lineage, failed transition
propagation, and buffer requirements are covered.

## Validation

The required validation is focused Render/Graphics tests, a Debug build,
`GraphicsSmoke`, Vulkan/OpenGL capture inspection, and the full suite because
the baseline includes common Graphics and Render header changes. The journal
records the actual command results and any environment limitations.
