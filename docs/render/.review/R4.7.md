## Evidence and interpretation

The [matched R4.6 RT-enabled runs](R4.6.md#matched-rt-enabled-debug-and-relwithdebinfo-runs--2026-09-27)
record RelWithDebInfo Sponza at 1094×619, four samples per dispatch and eight
maximum continuation bounces: path-trace GPU p50/p95 **34.261/37.187 ms**;
CPU frame elapsed p50/p95 **38.998/42.123 ms**. Latest GPU total 37.996 ms
and latest CPU frame 37.539 ms are individual snapshots, not medians.
Debug also has validation enabled; the Debug/RelWithDebInfo difference is
not a compiler-only experiment.

`RenderSystem::BeginFrame` starts the CPU frame timer before
`backend_->BeginFrame`; `VulkanFrameContext::BeginFrame` waits on a frame-slot
fence. Consequently CPU frame elapsed includes GPU-related waiting. The
reported 39 ms does not establish 39 ms of CPU busy work. GPU path tracing
is the principal measured optimization target; CPU candidates below are
confirmed operations, but their individual millisecond cost is unmeasured.
CPU and GPU times overlap and must not be added together.

The shader uses iterative continuation in ray generation. Its eight-bounce
budget is not eight levels of pipeline recursion. Russian roulette already
exists after bounce index three, and unchanged BLAS/TLAS builds are already
suppressed by signatures. Neither is a missing optimization.

## R4.7.2 runtime progress — 2026-09-27

The implementation is in the working tree. `TracePrimary` now performs one
pixel-center trace before the per-dispatch sample loop; primary deterministic
lighting is reused while continuation samples retain independent RNG streams.
Unused geometry/material payload fields are removed consistently across the
location-0 shaders. Closest-hit uses `transpose(mat3(gl_WorldToObjectEXT))`
for the same inverse-transpose normal transform, and reuses a single metallic /
roughness fetch only when both slots identify the same texture.

RelWithDebInfo builds and the Vulkan pipeline accepted the changed raygen and
closest-hit shaders. Cornell Runtime stats reached PT-active at 1094×619, 4
samples/dispatch and 8 bounces, but both `scene_color` and `primary_albedo`
captures are black while `base_color` is visible. Its RT pass query is 0 ms and
the fixed profile summary does not collect a window for this fixture. The
Sponza attempt created the RT pipeline/SBT but lost the Vulkan device during
upload-queue work before the scene became RT-active. Therefore neither image
equivalence nor performance improvement is established, and shader register
pressure remains unmeasured. Keep F2/F7 and R4.7.2 acceptance open until the
capture/runtime defect is diagnosed and a matched Sponza sample window passes.

The repeated texture/sampler errors were traced to the unbound environment
case: `UpdateEnvironment` clears `active_environment_`, but the PT descriptor
set still includes its panorama binding. The black fallback was previously
ensured only while preparing deferred lighting, which the pure PT graph skips.
`RecordRayTracingPathTracePass` now ensures the cached fallback before binding
the panorama. Short monitored Debug Cornell and RelWithDebInfo Sponza launches
after this fix produced no invalid texture/sampler lookups. The Cornell process
exited before Runtime stats were available; Sponza still lost the device in
upload-queue work seven seconds after startup. Static review then found that
asynchronous asset uploads and frame submission/presentation can call into
shared Vulkan queues without common host external synchronization. A
device-owned mutex now covers queue submit/wait, present, device-idle, and
upload command-pool allocation/free calls. Debug compiles with this change.
It is a concrete race candidate, not a confirmed cause of the device loss. A
guarded RelWithDebInfo launch exited with code 1 before producing a new engine
log, so it yielded no runtime evidence. A successful monitored runtime pass is
still needed before closing that issue.

The normal-transform equivalence follows the GLSL ray-tracing extension's
definition of `gl_WorldToObjectEXT` as the world-to-object transformation
matrix: [Khronos GLSL_EXT_ray_tracing](https://github.com/KhronosGroup/GLSL/blob/main/extensions/ext/GLSL_EXT_ray_tracing.txt).

## Open findings

Line numbers refer to the reviewed working tree and can move during implementation.
Priorities indicate investigation/implementation order, not measured speedups.

### F1 — P1: visibility rays execute full surface shading

**Open.** [Trace (line 96)](../../../asset/shader/ray_tracing_path_tracer.rgen)
uses only `gl_RayFlagsOpaqueEXT`. `DirectLight`, around lines 138–190, calls
that same helper for a blocker and consumes only `blocker.hit`. A shadow hit
therefore executes the closest-hit shader's index/vertex loads, normal
reconstruction and material texture fetches; a miss executes the regular
environment miss shader. It also seeks a closest hit rather than ending at
the first accepted occluder.

Use a separate boolean visibility payload, terminate-on-first-hit and
skip-closest-hit flags, with a dedicated miss record. Preserve current opaque
semantics, ray intervals and origin offsets. This is not alpha-transparency
support. The common [pipeline description (line 84)](../../../engine/runtime/graphics/backend/common/ray_tracing.h)
has exactly one miss shader; the Vulkan owner hardcodes three groups and a
one-record miss region around lines 320–421. Merely changing the ray flags
would leave the existing payload/miss protocol incorrect. Extend that small
portable contract and SBT validation together.

### F2 — P1: four identical primary rays and primary lighting evaluations

**Open.** [TraceSample (line 255)](../../../asset/shader/ray_tracing_path_tracer.rgen)
always generates a pixel-center primary ray; `main`, around line 316, invokes
it once for each of four samples. The sample index changes continuation RNG,
not primary visibility. At 1094×619 this issues **2,708,744 primary rays per
dispatch** instead of 677,186. Primary emission and the current deterministic
authored-light evaluation are repeated too, including eligible shadow rays.

Compute the primary hit once per pixel, retain independent continuation
streams and accumulate primary contributions with the correct weight. This
can remove 2,031,558 primary traces per dispatch; it is not a prediction of
75% total GPU savings. Passing a large hit structure across traces can itself
increase live state, so inspect shader registers and timings. Primary jitter,
depth of field, motion blur or stochastic primary lighting would require
revisiting reuse; do not introduce those changes into this optimization.

### F3 — P1: static AS construction has no trace-quality preference

**Open.** [Build flags (line 968)](../../../engine/runtime/graphics/backend/vulkan/vulkan_acceleration_structure_owner.cpp)
are either `ALLOW_UPDATE` or zero. No `PREFER_FAST_TRACE` is requested for
static BLAS or TLAS. Cached structures persist across many full-screen
dispatches, so traversal quality can matter more than their initial build
time. Test the preference for static geometry, consistently across build-size
queries and command recording. Measure startup/build cost as well as steady
GPU time; actual benefit depends on the driver and scene. Compaction and
mesh regrouping remain conditional follow-ups, not proven bottlenecks.

### F4 — P1: every dispatch allocates native bindings and a scene buffer

**Open.** [Pass recording (line 3366)](../../../engine/runtime/render/deferred_renderer.cpp)
zeros a fixed scene table, fills it, copies it into a byte vector, destroys
the previous logical binding set around line 3471, then creates another.
The table is **65,536 bytes**, from the checked struct sizes and capacities.
This is scene-table traffic, not shader-binding-table reconstruction.

The [Vulkan binding owner (line 456)](../../../engine/runtime/graphics/backend/vulkan/vulkan_acceleration_structure_owner.cpp)
creates a one-set descriptor pool and descriptor set, copies and patches
the table bytes, allocates/uploads a new table buffer, and writes descriptors.
Destruction marks the old set pending; submission/completion serials retire
its pool and owned table safely. The problem is repeated allocation and
upload, not evidence of unsafe immediate destruction or a per-frame device
idle call.

Separate persistent scene versions from per-frame camera/history bindings.
Cache bindings by frame slot, target parity and referenced resource generations;
publish changed tables without overwriting in-flight data. Do not retain a
frame-arena camera offset blindly or patch native addresses in Render.

### F5 — P2: AS caching does not cache CPU scene extraction

**Open.** [PrepareRayTracingScene (line 834)](../../../engine/runtime/render/deferred_renderer.cpp)
clears/reconstructs frame vectors and a local mesh lookup, visits visible
proxies, obtains geometry, hashes transforms and resolves section materials
and texture slots every active RT frame. Build signatures avoid static AS
rebuilds but not this preparation.

Cache derived geometry/material records using source revisions plus handle
generations. Cover transform, section overrides, material parameters, texture
residency and mesh replacement. Camera movement should reset accumulation
without rebuilding immutable material records. Continue including off-camera
geometry needed for indirect transport and shadows; camera-frustum culling
of the RT scene is not an acceptable shortcut.

### F6 — P2: raster shadow preparation precedes choosing the PT graph

**Open.** [Frame preparation (line 1378)](../../../engine/runtime/render/deferred_renderer.cpp)
always schedules directional/spot/point shadows before choosing active path
tracing around line 1518. Pure path-traced SceneColor can spend CPU time on
raster shadow fitting/stamps without consuming the corresponding passes.
This does not imply all raster GPU passes are currently executed.

Derive required preparation from the selected graph and actual capture/debug
consumers. Preserve deferred views, hybrid RT, toggling, and existing failure
behavior; skipped raster preparation must not leave stale state when returning
to raster. Resolve capability/readiness before pruning work.

### F7 — P2: closest-hit work and payload deserve targeted reduction

**Open.** [Closest-hit shading (line 155)](../../../asset/shader/ray_tracing_path_tracer.rchit)
computes an inverse object-to-world matrix per hit; the inverse transform is
already available as a ray-tracing builtin. Metallic/roughness fetches around
lines 171–173 are separate even when their slots refer to the same packed
texture. Geometry/material identifiers are written into the payload but are
not consumed by the current ray-generation integrator.

Test builtin inverse-transpose normal reconstruction, same-slot texture fetch
reuse, and removal of verified unused payload fields as separate changes.
Preserve nonuniform/mirrored transforms, channels and all probe views. Payload
layout must match every shader stage. Do not assume fewer source instructions
necessarily mean lower GPU time.

### F8 — P2: measurement overhead and window attribution

**Addressed by R4.7.0 instrumentation (2026-09-27).** Completed summaries are
cached in [render_profile.cpp](../../../engine/runtime/render/render_profile.cpp).
Runtime stats now expose Vulkan fence/acquire/present durations, fresh GPU
query counts, the active profile window, graph mode, render extent, camera,
scene/light/environment/history metadata, tracked texture residency, and
per-frame RT table/descriptor/AS counters. The table-write count is not a
dirty-diff metric: current code rewrites its records each dispatch. No
per-ray atomics were added.

The first three optimized windows lacked residency-completion telemetry. One
subsequent fully resident confirmation is recorded, but three matched fully
resident windows are still required before freezing the performance baseline.
The new counters identify recurring allocations; they do not establish that
profiling overhead explains the 34 ms PT GPU pass.

## Reference comparison

- [NVIDIA RTX best practices](https://developer.nvidia.com/blog/best-practices-for-using-nvidia-rtx-ray-tracing-updated/):
  supports first-hit visibility, small payloads, reduced live state and static
  trace-quality builds. Adopt selectively; vendor guidance is not a speedup
  guarantee. Existing opacity and AS reuse already match its recommendations.
- [Khronos descriptor management sample](https://docs.vulkan.org/samples/latest/samples/performance/descriptor_management/README.html):
  supports reusing descriptors/buffers with separate in-flight storage. Adapt
  to Graphics' submission retirement and Render's history parity; its mobile
  raster measurements do not predict desktop RT gains here.
- NVIDIA tutorial `v2` source:
  [rtshadowmiss.slang](https://raw.githubusercontent.com/nvpro-samples/vk_raytracing_tutorial_KHR/v2/raytrace_tutorial/05_shadow_miss/shaders/rtshadowmiss.slang)
  and [05_shadow_miss.cpp](https://raw.githubusercontent.com/nvpro-samples/vk_raytracing_tutorial_KHR/v2/raytrace_tutorial/05_shadow_miss/05_shadow_miss.cpp)
  were inspected directly. The shader separates visibility payload/miss;
  C++ creates the extra miss group. Adopt that protocol, retaining engine
  ownership boundaries rather than copying its Vulkan application framework.
  Our visibility traces originate in ray generation, so this does not require
  increasing pipeline recursion depth to the tutorial's value.

GitHub MCP discovery was unavailable. The connector-specific reference gate
is blocked; web discovery and direct NVIDIA source reads supplied the relevant
precedent. The local [gkNext study](../../graphics/gknext_reference.md) was
consulted; GitHub tree access did not supply fresh relevant source, so no new
gkNext implementation claim is used. NVIDIA source was read on moving branch
`v2`, not a pinned SHA. Implementation should pin the reference revision if
it needs to rely on subsequent changes.

## Review result and limits

There is credible optimization space at unchanged resolution, sample count,
bounce budget and authored lighting. GPU visibility/primary-ray/build-policy
work should be evaluated independently of CPU binding/preparation cleanup.
No per-finding speedup has been measured. Reducing SPP, bounces or resolution
is a quality/budget tradeoff and must be reported separately. Disabling Debug
validation is not the R4.7 performance solution. Startup asset verification,
R5 decomposition, denoising, SER and wavefront tracing are outside this review's
initial implementation boundary.

## F1 runtime progress

The optional `visibility_miss_shader` keeps one-miss pipeline descriptions
valid. The Vulkan owner creates a separate general miss group and lays out two
aligned miss records before the hit record. The ray-generation shader uses a
second scalar payload initialized to occluded; direct-light visibility rays
are opaque, terminate on first hit, and skip closest hit. Only the dedicated
visibility miss shader clears the payload. SPP, bounce budget, light bounds,
and the existing 0.002 surface-origin bias are unchanged.

The Debug Vulkan build succeeds. Startup logs show that the new shader compiled
and Vulkan created a two-record miss region. Cornell reached `path_trace_active`
with eight geometry records and one light in Runtime stats; the sample counter
advanced. A `base_color` Runtime capture shows the Cornell geometry, but
`scene_color` capture output is black and the hidden process's `engine_window`
capture is blank. The Cornell log also reports repeated invalid texture and
sampler handles. Sponza creates the pipeline but its run ends with
`VK_ERROR_DEVICE_LOST` from upload-queue work before scene records are
available. These observations do not establish whether the blank path-trace
capture is caused by the visibility path, screenshot graph selection, or a
separate Runtime resource issue. Do not mark the blocked/unblocked lighting or
visual acceptance gate complete until a valid PT image is captured and both
occluded and unoccluded direct-light cases are checked.

## R4.7.3 AS policy evaluation — 2026-09-27

The policy trials used the checked-in `level/sponza.level`, Vulkan on an RTX
4070 Laptop GPU, RelWithDebInfo (`NDEBUG`, validation off), authored camera,
1094×619, mailbox, 4 SPP and eight continuation bounces. Each usable steady
window followed 120 warm-up frames and collected 300 samples after tracked
texture residency completed. Trials were serialized. The new read-only Runtime
stat `ray_tracing_acceleration_structure_storage_bytes` sums backing storage
for live AS resources; it lets the policy cost be compared with traversal time.

| Policy | Startup to active PT | AS storage | PT GPU p50 / p95 | Total GPU p50 | CPU total p50 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Neither preference (baseline) | 9.47 s first-active; 22.29 s window capture | 728,189,952 B | 23.974 / 26.187 ms | 28.157 ms | 28.005 ms |
| TLAS `PREFER_FAST_TRACE` | 11.02 s first-active; 23.82 s window capture | 786,098,560 B | 24.813 / 28.067 ms | 28.870 ms | 28.844 ms |

The single TLAS candidate window was 0.839 ms slower at PT p50 and used
57,908,608 additional bytes (about 7.95%). One window per variant is not a
repeatable performance claim, but it supplies no reason to keep the extra
memory. The static-BLAS candidate reached PT-active with 786,098,304 B of AS
storage and 19.988 ms BLAS build CPU time, then its process hit
`vkQueueWaitIdle(upload) failed (VkResult=-4)` before a steady sampling window.
Per the runtime-error stop rule, that failed candidate was not relaunched; its
steady traversal effect remains unknown.

Neither fast-trace preference is retained in source. Build-size queries and
build/update commands therefore keep the pre-trial flags and update eligibility.
Runtime stats now expose AS storage bytes through the common read-only profiling
contract; GPU ownership and RT behavior are unchanged. Debug and RelWithDebInfo
engine builds pass. A guarded Debug Vulkan Sponza run reached active PT with
728,189,952 B, exported a Beauty capture at accumulation start, and had no new
error or validation-error log. That early Debug image is not treated as
converged visual evidence. The existing converged RelWithDebInfo baseline
capture is [here](../../../save/screenshots/validation/r473-baseline-sponza.png).

The policy gate remains open: static BLAS has no steady timing, and the TLAS
result needs repeated matched windows before a strong performance conclusion.
The current decision is to retain neither policy and keep the AS memory counter
for later experiments.

## R4.7.4 — Persistent scene tables and frame-safe bindings — 2026-09-27

The implementation replaces descriptor-set-owned per-frame address tables
with immutable Graphics-owned table versions. Render compares scene-table bytes
and source buffer patches, publishes only dirty versions, and retains binding
sets by frame slot and history/output parity. Camera uniforms use stable
per-frame-slot storage. Texture retirement invalidates RT bindings before the
image view is released; resize and shutdown retire descriptors/tables through
the existing submitted-work serial.

The R4.7.3 fully resident RelWithDebInfo Vulkan Sponza window is the performance
baseline: 1094×619, mailbox, 4 SPP/eight bounces, 120 warm-up and 300 samples,
PT GPU p50/p95 23.974/26.187 ms, total GPU p50 28.157 ms, CPU total p50
28.005 ms, and 728,189,952 B AS storage. Its steady-frame RT counters were one
65,536-byte scene-table upload, one descriptor pool/set, and 904 table records
written. In a matched *scene and API but Debug configuration* candidate
snapshot, all steady-frame allocation/write counters were zero. This confirms
the intended reuse behavior, not a performance delta; Debug GPU timing was
unavailable and is not compared with the RelWithDebInfo baseline.

Debug Vulkan validation used `level/sponza.level`. It reached active PT with
450 geometry records and 3 instances, advanced accumulation while the steady
table/descriptor counters stayed zero, and exported
`save/screenshots/validation/r474-debug-sponza.png`. Runtime exercises included
the resize request (subsequent viewport 574×413), one injected rejected
dispatch, and `level.reload`; PT recovered after each, and reload restored the
450/3 scene counts. The run log contained no `[Error]`, Vulkan validation
message, VUID, or device-loss entry. This does not prove equal-quality output
at matched RelWithDebInfo settings.

The RelWithDebInfo engine target compiled, but the candidate exited before the
scene became active. At 13:20:02, `vkQueueWaitIdle(upload)` returned
`VK_ERROR_DEVICE_LOST`; the render thread then stopped. Windows logged two
`nvlddmkm` Event 153 entries at 13:19:58 and 13:20:02 for `\Device\Video3`,
GPUID 100. The single failed run was stopped without relaunch to avoid
repeating the device-loss log. It matches the upload-queue failure from the
earlier R4.7.3 static-BLAS attempt. There is no candidate 120/300 timing
window, so the user-requested performance comparison is blocked and no speedup
is claimed. The R4.7.4 code is in place and its Debug reuse/lifetime checks
pass; the stage remains open for a clean matched RelWithDebInfo window and
repeated performance evidence.

### R4.7.4 correction and matched timing follow-up — 2026-09-27

The preceding review entries describe evidence available before the upload
correction. The inherited geometry upload path now uses a graphics-family
command pool and queue, with an explicit synchronization2 copy-write visibility
barrier. The earlier `VK_ERROR_DEVICE_LOST` is not attributed to that bug.
Scene-table profiling now distinguishes records packed on the CPU from records
uploaded to the GPU; the steady candidate packs 904 per frame and uploads zero.

Three corrected RelWithDebInfo Vulkan Sponza windows each completed 120 warm-up
and 300 samples at the matched 1094×619, 4-SPP/eight-bounce fully resident
configuration. Candidate median PT GPU p50 is 25.173 ms (windows 25.041,
25.173, 25.694 ms), compared with 23.974 ms baseline (+5.0%). Total GPU p50
median is 29.339 ms versus 28.157 ms (+4.2%); CPU total p50 is 29.310 ms versus
28.005 ms (+4.7%). No speedup is demonstrated. Each log is free of new
`[Error]`, VUID, Vulkan validation, and device-loss messages. The stage reuse
gate passes; broader quality/lifecycle gates and R4.7.5 remain open.
