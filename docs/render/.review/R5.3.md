# R5.3 pass-family ownership review

**Review state:** source ownership R5.3.1–R5.3.7 has been audited; the Debug
engine/affected target builds pass. Owner correctness, lifecycle,
cross-backend/runtime acceptance and the R5.2 prerequisite remain open.

## R5.3.1 — shared draw and fullscreen helpers

This section records the helper/schema review point before the R5.3.2 owner
move. Its line counts and open items below are historical for that point.

### Findings

- The shared draw snapshot, section packet cache, per-frame object/material
  caches, selection/object uniform keys, and draw recording now have one CPU
  owner. Shadow and GBuffer call the same helper, preserving the shared-cache
  requirement without adding GPU ownership.
- Fullscreen mesh and sampler handles have one explicit render owner. The
  helper preserves independent partial allocation and retry behavior, and
  cleanup is routed through the backend while it remains valid.
- `DeferredRenderer` remains the composition facade for frame orchestration.
  No facade backpointer, friend access, shared mutable state bag, or backend-
  native handle was introduced.
- Selection data retains its 16-byte aligned wrapper and existing uniform
  binding slot. Shared shader/Graphics ABI declarations were not moved.
- Environment texture bindings now use `EnvironmentFrameBindings`, shared by
  deferred lighting and path tracing without keeping the bundle nested inside
  `DeferredRenderer`.
- Shader hashing is a render utility. Path tracing's GPU scene/camera payloads,
  static layout assertions, and estimator/RNG constants now live under the
  ray-tracing scene-data contract. Shader-visible values and byte layout are
  unchanged.
- Shadow and GBuffer stable-uniform keys and point-shadow face resolution now
  live in pass-specific constant headers; unused shadow-atlas size constants
  were removed.
- Shadow caster fitting, light-volume tests, and shadow cache stamps now live
  in `ShadowPassUtils` with focused unit coverage. This is a preparatory
  boundary only: shadow scheduling, recording, cache state, and resources have
  not yet moved into a `ShadowPass` owner.
- Removed obsolete graph usage/scope conversion helpers from the facade; R5.2
  bindings/executor continue to own those transitions.

### Evidence

- Debug `RenderSystemTest` target and full Debug engine target build.
- All 33 tests in `RenderSystemTest` pass, including snapshot ownership,
  revision-stable section-packet reuse, and partial fullscreen-resource retry
  contracts for either partial-allocation direction. Resource-ready initialize
  and repeated cleanup are also covered. CTest discovery found no tests for
  this target in the current build, so the executable was run directly.
- Runtime Vulkan Sponza stats show 285 GBuffer sections, active path tracing,
  one point-shadow cache hit, and a completed 300-sample summary. A warmed
  `scene_color` capture is available at
  `save/screenshots/validation/r53-helper-sponza-vulkan-warm.png`.
- After the schema move, `RenderSystemTest` rebuilt and all 33 tests passed.
  The path-tracing GPU payload size and offset assertions compile from the new
  schema header.
- Debug `RenderPassScheduleTest` build passed; all 94 tests passed, including
  the four new `ShadowPassUtilsTest` cases. The full Debug engine build passed.
- `deferred_renderer.cpp` is currently 3,901 lines and `deferred_renderer.h`
  is 379 lines. This remains well above the plan's 800–1,200 line facade
  target; the pass-family owner extractions are still required.

### Open acceptance

- No matched pre-change capture/stat comparison was available. The screenshot
  demonstrates the current output, not image parity.
- OpenGL raster and shadow edit/reload/resize/lifecycle checks remain open.
- At this review point R5.3.2–R5.3.7 were not implemented. `DeferredRenderer` still contains the
  planned shadow, deferred-lighting/environment, tone-map/capture, ray-tracing
  scene, and path-tracing owner responsibilities.
- R5.2 remains in progress and is still a prerequisite for closing the whole
  R5.3 plan.

## R5.3.2 — ShadowPass ownership

### Findings

- `ShadowPass` now owns directional, spot, and point shadow scheduling and
  command recording; its frame outputs, cache-hit/validity stamps, recorded
  flags, pipeline, depth samplers, and cleanup live beside the implementation.
- `DeferredRenderer` keeps graph ordering and translates each graph-scoped
  shadow write into a borrowed target for the pass. Shared lighting and capture
  consumers read frame outputs and sampler handles through the owner.
- The RHI resource map and render targets remain owned by their existing
  resolver/target owners. `ShadowPass` owns only the persistent pipeline and
  sampler handles it creates.

### Evidence

- Debug `RenderSystemTest` build passed; its executable passed 33/33 tests.
- Debug `RenderPassScheduleTest` build passed; its executable passed 94/94
  tests. The current CTest tree reports no registered tests for that target, so
  both executables were run directly.
- The full Debug `KimPeanutEngine` target built successfully.
- Visible Vulkan Sponza Runtime stats report path tracing active, all three
  shadow passes executed, one point-shadow cache hit, zero required graph
  failures, and a complete 300-sample window. Captures before and after a live
  viewport extent change are saved under
  `save/screenshots/validation/r53-shadow-pass-vulkan*.png`.
- The separate `GraphicsSmoke` executable failed Vulkan validation at GBuffer
  indexed draws with an invalid descriptor at set 0, binding 5. The failure is
  not attributed to the shadow owner and needs separate baseline diagnosis.

### Open acceptance

- OpenGL runtime parity and shadow-light edit/reload behavior remain unverified.
- The runtime extent changed from 1094×631 to 722×389 and continued rendering,
  but explicit target recreation/lifecycle failure injection is not covered by
  the current shadow owner tests.
- R5.3.3–R5.3.7 remain open; the facade is still 3,386 lines at the R5.3.2 review point. R5.2 acceptance
  also remains a prerequisite to closing R5.3.

## R5.3.3 — deferred lighting source ownership

### Findings

- `DeferredLightingPass` now composes `EnvironmentBindingsOwner` and owns the
  `FrameLightingBinding` for the active frame. Environment updates/fallbacks,
  profile and path-tracing reads, and frame-binding cleanup go through this
  pass owner.
- `DeferredRenderer` still coordinates graph-scoped GBuffer/HDR/shadow targets,
  borrowed shadow/TLAS views, and shared fullscreen/shadow resources. The RHI
  texture resources remain owned by `RenderResourceResolver`.
- The pass owns the GBuffer and lighting recording algorithms. The facade's
  `PrepareDeferredLightingPassResources` coordinates shared fullscreen/shadow
  resources and environment fallback before requesting this pass's own
  pipelines. Graph targets and borrowed shadow/TLAS views are assembled at the
  graph-to-owner boundary; this does not transfer their resource ownership.

### Evidence

- Debug `RenderSystemTest` target builds successfully.
- `git diff --check` passes, with working-tree line-ending normalization
  warnings only.
- Tests and runtime were not run under the current instruction.

### Open acceptance

- Verify environment source updates, fallback, and cleanup; deferred raster and
  hybrid ray-query paths; Vulkan and OpenGL parity; and runtime output.
- R5.3.3 source ownership is implemented. Environment update/fallback behavior,
  owner lifecycle, hybrid-query behavior, Vulkan/OpenGL parity and runtime
  acceptance remain unverified. R5.3.4–R5.3.7 owner acceptance and the R5.2
  prerequisite remain open.

## R5.3.4 — tone-map and capture source ownership

### Findings

- `ToneMapPass` and `CaptureViewPass` own their respective pipeline creation,
  GPU policy data/recording and cleanup. The facade resolves graph outputs and
  supplies borrowed shared fullscreen and shadow resources.
- Tone-map exposure/operator/transfer policy is exposed by `ToneMapPass` and
  has been removed from the path-tracing scene schema. The PT history signature
  reads that policy through the tone-map owner.

### Evidence and open acceptance

- The Debug `RenderSystemTest` target builds with these changes.
- Tests and runtime were not run under the current instruction. Raster/PT
  output parity, simultaneous Capture/Viewer conversions, terminal ordering,
  and owner lifecycle remain unverified.

## R5.3.5 — RayTracingScene source ownership

### Findings

- `RayTracingScene` owns scene enumeration, retained mesh-section/material
  mapping, BLAS/TLAS state and build recording, path-tracing scene records,
  build-resource tokens, reference-table packing and cleanup.
- After binding graph imports, the facade asks `RayTracingScene` to prepare the
  reference table using the declared `SceneGeometry` buffer group. The PT pass
  consumes the prepared table through `RayTracingSceneView` and no longer
  mutates scene state or creates/uploads that table in its recording callback.
- The facade retains graph-variant choice, graph imports and graph pass
  callbacks. Common Graphics owns native AS/table resources and their
  retirement.

### Evidence and open acceptance

- Debug `RenderSystemTest` and full Debug engine targets build with the owner.
- An earlier `RenderSystemTest` execution passed 34/34, but the suite has no
  direct `RayTracingScene` owner cases. No tests or runtime were run under the
  current instruction.
- Retained section/material mapping, area-light table contents, static reuse,
  transform/material invalidation, build-token rollback and safe cleanup remain
  unverified.

## R5.3.6 — PathTracingPass source ownership

### Findings

- `PathTracingPass` owns pipeline preparation and shader signature; history and
  guide targets; history signature/reset/commit state; per-frame/per-parity
  binding caches; dispatch recording; availability/activity; dispatch failure
  injection; and scene-capacity policy/diagnostic suppression.
- It consumes `RenderGraphPassContext` for declared target, buffer and TLAS
  imports, and receives borrowed `RayTracingSceneView` and environment data.
  The facade keeps graph selection, import binding, graph execution/finalization,
  and profile aggregation.
- History and guide target preparation now rolls back the entire target set on
  invalid creation or an allocation exception, resetting sample/parity/signature
  state together.
- At the PathTracingPass extraction checkpoint, `DeferredRenderer` was 1,323
  `.cpp` lines and 178 header lines. The R5.3.7 reference-table preparation
  correction brings it to 1,346 `.cpp` lines. Its remaining long functions are
  frame orchestration,
  graph-binding assembly and graph-scoped adapter construction; the R5.3.7
  audit below confirms those responsibilities.

### Evidence and open acceptance

- `tools/kp.ps1 -Configuration Debug build RenderSystemTest` — passed.
- `tools/kp.ps1 -Configuration Debug build KimPeanutEngine` — passed after
  the owner extraction and shared-header cleanup.
- No tests or runtime were run. PT Beauty/hybrid/preview/denoise combinations,
  history reset/failure commit, binding reuse, resize/cleanup, and Vulkan runtime
  behavior remain unverified.

## R5.3.7 — facade source audit

### Findings

- `deferred_renderer.h` contains frame settings, graph/frame bindings, logical
  frame targets, profile state, capture/view state and owner members. Former
  shadow/RT/history/cache state groups and pass-owned GPU handles are absent.
- Source search found no pipeline descriptions/creation, sampler creation,
  ray dispatch binding, acceleration-structure build recording, scene-table
  packing or resource-transition implementation in `deferred_renderer.cpp`.
- Graph bindings now take `RayTracingSceneView` after build-resource
  preparation, which rebuilds the owner's frame vectors. Cleanup resets scene
  signatures, capacities, build flags and CPU views even when no Graphics RT
  resource owner is available; native resources are destroyed when one is.
- A failed BLAS allocation no longer caches an incomplete scene as valid, so
  skipped mesh sections are retried on the next frame instead of remaining
  absent until a world/material revision. The current frame still uses the
  prior skip-and-continue fallback; this recovery path is not runtime-tested.
- Reference-table update/upload moved out of `PathTracingPass::Record()` to
  the pre-record graph-binding phase, so the pass reads only the prepared table
  supplied by the scene view.
- `RecordFrame` (about 376 lines) composes frame settings and owner inputs,
  graph variant selection, transient acquisition, execution callbacks and
  profile aggregation. `BuildFrameResourceBindings` (about 201 lines) maps
  compiled imports to targets, transient leases and prepared RT resources.
  Both are retained at the composition boundary; splitting them into a shared
  mutable context would conflict with the no-state-bag constraint.
- The facade fell from the plan's 4,587-line baseline to 1,346 `.cpp` lines
  and from 379 to 178 header lines. The remaining `.cpp` is 146 lines above
  the planning target's upper end, which is a target rather than a hard gate.

### Evidence and open acceptance

- Debug `KimPeanutEngine` and `RenderSystemTest` targets build successfully;
  `git diff --check` passes with line-ending normalization warnings.
- After the stale-view and cleanup corrections, the Debug
  `KimPeanutEngine` target rebuilt successfully.
- `RenderSystemTest` compiled after the PathTracingPass API change; the
  executable was not run.
- The Debug engine target rebuilt after the path-tracing target rollback change.
- The Debug engine target rebuilt after the BLAS cache retry correction.
- No tests or runtime were run under the current instruction. The source audit
  does not close owner correctness/lifecycle acceptance or the R5.2 prerequisite.

### Frame-local draw-cache key correction — 2026-09-29

- Replaced lossy XOR cache keys with typed keys that compare every identity
  field. Object-state entries now key on renderable handle plus material pass;
  material-binding entries also include material handle and the per-pass buffer
  handle, offset and range. This prevents unrelated handles/passes or binding
  ranges from reusing another draw's cached state.
- Stable per-object and selection uniform IDs now use explicit 16-bit domains
  above the complete 32-bit handle ID and 16-bit generation, avoiding overlap
  between identity fields and domain tags.
- `tools/kp.ps1 -Configuration Debug build RenderSystemTest` — passed
  (compile/link only).
- `tools/kp.ps1 -Configuration Debug build KimPeanutEngine` — passed.
  No tests or runtime were run, per instruction. Direct collision/cache-reuse
  assertions remain part of owner acceptance.

### Aborted-frame borrow cleanup — 2026-09-29

- `RecordFrame` now clears its borrowed `FrameContext` and `RenderWorld` pointers,
  per-frame capture/view requests and lighting binding on every preparation
  failure exit. A rejected second `RecordFrame` call leaves an already-active
  graph's inputs intact. `Cleanup` clears these views immediately after aborting
  the graph, before pass owners are cleaned up; `FinalizeFrame` uses the same
  helper after releasing graph leases and bindings.
- This keeps frame-scoped composition inputs from surviving an unsuccessful
  graph preparation or owner teardown. No pass/GPU ownership changed.
- `tools/kp.ps1 -Configuration Debug build KimPeanutEngine` — passed.
  Tests and runtime were not run per instruction; failure-path lifecycle
  behavior remains unverified.
- After the frame-cleanup and profile-scope guards, `DeferredRenderer` measures
  1,370 `.cpp` lines and 179 header lines.

### Pass-profile scope cleanup — 2026-09-29

- `ExecutePass` now binds `active_profile_pass_` with a scope guard so exceptions
  from an owner recorder cannot leave the facade attributing later profile work
  to a pass that already unwound.
- `tools/kp.ps1 -Configuration Debug build KimPeanutEngine` — passed. Tests and
  runtime were not run per instruction; exception-path profiling remains
  unverified.
