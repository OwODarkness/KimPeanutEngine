# R5 architecture review — Render, Render Graph, and Graphics

- Review date: 2026-09-22
- Status: design review only; no R5 implementation authorized or started
- Baseline: current working tree, including uncommitted R4.6 work; findings must be rechecked after R4.6 closes
- Follow-on design: [R5 stage plan](../.plan/R5.md)
- Gate: R4.6 must first produce accepted, real `vkCmdTraceRaysKHR` runtime and Cornell comparison evidence; see [R4.6 review](R4.6.md)

## Review question and decision

How can the growing deferred renderer be decoupled without moving render policy into Graphics, weakening graph correctness, or destabilizing R4.6? The recommended boundary is **a small Render-owned frame coordinator, a reusable graph execution/binding service, and concrete pass-family collaborators**. Graphics remains the owner of physical GPU objects, command translation, synchronization, and safe retirement. The graph owns logical dependency and state intent; it does not become a Vulkan abstraction or an asset loader.

The first priority is semantic correctness, not file splitting. In particular, active conditional pass failure and resource binding/transition coverage need explicit contracts before moving code. No R5 source change should be made while R4.6 is blocked or while its reference/evidence contract is being repaired.

## Current ownership map

| Concern | Current home | Review |
| --- | --- | --- |
| Scene snapshots, visibility, material resolution, light/shadow selection | Render coordinator, resolver, `DeferredRenderer` | Policy belongs in Render; frame packet creation and pass recording are unnecessarily entangled. |
| Pass identity, dependencies, SSA-like resource versions, state intents | Render pass declaration and graph compiler | Correct module, but pass criticality and physical binding contracts are incomplete. |
| Physical resource lookup, transient acquisition, transitions, attachment brackets, graph callback dispatch | `DeferredRenderer` | This is the missing `RenderGraphExecutor` named in graph architecture docs. It should be a Render-side execution service, with Graphics calls only through common contracts. |
| Per-pass pipelines, descriptors, draw/dispatch recording | `DeferredRenderer` | Split by concrete pass family with explicit shared frame inputs; avoid one polymorphic object per tiny pass. |
| GPU allocation, AS/pipeline/SBT, command translation, native synchronization and retirement | Graphics backends | Correct direction. The Vulkan backend already delegates many services; size alone is not evidence to split the facade. |
| API-neutral Graphics facade | `RenderBackend` | Useful stable seam, but includes Render shader-data structs and a Render profile pass count. Split contracts only for demonstrated consumers. |

Graphics is already internally composed rather than one undivided Vulkan file:
`VulkanBackend` owns a device/swapchain/frame context and delegates recording,
targets/transient pooling, uploads, buffers, pipelines, descriptors, textures,
readback, Editor presentation, and AS/RT work to private services
(`vulkan_backend.h:115-146`). `Graphics` selects backend sources in
`engine/runtime/graphics/CMakeLists.txt`; Render links the common target and
does not need native backend headers. Keep that composition root. The remaining
Graphics design pressure is at its **public contract and RT sub-owner
lifetimes**, not the number of `VulkanBackend` methods. OpenGL has the same
common facade but no full RT pipeline path, which makes capability/fallback
preservation a required compatibility test.

## Findings, ordered by risk

### R5-F1 — P1: enabled conditional passes can fail without failing the frame

`render_pass_declaration.cpp:188-191` maps every non-`Always` authored condition to `RenderGraphPassCondition::Optional`, even when the condition is true in the selected compiled variant. `render_graph_frame.cpp:67-73` marks `required_failure_` only for `Always`. `deferred_renderer.cpp:1185-1186` reports normal recording complete from that flag. Therefore an enabled path-trace pass (or another enabled conditional producer) can return false yet leave the graph frame reported complete. A downstream consumer can then see old or undefined output. This is a **source-proven outcome-path defect**, not a claim that the present R4.6 crash is caused by it. Separate *variant inclusion* from *failure severity*: once a producer is enabled and needed for exported output, failure is fatal to that frame; truly best-effort capture may remain optional by explicit policy. Add a focused graph-frame regression before altering implementation.

### R5-F2 — P1: graph logical resources and physical RT bindings are reconciled by names

`deferred_renderer.cpp:1471-1634` resolves graph lifetimes to targets/buffers/AS, with special cases for `SceneGeometry` and `SceneBLAS`; `:1721-1831` expands some transition intents via the same names. One logical `SceneGeometry` buffer stands for multiple mesh vertex buffers, while instance/scratch and AS build payloads have different physical multiplicity. This makes undeclared or partially transitioned physical work hard to detect. Preserve logical graph handles, but supply a **typed per-frame binding table** with one-to-many binding groups and explicit access coverage. Validate every live pass use against its resolved physical members; Graphics translates state intents for those physical handles. No native handles should enter the graph compiler.

### R5-F3 — P1: `DeferredRenderer` has too many reasons to change

The class holds graph-plan variants, frame resource bindings and transients, render-world/section caches, shadow schedules/cache state, RT BLAS/TLAS/build arrays, environment/pipeline/sampler state, capture/profile state, and every pass recorder. `RecordFrame` (`deferred_renderer.cpp:1021-1206`) both prepares the scene and executes the graph, including physical transitions and pass dispatch. `Cleanup` (`:461-558`) retires many unrelated owners in one procedure. This amplifies RT and deferred changes and makes lifetime review difficult. Split **state by owner and lifetime**, not merely by method count. Keep a small renderer coordinator with explicit initialization/teardown order; give graph execution, shadow/deferred, RT scene/path, and capture narrow concrete collaborators as justified by existing state.

### R5-F4 — P2: graph policy is represented by fixed, cross-layer special cases

`AcquireFrameTransients` (`deferred_renderer.cpp:1664-1702`) currently implements only `SceneHdr`; `ConfigureFramePlans` (`:1833-1870`) eagerly compiles 32 condition combinations; the pass declaration is a fixed resource/name registry. These decisions were reasonable for R3 and should not be replaced by a general dynamic graph without measured pressure. The immediate problem is that adding R4.6 history/storage resources requires another manual resolver branch and cross-product of conditions. Introduce a typed resource catalogue/descriptor and explicit graph-variant key; cache only variants that have a current consumer or prove that the 32-plan eager cost matters before changing it. Preserve deterministic compilation and imported/transient ownership.

### R5-F5 — P2: common Graphics exposes some Render-specific schema

`render_backend.h:31-49` defines `CameraData`, `PerPassData`, `PerObjectData`, and a GPU profile pass-count constant that Render statically checks. The Graphics facade also combines device resource factory, frame lifecycle, presentation, readback, diagnostics, and RT capability. This is not a mandate to build many virtual interfaces: first move only Render-owned uniform schemas and pass-count knowledge out of Graphics, retain common GPU value types and pass-ID timing, and create narrower capability accessors only when a real caller benefits. The OpenGL fallback and existing Editor bridge must retain their contracts.

### R5-F6 — P2: Vulkan RT owner needs a focused lifetime/contract audit after R4.6

`vulkan_acceleration_structure_owner.cpp` is about 1,049 lines and contains AS build/storage, RT pipeline/SBT, descriptor binding, and trace dispatch. These are related but have different lifetime and validation paths. R4.6's native dispatch is currently blocked, so splitting this owner now would obscure the failure. After R4.6 passes, characterize create/bind/dispatch/destroy and in-flight retirement; split AS management from RT pipeline/SBT only if the tests expose a stable internal seam. Do not change the common RT interface just to reduce source-file length.

There is a concrete lifetime question to test: AS destruction sets
`pending_destroy` (`vulkan_acceleration_structure_owner.cpp:118-133`) and
`RetireSubmitted` assigns serials to AS and descriptor sets (`:999-1021`),
whereas `DestroyRayTracingPipeline` calls native resource destruction
immediately (`:347-357`). This may be safe under the current call sites' idle
ordering; it is **not** yet proof of an in-flight use-after-free. R5 must make
that assumption explicit and test destroy/recreate while frames are in flight
before moving or changing the owner.

## Dependency and lifecycle invariants for R5

1. Asset/Resource preparation stays outside Render pass callbacks; Render consumes prepared artifacts and immutable scene/frame records.
2. Render declares *what* accesses happen and when; Graphics allocates, translates, submits, and retires *physical* resources. The graph executor may hold borrowed common handles during a frame, never native Vulkan/OpenGL objects.
3. Compiled plans outlive frames; imported bindings and transient leases are frame-scoped. A compiled callback cannot capture frame-local pointers.
4. A pass cannot record work using undeclared graph resources. Any virtual one-to-many import must expose every actual physical member to validation and transition application.
5. Failed required producers block dependent presentation/readback; cleanup releases only after submitted work is safe. Editor terminal composition remains explicit and last.
6. Vulkan RT capability is optional; OpenGL keeps the raster fallback. No architecture stage may substitute that fallback for R4.6 RT validation.

## External pattern check (adapt, do not copy)

- The pinned [Sakura graph source study](../render_graph/sakura_analysis.md) supports separate builder/compile/execute phases, typed resources, explicit imports/transients, and state handoff. Its source-level study also warns against copying a full per-frame rebuild, string-driven physical binding, premature aliasing, or multi-queue scheduling into this engine.
- [Godot's RenderingDevice scene renderer source](https://github.com/godotengine/godot/blob/master/servers/rendering/renderer_rd/renderer_scene_render_rd.cpp) shows scene buffer/service collaborators around a scene renderer. This supports separating resource ownership and scene policy, but its own broad renderer is a caution against treating class extraction alone as decoupling.
- [bgfx internal backend source](https://github.com/bkaradzic/bgfx/blob/master/src/bgfx_p.h) is a comparison for keeping API translation and backend data below a common frontend. KimPeanutEngine should retain its existing handle/description contract rather than import bgfx's command model.

## Review disposition

Propose [R5](../.plan/R5.md) as a post-R4.6 architecture stage, not an immediate refactor. Re-run this review against the accepted R4.6 tree; if R4.6 changes the graph/RT ownership shape, amend the stage plan before implementation. R5-F1 and R5-F2 are correctness gates; file-size reduction and performance are secondary and must have measured baselines.
