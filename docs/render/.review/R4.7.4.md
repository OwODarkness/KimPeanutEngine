## Findings

### F1 — P1, open: exclusive geometry buffers cross queue families without ownership transfer

Locations: `engine/runtime/graphics/backend/vulkan/vulkan_device.cpp:105`,
`vulkan_mesh.cpp:22`, `vulkan_upload_context.cpp:147–156`, and
`vulkan_backend.cpp:829–837` in the same backend directory.

Queue selection assigns graphics from a graphics-capable family and transfer
from a non-graphics family via an `else if`; successful selection therefore
uses different family indices. Mesh vertex/index buffers use
`VK_SHARING_MODE_EXCLUSIVE`. `UploadBuffer` copies them on the transfer queue,
then waits idle and returns, without a buffer ownership release/acquire.
Graphics subsequently consumes those buffers for raster drawing and AS input.
The backend has no matching buffer queue-family transfer implementation.

This is a definite source-level ownership defect. Queue completion and the
queue mutex do not transfer exclusive ownership. The requirement follows the
[Vulkan command-buffer valid usage](https://docs.vulkan.org/spec/latest/chapters/cmdbuffers.html)
and [queue-family ownership rules](https://docs.vulkan.org/spec/latest/chapters/synchronization.html).
It can invalidate mesh/AS consumption, but the available log does not establish
that this particular invalid access caused the driver reset. In particular,
loss observed during an upload does not identify whether that buffer was already
consumed or whether earlier work on another queue faulted.

Both exclusive allocation and the transfer upload path are present in HEAD
`e5cd4fb`; this is inherited infrastructure, not introduced by R4.7.4.
Debug passing once does not make the ownership contract correct.

Smallest diagnostic correction: submit these synchronous geometry uploads on
the graphics family, with the appropriate consumer memory dependency. If a
dedicated transfer queue is retained, implement matched ownership barriers and
queue ordering, or deliberately use concurrent sharing with valid synchronization.
Ownership of this correction belongs to Graphics/RHI, not Render.

### F2 — P2, open: zero record-write metric hides per-frame CPU table reconstruction

Locations: `engine/runtime/render/deferred_renderer.cpp:3440`, `:3470`,
`:3493`, `:3502`, `:3518`, `:3553`, and `:3594`.

Every dispatch value-initializes the full scene table, fills geometry,
instance, material and light records, builds address patches, and compares
the table bytes. The record-write counter is assigned only when a new GPU
table version is created. Consequently an unchanged scene reports zero
record writes even though those CPU writes still happen every frame.

Zero GPU upload bytes and zero native descriptor allocations are supported by
the reported Debug counters. Zero CPU scene-record work is not. Count CPU
packing separately from version upload, or explicitly label this metric as
records uploaded. Revision-driven packing remains R4.7.5 work; this finding
does not itself explain device loss.

## Lifecycle assessment and remaining diagnosis

The candidate keeps immutable backing tables alive through descriptor reference
counts and submission retirement, and camera uniform storage is per frame slot.
No demonstrated premature table free was found in these paths. This is a source
review result, not blanket acceptance of runtime lifetime safety.

Before another risky launch, add bounded upload diagnostics: operation type,
resource size/identity, graphics/transfer family indices, and last submitted
frame/AS/PT markers. Preserve a device-fault report or NVIDIA GPU crash dump if
available. These are needed to identify the first failing operation; the current
error records only the common upload wait. After correcting F1, validate small
geometry uploads and Cornell under Debug validation before testing Sponza.
Repeat performance measurement only after a clean candidate residency window.

## Correction and runtime follow-up — 2026-09-27

The geometry upload correction creates its synchronous upload command pool for
the graphics queue family, records `UploadBuffer` copies there, and submits
them to the graphics queue. A synchronization2 buffer barrier makes copy
writes visible to later consumers. This keeps exclusive mesh buffers on one
queue family; queue idle remains only the completion wait and is not described
as an ownership transfer. The earlier device-loss cause remains unproven.

The profiler now reports `ray_tracing_scene_table_records_packed`,
`ray_tracing_scene_table_records_uploaded`, and
`cpu_ray_tracing_scene_table_pack_ms` separately. Cornell Debug Vulkan
validation rendered active path tracing with 18 records packed, zero uploaded,
and about 0.08 ms CPU packing time. The run logged no new Error, VUID,
validation-error, or device-loss entries.

Three post-correction Sponza Vulkan RelWithDebInfo windows each completed 120
warm-up frames and 300 samples at 1094×619, with 4 SPP/eight continuation
bounces, complete texture residency, and active path tracing. The fixed-camera
Beauty capture is visually consistent with the preceding Sponza reference.
Each sample reports 904 records packed and zero uploaded. The final-snapshot
CPU packing readings were 0.0543, 0.0429, and 0.0531 ms; these are snapshot
readings, not window percentiles.
