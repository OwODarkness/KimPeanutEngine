# R3.5 Render Graph Resource-State Design Review

- Status: complete — submitted for implementation authorization
- Stage: [R3](../.plan/R3.md)
- Scope: R3.5 portable resource-state contract
- Predecessor review: [R3.4](R3.4.md)
- Review date: 2026-09-17

## Baseline inspected

- [Render Graph plans](../render_graph/PLANS.md) declaration/compilation/execution
  sections and the [Sakura analysis](../render_graph/sakura_analysis.md)
  adopted/modified patterns for portable state
- Common graphics contract: `command_recorder.h`, `render_target.h`,
  `common/enum.h`
- Vulkan transition and layout ownership: `vulkan_render_target_manager`,
  `vulkan_frame_context`, and the readback and upload owners
- OpenGL pass-boundary state repair
- The authored declaration and every pass's target acquisition and texture reads

## Findings and decisions

1. **Resolved — the common layer owns the vocabulary, the backend the mechanism.**
   No transition vocabulary exists in the common layer today, but the house
   pattern does: `RenderTargetReadbackState` supplies portable lifetime vocabulary
   while the backend attaches native fence state, and the load/store enums are
   translated per backend at the pass boundary. R3.5b follows that pattern rather
   than inventing a new one.

2. **Resolved — intents are stated as required usage, never as layouts.** Vulkan
   already persists each attachment's layout across frames in `TargetState`, and
   the readback path temporarily mutates and restores it from outside the manager.
   An absolute from-layout in the plan would fight that ownership. The compiled
   intent therefore says only what a resource must be in; the backend resolves
   the from-state from its own tracked layout, exactly as it does for depth today.

3. **Resolved — whole-resource granularity, with a retained range field.** A
   logical resource is not one image: `GBuffer` is four color attachments plus
   sampled depth in a single render target, and the shadow resources are
   depth-only. Expanding one intent into per-attachment barriers is manager
   knowledge and stays there. The Sakura study's guidance — begin whole-resource,
   retain a range field so mip/layer tracking can be added without replacing
   handles — is adopted, and the range is not populated in this stage.

4. **Resolved — the attachment boundary does not move in R3.5b.** The R3.4 review
   kept `BeginRecording`/`EndRecording` inside the pass callbacks and called an
   executor-owned boundary a richer contract than that stage should introduce.
   R3.5b keeps that decision and reaches the compiled intents through the seam
   that already exists: the executor's sweep hands the whole compiled pass to its
   callback, so a pass's intents are available without relocating the bracket.
   Moving the bracket is R3.5c, kept separate so the vocabulary, the backend
   translation, and the ownership change can each be validated and stopped
   independently.

5. **Resolved — imported-resource handoff is deferred, not stubbed.** The stage's
   stated "explicit portable initial/final usage handoff for imported resources"
   has no consumer: there is no path by which Render can hand Graphics a resource
   it did not create, every logical resource is created transient, and
   `RenderGraphResourceLifetime::Imported` is currently unreachable. Defining an
   API with no caller would be scaffolding. It is deferred until an import path
   exists, and this review records that as a deliberate gap rather than an
   oversight.

6. **Resolved — Vulkan will emit fewer barriers, and that is intended.**
   `EndRendering` currently moves every color attachment to `SHADER_READ_ONLY`
   unconditionally, including a target that is never sampled afterwards. A
   usage-driven plan elides those. This is behaviorally equivalent and is the
   point of the stage, but it is a real change in the emitted barrier set, so it
   is validated by the both-API capture gate rather than assumed safe.

7. **Resolved — the plan must replace, not duplicate, the backend's transitions.**
   The manager's hardcoded `BeginRendering`/`EndRendering` transitions and the
   plan-supplied intents cannot both be active; a second transition pass would
   emit redundant and possibly conflicting barriers. Each slice must prove the
   emitted barrier set is what it intends, which is why Vulkan validation
   cleanliness is part of acceptance — the layers are enabled in any non-`NDEBUG`
   build.

8. **Open — a graph/renderer discrepancy to resolve during R3.5a.**
   `CaptureViewPass` declares a `RenderPassResource::SceneColor` read, but
   `RecordCaptureViewPass` never acquires or binds `SceneColor`. The declaration
   claims a read that does not happen on the GPU, which will produce a spurious
   transition intent once intents are derived from uses. Either the declaration
   is corrected or the read is made real; leaving it would have the plan schedule
   a transition for a read that never occurs.

## Review conclusion

No blocking design finding remains. The authorized work is the three slices
described in the [R3.5 plan](../../../docs/render/.plan/R3.md): vocabulary and
compiled intents (CPU only), the common contract with backend translation, and
the executor-owned boundary. Subresource tracking, aliasing, transients, and the
imported-resource handoff are explicitly out of scope.

The stage's value is correctness and a state boundary for later work, not
performance; it makes no submission-performance claim.

## Validation

R3.5 touches common Graphics headers, so the validation matrix escalates to full
for every slice: complete build, complete suite, `GraphicsSmoke`, and both-API
runtime captures diffed against the current build. Expected result is zero
differing pixels, since the intent is to preserve behavior; Vulkan barrier
cleanliness is checked through the validation layers active in Debug.
