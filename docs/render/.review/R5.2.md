## Why the AS bridge is still unverified

The retained Cornell final probe is **frame 1745**, with PT active and both build-pass outcomes `not_in_plan`. Other Cornell probes are frames 1000 and 1933. These are snapshots of late frames, not a history of startup execution. The source clears build requests each preparation, then requests BLAS only for unbuilt mesh records and TLAS only for an unbuilt target or changed instance signature (`deferred_renderer.cpp:884`, `:938`, `:1252–1277`). `RecordFrame` selects its variant using those flags (`:1809–1817`). Build passes are explicitly retained as side effects in the graph declaration; they are not automatically removed just because PT is enabled (`render_pass_declaration.cpp:292–298`).

Thus a cached frame legitimately has no build passes. **The probes do not prove that Cornell or Sponza never selected a build variant.** Nor do they prove that the current preparation bridge recorded and submitted a successful build. Active PT and a screenshot validate the resulting rendering path, not the exact prepare/build/retire sequence.

The exported build counters in those JSON snapshots are also zero. Current Vulkan owner code increments its counters on build recording and returns cumulative counters; do not interpret these snapshot zeros as confirmed startup execution. The executable revision and publication of completed-frame counters need reconciliation with a fresh instrumented run.

There is also real earlier failure evidence: Cornell log `save/logs/2026-09-28/KimPeanutEngineLog-2026.09.28-17.05.23.txt:36` repeatedly reports that Graphics could not prepare TLAS resources, followed by binding/finalization failures. Earlier 16:48 and 17:02 logs contain image-layout validation messages. These are intermediate runs; their binaries are not proven to match this reviewed tree. The implementation journal reports a later successful smoke. Preserve both facts: an earlier failure existed, and its branch-level cause/resolution has not been tied to a captured successful build frame. Later 17:36 logs include test fixtures and OpenGL, so the newest filename alone is not the relevant Vulkan engine run.

## Findings and remediation

### R5.2-F1 — P1, open: build/abort/retirement acceptance is missing

The bridge prepares native storage and temporary instance/scratch buffers before graph transitions (`vulkan_acceleration_structure_owner.cpp:980–1148`); recording consumes the token and queues buffers for retirement (`:1321–1348`), while cancellation queues unused prepared buffers (`:1151–1159`). `RetireSubmitted` assigns a submission serial and collection waits for its completion (`:1503–1538`). This ownership direction is appropriate, but the saved runtime probes cover none of these boundary events directly. The historical TLAS failure makes this a correctness gate, not merely missing paperwork.

**Solve:** retain a bounded event record for each requested build frame, including prepare result/reason, variant key, build descriptors and counts, physical inputs/scratch, token consumption/cancellation, pass outcomes, submission serial and retirement serial. Exercise successful cold BLAS+TLAS, TLAS-only update, preparation failure after partial allocation, recording failure after some BLAS commands, abort before submission and cleanup. Do not release recorded scratch until its submission completes; cancellation of never-recorded batches needs an explicit reclamation policy even when no later submission occurs. Record the failing prepare branch rather than a generic `nullopt` message.

### R5.2-F2 — P1, open stage contract: RT recording still bypasses declared physical bindings

The graph imports exact buffer and AS groups, but `RecordRayTracingBlasBuild` and `RecordRayTracingTlasBuild` obtain the recorder and build arrays from facade/backend state (`deferred_renderer.cpp:1401–1445`). PT selects the backend-global active TLAS (`:3506–3507`), and ray-query descriptors also use that global accessor (`:3170`). These methods do not consume AS/buffer handles through `RenderGraphPassContext`. Therefore successful binding validation does not establish that the resources actually recorded are the same resources that the graph transitioned. This is a source-proven gap in R5.2's authoritative-graph contract, not evidence of a current visual mismatch.

**Solve:** retain scene policy in Render and GPU ownership in Graphics, but feed recording the pass context's recorder and exact declared AS/buffer groups. Validate every build target, geometry input, prepared instance and scratch member against those groups. Bind PT/query descriptors to the declared `SceneTlas`, not a global fallback. Address-table inputs require the same explicit coverage audit; do not simply move the bypass into an R5.3 owner.

### R5.2-F3 — P2, open: a second external call can erase a transition failure

The typed `ExecuteExternal` resets `external_transition_failed_` before asking the cursor to execute (`render_graph_executor.cpp:228`). On transition failure its void cursor callback returns early, but `RenderGraphFrame::ExecuteExternal` still marks that terminal `Executed`. A second typed call resets the failure flag and is then rejected by the exactly-once cursor guard. `Finalize` can consequently report frame success despite the first transition failure (`render_graph_executor.cpp:267–269`). The production facade's `CanExecuteExternal` guard and sticky `frame_execution_failed_` mitigate this path; the reusable executor contract remains incorrect, and the pass outcome is misleading even after a single failure.

**Solve:** let external execution return an explicit success/failure result to the cursor, record `Failed`, and preserve the first failure/diagnostic until abort or a new frame. Add a regression for failed transition → rejected duplicate → finalize, alongside successful duplicate rejection. A rejected duplicate must neither invent a failure nor erase an existing one.

### R5.2-F4 — P2, open: undeclared lookup is rejected, but recording need not fail

Context resolution returns null/empty for an undeclared handle (`render_graph_executor.cpp:59–74`), but the executor accepts only the callback's bool (`:196`). A callback can ignore the rejected lookup and return true. The plan's stronger requirement that undeclared resource access fails recording is therefore not enforced by the context. This compounds F2's direct access bypasses.

**Solve:** accumulate a context violation with pass/resource identity and require both callback success and a clean context for an executed outcome. Test ignored invalid lookup, foreign generation/version and wrong access intent. Keep Graphics scope/handle validation as an additional backend check.

### R5.2-F5 — P2, open: prepared token is not bound to an immutable build description

Preparation sizes scratch and uploads instance records from one descriptor set. Later `Build` checks batch length and target identity (`vulkan_acceleration_structure_owner.cpp:1326–1338`), but not mode, geometry/counts or instance content. `BuildOne` recomputes sizes using the later descriptor without checking the prepared scratch capacity (`:1255–1280`). Reusing the same target/token with altered descriptors can record different input requirements against old storage or uploaded instances. The present facade appears to preserve its arrays between prepare and record; this is an exposed common-contract hazard introduced by the split API, not an observed current crash.

**Solve:** make the prepared batch own an immutable description snapshot and record from it, or store and validate a complete descriptor identity plus capacities before emitting any commands. Cover mode/count/input changes and token reuse. Continue to expose only common handles/tokens to Render.

## Concrete way to close the build-frame blocker

1. Rebuild the exact Debug tree with Vulkan validation enabled and record its commit/diff identity. Add bounded first-build diagnostics before launching; avoid trying to catch a brief startup frame through repeated live polling.
2. Start a fresh process with the checked-in Cornell fixture on the approved Default desktop. Observe the first nonempty scene's flags and selected variant. If flags are true but the variant lacks build passes, inspect variant-key selection/declaration; if flags are false, log cache state, RT capability and geometry/instance counts. If preparation fails, stop at its exact branch before claiming any pass executed.
3. Require BLAS preparation to allocate native storage before TLAS preparation resolves BLAS addresses. The current binding builder already prepares BLAS first (`deferred_renderer.cpp:2333–2359`); preserve that order. Actual GPU work must remain graph ordered: BLAS → TLAS → PT/query consumer.
4. If startup observation is insufficient, add a one-shot Runtime validation request at a frame boundary that retires/invalidate the Render-owned AS cache safely and schedules a fresh build. Return a retained result keyed by frame/request ID. This is a proposed diagnostic, not an existing command. Do not clear native objects directly from the command thread or disable AS reuse permanently. A transform edit tests TLAS update only; a reload can reuse BLAS and is not proof of a full rebuild.
5. Save one successful build-frame record with nonempty exact physical groups, both pass outcomes `executed`, token consumption, submission completion and eventual temporary-buffer retirement. Save the next unchanged frame with both build passes absent and no fresh preparation allocations. Repeat on Sponza after full residency, then perform a transform-only TLAS update.
6. Inject prepare/record failure and verify required dependents are skipped, no PT history is committed for failed required work, and leases/tokens retire safely. Close the remaining raster/PT, Capture/Viewer, resize/reload, OpenGL and matched-image gates from the stage plan. RelWithDebInfo performance checks follow correctness; this review makes no timing claim.

This approach makes graph execution observable while retaining general scene behavior and AS caching. It does not require Cornell- or Sponza-specific rendering branches.

## Test coverage and validation limits

The new executor tests contain two cursor/abort tests using the overload without physical bindings. New binding tests cover exact groups and missing/foreign/duplicate/empty imports, using dummy texture pointers. They do not exercise the typed executor's transitions, attachments, temporary lease rollback, AS prepare/record contract, external transition failure or context violations. The journal's reported 203/203 labeled tests are valid historical results, but do not cover these missing contracts.

This review inspected source, working-tree diffs, journal, saved stats and relevant logs. No compilation, test execution, engine launch, visual comparison or performance measurement was performed. Documentation validation is recorded in the appended journal entry. All findings remain open; no GPU ownership or production behavior changed.
