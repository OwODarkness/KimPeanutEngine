## Findings and decisions

1. **Resolved — the execution cursor belongs to Render, not Graphics.**
   `CompiledRenderGraph` is pure planning data; every runtime concern (cursor,
   per-pass outcome, required-failure latch, external-terminal policy, finalize
   validation) lives in `FixedRenderPassFrame`. R3.4 therefore adds a
   `RenderGraphFrame` under `render_graph/` reproducing that same contract over a
   compiled plan: renderer sweep, external terminal, finalize, outcome query, and
   required-failure query. It stays a value type over a borrowed compiled plan —
   consistent with the existing executor contract rather than a new abstraction.

2. **Resolved — conditional topology uses compiled variants, not runtime conditions.**
   The compiler culls disabled passes out of the order entirely, and the fixed
   oracle instead visits them and records `SkippedCondition`. These are different
   shapes, and exactly one of them can be authoritative. The deciding evidence is
   that the only condition input is resolved once per frame *before* any pass runs
   and never changes mid-frame. The graph therefore keeps its compile-time culling
   and R3.4 selects a compiled variant from the resolved condition set; the
   executor gains no runtime condition evaluation. This is also what the
   performance policy requires, since it keeps compiled topology reusable while
   unchanged. Per-variant compilation is cached by that condition set.

3. **Resolved — the external terminal is an always-enabled side-effect root.**
   Whether the Editor terminal will execute is not known when the frame's graph is
   declared, because the call arrives after the renderer sweep, and a missing
   terminal is a legitimate `SkippedExternal` outcome rather than an error. The
   graph therefore declares it enabled and side-effecting so it is always compiled
   and always roots its producer chain, and the executor decides at execution time
   whether to run or skip it. The two-phase shape is preserved: renderer sweep,
   then external, then finalize. `RenderSystem::EndFrame` discards the finalize
   result today; R3.4 preserves that failure policy rather than tightening it,
   because changing it is a separate behavioral decision.

4. **Resolved — typed pass identity is carried, not re-derived from position.**
   Pass ordinals are locked in three independent places: the profile array is
   indexed by the `FixedRenderPassId` ordinal, `RenderProfilePass` duplicates that
   order positionally, and both backends hard-code eight GPU-profile slots. The
   fixed sequence additionally requires each entry's id to equal its ordinal. A
   scheduler that reorders, inserts, or drops a pass desynchronizes all of them at
   once. The graph declaration therefore carries the typed pass id as a
   caller-owned payload, and the executor dispatches on that payload rather than on
   compiled position — position is not stable once culling or ordering changes.

5. **Resolved — the minimum pass context is identity plus typed key.**
   The callback needs to know which pass it is and to reach frame inputs it already
   receives. It does not need resource views, bindings, or a recorder handle,
   because R3.4 does not move resource binding into the executor. This keeps the
   existing `Record*Pass` methods as execution callbacks and avoids the per-pass
   virtual hierarchy the architecture explicitly rejects.

6. **Resolved — attachment begin/end does not move in R3.4.**
   Render-target recording is private to three render classes, and every recording
   method pairs begin with an end on all of its early-return paths. Native
   transitions are derived purely from the *order* of begin/end calls: Vulkan
   remembers and re-transitions tracked layout state, and OpenGL repairs sRGB and
   depth-mask global state on the next begin. Moving the bracket into the executor
   would change transitions while changing nothing about scheduling, and it would
   require a richer common attachment contract than this stage should introduce.
   R3.4 keeps the bracket inside pass callbacks; portable transition intents remain
   R3.5. This closes the open decision on when attachment begin/end moves.

7. **Resolved — the seven whole-target logical resources stay whole.**
   `GBuffer` is one logical resource but physically four color attachments plus a
   sampled depth attachment, and different passes touch different attachments of
   it. Splitting it now would change the declaration and invalidate the R3.3 parity
   proof, so R3.4 keeps the proven granularity. Subresource granularity must be
   decided in R3.5, before transition inference leans on these names, because
   transition inference over a whole `GBuffer` cannot be correct at attachment
   level.

8. **Resolved — R3.4 pins execution order parity; undeclared cross-pass state is a
   recorded hazard.**
   Several passes communicate through renderer members that are not graph
   resources: the spot and point shadow "recorded" latches are written by the shadow
   passes and read by deferred lighting and capture; the scheduled shadow frames and
   the section packets are produced before any pass runs; the lighting binding is
   produced and consumed inside a single pass body. The graph has no edges for any
   of these. R3.4 is correct only because the compiled plan's order equals the
   declaration order for this declaration, so R3.4 pins that invariant and
   validates it, and the executor gains no reordering freedom in this stage.
   Declaring or eliminating these latches is required before any later stage may
   reorder or parallelize passes, and is carried forward to the roadmap.

9. **Resolved — one authored declaration.**
   The fixed sequence and the compatibility test are two hand-maintained copies of
   the same eight passes, with further hand-maintained copies of resource and target
   names elsewhere. R3.4 promotes a single canonical declaration into Render and
   derives both the graph and `FixedRenderPassSequence` from it during the dual-path
   phase, so the two cannot drift, and the tests consume the production declaration
   instead of restating it. Adding a fourth encoding is not acceptable; the
   existing duplicates are removed as the fixed path is retired.

10. **Resolved — dual-path parity precedes removal.**
    During migration the fixed frame remains the live oracle running beside the
    graph executor, and the two are compared per frame on visited order, outcomes,
    required-failure state, and capture readiness. Both result bits are reproduced
    even though only the capture bit is currently consumed. The fixed path is
    removed only after focused, full, smoke, and visual evidence passes on both
    APIs, which satisfies the stage's "no duplicate manual order after migration"
    criterion.

## Validation

R3.4 changes public Render behavior, so it requires at least validation level 3,
escalating to full validation if common headers or CMake boundaries change:

```powershell
cmake --build build --config Debug --target RenderGraphTest RenderPassScheduleTest GraphicsContractTest GraphicsSmoke
ctest --test-dir build -C Debug -R "RenderGraphTest|RenderGraphCompatibilityTest|RenderPassScheduleTest|GraphicsContractTest" --output-on-failure
.\tools\kp.ps1 smoke
```

New coverage required by this review: a `RenderGraphFrameTest` for the execution
contract (sweep order, external terminal exactly once, skip, required failure,
finalize rules) and an extension of `RenderGraphCompatibilityTest` that drives the
production declaration rather than a test-local copy. `RenderPassScheduleTest`
stays unchanged and continues to define the oracle contract.

Runtime proof uses the checked-in startup fixtures and the command registry on both
APIs. Captures remain below `save/screenshots/validation/`, use new filenames, are
inspected against the R3.0 baseline, and are accompanied by per-pass and graph
CPU/GPU metrics. Compilation alone does not close this stage.

This review is documentation-only and was validated at level 0: links inspected,
`git diff --check` clean.

## Review conclusion

No blocking design finding remains for the R3.4 boundary, and the three decisions
that the roadmap listed as outstanding before execution are closed above. The
authorized work is narrow: a graph execution frame, a single authored declaration,
dual-path parity, and the switch — with no backend change, no move of attachment
begin/end, no subresource split, and no new pass abstraction.

R3.1's review authorized only the R3.2 CPU-only boundary and explicitly did not
authorize R3.4. This record is a design review, not an execution authorization; the
fixed execution path may be replaced only after the user authorizes R3.4 and the
parity evidence above exists. R3.5 through R3.7 remain separately gated.
