# D6 — Light and shadow expansion

Parent: [Deferred PBR plans](../PLANS.md) · Roadmap: [TODO](../TODO.md) ·
Spec: [render-deferred-pbr](../../../../.spec/specs/render-deferred-pbr.md)

## Local problem

D6.1 and D6.2 already carry point and spot records through the existing
Gameplay → Render light boundary and evaluate them unshadowed. `Spot2D` exists
in the typed shadow ABI, but the live renderer can resolve only one directional
shadow, owns only one directional depth target, and uploads only one shadow
transform. Adding a spotlight shadow therefore requires a bounded multi-shadow
frame policy; it does not require a new material path, proxy type, render graph,
or common-RHI abstraction.

## Chosen D6.3 boundary

Implement one shadowed spotlight alongside the existing directional shadow.
The first punctual-shadow budget is deliberately fixed:

- at most one `Directional2D` job at binding slot 0;
- at most one `Spot2D` job at binding slot 1;
- one Render-owned 1024×1024 sampled D32 spot target;
- `PointCube`, multiple spot maps, atlases, variable resolution, and eviction
  remain out of scope.

Light snapshot order is already deterministic, so the first eligible authored
spotlight wins the single spot budget. Other eligible spotlights continue to
light the scene but resolve as explicitly unshadowed. This is a temporary,
testable selection rule, not a claim that handle order is a future quality
metric.

## D6.3.1 — authored intent and frame selection

Add `casts_shadow` to the copied spot source description and Gameplay spot
component/factory, matching the directional-light authoring seam. The source
registry alone creates, replaces, and retires the private `ShadowHandle`; no
Gameplay type receives that identity or a target/binding value.

At the frame boundary, select only a light that is enabled, typed as `Spot`,
has a valid authored shadow identity, valid position/direction/range/cones, and
fits the one-job budget. Disabled, stale, malformed, incompatible, and
over-budget records schedule no producer and remain unshadowed in
`LightGpuData`. Destroying or disabling the selected source must stop the job
on the next drained snapshot without leaving the previous target shader-visible.

## D6.3.2 — target, projection, and caster producer

Add a `SpotShadow` logical pass resource and frame target. Graphics continues
to own allocation, transitions, read/write compatibility, and safe retirement;
Render owns only the fixed target policy and scheduled job.

Build the spot view from authored position and travel direction, with the same
stable alternate-up rule used by the directional path. Build a square
perspective projection whose vertical field of view is twice the validated
outer cone, whose far plane is the authored range, and whose positive near
plane is clamped relative to range so it cannot meet or cross the far plane.
Use the resulting light frustum to reject out-of-cone proxy bounds before draw
recording. The final caster predicate remains visible, ready, opaque, and
`casts_shadow`; malformed bounds stay conservative rather than becoming a
reason to lose a shadow.

Generalize the current depth-only shadow recorder/pipeline so directional and
spot jobs share the pass/material override and per-object constants. Keep the
projection and target choice in their typed job frames. Do not add a
backend-specific depth-bias API in this slice; retain receiver-side bias and
record the portable raster-bias question as later RHI work.

## D6.3.3 — frame bindings and deferred consumption

Replace the single optional resolved-shadow input with a bounded collection of
resolved bindings. Promote a light only when source `LightHandle`, authored
`ShadowHandle`, shadow kind, scheduled slot, and successfully recorded target
all agree. The existing `LightGpuData` layout and ABI version remain unchanged;
the already-present `shadow_kind` and `shadow_binding_slot` fields distinguish
directional slot 0 from spot slot 1.

Extend the Render-private deferred-lighting constants with one spot
view-projection matrix and PCF parameters, and bind the sampled spot depth at a
new pass-local texture binding. In the spot-light branch, evaluate shadow
visibility only for `Spot2D` plus slot 1. Reuse the cross-backend clip-depth and
framebuffer-origin normalization already proven by D5.3, with an independently
tunable receiver bias and 3×3 PCF kernel. A missing or mismatched binding must
return visibility 1.0.

## D6.3.4 — diagnostics and proof

Add semantic `SpotShadowDepth` and `SpotShadowVisibility` capture views. The
depth view goes through Render's conversion target; neither Runtime nor Editor
reads the native depth attachment. Use a deterministic fixture in which the
existing bootstrap spotlight illuminates a receiver and a distinct opaque
caster inside its outer cone.

Required tests and evidence:

- light-source tests for spot shadow create/update/disable/destroy and private
  handle retirement;
- scheduler/binding tests for deterministic selection, disabled, stale,
  incompatible, no-caster, and over-budget inputs;
- pass-schedule and target tests proving spot write-before-read, fixed extent,
  sampled D32 compatibility, resize rebuild, and teardown;
- shader/contract tests proving directional and spot bindings can coexist
  without changing `LightGpuData` stride or silently sampling the other slot;
- `RenderPassScheduleTest`, `GraphicsContractTest`, and `GraphicsSmoke`, then
  inspected Vulkan and OpenGL final-color, spot-depth, and spot-visibility
  runtime captures.

## Reference comparison

- [Filament `ShadowMap::updateSpot`](https://github.com/google/filament/blob/main/filament/src/ShadowMap.cpp)
  uses the light position/direction, a perspective field of view equal to twice
  the outer cone, and the light radius as the far bound. D6.3 adopts that
  projection shape, but not Filament's atlas, frame graph, VSM/PCSS, or
  renderer-wide shadow system.
- [bgfx simple shadow maps](https://github.com/bkaradzic/bgfx/blob/master/examples/15-shadowmaps-simple/shadowmaps_simple.cpp)
  keeps depth production, sampled consumption, and backend coordinate
  normalization explicit. KimPeanut already has those boundaries and extends
  them with a second typed Render-owned target rather than importing bgfx's
  example state model.
- [Godot `LightStorage::shadow_atlas_update_light`](https://github.com/godotengine/godot/blob/master/servers/rendering/renderer_rd/storage_rd/light_storage.cpp)
  demonstrates that an atlas entails coverage sizing, subdivision,
  reallocation tolerance, ownership tracking, and eviction. Those policies are
  intentionally rejected until more than one punctual shadow is justified by
  measured scene pressure.

## Later D6 work

[D6.4](D6.4.md) plans one fixed-budget `PointCube` job as a six-face 2D depth
atlas. This avoids treating the currently incomplete common cubemap path as
working while still proving point-shadow selection, six-view production,
filtering, diagnostics, and cross-backend behavior. True cube resources,
multiple punctual jobs, variable resolution, caching, and a general atlas or
render graph remain later evidence-driven decisions.

## Acceptance

D6.3 is complete when one authored spotlight can produce and consume a typed
shadow on Vulkan and OpenGL, coexist with the directional shadow, fail safely
for every unscheduled case, and provide diagnostic captures without changing
Asset ownership, MeshProxy, the material system, or common recorder contracts.
