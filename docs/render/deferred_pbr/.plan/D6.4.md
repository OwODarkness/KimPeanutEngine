# D6.4 — Bounded point-light shadows

Parent: [D6 light and shadow expansion](D6.md) · Roadmap: [TODO](../TODO.md) ·
Spec: [render-deferred-pbr](../../../../.spec/specs/render-deferred-pbr.md)

## Local problem

D6.1 already evaluates point lights, and D6.3 established a bounded collection
of resolved shadow identities with directional slot 0 and spot slot 1. The
typed ABI also reserves `PointCube`, but point authoring has no shadow intent,
the frame selector rejects point shadow bindings, and the renderer owns no
omnidirectional depth producer or consumer.

The nominal common texture enum is not sufficient for a real cubemap target:

- Vulkan currently translates cube textures to a 3D image, omits the
  cube-compatible creation flag, and creates a view over only one array layer;
- OpenGL allocates cube storage but its upload path treats the cube as one 2D
  image;
- `RenderTargetDesc` and `CommandRecorder` cannot select an attachment layer or
  cube face.

Fixing generic cube upload, layered attachment views, face selection, readback,
and lifetime in the same stage would turn a Render feature into a broad RHI
reconstruction. D6.4 instead proves point-shadow policy with existing 2D
target semantics.

## Chosen boundary

Implement one shadowed point light as six 90-degree faces packed into one
Render-owned sampled D32 atlas:

- at most one `PointCube` job per frame at binding slot 2;
- 512×512 texels per face in a fixed 3×2 atlas (1536×1024 total);
- one target, one sampled texture binding, and up to six sequential caster
  views inside one target recording;
- no true cubemap, array-layer rendering, geometry shader, dual-paraboloid
  projection, general shadow-atlas allocator, caching, or multiple point jobs.

This is a representation choice below the typed `PointCube` job. Gameplay and
the light ABI express omnidirectional shadow intent; only Render knows that the
first physical representation is a six-face 2D atlas.

The fixed allocation is 6 MiB for D32 depth. The hard execution budget is one
selected point light, at most six face views, and no per-frame GPU allocation.
Over-budget point lights continue contributing unshadowed direct light.

## D6.4.1 — authored intent and deterministic selection

Add `casts_shadow` to `PointLightSourceDesc`, `PointLightComponent`, and
`PointLightActorDesc`, matching directional and spot authoring. The source
registry alone creates and retires the private `ShadowHandle`; Gameplay keeps
only its opaque source token.

Select the first eligible point light from the deterministic immutable light
snapshot. Eligibility requires enabled state, `LightType::Point`, a valid
authored shadow identity, finite position, positive finite range, and at least
one ready opaque shadow caster intersecting the light's range sphere. Disabled,
destroyed, stale, malformed, incompatible, empty, or over-budget inputs produce
no point pass and remain explicitly unshadowed.

Extend resolved-binding validation to accept only `PointCube` at slot 2. The
existing `LightGpuData` size, stride, and ABI version stay unchanged.

## D6.4.2 — six-face atlas producer

Add `PointShadow` to the logical pass-resource and frame-target sets. Its fixed
target is sampled D32 at 1536×1024 and follows the existing Render-owned target
and Graphics-owned allocation/transition/retirement boundary.

Define one canonical, unit-tested face table containing face identity,
direction, up vector, and atlas tile. Use the conventional axes:

| Face | Direction | Up | Tile |
| --- | --- | --- | --- |
| +X | `(1, 0, 0)` | `(0, -1, 0)` | `(0, 0)` |
| -X | `(-1, 0, 0)` | `(0, -1, 0)` | `(1, 0)` |
| +Y | `(0, 1, 0)` | `(0, 0, 1)` | `(2, 0)` |
| -Y | `(0, -1, 0)` | `(0, 0, -1)` | `(0, 1)` |
| +Z | `(0, 0, 1)` | `(0, -1, 0)` | `(1, 1)` |
| -Z | `(0, 0, -1)` | `(0, -1, 0)` | `(2, 1)` |

Each face uses the point position, a 90-degree square perspective projection,
the same positive range-relative near-plane rule as the spot path, and the
authored range as its far plane. Build the range-intersecting caster candidates
once, then apply per-face frustum culling. Invalid bounds stay conservative;
the final draw predicate remains visible, ready, opaque, and `casts_shadow`.

Begin the atlas target once, clear it once, and record each non-empty face by
setting its tile viewport before using the generalized shadow-depth pipeline.
Do not introduce layered rendering or change `BeginRenderTarget`. The producer
is considered available only when target recording begins successfully; a
failed producer never promotes the point light to slot 2.

## D6.4.3 — deferred consumer and filtering

Bind the point atlas at one new deferred-lighting texture binding. Add a
separate Render-private point-shadow uniform block rather than expanding the
already-locked D6.3 deferred constants. It carries the six transposed
view-projection matrices plus atlas texel size, receiver-bias parameters, and
an enabled marker.

For a `PointCube` light at slot 2:

1. derive light-to-receiver direction from the point position;
2. choose the dominant-axis face with a specified deterministic tie order;
3. project the receiver with that face's exact producer matrix;
4. apply the existing Vulkan/OpenGL clip-depth and local-UV normalization;
5. remap local UV into the face tile and compare against atlas depth;
6. apply receiver-normal bias and 3×3 PCF, clamping taps to the selected tile
   with a half-texel guard so adjacent faces cannot bleed.

Missing, mismatched, disabled, partially prepared, or stale point bindings
return visibility 1.0. Face-edge PCF does not cross into the neighboring cube
face in this first representation; visible seams at extreme face boundaries
are a known quality risk and part of runtime inspection.

## D6.4.4 — diagnostics and validation

Add semantic `PointShadowDepth` and `PointShadowVisibility` captures. The depth
view presents the 3×2 face atlas through Render's existing RGBA8 conversion;
the visibility view evaluates the selected point shadow over camera-visible
receivers. Runtime and Editor never receive a native depth texture.

Use a deterministic fixture with the authored point light, an asymmetric
caster, and receivers in at least three different point-shadow faces. This is
necessary to catch face-order, up-vector, atlas-tile, and backend-origin errors
that a single floor shadow would miss.

Required validation:

- Gameplay/source tests for point shadow create, update, disable, destroy, and
  private `ShadowHandle` retirement;
- selector/binding tests for slot 2, coexistence with slots 0 and 1, stale and
  incompatible identities, no-caster behavior, and deterministic over-budget
  fallback;
- math tests for all six view matrices, dominant-axis face selection, tile
  mapping, and range-relative near/far validity;
- pass/target tests for one write-before-read resource, fixed atlas extent,
  sampled D32 compatibility, resize rebuild, and teardown;
- shader syntax/translation and descriptor tests for the point atlas and
  point-shadow uniform block without a `LightGpuData` ABI change;
- `GraphicsContractTest`, `RenderPassScheduleTest`, `GameplayUnitTest`, and
  dual-backend `GraphicsSmoke`;
- inspected Vulkan and OpenGL `SceneColor`, `PointShadowDepth`, and
  `PointShadowVisibility` runtime captures, including face-boundary inspection
  and resize/teardown evidence.

Because D6.4 changes public Gameplay/Render headers, the pass-resource contract,
shader bindings, and backend-executed rendering, final validation escalates to
the full Debug build and complete CTest suite after the focused checks pass.

## Reference comparison

- [Filament `ShadowMap::updatePoint`](https://github.com/google/filament/blob/main/filament/src/ShadowMap.cpp)
  builds one 90-degree punctual projection per cube face and uses the light
  radius as the far plane. D6.4 adopts the six canonical views and bounded
  range, but records them into one 2D atlas because KimPeanut lacks a valid
  cube-layer target contract.
- [bgfx shadowmaps example](https://github.com/bkaradzic/bgfx/blob/master/examples/16-shadowmaps/shadowmaps.cpp)
  demonstrates an omni alternative using four packed shadow targets and
  tetrahedral projection. That reduces view count but adds projection,
  reconstruction, packing, and filtering complexity; it is rejected for the
  first correctness-focused point-shadow slice.
- [Godot `OmniLight3D`](https://github.com/godotengine/godot/blob/master/scene/3d/light_3d.cpp)
  exposes dual-paraboloid and cube modes and defaults to cube. D6.4 likewise
  chooses cube-face semantics, while deferring the physical cubemap and the
  alternative projection until quality and performance are measured locally.

## Rejected alternatives and follow-up

- **True cubemap now:** rejected because the current common texture and target
  implementations do not correctly create, address, render, transition,
  upload, or read back all six faces on both backends.
- **Six independent sampled textures:** correct but consumes six descriptor
  bindings and complicates diagnostics; one 2D atlas uses the existing target
  path and one binding.
- **Layered/geometry-shader rendering:** rejected because it expands shader and
  common-recorder capabilities before a six-pass correctness baseline exists.
- **Dual paraboloid or tetrahedral packing:** rejected because it introduces
  distortion and custom filtering/reconstruction before the ordinary six-face
  behavior is proven.

After D6.4 lands, profile face draw counts and GPU time. A later stage may move
the same logical `PointCube` job to a real cubemap/cube-array, cached static
shadows, variable resolution, or multiple point jobs. That decision must first
repair and test the generic cube resource contract and compare measured cost
and seam quality against this atlas baseline.

## Acceptance

D6.4 is complete when one authored point light produces omnidirectional
shadows across all six faces on Vulkan and OpenGL, coexists with directional
and spot shadows, fails safely for all unscheduled cases, and supplies useful
depth/visibility captures without exposing atlas or GPU identities to Gameplay,
Asset, Material, or MeshProxy.

Status: complete 2026-09-01. The fixed six-face atlas is the fixed-budget
baseline; the profile hook is ready for a longer warm-runtime sample while
true cube resources, multiple point jobs, and alternative packing remain
separate future design decisions.
