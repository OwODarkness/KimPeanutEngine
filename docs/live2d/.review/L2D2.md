# Review — L2D2 Live2D Asset Integration

**Review date: 2026-09-08.**

**Disposition: P0 findings resolved; P1/P2 findings remain open before
L2D2.4 or L2D4 instance work.**

The generic Asset extension is used correctly, but the current slice collapses
product, runtime-Asset, and offline-import responsibilities. The passing tests
prove the checked-in source-tree path; they do not yet prove a relocatable
native product, safe Cubism instance input, or the documented target boundary.

Related records: [stage plan](../.plan/L2D2.md),
[Live2D architecture](../PLANS.md), [roadmap](../TODO.md),
[V1 spec](../../../.spec/specs/live2d-v1-rendering.md), and
[execution journal](../../../.spec/journal/2026-09-08-live2d-l2d2.md).

## Scope and acceptance basis

This review covers the L2D2 product/payload/loader/importer implementation,
target wiring, module composition, tests, and the handoff to later instance
work. It focuses on risky coupling and ownership. It does not review the
unrelated camera, editor, gameplay, or MCP changes in the working tree.

Acceptance requires:

- runtime loading from native products without reading authored source files;
- an offline importer that is absent from runtime-only composition;
- a product codec independent of `AssetManager` and Runtime globals;
- immutable shared source state and independent mutable instances;
- Cubism compatibility/required-feature rejection before cache publication or
  instance creation;
- one authoritative stage boundary between L2D2, L2D3, and L2D4.

## Findings

### L2D2-F1 — P0: the native root still depends on authored PNG source files

**Status: resolved 2026-09-08.**

The importer now cooks each atlas through the generic native Texture importer,
publishes the content-addressed `.archive/textures/<sha256>.texture` product,
and serializes that canonical native reference. The runtime adapter resolves
the reference relative to the `.live2d` product and declares it as an ordinary
Texture dependency; it no longer consults `GetAssetDirectory()` or authored
PNG paths.

The regression test writes the product and native closure to a temporary
isolated root, then loads the `.live2d` after never copying the authored JSON,
MOC, or PNG files. Native texture verification now accepts any canonical
`.archive` root while retaining the canonical layout and hash checks.

### L2D2-F2 — P0: runtime composition owns the offline importer and the product target hides Runtime dependencies

**Status: resolved 2026-09-08.**

`Live2DProduct` is now a pure codec target with only product DTOs and no Asset,
Config, Cubism, importer, or runtime-global dependency. `Live2DAssetRuntime`
contains the Asset payload adapter and native loader. `Live2DImport` is an
authoring-only target linked to `AssetImport`, while the `Live2D` runtime
aggregate links only `Live2DProduct`, `Live2DAssetRuntime`,
`Live2DRegistration`, and `Live2DRuntime`.

`Live2DModule` no longer owns an importer registry or registers offline
providers during runtime module composition. The unit test links `Live2DImport`
explicitly, demonstrating the authoring boundary.

### L2D2-F3 — P1: arbitrary non-empty MOC bytes pass import and product validation

**Status: open.**

The importer checks only the `.moc3` extension and that the file can be read
(`live2d_import.cpp`, lines 225–237). The product validator checks only that the
MOC blob is non-empty and below one MiB (`live2d_product.cpp`, lines 123–154).
`Live2DImport` has no Cubism validation dependency. There is no MOC consistency
check, supported-version record, required-feature policy, or payload digest,
even though the stage plan marks compatibility validation, integrity checking,
and unsupported-required-feature rejection as importer responsibilities.

This defers untrusted/corrupt input to `CreateInstance`, exactly where L2D2.4
expects a safe immutable handoff. Official Cubism model loading exposes MOC
version and consistency checks; use those during import, record the validated
compatibility/features in the product header, and test arbitrary/truncated/newer
MOC rejection. The product's one-MiB per-field ceiling should also be justified
or replaced with bounded totals because it is unrelated to the 512-MiB file
ceiling and may reject legitimate models.

### L2D2-F4 — P1: `Live2DModelResource` is mutable despite being the shared immutable boundary

**Status: resolved 2026-09-08 as part of the P0 boundary split.**

`Live2DModelResource` now holds a `shared_ptr<const Live2DProductData>` and
exposes only a const product accessor. The Asset payload remains the narrow
runtime adapter, while the codec/importer operate on the separate product DTO;
instance construction can retain the const snapshot without exposing mutable
source vectors through the shared payload.

### L2D2-F5 — P1: the roadmap has two owners for product/import work and puts instance work in two stages

**Status: open.**

The V1 spec and roadmap assign native product, importer, and runtime loader to
L2D3, but the L2D2 plan marks those items landed. Conversely L2D2.4 owns the
instance handoff while the V1 spec assigns the mutable instance model to L2D4.
The TODO still lists unresolved L2D3 product decisions after reporting the
product implementation as landed.

This ambiguity weakens acceptance: a partial source-linked format can be called
complete in L2D2 while the same work remains open in L2D3. Restore the parent
stage split or intentionally merge/delete one stage. The lower-risk split is:
L2D2 owns the generic Asset consumer adapter and type registration; L2D3 owns
the pure product, Cubism-validating importer, native Texture publication, and
runtime loader; L2D4 owns instances and rendering.

### L2D2-F6 — P2: the recorded acceptance evidence is broader than the tests

**Status: open.**

The three Asset tests cover deterministic bytes for one package, lexical `..`
escape, generic JSON non-selection, one successful dependency load/unload, and
one bad-magic product. They do not cover missing Texture rollback, cache
deduplication, stale IDs, unsupported versions/features, invalid MOC,
truncation/bounds across every field, re-read/integrity verification, or
symlink/junction escape. No product is published by the import test, so it
cannot prove transactional root publication.

Keep the existing tests, but move claims for untested behavior back to open
acceptance items and add isolated-root fixtures. Resolve paths with canonical
filesystem identities when the importer must reject junction/symlink escape;
lexical string-prefix checks alone do not establish containment.

## Recommended decoupled design

```text
Live2DProduct
  Live2DProductData + versioned codec only
  -> Core/Data; no Asset, Config, Cubism, importer, or runtime globals

Live2DImport
  model3 source-closure parser + Cubism MOC validator + Texture cooker port
  -> Live2DProduct + AssetImport contract + ImageIO/JSON + Cubism validation
  -> linked only by asset tools/editor authoring composition

Live2DAssetRuntime
  Live2DModelResource : IAssetPayload + native loader + type registration
  -> Live2DProduct + AssetRuntime

Live2DRuntime
  Cubism lifecycle and mutable instances consuming const product snapshots
  -> Live2DProduct + Live2DAssetRuntime + Cubism Core/Framework

Live2DModule
  runtime type registration + Live2DSystem lifecycle only
  -> no importer registry or authoring provider state
```

The product should contain canonical native Texture dependency references,
MOC compatibility/required-feature metadata, layout data needed for instance
creation, and an integrity/source-closure identity. Import publication remains
transactional and root-last. Runtime loading decodes only native bytes and
declares dependency requests; it does not reinterpret source paths or consult
an authoring database.
