# Review — L2D4.4 Packed Masks and Runtime Result

**Review date: 2026-09-11.**

**Disposition: not accepted as an end-to-end rendering stage. The CPU mask
planner and generic two-pass submission are present, and the preview ownership
bug is corrected by configuration-driven native-product selection. The result
is still not composed into the scene view, and the documented cross-backend
readback gate remains open.**

Related records: [stage plan](../.plan/L2D4.4.md),
[Live2D architecture](../PLANS.md), [roadmap](../TODO.md),
[V1 spec](../../../.spec/specs/live2d-v1-rendering.md),
[L2D4.4 journal](../../../.spec/journal/2026-09-11-live2d-l2d4-4.md), and
[concrete-renderer journal](../../../.spec/journal/2026-09-11-live2d-renderer.md).

## Scope and observed failure

This review investigates why launching
`level/live2d_test.level` does not produce a Live2D result attributable to
L2D4.4. It covers the level fixture, module bootstrap, render-extension path,
offscreen output, editor presentation, capture routing, and L2D4.4 acceptance
evidence. It does not implement a fix or review unrelated working-tree changes.

The expected result was a level-driven, visible and capturable Hiyori render.
The actual architecture contains two independent paths:

```text
live2d_test.level (camera only) -> ordinary scene -> scene-color viewport

config/live2d.json -> native `.live2d` AssetManager load -> Live2DRenderer
  -> private offscreen target -> Live2D Viewer or capture view "live2d"
```

There is no level reference that connects the first path to the second, and no
composition pass that places the second path in scene color.

## Findings

### L2D4.4-F1 — P0: the test level contains no Live2D content

**Status: fixed for the current preview boundary.**

`asset/level/live2d_test.level`, lines 1–20, intentionally contains one enabled camera and no
Live2D model, asset reference, component, or render-extension declaration.
Consequently, selecting this fixture does not own or instantiate Hiyori; that
is now selected by `config/live2d.json`. The level remains a cheap camera host,
and this boundary does not claim scene integration.

The module loads the configured native `.live2d` product through AssetManager
and registers the renderer independently of the level. The expected image is
therefore in the dedicated Live2D Viewer or `live2d` capture output, not scene
color.

### L2D4.4-F2 — P0: Live2D renders to a separate target and is never composed into the scene

**Status: intentional current boundary; scene composition remains deferred.**

`live2d_renderer.cpp`, lines 169–188, creates fixed offscreen output and mask
targets, and lines 452–455 expose only the output view. `render_system.cpp`,
lines 332–345, records the extension after ordinary rendering, but has no pass
that samples its output into the scene target. Lines 603–617 expose scene and
extension views through separate accessors.

The only visible consumer is the editor's dedicated `Live2D Viewer` window
(`live2d_editor_viewer_component.cpp`, lines 14–60). Capture also requires the
explicit `live2d` view (`render_system.cpp`, lines 199–208 and 346–358).
Looking at the main viewport or requesting `scene_color` while using the
camera-only fixture therefore cannot show Live2D by construction.

The current owner is the dedicated Live2D Viewer and the named `live2d`
capture view. Later scene integration may introduce a level component and an
explicit composition policy; L2D4.4 does not implicitly claim that boundary.

### L2D4.4-F3 — P1: runtime bootstrap rebuilds an authored source package

**Status: fixed.**

The previous `PrepareHiyoriAsset` path deleted and recreated a temporary
preview root, ran an importer, wrote a temporary `.live2d` product, and
manually registered its dependencies. That helper has been removed.

`Live2DModule` now reads `config/live2d.json` and loads the selected native
product through AssetManager, which resolves its declared texture dependencies.

The preview product is generated offline by `KimPeanutAssetTool
import-live2d`; runtime startup no longer depends on an authored SDK sample
path or writes a process-global temporary directory.

### L2D4.4-F4 — P1: the documented GPU/backend gate is not met

**Status: open.**

The L2D4.4 gate requires planner tests plus OpenGL and Vulkan clipped pixel
readbacks (`L2D4.4.md`, lines 67–85), including an atlas readback and repeated
moving-mask frames. The L2D4.4 journal, lines 49–54, explicitly records that no
shader source, pipeline creation, mask-target creation, viewer scheduling, or
backend pixel readback was added in that stage.

The later concrete-renderer journal reports a successful OpenGL preview but
corrupted Vulkan sampled colors (lines 24–39). That separate preview is useful
investigation evidence, but it does not satisfy L2D4.4's two-backend acceptance
gate. Passing CPU tests prove deterministic planning and generic work shape;
they do not prove mask attachment writes, texture sampling, blending, target
transitions, or final pixels through either RHI backend.

## Root cause

The immediate failure was an ownership and presentation mismatch rather than a
single topology, shader, or mask-planner bug. L2D4.4 produces generic offscreen
work. The requested level contains no Live2D entity, and the preview is owned
by the module configuration and native AssetManager path. Its output is
available only through a separate editor window or the named `live2d` capture
view, not through the level's scene-color result. In parallel, Vulkan sampling
remains a real backend defect, so even the separate preview path is not
cross-backend complete.

## Required correction boundary

1. Keep L2D4.4 described as CPU planning and generic pass emission until its
   documented OpenGL/Vulkan pixel-readback gate passes.
2. Use L2D5 for an explicit viewer command that selects a native `.live2d`
   product, owns presentation, and captures the `live2d` output deterministically.
3. Reserve level-owned Live2D components and scene composition for L2D10 unless
   the roadmap is deliberately revised first.
4. **Done:** runtime source import and the hard-coded Hiyori dependency were
   removed from `Live2DModule`; configuration now feeds the renderer through
   the native Asset boundary.
5. Add backend evidence for nontrivial atlas pixels, ordinary and inverted
   clipped output, repeated frame slots, and both OpenGL and Vulkan. Diagnose
   the known Vulkan sampled-texture corruption before claiming the visual gate.
6. If the current level remains, rename/document it as a camera-only host
   fixture and state that the expected image appears in `Live2D Viewer`, not in
   scene color.

## Reference comparison

The pinned official Cubism Native Samples are applications that explicitly
display model resources and distinguish direct presentation from rendering a
model to a texture. Sakura's pinned `live2d-viewer` likewise provides a
standalone consumer around its Live2D model and renderer. These references
support an explicit viewer/model-selection boundary for current validation;
they do not justify making a camera-only level implicitly own a global model.

Sources inspected: [Cubism Native Samples at `b8024738`](https://github.com/Live2D/CubismNativeSamples/tree/b8024738f108e6003e4925193e8d5ec04cd18196)
and the locally recorded [Sakura study](../PLANS.md#sakura-engine). Direct web
retrieval of Sakura's pinned source file failed with a cache error, so no new
source-level claim beyond the existing local study is made here.

## Validation performed

```powershell
.\tools\kp.ps1 build KimPeanutEngine
build\engine\test\unit\live2d\Debug\Live2DMaskPlannerTest.exe
build\engine\test\unit\live2d\Debug\Live2DRenderPlannerTest.exe
build\Debug\KimPeanutEngine.exe --graphics-api opengl `
  --startup-level level/live2d_test.level --agent-port 37373
```

Results:

- `KimPeanutEngine` build: passed.
- `Live2DMaskAtlasPlannerTest`: 4/4 passed.
- `Live2DRenderPlannerTest`: 3/3 passed.
- OpenGL runtime loaded the configured native product and exported a correct
  Hiyori image from the `live2d` capture view.
- The requested loopback capture could not be completed because no listener
  appeared on `127.0.0.1:37373`; the connection was refused. This is recorded
  as a runtime validation limitation, not as evidence that pixels passed.
- Vulkan runtime/readback was not rerun. The existing concrete-renderer journal
  already records corrupted sampled texture colors, so the cross-backend gate
  remains open.

## Review conclusion

L2D4.4's CPU-side implementation is coherent enough for its focused tests, but
`live2d_test.level` cannot render a level-owned Live2D result because it contains
only a camera. The current preview follows a separate global, hard-coded,
offscreen path whose image is not composed into scene color. The stage must not
be marked visually complete until presentation ownership is made explicit and
the documented OpenGL/Vulkan readback evidence passes.
