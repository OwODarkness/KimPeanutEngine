## Goal

Close V1 acceptance items 9 and 11: prove the representative clipped model
exercises all three blend modes, and either produce an official-reference
capture or record a limitation that states what is unproven.

## Fixture

The current fixture renders correctly on both backends but nothing asserts that
Additive and Multiplicative drawables are present — the counters report draw
count, not blend distribution. Per L2D5.0's fixture decision:

- record the fixture's redistribution basis *before* it is checked in;
- assert blend-mode coverage from the fixture itself, so item 9's claim is
  derived from data rather than from code reading;
- keep the existing licensed package as an environmental prerequisite only, and
  never as a redistributed artifact.

Note that no `.moc3` is synthesizable, so a purely synthetic fixture still needs
a model at run time; the synthetic part is the JSON, expressions, and blend-mode
drawable configuration.

## Cross-backend captures

Capture the representative clipped model on both backends at the frozen L2D4.0
tolerances using `tools/compare_capture_regions.py`, and record every region's
result. Region results already green for non-edge opaque, partial alpha,
transparent background, and filtered edge are re-confirmed rather than assumed,
and the blend-mode regions are added to that set.

## Official reference

Per L2D5.0's reference decision, either:

- build the official sample executable from the pinned SDK's `Samples/` sources
  in an output directory outside both the repository and the SDK tree, use it to
  produce the reference capture, and compare within the frozen tolerances; or
- record item 11 as an **accepted limitation**, stating the reason, that the
  affected claim is "the engine's output matches the official renderer", and
  that the residual risk is an engine-side systematic deviation that
  cross-backend agreement cannot detect because both backends share the engine's
  PMA and blend equations.

Cross-backend agreement is explicitly not a substitute for item 11 and must
never be recorded as satisfying it.

## Tooling

Add a Live2D rule to `tools/kp.ps1` so changes under `engine/module/live2d/` and
`engine/test/unit/live2d/` map to Live2D-focused validation instead of falling
through to a full build.

## Gate

Item 9's blend-mode coverage is asserted from fixture data on both backends, and
item 11 is either satisfied by an official-reference capture inside the frozen
tolerances or recorded as an accepted limitation with a named residual risk.
