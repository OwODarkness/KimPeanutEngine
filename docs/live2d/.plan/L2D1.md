# L2D1 — Cubism SDK Integration

- Status: proposed
- Parent roadmap: [Live2D TODO](../TODO.md#v1--import-and-render-one-live2d-model)
- Architecture: [Live2D Module Plans](../PLANS.md)
- V1 spec: [Live2D V1 rendering](../../../.spec/specs/live2d-v1-rendering.md)

## Objective

Create a license-aware, optional, version-pinned build and process-lifecycle
boundary for Live2D Cubism 5 SDK for Native R5 (`5-r.5`). This stage proves
that KimPeanutEngine can initialize Core/Framework, load and validate minimal
`.moc3` data in a headless test, create two independent model instances, and
shut down repeatedly. Live2D is enabled by default for engine development;
SDK-free builds explicitly disable it.

L2D1 is SDK integration only. It does not add Asset extension, `.model3.json`
import, GPU drawing, a viewer, motion policy, expressions, physics, or TTS.

## Concrete design question

How can one MSVC/Windows engine build consume the proprietary Cubism Core and
source Framework while preserving optional-module isolation, runtime OpenGL/
Vulkan selection, reproducible SDK versions, and deterministic lifecycle?

## Baseline and constraints

- Pin Cubism Native Framework tag `5-r.5` / commit
  `145155d2c5bdd8d23475cef9cc3ab46d3220190c`.
- Require the matching Cubism 5 SDK for Native R5 Core package downloaded by
  the developer; do not fetch or commit it.
- Support the repository's current MSVC x64 configuration first.
- Keep an explicit `KPENGINE_ENABLE_LIVE2D=OFF` path for SDK-free builds; the
  development default is `ON`.
- Do not compile the official OpenGL and Vulkan renderers into the production
  module. The later custom renderer must use the engine RHI.
- Preserve all non-Live2D build configurations and targets.

## Proposed CMake boundary

Add a narrow finder/integration module, for example
`cmake/FindLive2DCubism.cmake`, and the optional
`engine/module/live2d/CMakeLists.txt`.

Configuration inputs:

```cmake
option(KPENGINE_ENABLE_LIVE2D "Build the optional Live2D module" ON)
set(KPENGINE_CUBISM_SDK_ROOT "" CACHE PATH
    "Cubism SDK for Native R5 root containing matching Core and Framework")
```

When explicitly disabled, no Live2D source, include path, binary, runtime copy
step, or test is added. When enabled, configuration must verify:

- `Core/include/Live2DCubismCore.h` exists;
- an MSVC x64 Core import/static library from the R5 package is selected;
- a required runtime DLL is identified when using the dynamic Core variant;
- the Framework checkout/package identifies release `5-r.5`;
- Core and Framework architecture/runtime-library expectations match the
  active target;
- license and redistributable-file documents are discoverable for packaging
  diagnostics.

Expose private imported/build targets such as:

```text
Live2D::CubismCore
Live2D::CubismFrameworkRuntime
```

Only `engine/module/live2d` links these targets. Do not add their include paths
or libraries to `Core`, `RuntimeLib`, `Graphics`, `Render`, `AssetRuntime`, or
the root `EngineLib` unconditionally.

## Framework source strategy

The official Framework CMake selects one concrete renderer implementation.
That does not fit a single KimPeanutEngine executable that selects OpenGL or
Vulkan at runtime. L2D1 should therefore compile an audited Framework runtime
source set containing settings, ID, math, model, motion, physics, effects,
types, utilities, and the backend-neutral renderer base only as needed by
Framework lifecycle.

Do not edit the external SDK in place. Keep the source list/version adapter in
the Live2D integration target, with a test that detects expected source/header
presence when the pinned SDK is upgraded. Any small required adapter that is a
derivative of Framework code must retain the required Live2D license notice.

L2D1 does not call `CubismUserModel::CreateRenderer`. A later
`Live2DModelInstance` owns the Cubism model, while `Live2DRender` owns a custom
engine renderer.

## Lifecycle adapter

Add a module-private lifecycle service with explicit state:

```text
Uninitialized -> Started -> Initialized -> Disposing -> ShutDown
```

Responsibilities:

- own an `ICubismAllocator` adapter using aligned engine/system allocation;
- bridge Cubism/Core log messages into the engine Log category without
  throwing across the C callback;
- call `CubismFramework::StartUp` then `Initialize` exactly once;
- expose Core/Framework version diagnostics and the latest supported MOC
  version;
- count or otherwise prove that no model instances remain at shutdown;
- call `Dispose` then `CleanUp` in the documented order;
- make repeated initialize/shutdown calls deterministic and diagnostic rather
  than relying on static destruction order.

The service initially runs on the caller/runtime thread. It must not initialize
from a global constructor. Threaded instance evaluation is a later design.

## Headless proof

Use a legally approved minimal `.moc3` test fixture or an externally supplied
SDK sample path. The focused test should:

1. initialize the lifecycle adapter;
2. report and validate the selected Core version/MOC compatibility;
3. create an immutable byte owner for the fixture;
4. create two Cubism model instances from the same immutable definition;
5. change one instance parameter and update it;
6. prove the other instance's parameter/drawable state did not change;
7. destroy both instances;
8. dispose/clean up;
9. repeat the complete cycle in the same process.

If licensing prevents committing a `.moc3`, keep the binary-dependent test
explicitly skipped with a precise reason and provide a developer command that
points to a local SDK sample. Lifecycle tests that need no model still run in
CI when the optional SDK is present.

## Failure behavior

- Missing SDK while disabled: success; Live2D targets do not exist.
- Missing SDK while enabled: configure failure naming the missing component.
- Framework/Core version mismatch: configure or initialization failure before
  model creation.
- Unsupported/corrupt MOC: stable failure result; no partially live instance.
- Allocation failure: failure result and cleanup of already-created state.
- Shutdown with live instances: hard diagnostic and refused/ordered shutdown;
  never free Framework globals underneath live models.
- Repeated initialization: idempotent success only when configuration matches;
  conflicting configuration is rejected.

## Implementation sequence

1. Record/download instructions and the exact R5 package layout accepted by the
   finder without adding proprietary files to Git.
2. Add the opt-in CMake finder and private imported Core target.
3. Add the pinned Framework runtime target and source-presence/version guards.
4. Add allocator and no-throw log adapters.
5. Add the explicit lifecycle service and version diagnostics.
6. Add headless lifecycle/instance-isolation tests and optional local-fixture
   configuration.
7. Verify an ordinary non-Live2D configure/build remains unchanged.
8. Record results and licensing/fixture limitations in a new V1 journal.

## Acceptance criteria

- [ ] Explicitly disabling Live2D allows configuration on a machine with no
  Cubism SDK.
- [ ] Enabling Live2D with no or incomplete SDK fails early and precisely.
- [ ] The selected Framework revision and downloaded Core are both R5 and their
  versions appear in diagnostics.
- [ ] Cubism headers/libraries are private to Live2D targets.
- [ ] No official OpenGL/Vulkan renderer or native graphics type enters a
  common engine target.
- [ ] Framework initialization and shutdown are explicit and repeatable.
- [ ] Allocator alignment and log callback behavior have focused tests.
- [ ] Two model instances created from one definition have independent mutable
  state.
- [ ] Corrupt/unsupported model data fails without leaks or partial instances.
- [ ] Runtime DLL staging, if required, is bounded to Live2D executables/tests.
- [ ] License files, Core redistribution constraints, and the fixture license
  are recorded before any binary/model is committed or packaged.

## Validation plan

This stage changes CMake target boundaries and adds optional native binary
integration, so it requires configuration/build evidence beyond documentation:

```powershell
# Default/no-SDK path
cmake -S . -B build-live2d-off -G "Visual Studio 17 2022" -DKPENGINE_ENABLE_LIVE2D=OFF
cmake --build build-live2d-off --config Debug --target KimPeanutEngine

# Enabled path, using an approved local R5 package
cmake -S . -B build-live2d -G "Visual Studio 17 2022" -DKPENGINE_ENABLE_LIVE2D=ON -DKPENGINE_CUBISM_SDK_ROOT=<absolute-r5-sdk-path>
cmake --build build-live2d --config Debug --target Live2DCoreTest
ctest --test-dir build-live2d -C Debug -R Live2DCore
```

Also run `git diff --check` and inspect the enabled and disabled target graphs
for accidental public Cubism dependencies. Do not run two MSBuild/CMake builds
concurrently.

## Remaining uncertainty

- The exact downloaded R5 Windows Core file layout and dynamic/static runtime
  choice must be verified from the user's SDK package; proprietary binaries are
  intentionally absent from the public repositories inspected for this plan.
- The precise Framework source subset may require one local adapter for an
  otherwise unresolved renderer factory symbol. Resolve this by inspecting the
  pinned build/link result; do not fall back to compiling both native renderers.
- A redistributable automated `.moc3` fixture has not yet been approved.
