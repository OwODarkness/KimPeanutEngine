# L2D4.3 — Generic Submission and Unmasked Live2D Planning

- Status: landed (2026-09-10) — [journal](../../.spec/journal/2026-09-10-live2d-l2d4-3.md)
- Parent: [L2D4 — Live2D Planning and Generic Render Submission](L2D4.md)
- Depends on: [L2D4.1](L2D4.1.md), [L2D4.2](L2D4.2.md)

## Goal

Create a narrow generic Render submission/execution seam, then make Live2D
compile its unmasked semantic plan into that seam. Generic Render must execute
the work without knowing why a draw exists.

## Boundary

```text
Live2DModelInstance
  -> Live2DStaticModelData + Live2DFrameSnapshot
  -> Live2DRenderPlanner
  -> Live2DRenderSubmission { render::RenderSubmission work, diagnostics }

render::RenderSubmission
  -> RenderSubmissionExecutor
  -> FrameContext + graphics::CommandRecorder
  -> Graphics backend
```

`Live2DRenderPlanner` owns semantic interpretation: visibility, stable render
order, opacity, color modifiers, blend/cull pipeline selection, texture choice,
and drawable ranges. The GPU owns texture sampling, color equations, PMA output,
and fixed-function blending.

`RenderSubmissionExecutor` owns generic frame preparation and command recording.
It does not include Live2D headers, inspect source type, sort draws, select a
blend mode, calculate masks, or create a second frame lifecycle.

## Generic Render submission contract

Add value types under `engine/runtime/render/`, with names equivalent to:

```cpp
struct SubmissionBufferWrite
{
    graphics::BufferHandle destination;
    std::size_t offset = 0;
    std::vector<std::byte> bytes;
};

struct SubmissionUniformData
{
    std::uint32_t set = 0;
    std::uint32_t binding = 0;
    std::vector<std::byte> bytes;
};

struct SubmissionSampledTexture
{
    std::uint32_t set = 0;
    std::uint32_t binding = 0;
    graphics::TextureHandle texture;
    graphics::SamplerHandle sampler;
};

struct SubmissionDraw
{
    graphics::PipelineHandle pipeline;
    graphics::GeometryView geometry;
    std::vector<SubmissionUniformData> uniforms;
    std::vector<SubmissionSampledTexture> textures;
    graphics::Viewport viewport;
    std::optional<graphics::Scissor> scissor;
    std::uint32_t index_count = 0;
    std::uint32_t first_index = 0;
    std::int32_t vertex_offset = 0;
};

struct SubmissionPass
{
    graphics::RenderTargetHandle target;
    std::vector<SubmissionDraw> draws;
};

struct RenderSubmission
{
    std::vector<SubmissionBufferWrite> buffer_writes;
    std::vector<SubmissionPass> passes;
};
```

The final names may follow local conventions, but these semantics are fixed:

- the submission owns all CPU byte storage until execution returns;
- GPU handles are borrowed and their owners outlive execution;
- pass and draw vector order is authoritative and preserved exactly;
- target clear/load policy remains part of its Render-owned target description;
- pipeline handles already encode shaders, vertex layout, blend, culling,
  attachment compatibility, and descriptor layout;
- uniform bytes are logical bindings; the executor allocates frame-local ranges
  and converts them into ordinary `ResourceBindingSetDesc` values;
- sampled textures are ordinary common handles; there is no Live2D binding type;
- V1 permits indexed, non-instanced draws only. General indirect/compute work is
  not added speculatively.

This contract is intentionally smaller than a render graph. It contains an
already ordered list and makes no dependency, aliasing, synchronization, or
scheduling inference. It is also a value protocol rather than an abstract
producer hierarchy; L2D4 does not add registration or source dispatch to
`RenderSystem`.

Expected files are `render_submission.h/.cpp` for values/validation and
`render_submission_executor.h/.cpp` for frame preparation/recording. They
remain part of the existing Render target; L2D4 does not create a parallel
renderer library or a new `RenderSystem` facade.

## Executor algorithm

`RenderSubmissionExecutor::Execute` receives a const submission, the active
`FrameContext`, and the current `CommandRecorder`.

It performs three phases:

1. **Structural validation before mutation**
   - validate buffer-write handles, non-empty byte ranges, and offset/size
     arithmetic without mutating Graphics state;
   - validate target, pipeline, geometry, index range, viewport/scissor, and
     unique `(set, binding)` entries;
   - reject empty uniform byte ranges, default-invalid handles, duplicate
     bindings, and arithmetic overflow. Pipeline descriptions are created for
     their target formats by the producer; the RHI still performs the final
     handle/target compatibility check when binding.
2. **Frame preparation before the first pass**
   - allocate every uniform through `FrameContext::AllocateUniform`;
   - copy bytes and construct every frame-local resource binding set;
   - if any allocation/binding fails, return without beginning a target or
     writing a per-frame geometry buffer.
3. **Execution in authored order**
   - apply all buffer writes before beginning a target; the RHI performs the
     final role, capacity, and current-frame validation;
   - for each pass, begin its target, then record each draw's viewport/scissor,
     pipeline, geometry, bindings, and indexed arguments in vector order;
   - end every begun target on both success and fail-soft command rejection;
     reject the frame result if the common recorder reports a failure.

The executor returns a structured generic result with diagnostic and counts for
passes, draws, upload bytes, uniform bytes, and binding allocations. It never
logs or reports a Live2D drawable/context ID.

## Live2D resource ownership

Introduce module-owned, move-only:

- `Live2DRenderResourceSet` — processed shader pipelines and common sampler;
- `Live2DRenderProxy` — immutable UV/index buffers, per-frame position buffer,
  ordered Texture handles, output target, and immutable drawable ranges;
- `Live2DRenderPlanner` — stateless/borrowed semantic compiler;
- `Live2DRenderSubmission` — generic work plus Live2D feature report, counters,
  topology revision, and frame sequence.

Resource-set initialization and proxy creation use only common Render/Graphics
descriptions and are independently transactional. They may request GPU objects
through the API-neutral resource boundary, but neither the planner nor proxy
records commands. A creation failure destroys all earlier handles; proxies die
before the shared resource set after an existing safe idle point.

## Unmasked planning

For one validated snapshot, the planner:

1. checks topology revision, frame sequence, counts, ranges, and finite values;
2. copies all current position bytes into one generic buffer-write command;
3. stable-sorts drawable indices by `(render_order, drawable_index)`;
4. skips invisible, zero-opacity, and zero-index drawables;
5. selects the already-created normal/add/multiply and cull/no-cull pipeline;
6. emits model/multiply/screen/opacity/transform constants and the selected
   sampled Texture binding;
7. emits one generic model pass targeting the proxy output.

The planner returns no partial submission. All semantic validation completes in
temporary storage before `work` is published.

## Tests

### Generic Render tests

Use an ordinary `FrameContext` over a fake backend/recorder to verify:

- exact preservation of pass/draw order;
- buffer writes occur after full preparation and before the first pass;
- uniform bytes become aligned frame-local bindings;
- texture bindings, viewport/scissor, geometry, and indexed arguments are
  forwarded unchanged;
- invalid handles/ranges/duplicates and injected uniform/binding exhaustion
  record zero passes;
- a failure after a target begins still closes that target;
- generic test fixtures and production Render source contain no Live2D type or
  include.

### Live2D planning tests

Build a CPU oracle from synthetic snapshots and compare the generic work for
order, skip rules, buffer bytes, ranges, Texture selection, pipeline choice, and
constant values. Cover mismatch/NaN/invalid-range failures and injected proxy
resource-creation failures.

Run a small unmasked submission through the executor on both native backends.
Readback covers transparent background, overlapping order, partial opacity,
three blend modes, multiply/screen color, culling, base vertex, and more than
two frame-slot cycles with changed positions.

## Gate

Generic Render contract tests, Live2D planner tests, `GraphicsContractTest`, and
both backend readbacks pass. Render/Graphics contain no Live2D dependency or
semantic branch. Live2D planning contains no `CommandRecorder` call. Mask work
does not begin until the unmasked generic path is independently correct.
