# L2D4 — Live2D Planning and Generic Render Submission

- Status: active; L2D4.0 landed, L2D4.1–L2D4.5 planned
- Parent roadmap: [Live2D Module Roadmap](../TODO.md)
- Module architecture: [Live2D Module Plans](../PLANS.md)
- V1 specification: [Live2D V1 Rendering](../../../.spec/specs/live2d-v1-rendering.md)

## Outcome

Convert the current state of one `Live2DModelInstance` into a backend-neutral
submission, then execute that submission through generic Render and the common
Graphics API into an engine-owned offscreen color target on OpenGL and Vulkan.
L2D4 owns the reusable runtime/render foundation; window creation,
presentation, command-line UX, capture integration, and final official-image
comparison remain L2D5.

This stage is deliberately split because it crosses three lifetime domains:

```text
Cubism owner thread        Live2D render planning       Generic Render       Graphics/RHI
mutable model instance  -> Live2DRenderSubmission  ->  RenderSubmission  -> GPU commands
SDK semantics stay here    generic work nested inside   no Cubism concepts    native execution
```

The stage is complete only when unmasked and clipped representative draws work
on both backends, all negative paths diagnose rather than approximate, and GPU
resources survive update, resize, and shutdown tests without in-flight reuse.

## Design question

What is the smallest generic submission and Graphics contract that lets Live2D
calculate its deformed geometry, draw order, blend selection, and mask plan,
while generic Render sees only resources, pipeline state, and draw commands and
Graphics remains the only native execution owner?

The answer is an immutable Live2D frame snapshot, a module-owned semantic
planner, a value-only generic `render::RenderSubmission`, and a generic
`RenderSubmissionExecutor` over `FrameContext` and `CommandRecorder`. It is not
a Live2D-specific RHI entry point, a `RenderSystem` Live2D branch, or either
official native renderer hidden behind an interface.

## Scope

In scope:

- immutable, SDK-free static topology and per-frame drawable snapshots;
- ordered Texture payload retention for the lifetime of an instance/proxy;
- common immutable/per-frame Vertex and Index buffer descriptions;
- backend-internal frame-slot storage for per-frame buffers;
- explicit multi-stream vertex and typed index-buffer binding;
- generic buffer-upload, pass, binding, constant-data, and indexed-draw
  submission values plus one generic executor;
- model transform, visibility, opacity, multiply/screen colors, culling, and
  normal/additive/multiplicative blend modes;
- packed RGBA mask-atlas rendering with normal and inverted clipping;
- API-neutral shaders, pipelines, bindings, and offscreen targets;
- common, backend, CPU-reference, and Live2D integration tests.

Out of scope:

- a viewer window, swapchain presentation, screenshot command, or Editor panel;
- motions, expressions, physics, pose, eye blink, gaze, lip sync, or policy;
- Cubism 5.3 offscreen/blend groups or high-precision mask mode;
- render-graph integration, shared cross-model atlases, bindless batching,
  hot reload, async proxy creation, or topology-changing MOC reload;
- replacing the existing static `MeshHandle` path;
- registering Live2D-specific passes or semantic types in `RenderSystem`;
- a generic render graph, arbitrary resource dependency compiler, or plugin
  scheduler; L2D4 submits an already ordered pass list.

## Frozen decisions

### 1. Snapshot boundary

`Live2DModelInstance` remains the sole owner of `CubismMoc` and `CubismModel`.
After parameter changes and `Update()`, its owner calls an extraction method
that copies current state into SDK-free values:

```cpp
struct Live2DStaticModelData;
struct Live2DFrameSnapshot;

bool BuildStaticModelData(Live2DStaticModelData& out,
                          std::string& diagnostic) const;
bool BuildFrameSnapshot(Live2DFrameSnapshot& out,
                        std::string& diagnostic) const;
```

`Live2DStaticModelData` contains canvas metrics, concatenated UVs and indices,
per-drawable ranges, texture indices, mask-source sets, and maximum position
bytes. `Live2DFrameSnapshot` contains concatenated current positions and the
current visibility, render order, opacity, culling, blend mode, inverted-mask,
multiply-color, and screen-color values. Neither type contains an SDK pointer,
view, allocator, GPU handle, or `AssetManager` pointer.

Extraction and `Update()` run on the instance-owner thread and may not overlap.
Rendering consumes a complete snapshot by const reference and never calls
Cubism. Static and frame data carry the same immutable `topology_revision`;
each successful frame extraction also increments `frame_sequence`. The renderer
rejects topology mismatches and can diagnose repeated/out-of-order snapshots.
Asynchronous queues and interpolation are later work.

### 2. Texture dependency lifetime

`Live2DSystem::CreateInstance` resolves every ordered dependency with
`AssetManager::ResolveDependency`, obtains its `TextureResource`, and stores a
`shared_ptr<const TextureResource>` in texture-index order. The instance may
therefore outlive the Asset wrapper without retaining a raw `Asset*` or adding
a new Asset reference-counting policy. Proxy creation copies those shared
payload references long enough to upload textures; Asset remains unaware of
Live2D and Graphics.

A missing dependency, wrong type, count mismatch, invalid Texture payload, or
out-of-range drawable texture index fails instance/proxy creation before the
first GPU object is published.

### 3. Common buffer contract

Add one general buffer description alongside the existing convenience
functions:

```cpp
enum class BufferRole { Vertex, Index };
enum class BufferUpdateMode { Immutable, PerFrame };
enum class IndexElementType { UInt16, UInt32 };

struct BufferDesc {
    BufferRole role;
    BufferUpdateMode update_mode;
    std::size_t capacity_bytes;
};

BufferHandle CreateBuffer(const BufferDesc& desc,
                          const void* initial_data,
                          std::size_t initial_size);
bool WriteFrameBuffer(BufferHandle buffer, std::size_t offset,
                      const void* data, std::size_t size);
```

An immutable buffer cannot be updated. A per-frame buffer owns one native
storage allocation per backend frame slot behind one common handle.
`WriteFrameBuffer` is valid only between `BeginFrame()` and `EndFrame()`, writes
the current slot, rejects overflow, and cannot overwrite storage whose fence
has not completed. Existing `CreateVertexBuffer`/`CreateIndexBuffer` remain
source-compatible wrappers; existing static meshes are not migrated in L2D4.

The recorder gains an explicit geometry view:

```cpp
struct VertexBufferView { uint32_t binding; BufferHandle buffer; size_t offset; };
struct IndexBufferView  { BufferHandle buffer; size_t offset; IndexElementType type; };
struct GeometryView     { std::vector<VertexBufferView> vertices; IndexBufferView indices; };

bool BindGeometry(const GeometryView& geometry);
bool BindPipeline(PipelineHandle pipeline);
bool BindResourceBindings(PipelineHandle pipeline,
                          DescriptorSetHandle bindings,
                          const DynamicUniformOffsets& offsets = {});
```

Vertex stride and attributes remain properties of `PipelineDesc`. The view
supplies buffers and byte offsets only. `DrawIndexed` retains its element-based
`first_index` and signed `vertex_offset`; both backends must honor both values.
The existing bind operations return success so a generic executor can close a
target and invalidate the frame after a rejected pipeline or resource binding;
existing callers may ignore the return. `BindMesh` remains intact and may later
delegate to the same backend machinery.

### 4. Resource, planning, and execution ownership

One `Live2DRenderResourceSet` owns common pipeline handles baked for the active
backend and the common sampler. One `Live2DRenderProxy` owns:

- one immutable UV buffer and one immutable UInt16 index buffer;
- one per-frame position buffer sized for all drawables;
- Texture handles in Cubism texture-index order;
- the mask render target when the model uses clipping;
- its sampled output color target;
- immutable drawable ranges and mask-plan data;
- no `CubismModel`, `AssetID`, file path, or mutable behavior state.

`Live2DRenderPlanner` borrows the resource set and proxy, consumes the static
model data plus one frame snapshot, and produces:

```cpp
struct Live2DRenderSubmission
{
    render::RenderSubmission work;
    Live2DRenderFeatureReport features;
    Live2DRenderCounters counters;
    std::uint64_t topology_revision = 0;
    std::uint64_t frame_sequence = 0;
};
```

Only Live2D interprets drawable, mask-context, blend-mode, and color-modifier
semantics. `work` contains already selected pipeline handles, geometry views,
sampled textures, constant bytes, ordered targets/passes, and indexed draw
arguments. `RenderSubmissionExecutor` receives only `work`; it validates and
materializes frame-local uniforms/bindings, records common commands, and never
includes or switches on a Live2D type.

The extension seam is this value protocol, not a virtual
`IRenderSubmissionProducer` registry. L2D4 has one concrete producer and one
concrete consumer; source registration and scheduling remain deferred until a
second engine integration consumer proves that abstraction necessary.

Positions, UVs, and indices use separate bindings. Indices remain local to each
drawable; `first_index` selects its static index range and `vertex_offset`
selects its concatenated vertex range. This makes the existing OpenGL omission
of base-vertex behavior a contract bug that L2D4.1 must fix and test.

Resource-set initialization and proxy creation are separate transactions:
temporary handles are destroyed on failure and neither owner becomes visible
until its complete resource closure validates. L2D4 uses fixed capacities
derived from static model data, so no buffer grows mid-frame. Proxies are
destroyed before their resource set. Both operations occur outside an active
frame after `RenderBackend::WaitIdle`; deferred arbitrary-time destruction is
not introduced in this stage.

### 5. Draw contract

Each frame follows this exact order:

1. caller mutates parameters and calls `Live2DModelInstance::Update()`;
2. caller builds one complete `Live2DFrameSnapshot`;
3. `Live2DRenderPlanner` validates the complete frame, calculates active mask
   layout/bindings and stable drawable order, selects pipelines, and emits one
   `Live2DRenderSubmission` containing generic ordered work;
4. `BeginFrame()` selects a backend frame slot and activates `FrameContext`;
5. `RenderSubmissionExecutor` validates the complete generic submission,
   allocates all required frame-local uniforms/bindings, then applies the
   position-buffer upload;
6. the executor records the already ordered mask pass, when present, followed
   by the model pass;
7. the caller ends the frame and Graphics submits it.

Live2D, not generic Render, stable-sorts equal render-order values by drawable
index. Invalid render orders, non-finite positions/colors, or range overflow
prevent submission publication. A failed frame-buffer write or unexpected
recording rejection invalidates the output for that frame and returns a
diagnostic; the executor closes any active target and the caller must not
present the partial result.

Render performs two validation phases. Structural validation occurs before any
frame-local allocation or command recording. Preparation allocates every
uniform and binding before the first render target begins. If either phase
fails, no pass is recorded. The executor does not reinterpret pipeline state,
sort draws, calculate masks, or evaluate per-pixel equations.

The color target is transparent `RGBA8_SRGB`. Atlas storage is linear
`RGBA8_UNORM`. Source textures remain color/sRGB assets; shader math occurs in
linear space and outputs premultiplied color. Exact model blend equations and
the official reference tolerance are frozen in L2D4.0 before shader code lands.

### 6. Mask contract

V1 uses the official packed-mask shape: equivalent mask-source sets share one
context; active contexts are assigned deterministically across RGBA channels
and rectangular subdivisions of a fixed atlas. The atlas is cleared to one,
mask sources reduce the selected channel, and the model pass samples that
channel using a per-context draw matrix. A 5% model-space margin is included in
the bounds calculation, matching the official Framework algorithm.

Mask planning and matrix generation are module-owned, CPU-only functions with
golden numeric tests. The planner emits an ordinary first render pass targeting
the atlas and an ordinary second pass targeting the color output. Generic
Render sees target handles, clear policy, viewports/scissors, pipeline/resource
bindings, and draws; it never sees a mask context or mask polarity. The GPU
shaders still perform texture sampling, multiply/screen color, mask sampling,
premultiplied output, and fixed-function blending. The implementation may reuse
backend-neutral Framework math, but no official OpenGL/Vulkan renderer source
or native object enters `Live2DRender`.

One atlas supports the official packed capacity selected in L2D4.0. A model
that exceeds it fails proxy creation with its active-context count. Multiple
atlases and high-precision masks are later extensions, not silent fallbacks.

### 7. Unsupported Cubism features

Before GPU creation, static extraction rejects:

- Cubism 5.3 offscreen/blend groups (`IsBlendModeEnabled()` or non-zero
  offscreen objects);
- topology/count changes after proxy creation;
- invalid texture indices or unsupported drawable blend values;
- mask plans beyond the frozen V1 atlas capacity.

The native product feature bits continue to reject unknown required imported
features. L2D4 adds runtime Core inspection because `.moc3` capability cannot
be trusted to source JSON metadata alone. The diagnostic names the feature and
the L2D4 limitation.

## Target and file ownership

Planned target boundary:

```text
Live2DRuntime              -> AssetRuntime + Cubism model evaluation
Render submission seam     -> value contract + executor over common Graphics
Live2DRender               -> Live2DRuntime + Render submission seam
Live2D                     -> aggregate Live2DRuntime + Live2DRender + registrations
```

Expected implementation areas:

- `engine/runtime/graphics/backend/common/` — buffer/view descriptions and
  validation;
- `engine/runtime/graphics/backend/opengl/` and `backend/vulkan/` — native
  storage, current-slot writes, explicit geometry binding, base vertex;
- `engine/runtime/render/` — generic submission values, structural validation,
  frame preparation, and execution; no Live2D dependency or semantic enum;
- `engine/module/live2d/runtime/` — extraction and retained Texture payloads;
- `engine/module/live2d/render/` — resource set, proxy, semantic planner,
  Live2D submission wrapper, mask planner, and shaders;
- `engine/test/unit/graphics/` and `engine/test/unit/live2d/` — contracts and
  CPU behavior;
- the existing graphics smoke harness — backend execution evidence.

`Live2DRender` may consume `data::ShaderData`/`data::TextureData`, generic Render
submission values, and common Graphics descriptions. It must not load files,
import assets, depend on Editor, include backend headers, or record through
`CommandRecorder` itself. Shader compilation stays in the existing Resource
pipeline; Graphics only bakes supplied shader data.

The generic executor is a focused Render collaborator, not a new permanent
home for every renderer. L2D4 does not add a Live2D entry to the closed deferred
pass sequence or a general submission-source registry. The standalone L2D5
composition calls the executor explicitly. Later main-engine integration may
add a generic scheduling/registration seam only when that consumer exists.

## Acceptance criteria

- [ ] Public Live2D snapshot/render headers contain no Cubism, OpenGL, Vulkan,
  `Asset*`, or source-file types.
- [ ] Two instances from one asset retain ordered Texture payloads and produce
  isolated current positions/parameters.
- [ ] Per-frame buffers select storage by the backend's current frame slot and
  reject writes outside a frame, immutable writes, and range overflow.
- [ ] Explicit geometry binding supports two vertex streams, UInt16 indices,
  `first_index`, and non-zero `vertex_offset` on OpenGL and Vulkan.
- [ ] `render::RenderSubmission` contains only generic uploads, passes,
  geometry, pipelines, bindings/constants, state, and draw arguments; Render
  source contains no Live2D name, include, or semantic branch.
- [ ] `Live2DRenderPlanner` is the only owner of Cubism drawable order, blend,
  color, culling, and mask-context interpretation; it emits a fully ordered
  generic submission without calling `CommandRecorder`.
- [ ] `RenderSubmissionExecutor` validates and prepares the whole submission
  before beginning a target, then records it without sorting or semantic policy.
- [ ] Proxy construction and every failure path leave no live GPU handles.
- [ ] Unmasked rendering covers stable order, visibility, opacity,
  multiply/screen colors, culling, and all three blend modes.
- [ ] Packed clipping covers shared masks, multiple channels/regions, inverted
  masks, transparent edges, and an over-capacity diagnostic.
- [ ] Offscreen/blend-group models fail before GPU publication with a precise
  unsupported-feature diagnostic.
- [ ] Repeated update/render, resize-triggered target replacement, and shutdown
  complete without stale-frame reuse or Graphics validation errors.
- [ ] OpenGL and Vulkan images agree with the CPU/reference cases within the
  tolerance frozen in L2D4.0.

contract, both backends, target wiring, runtime rendering, and GPU lifetime.
Compilation alone cannot close L2D4.

## Reference findings

- The pinned official Framework renderer builds a clipping context per unique
  mask set, calculates the total clipped bounds, applies a 5% margin, clears
  mask storage to one, then draws model objects in render-order sequence. It
  also forces high-precision masks when Cubism offscreen blend mode is enabled.
  KimPeanutEngine adopts the observable algorithm, not the native renderer or
  its global API state.
- The official OpenGL and Vulkan implementations are conformance sources but
  own incompatible native buffers, descriptors, render targets, and state.
  Wrapping them would bypass common RHI ownership.
- Sakura separates CPU model resources from a GPU render model and updates
  current drawable geometry before mask/model effects. That ownership split
  applies; Sakura's render graph, ECS, async VRAM stack, and batching do not.
- bgfx distinguishes static, dynamic, and frame-transient geometry and keeps
  transient lifetime tied to frame consumption. That supports frame-slot
  storage hidden behind a common handle instead of per-frame resource churn.
- KimPeanutEngine already uses value-only section/draw packets and keeps
  `FrameContext` allocation separate from `CommandRecorder` execution. The
  generic submission follows that local pattern, but does not force Live2D into
  `MeshProxy`, the deferred material system, or the fixed scene-pass schedule.

The reference audit therefore changes the execution boundary, not the frozen
Cubism equations: official Cubism remains the semantic oracle, Sakura supports
module-owned render planning/resources, bgfx supports frame-consumed geometry,
and KimPeanutEngine's local packet/`FrameContext` pattern supplies the generic
execution seam.

## Stop conditions

Stop and revise this plan rather than expanding scope when:

- the selected fixture requires offscreen/blend groups or more mask contexts
  than V1 supports;
- correct rendering requires a native API type above Graphics;
- generic Render needs a Live2D include, enum, dynamic cast, or pass switch;
- the submission executor starts sorting draws or calculating mask/color policy;
- per-frame buffer safety cannot be proven with existing `BeginFrame` fence
  semantics;
- Texture alpha/color-space behavior cannot match one official R5 capture;
- proxy destruction would require immediate release of in-flight resources;
- L2D5 would need to reach into a backend to present or capture the result.
