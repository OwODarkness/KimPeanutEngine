# L2D5.0 — Evidence Contract Freeze

- Status: complete (2026-09-12) — [journal](../../../.spec/journal/2026-09-12-live2d-l2d5-0.md)
- Parent: [L2D5 — V1 Evidence Completion and Viewer Closeout](L2D5.md)
- Depends on: L2D4 acceptance evidence.

## Goal

Freeze the capture-view, resize, shutdown-accounting, fixture, and
official-reference decisions before L2D5 changes a Render contract, a launch
surface, or a checked-in asset. No production code.

## Why this stage exists

Three of the four L2D5 subtasks change a contract that later evidence depends
on. L2D5.1 renames a value in Render's public capture enum; L2D5.2 adds a launch
option and needs a place for an assertion to live; L2D5.3 decides what asset may
be redistributed. Each is cheap to decide now and expensive to revisit after
captures and tests reference the old shape.

## Investigation inputs already gathered

These were established while scoping the stage and do not need re-deriving.

**Capture view.** `CaptureView` mixes deferred views with host-resolved ones.
[`render_capture_service.h:27`](../../../engine/runtime/render/render_capture_service.h#L27)
declares `Live2D`;
[`deferred_renderer.cpp:613`](../../../engine/runtime/render/deferred_renderer.cpp#L613)
excludes it by name when deciding whether a capture is deferred;
[`render_capture_service.cpp:29`](../../../engine/runtime/render/render_capture_service.cpp#L29)
whitelists it. Production is
[`live2d_viewer_host.cpp:185`](../../../engine/module/live2d/live2d_viewer_host.cpp#L185)
(resolver) and `:206` (startup request); the module never appears in Scene3D.
The string `"live2d"` maps to it at
[`screenshot_command_provider.cpp:73`](../../../engine/runtime/screenshot/screenshot_command_provider.cpp#L73),
and Render already special-cases non-debug views at
[`render_system.cpp:582`](../../../engine/runtime/render/render_system.cpp#L582).

**Resize.** The viewer window is fixed at 720×960
([`live2d_viewer_host.cpp:89-92`](../../../engine/module/live2d/live2d_viewer_host.cpp#L89-L92));
`ResizeOutput` is called every frame from the backend extent (`:292`, `:301`) so
the path runs but never sees a change. There is no launch option for a size or a
resize, no resize command, and `--agent-port` is refused in viewer mode
([`launch_options.cpp:261-264`](../../../engine/runtime/launch_options.cpp#L261-L264)).
A programmatic resize precedent exists at
[`rhi_example.cpp:734`](../../../engine/example/graphics/rhi_example.cpp#L734).
`Live2DRenderer::ResizeOutput` needs only a non-null backend, obtains that
backend from `Initialize`, and is transactional by construction
([`live2d_renderer.cpp:217+`](../../../engine/module/live2d/render/live2d_renderer.cpp#L217)).
A `FakeBackend final : public graphics::RenderBackend` already exists at
[`render_system_test.cpp:130`](../../../engine/test/unit/render/render_system_test.cpp#L130).

**Shutdown accounting.** Two counters exist and neither is asserted anywhere:
`Live2DRenderer::GetLiveGpuHandleCount()`
([`live2d_renderer.cpp:557-577`](../../../engine/module/live2d/render/live2d_renderer.cpp#L557-L577)),
observed only by a warning in `Live2DViewerHost::CleanupGpu()` (`:542-561`) and
an ImGui profiler line (UI-only, invisible headless); and
`CubismLifecycle::LiveModelInstanceCount()`
([`live2d_cubism_lifecycle.cpp:304-307`](../../../engine/module/live2d/runtime/live2d_cubism_lifecycle.cpp#L304-L307)),
which *is* asserted in `Live2DCoreTest` for the SDK path. There is no Vulkan
validation-error counter — the debug-utils callback logs and returns
([`vulkan_device.cpp:37-55`](../../../engine/runtime/graphics/backend/vulkan/vulkan_device.cpp#L37-L55)),
so "no validation errors" can only ever be a log observation.

**Fixture and reference.** The pinned SDK at `D:/library/CubismSdkForNative-5-r.5`
ships sample *sources* (`Samples/OpenGL`, `Samples/Vulkan`, `Samples/D3D11`, …,
each with `Demo/proj.win.cmake/` and `proj_msvc20*.bat` under `scripts/`) and
`Samples/Resources/` with eight official models (Haru, Hiyori, Mao, Mark,
Natori, Ren, Rice, Wanko). No `.exe`, no build output, and no `.sln` exist
anywhere on the machine, and `Samples/Resources/` contains no per-model license
or readme file. The repository's own `asset/live2d/hiyori_pro` is a separate,
separately licensed package. `tools/compare_capture_regions.py` is the frozen
cross-backend comparator and requires equal dimensions.

## Decisions to freeze

Each decision below names its recommendation. Confirm or overrule before
L2D5.1 starts.

1. **Generic host capture view.** Rename `CaptureView::Live2D` to a
   role-named value for "the standalone host's own output target, resolved by
   the host's capture-target resolver." Recommended name: `HostOutput`. Do not
   add a host-view registry; a second host does not exist, so a registry would
   be an abstraction with no consumer.
2. **Deferred predicate.** Replace the negative test at
   `deferred_renderer.cpp:611-614` with a positive predicate over the views the
   deferred renderer converts — the ten diagnostic views only, **not**
   `SceneColor` (read back directly, no conversion) and not either host view —
   so a future host view cannot silently take the wrong branch. Implemented as
   `RequiresCaptureViewConversionPass`; see the L2D5.1 journal for why the name
   is explicit about the pass rather than about "deferred".
3. **Tooling string policy.** Whether the `capture.screenshot` enum value and
   `--capture-view` string stay `"live2d"` as a documented tooling-level alias,
   or become generic (`host_output`) as well. Recommended: keep `"live2d"` as an
   alias so recorded L2D4.5 validation procedures keep working, and document it
   as a launch-time alias rather than a Render semantic. Note that the alias is
   effectively unreachable from the agent transport, which viewer mode refuses.
4. **Resize evidence mechanism.** Whether to add a validation-only launch option
   that changes the viewer's window extent once mid-run. Recommended: yes, a
   single option, justified the same way `--exit-after-capture` already is.
   Freeze its exact spelling, the frame at which it applies, and whether a
   second resize is allowed. If this is refused, item 10's runtime half has no
   mechanism and must be dispositioned instead of closed.
5. **Shutdown assertion surface.** Where a zero live-handle assertion can live,
   given the counter exists only inside a viewer run. Options: an extended
   machine-readable startup result, a test that drives the same teardown through
   the fake backend, or a both-of-the-above split where the test covers the
   renderer contract and the run covers the process. Recommended: the split.
6. **Fixture.** Which model evidences items 9 and 10 and on what redistribution
   basis. Candidates: synthetic blend-mode geometry (redistributable, but needs
   a `.moc3` for a live model), the existing licensed Hiyori package
   (environmental prerequisite, not redistributable), or an official
   `Samples/Resources` model (needs its terms read before it is relied on).
   This is a licensing decision, not an engineering one.
7. **Official reference.** Whether to attempt building the official sample
   executable from the pinned SDK's `Samples/` sources, or to record item 11 as
   an accepted limitation. Recommended: attempt the build in a separate output
   directory outside both the repository and the SDK tree; if it fails, record
   the limitation. Note that a build writes build output near a shared library
   directory, which is why this is a user decision.
8. **Blend-mode evidence.** How item 9's "all three blend modes" claim is
   asserted, given the current fixture proves partial-alpha coverage but not
   that Additive and Multiplicative drawables exist. Recommended: a synthetic
   fixture plus a fixture-derived assertion, not a code-reading claim.
9. **Carried import tests.** Whether the missing-`.moc3`/invalid-MOC import tests
   and the `--capture-alpha` regression test are L2D5 scope. Recommended: yes —
   both are V1 ledger items.
10. **Content gap.** Whether `LevelLoaderTest.LoadsCheckedInGameplayLevelFixtures`
    (missing `model/rock1-bl/rock2` archive content) is L2D5 scope or explicitly
    deferred. Recommended: explicitly deferred, recorded as unrelated to Live2D,
    because closing it needs an AssetTool import outside this stage's boundary.

- The per-item disposition table for V1 acceptance items 8–11 and the three
