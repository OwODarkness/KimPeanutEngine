# A2 — Cancellable streaming speech

Status: in progress. Parent: [audio roadmap](../TODO.md). Dependency:

findings: [A2 review](../.review/A2.md).

## Contract

`TTSSystem` accepts a request with a turn ID and returns a job token.
It emits copied state transitions (`Queued`, `Connecting`, `Generating`,
`Playing`, `Buffering`, `Draining`, `Completed`, `Cancelled`, `Failed`) plus
diagnostics through a thread-safe event queue consumed by the application.
`Completed` means playback drained; network EOF is a separate event. A
cancelled or failed job cannot later emit playable audio. Provider cancellation
must break the HTTP receive loop when possible, while generation tokens let
the session reject an unavoidable late result.

The provider produces format-tagged encoded chunks or PCM into a bounded
decoder/stream path. Decoder validates container, channel count, sample rate,
data size, and incomplete final chunks before publication. GPT-SoVITS uses
one pinned, tested API mode/media combination. Check HTTP status and content
type before interpreting the body as WAV; if the HTTP client exposes headers
only after the body callback, quarantine a bounded response prefix until the
status is known or change its request path so status is available first.
Propagate a receiver abort as a failed/cancelled request. Any error body is
surfaced as a bounded diagnostic,
not played or logged in full. Keep server-side reference-audio paths explicit.

Replace text-length FIFO sizing with fixed memory and high/low watermarks.
Pause producer delivery when full (or abort explicitly if the provider cannot
backpressure); never discard the oldest speech samples. Permit a controlled
prefill threshold and measure first-audio latency. A request can be cancelled
while queued, connecting, decoding, buffering, or playing. Shutdown stops
accepting work, cancels active providers, retires voices, and joins workers
without leaving callbacks that capture a destroyed `TTSSystem`.

## Acceptance and validation

- [x] Fake providers exercise success, empty response, non-200 response,
  wrong media type, truncated/fragmented WAV, decode failure, slow delivery,
  fast delivery, and provider abort.
- [x] Accepted PCM frames are heard once and in order, with no drop-oldest
  behavior. Underflow is observable and playback resumes.
- [x] Cancellation across queued, buffering, generating, playing, and draining
  yields one terminal event, retires the
  voice, and allows the next job to start promptly; old callbacks cannot
  affect a new turn.
- [x] Telemetry records request-to-first-audio, synthesis completion,
  audible drain, underruns, and queue occupancy. Request-to-first-text belongs
  to the upstream response/session stage because TTS receives completed text.
- [x] Debug Audio/TTS target build and focused tests pass; a visible runtime
  smoke with the configured server is recorded separately from deterministic
  fake-provider tests.

Audio remains provider-agnostic. TTS does not access Live2D or ImGui.

## A2 implementation progress — 2026-10-01

The TTS API now includes turn IDs, monotonic job tokens, copied lifecycle events,
a separate successful network-finished event, a drain monitor, queue occupancy
and playback telemetry, provider injection, and per-job cancellation. The HTTP
provider creates a client per active job so cancelling one job stops only that
request. Contracts cover active/queued cancellation, active HTTP abort,
audible-drain completion, HTTP 503, wrong media type, empty response, valid WAV,
and consumer abort. Audio
contracts cover fragmented/truncated WAV, the service's zero-sized streaming
data header, ordered FIFO preservation, and cancellable producer backpressure.

The `TTSServiceSmoke` target performs a bounded real request and waits for the
player to drain. On 2026-10-01 it successfully synthesized through the service
at `127.0.0.1:9880`, initialized the Senary Audio speaker, and reached playback
drain. The service's `audio/wav` response declares a zero-byte data chunk while
including PCM; the decoder accepts zero as an unspecified streaming length and
still requires actual decoded samples at EOF. The provider validates response
headers before forwarding body chunks, then streams directly into the decoder;
a delayed local-server contract proves audio arrives before HTTP EOF. The
bounded decoder FIFO applies cancellable backpressure and caps the response at
32 MiB.

Remaining acceptance: the TTS service code/deployment is not in this repository.
Its OpenAPI metadata reports FastAPI version `0.1.0` but no source revision or
commit, so the server build cannot be pinned here. The tested client contract is
`POST /tts`, `streaming_mode=true`, and `audio/wav` with a zero-sized streaming
data chunk; pin the deployment revision when its source or image is available.

Validation on 2026-10-01: Debug `AudioUnitTest`, `TTSUnitTest`, and
`TTSServiceSmoke` build. `ctest --test-dir build -C Debug -R 'Audio|TTS|Tts'
--output-on-failure` passed all 35 Audio/TTS tests. Contracts cover cancellation
while queued, buffering, generating, playing, and draining; late callback
rejection; underrun/resume and telemetry; HTTP abort; and progressive response
delivery. The live smoke returned success after audible playback drain.
