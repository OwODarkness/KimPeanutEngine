# P1 review — reusable audio player presentation

- Review date: 2026-10-02
- Baseline: `53a731e` plus the current working tree. The ongoing progress-bar
  color edits in `audio_preview_widget.cpp` and its journal were inspected but
  not changed by this review.
- Scope: standalone Audio Player controller, preview widget, editor adapter,
  build boundary, and the TTS job surface. Design target: a compact TTS strip
  with only relevant buttons, state, and audible playback progress.
- Method: static source and dependency inspection. No engine launch, build, or
  audible test was performed for this documentation review.
- Parent: [P1 plan](../.plan/P1.md) and [audio roadmap](../TODO.md).

## Assessment

The full preview already has a useful presentation seam: `AudioPreviewState`
borrows frame-local display data and `DrawAudioPreview` returns actions without
calling playback APIs. That seam is too large to reuse as a TTS mini-player.
The only public draw function always creates the full music surface, and its
library target also owns the queue, importer, host, and Runtime dependencies.
TTS currently cannot supply a truthful playback fraction for streaming speech
from its copied telemetry. Extract **presentation only** first; keep music
queue/import policy in the standalone controller and TTS job policy in TTS.

## Proposed component boundary

The smallest shared unit is a **presentation-only transport strip**, not a
shared music/TTS controller. Its input is a copied frame snapshot with a stable
instance ID, display label/state, elapsed playback time, optional duration,
optional buffered extent, and explicit capabilities (`play_pause`, `seek`,
`stop`, `cancel`). Its output is intent (`toggle_play_pause`, `seek_seconds`,
`stop_voice`, `cancel_job`). No source path, queue, `AudioHandle`, provider
token, waveform, subtitle, FFT, or ownership pointer enters this API. The
input spans/views, if any, remain valid only for the draw call.

The full music preview composes the strip below its waveform and adds
previous/next, rate, volume, scope, subtitles, and queue-specific controls.
Before wiring TTS, expose a control-thread-safe read-only speech playback
snapshot keyed by `JobToken`: the job owner resolves its retained audio handle
under the existing lifetime rules and copies Audio's played cursor and any
known total. The TTS editor adapter maps that snapshot to the strip; ImGui
never calls `GetAudioPlayer` or retains a handle. A queued or generating job
shows Cancel and an indeterminate job state. Audible streaming speech shows
elapsed played time, Buffering/Playing
status, and Cancel; it shows a fraction only after a trustworthy total exists.
A finished buffered speech clip may expose replay and seek if the conversation
owner explicitly retains and controls that voice. The presentation layer
never calls TTS or Audio directly.

Keep the base strip usable without icon assets or glow. The current full
preview's editor glow markers and icon alpha data can remain an optional
presentation style rather than a requirement of the compact contract.

## Acceptance checks for a later implementation

1. The full standalone panel and a compact TTS strip use the same transport
   and progress drawing code with separate stable IDs in one ImGui frame.
2. The compact strip fits a narrow editor panel, shows only available actions,
   and remains keyboard reachable at 100–200% DPI.
3. Unknown-duration streaming never displays a fabricated completion fraction
   or enables seek. Known-duration buffered speech follows Audio's consumed
   frame cursor through pause, resume, buffering, and completion.
4. Cancel during generation or playback stops the TTS job and prevents late
   audio; stopping a music voice has no effect on the TTS job.
5. Core TTS and Runtime Audio still build without Editor/ImGui; both visible
   Vulkan and OpenGL UI paths are inspected after the extraction.
